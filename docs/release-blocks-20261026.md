Для отдельных выпусков использовать ветки от актуального master либо последовательный стек зависимых PR. Обычный push одной объединённой ветки отправит всю её историю и не обеспечит выборочную публикацию блоков. Перед каждым выделением и принятием обновлять master; после извлечения блока повторять его проверки на собственной базе.

## Разрешение конфликтов

Конфликты были в 11 файлах:

- `app/core/constants.py`: сохранены локальные константы Ozon/FBO, расписания вынесены перед потребителем, метаданные поставок берутся из JOBS; дубли полей отсутствуют.
- `app/jobs/background.py`: сохранены WB-снимки, расписание поставок и новые задачи Ozon; сохранена локальная синхронизация учтённых FBO-поставок.
- `app/jobs/catalog.py`: задачи поставок и недельного стока зарегистрированы ровно один раз; метаданные поставок используются через `from_metadata`.
- `app/jobs/wb_ephemerides.py`, `app/repositories/ephemerides.py`: сохранён вариант master с типизированным снимком, инфраструктурным репозиторием, границей понедельника 00:05, изоляцией ошибок и `SyncGroupReport`.
- `app/web/routers/inbound_supplies.py`, `templates/stock/inbound-supplies.html`: сохранены локальный JSON API и клиентская отрисовка; актуальное расписание передаётся через UI-контекст.
- `docs/README.md`, `docs/ephemerides.md`, `docs/inbound-supplies.md`, `docs/project-sheet-export.md`: объединены описания функций, сохранён новый контракт WB и убрано устаревшее интервальное расписание. Также устранены повторные ссылки индекса.

## Проверки и ограничения

В объединённой копии выполнены:

- Ruff check по `app`, `scripts`, `run.py`: успешно.
- mypy: успешно, 133 модуля.
- `node --check`: успешно для всех 32 изменённых существующих JS-файлов.
- Семь временных Python-проверок: уникальность определений/обработчиков/правил расписания; календарные границы поставок; запрет недельного снимка до понедельника 00:05; изоляция ошибок магазинов и типизированный результат; повторная инициализация SQLite и запрет перезаписи недельного снимка; формирование клиентской страницы и наличие HTTP-контрактов; отсутствие повторных полей констант.
- Проверка diff и отсутствия неразрешённых конфликтов.

Общий Ruff format остаётся неуспешным по 24 ранее существовавшим файлам: 23 идентичны master, один (`app/repositories/unit_economics_data_errors.py`) уже имел локальные правки до слияния. Форматирование изменённого при разрешении конфликтов кода проверено отдельно. Массовое форматирование соседних модулей в задачу не включалось.

Известная недоработка блока 5: `_sync_states` в `app/web/routers/integrations.py` не передаёт `effective_enabled` для WB/ЯМ, а `applyRunState` в `static/integrations/index.js` считает отсутствие поля выключенным расписанием. До выпуска нужно передавать фактическое состояние с учётом общей настройки, конфигурации задачи и выбранных целей; проверить включение, выключение и отсутствие выбранных магазинов. Для задач Ozon этот расчёт уже есть в `IntegrationViews.state`.

Проверки подтверждают согласованность слияния, но не готовность всех новых функций к эксплуатации. Реальный PostgreSQL, внешние API, Google/FTP и браузерные пользовательские сценарии в этой задаче не проверялись. Полный набор существующих WB-тестов не запускался: его 14 файлов удалены в исходном рабочем состоянии. Для FBO перед выпуском особенно нужны проверки конкурирующих проведений, нехватки, повторов, отмен/приёмки и совместимости сохранённых партий на обеих поддерживаемых СУБД.
