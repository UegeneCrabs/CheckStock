# Дневной календарь параметров WB, Ozon и Яндекс Маркета

Общий переключатель `CHECKSTOCK_ECONOMICS_PREVIEW_ENABLED` открывает календарь и новую таблицу Ozon всем активным пользователям (`1`) либо выключает их (`0`, прямые запросы возвращают 404). Если новая переменная отсутствует, положительный прежний `CHECKSTOCK_ECONOMICS_PREVIEW_USER_ID` означает включение для всех. После изменения настройки требуется перезапуск приложения. [Контракт учётных записей](authentication.md).

В разделе юнит-экономики каждой площадки есть ссылка **«Параметры по дням»**. Страницы используют существующие маршруты с `?calendar=1`:

- `/sales/unit-economics-1c?calendar=1`
- `/sales/unit-economics-1c/yandex-market?calendar=1`
- `/sales/unit-economics-1c/ozon?calendar=1`

## Работа с календарём

Выберите магазин и дату. История начинается с первого реально сохранённого снимка доступных пользователю товаров. Сегодня помечено как предварительный день. Есть поиск по названию, артикулу и баркоду, страницы по 20/50/100 товаров, фотографии и копирование идентификаторов. Число товаров не ограничено размером страницы.

Нажатие на ячейку открывает источник, отдельно время сохранения снимка и известное время получения исходных данных, первоначальное и последнее значения, историю изменений. Если источник не сохранил время, интерфейс сообщает об этом явно. Разворачиваемый блок содержит сохранённые исходные записи адаптеров и доступные в них ответы источников; утраченные старые HTTP-ответы не восстанавливаются.

Исходные параметры может исправить любой активный пользователь: введите значение и причину, нажмите «Проверить влияние», проверьте изменения маржи, ROI и прибыли, затем подтвердите применение к указанной дате. Отмена ручной корректировки проходит такой же предварительный расчёт и возвращает последнее значение источника. Маржинальность, ROI, прибыль и производные параметры напрямую не редактируются. Корректировка не меняет цены в кабинете маркетплейса или настройки других дат.

Отсутствующее значение сохраняется как `null`, показано красным и отличается от сохранённого нуля. В WB/ЯМ при доступной цене вычисляется известная часть маржи с пометкой **«Неполный расчёт»** и перечнем недостающих входов. Без базы расчёта результат не определяется. ROI при неизвестной или нулевой закупке не определяется. Маржа на единицу и ROI WB/ЯМ не включают рекламу; прибыль дня отдельно учитывает заказы, выкуп и рекламу. Итог по найденным товарам включает вычисляемые суммы и раскрывает, что не учтено. Известные нулевые заказы позволяют показать реальные рекламные расходы даже без полной себестоимости. Формула Ozon описана ниже отдельно.

## Хранение и совместимость

Добавлены таблицы `economics_daily` и `economics_daily_events`, зарегистрированные в обычной инициализации схемы. Старые таблицы не удаляются и не переписываются. Ключ записи: маркетплейс, магазин, артикул, дата. Запись хранит неизменяемое первоначальное наблюдение, последнее наблюдение источника, ручные корректировки, входы, версию и результат расчёта. Журнал сохраняет автора, время, причину, значения до/после и наблюдения источников.

Изменение записи, расчёт и событие журнала выполняются одной транзакцией. Проверка ревизии защищает от одновременных правок и синхронизации после предварительного просмотра. После конфликта нужно заново открыть ячейку и проверить результат. Последующая синхронизация сохраняет ручные корректировки.

GET-запросы только читают данные. Старые снимки WB и общие (`COMMON`) дневные записи ЯМ доступны без массовой миграции. Они отмечаются как ранее сохранённые; достоверность исторического времени получения не подразумевается. Первый ручной пересчёт такой записи переносит её в новый журнал, сохраняя оригинал. Отдельные старые сценарии ЯМ FBY/FBS автоматически не смешиваются.

WB сохраняет наблюдения текущего дня каждые 30 минут через существующую фоновую задачу `unit_economics_1c_daily_margin_snapshot_00_msk` (имя оставлено ради настроек включения, запуск после готовности каталога). ЯМ сохраняет текущий день в обычной синхронизации экономики. Сохранение сегодняшних параметров задним числом запрещено. Поздно поступившие заказы и реклама обновляют только метрики своей даты поверх сохранённых исторических входов. Неизвестная история не заполняется сегодняшними затратами.

Существующие отчёты и дневные читатели получают действующие значения из нового журнала. API проверяет активную учётную запись, общий переключатель функции и существование магазина/товара. Автоматического ограничения по ФИО менеджера нет. Бизнес-проверки ревизии и полноты данных сохраняются.

## Ozon

Ozon переиспользует общий шаблон, таблицу, стили и редактор календаря. API расположен
в `/api/unit-economics-1c/ozon/calendar`: GET корня возвращает товары выбранного
магазина и дня, `/config` — магазины и московскую дату, `/cell` — снимок и журнал;
POST `/preview` и `/correction` выполняют проверку влияния и подтверждённую запись.
Поиск и размеры страниц совпадают с WB/ЯМ. Суммы и полнота считаются по всем
найденным товарам, включая товары вне показанной страницы.

Источником параметров служит `ozon_margin_daily`. Чтение не создаёт снимки и не
восстанавливает прошлые дни сегодняшними параметрами. В таблице видны сохранённые
цена с учётом акции, закупка, ФФ, денежные суммы комиссии Ozon FBO, логистики,
хранения, эквайринга, комиссии компании, НДС, УСН и процент выкупа. Их можно
исправить на выбранный день. Это денежные параметры снимка: изменение цены
не подменяет сохранённые суммы расходов автоматически рассчитанными по текущим
тарифам. Заказы FBO + FBS до отмен, расходы на рекламу выбранного дня и реклама
на ожидаемый выкуп берутся из сохранённых дневных источников и доступны для
просмотра. Будущие даты и неподдерживаемые поля записи отклоняются сервером.

Расчёт совпадает с [маржой Ozon](ozon-margin.md): маржа на штуку и ROI включают
рекламу; прибыль дня учитывает ожидаемые выкупы и расходы дня. При нулевых заказах
прибыль равна минус известная реклама, а маржа на штуку и ROI не определены.
Неизвестные значения остаются `null`, подтверждённые нули сохраняются отдельно.

Новые наблюдения сохраняются вместе со штатным часовым снимком Ozon в одной
асинхронной транзакции. Раздел Ozon в `economics_daily` хранит первый доступный
снимок, последнее наблюдение источника и ручные корректировки;
`economics_daily_events` хранит обновления источника, автора, причину, применение
и отмену. Прежние записи WB/ЯМ и исходные снимки Ozon не переписываются.
Старый снимок Ozon без журнала доступен сразу; первый подтверждённый пересчёт
сохраняет его как первоначальный. История до начала журналирования не выдумывается;
отдельное время получения каждого параметра внешним API неизвестно.

Токен предварительного просмотра учитывает источник, ревизию, дневной расчёт и
содержание правки. Подтверждение повторно проверяет токены, а запись блокирует
исходный снимок и ревизию журнала. После обновления источника или чужой правки
нужно открыть ячейку снова. Ручные значения переживают синхронизацию; отмена
возвращает последнее значение источника. Изменённые параметры используются
текущей экономикой, историческим диапазоном и отчётами Ozon. Внешних запросов
на изменение кабинета маркетплейса этот сценарий не создаёт.

Контракты находятся в `app/dto/ozon_calendar.py`, сценарий — в
`app/application/ozon_calendar.py`, асинхронное хранение — в
`app/infrastructure/ozon_calendar_repository.py`, чистые преобразования — в
`app/economics/ozon_calendar.py`, маршруты — в `app/web/routers/ozon_calendar.py`.
Подписи, источники и настройки общего интерфейса Ozon размещены в
`static/economics/ozon/calendar.js`.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m ruff check --no-cache app/repositories/daily_economics.py app/economics/daily_metrics.py app/web/routers/economics_calendar.py app/infrastructure/daily_economics_orm.py
node --check static/economics/shared/calendar.js
node --check static/economics/ozon/calendar.js
.\.venv\Scripts\python.exe -m mypy app/dto/ozon_calendar.py app/economics/ozon_calendar.py app/application/ozon_calendar.py app/infrastructure/ozon_calendar_repository.py app/web/routers/ozon_calendar.py
```

При первоначальной приёмке на временной SQLite проверялись оба маркетплейса, старые снимки, корректировка/отмена, журнал и атомарный откат, конфликт правок, отсутствие записей при GET, права, пагинация 723 товаров, частичный итог и нулевые заказы, обновление дневных метрик, время источника и запрет сохранения текущих настроек в прошлом. DDL обеих таблиц проверялся компиляцией для SQLite/PostgreSQL. При выкладке дополнительно проверяют чтение календаря на PostgreSQL: одного SQLite недостаточно для проверки параметров SQL.

При локальной проверке Ozon 30 октября 2026 года использовалась временная SQLite
со 123 синтетическими товарами. Проверены поиск основного и дополнительного
баркода, страницы, дневная формула с отменами, нули и отсутствие снимка, неизменность
БД при GET, предварительный расчёт, применение/отмена, историческая дата, журнал,
обновление источника поверх корректировки, одновременные правки, атомарный откат
при ошибке события, валидация и доступ. Данные WB сохранены неизменными. Шесть
временных Node-проверок охватили общий календарь WB/ЯМ/Ozon и смену поиска во время
загрузки ячейки. В браузере проверены ссылка из юнитки Ozon, поиск, история,
предварительный расчёт, применение и отмена. Ruff и mypy затронутых модулей
календаря прошли. Живая PostgreSQL и внешние API в этой проверке не использовались;
SQL-схема проверена компиляцией для SQLite/PostgreSQL.

При ручной проверке учитывают общий переключатель, активность учётной записи и сохранность данных. Общая загрузка данных 1С WB/ЯМ не включает загрузку Ozon.

## Закрытая выкладка

Сначала создайте полный `pg_dump -Fc` и проверьте чтение архива через `pg_restore`. Затем зафиксируйте изменения и отправьте коммит в Git; сервер должен получить этот коммит из репозитория. Перед переключением проверьте новую версию и запуск схемы на отдельной копии базы. Сохраните прежний образ и настройки для отката приложения. Рабочую базу при откате приложения автоматически не восстанавливайте: это уничтожило бы записи, появившиеся после резервного копирования.

Для ручной проверки используют отдельную локальную копию приложения с синтетическими товарами и временной БД. В браузере проверяют WB/ЯМ, поиск, прошлую дату, частичные результаты, предварительный расчёт, применение и отмену с историей, просмотр вычисляемого поля. Рабочая БД, секреты и внешние интеграции для проверки не используются.

Для ЯМ дневной снимок хранит исходные `orders_count` и `cancel_count` раздельно. Редактируемое количество заказов остаётся общим: отмены вычитаются после применения ручной корректировки. Расчётные выкупы, прибыль и закупка используют `max(orders_count − cancel_count, 0)`. Синхронизация обновляет отмены даже при неизменных заказах и рекламе; исходный снимок, исторические цены и ручные корректировки сохраняются, изменение отражается в журнале. Для существующих дней отмены обновляются из локальной истории ЯМ штатным `close_days`, без API и без сегодняшних цен.
