# Дневной календарь параметров WB и Яндекс Маркета

Временный закрытый доступ задаётся `CHECKSTOCK_ECONOMICS_PREVIEW_USER_ID`: ID единственного активного аккаунта, которому доступны календарь и новая таблица Ozon. Значение `0` закрывает доступ всем. Проверка ID дополняет обычные права; роль суперадминистратора её не обходит. Ссылки и новые задачи Ozon скрыты от остальных, прямые запросы к календарю и новым данным возвращают 404. Для остальных аккаунтов Ozon сохраняет прежнюю заглушку. После изменения настройки требуется пересоздать контейнер приложения.

В разделе юнит-экономики WB и Яндекс Маркета появилась ссылка **«Параметры по дням»**. Страницы используют существующие маршруты с `?calendar=1`:

- `/sales/unit-economics-1c?calendar=1`
- `/sales/unit-economics-1c/yandex-market?calendar=1`

## Работа с календарём

Выберите магазин и дату. История начинается с первого реально сохранённого снимка доступных пользователю товаров. Сегодня помечено как предварительный день. Есть поиск по названию, артикулу и баркоду, страницы по 20/50/100 товаров, фотографии и копирование идентификаторов. Число товаров не ограничено размером страницы.

Нажатие на ячейку открывает источник, отдельно время сохранения снимка и известное время получения исходных данных, первоначальное и последнее значения, историю изменений. Если источник не сохранил время, интерфейс сообщает об этом явно. Разворачиваемый блок содержит сохранённые исходные записи адаптеров и доступные в них ответы источников; утраченные старые HTTP-ответы не восстанавливаются.

Исходные параметры можно исправить при наличии права записи: введите значение и причину, нажмите «Проверить влияние», проверьте изменения маржи, ROI и прибыли, затем подтвердите применение к указанной дате. Отмена ручной корректировки проходит такой же предварительный расчёт и возвращает последнее значение источника. Маржинальность, ROI, прибыль и производные параметры напрямую не редактируются. Корректировка не меняет цены в кабинете маркетплейса или настройки других дат.

Отсутствующее значение сохраняется как `null`, показано красным и отличается от сохранённого нуля. При доступной цене вычисляется известная часть маржи с пометкой **«Неполный расчёт»** и перечнем недостающих входов. Без базы расчёта результат не определяется. ROI при неизвестной или нулевой закупке не определяется. Маржа на единицу и ROI не включают рекламу; прибыль дня отдельно учитывает заказы, выкуп и рекламу. Итог по найденным товарам включает вычисляемые суммы и раскрывает, что не учтено. Известные нулевые заказы позволяют показать реальные рекламные расходы даже без полной себестоимости.

## Хранение и совместимость

Добавлены таблицы `economics_daily` и `economics_daily_events`, зарегистрированные в обычной инициализации схемы. Старые таблицы не удаляются и не переписываются. Ключ записи: маркетплейс, магазин, артикул, дата. Запись хранит неизменяемое первоначальное наблюдение, последнее наблюдение источника, ручные корректировки, входы, версию и результат расчёта. Журнал сохраняет автора, время, причину, значения до/после и наблюдения источников.

Изменение записи, расчёт и событие журнала выполняются одной транзакцией. Проверка ревизии защищает от одновременных правок и синхронизации после предварительного просмотра. После конфликта нужно заново открыть ячейку и проверить результат. Последующая синхронизация сохраняет ручные корректировки.

GET-запросы только читают данные. Старые снимки WB и общие (`COMMON`) дневные записи ЯМ доступны без массовой миграции. Они отмечаются как ранее сохранённые; достоверность исторического времени получения не подразумевается. Первый ручной пересчёт такой записи переносит её в новый журнал, сохраняя оригинал. Отдельные старые сценарии ЯМ FBY/FBS автоматически не смешиваются.

WB сохраняет наблюдения текущего дня каждые 30 минут через существующую фоновую задачу `unit_economics_1c_daily_margin_snapshot_00_msk` (имя оставлено ради настроек включения, запуск после готовности каталога). ЯМ сохраняет текущий день в обычной синхронизации экономики. Сохранение сегодняшних параметров задним числом запрещено. Поздно поступившие заказы и реклама обновляют только метрики своей даты поверх сохранённых исторических входов. Неизвестная история не заполняется сегодняшними затратами.

Существующие отчёты и дневные читатели получают действующие значения из нового журнала. Доступ к API проверяется по разделу, маркетплейсу, магазину и товарам менеджера; просмотр не даёт права записи. Нового механизма восстановления данных и кнопки повторной загрузки источников нет.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_economics_calendar.py -v
.\.venv\Scripts\python.exe -m ruff check --no-cache app/repositories/daily_economics.py app/economics/daily_metrics.py app/web/routers/economics_calendar.py app/infrastructure/daily_economics_orm.py tests/test_economics_calendar.py tests/preview_economics_calendar.py
node --check static/economics/shared/calendar.js
```

18 регрессионных тестов используют временную SQLite, отключённый dotenv и собственный FastAPI без запуска фоновых задач. Они проверяют оба маркетплейса, старые снимки, корректировку/отмену, журнал и атомарный откат, конфликт правок, отсутствие записей при GET, права, пагинацию 723 товаров, частичный итог и нулевые заказы, обновление дневных метрик, время источника и запрет сохранения текущих настроек в прошлом. DDL обеих таблиц проверяется компиляцией для SQLite/PostgreSQL. Проверки выкладки дополнительно читают календарь на PostgreSQL: одного SQLite недостаточно для проверки параметров SQL.

В `test_economics_preview_access.py` восемь тестов проверяют закрытый доступ через настоящий middleware: календарь, Ozon, задачи синхронизации, чужого суперадминистратора, отсутствие авторизации и обычные права раздела. Общая загрузка данных 1С WB/ЯМ не включает закрытую загрузку Ozon.

## Закрытая выкладка

Сначала создайте полный `pg_dump -Fc` и проверьте чтение архива через `pg_restore`. Затем зафиксируйте изменения и отправьте коммит в Git; сервер должен получить этот коммит из репозитория. Перед переключением проверьте новую версию и запуск схемы на отдельной копии базы. Сохраните прежний образ и настройки для отката приложения. Рабочую базу при откате приложения автоматически не восстанавливайте: это уничтожило бы записи, появившиеся после резервного копирования.

Для ручной проверки есть `tests/preview_economics_calendar.py`: отдельный localhost-сервер на `127.0.0.1:8769` с синтетическими товарами и временной БД. В браузере проверены WB/ЯМ, поиск, прошлая дата, частичные результаты, предварительный расчёт, применение и отмена с историей, просмотр вычисляемого поля. Рабочая БД, секреты и внешние интеграции для проверки не используются.
