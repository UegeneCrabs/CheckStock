# Новинки Ozon

С 20 октября 2026 столбец «Новинка» использует возраст по всей сохранённой истории
магазина и артикула, независимо от выбранного периода экономики.

## Что проверено в API

Проверены реальные ответы Seller API 20 октября 2026:

- [`/v3/product/info/list`](https://docs.ozon.ru/api/seller/#operation/ProductAPI_GetProductInfoList)
  содержит `created_at`, `sources[].created_at`, `updated_at`,
  `statuses.status_updated_at`. Они описывают карточку, её источник и обновления,
  а не подтверждают начало продаж. Карточка может долго существовать без остатка.
- `/v1/analytics/stocks` содержит текущие остатки, `item_tags`,
  `days_without_sales` и `days_without_sales_cluster`. В проверенном ответе нет
  даты первого заказа или первого положительного остатка. Дни без продаж не
  означают возраст товара; метки Ozon не задают наш порог 21 день.

Страница официальной документации при проверке возвращала HTTP 403; выводы
сверены с ответами API, а не с неофициальным SDK. Отдельный подходящий источник
даты начала продаж в проверенных методах не найден, поэтому используется история.

## Правило

Берётся более ранняя из двух дат:

1. Первый сохранённый заказ Ozon с `quantity > 0` в `sales_order_lines`.
   Отмена или возврат не отменяют факт того, что товар уже заказывали.
2. Первый сохранённый положительный остаток FBO/FBS в
   `marketplace_stock_daily_history`. История FBS уже включает rFBS по действующему
   контракту снимков. Остатки собственного ФФ не подтверждают продажу на Ozon.

Возраст — разница между сегодняшней датой МСК и датой события в календарных днях.
Сегодняшнее событие даёт 0 дней, ровно 21 день — ещё «Новинка», 22 — «Обычный».
Будущие события, нулевые/отрицательные остатки и нулевые количества заказов
не учитываются. Магазины и маркетплейсы изолированы, даже если артикулы совпадают.

Если нет обоих источников, `is_new=null`, в таблице — «— / нет данных».
Пропуски истории не доказывают новизну. Классификация при наличии недавних событий
опирается на известную историю и может уточниться после загрузки старых дат.
Возраст помечен `≥`, поскольку первое известное событие может быть позже реального
старта. Подсказка показывает обе даты и правило. Старый товар остаётся обычным
после обнуления текущих остатков: используются сохранённые события.

WB сохраняет своё правило 28 дней от первого загруженного заказа с подстановкой
даты создания карточки. ЯМ сохраняет проверку заказов в дни `today−28 … today−22`
и закрепление статуса `old`. Их формулы не менялись.

## Реализация и проверки

- Константа: `OZON_NEWNESS.max_days=21`.
- DTO: `app/dto/ozon_newness.py`; правило: `app/ozon/newness.py`.
- Асинхронное чтение: `app/infrastructure/ozon_newness_repository.py`.
- `OzonEconomicsRepository` заполняет `product.newness`, `is_new`, `sales_days`
  для списка и карточки. Поле `sales_days` здесь означает наблюдаемый возраст,
  а не количество дней с продажами и не гарантированный возраст карточки.
- `newness` содержит `first_order_day`, `first_stock_day`, `observed_since`,
  `observed_days`, `is_new`, `threshold_days`. Все даты — ISO `YYYY-MM-DD`.
- Отдельной задачи или таблицы нет: возраст пересчитывается при чтении по уже
  сохранённым заказам и дневным остаткам. Запрос страницы не вызывает Ozon API.
  Удаление/исправление исторических фактов закономерно может изменить результат.

Проверены границы 0/20/21/22 дней, неизвестные и будущие даты, отменённые заказы,
ранний остаток, отсутствие заказов, обнуление стока, разделение магазинов и
маркетплейсов, фильтрация нулей. Временные проверки выполнялись на SQLite;
запросы также компилировались для PostgreSQL, живая PostgreSQL не проверялась.
Схема БД не менялась. Общие тесты, Ruff, mypy и синтаксис JavaScript прошли.
В браузере проверены обычный товар, новинка, поиск по статусу и неизменность
возраста при переключении периода с 7 на 30 дней. Общая ячейка WB и ЯМ
отрисовывается с прежними значениями, без ошибок JavaScript.
