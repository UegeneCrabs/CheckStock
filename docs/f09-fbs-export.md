# F09: проверенный период заказов перед FBS-выгрузкой

Экспорт сохраняет прежние разрешённые статусы, идентификаторы, объединение магазинов
(в том числе companion stores) и структуру листов. Количество — сумма товарных единиц
FBS за 30 завершённых московских дней `[начало периода, начало дня выгрузки)`.

Перед публикацией ЯМ/Ozon `refresh_fbs_order_totals` использует загрузчики и
нормализаторы `app/stock/sales.py` в строгом режиме. Ozon запрашивает только FBS v4,
без ограничения статусами и без зависимости от 21-дневной синхронизации экономики.
ЯМ читает заказы кабинета со всеми статусами. Все страницы и части периода должны
завершиться успешно; недостающий список, незавершённая пустая страница, повтор
курсора/идентификатора, отсутствие обязательных данных или достижение предела
обхода вызывают ошибку. Полный ответ с пустым списком допустим.

После проверки выполняется транзакция `replace_fbs_order_period`: обновление
статусов/количеств и предоставленных идентифицирующих полей, удаление отсутствующих
строк только в соответствующем FBS-окне, чтение итогов и commit. Финансовые суммы,
даты продаж, возвраты и отсутствующие поля обогащения этим обновлением не заменяются.
Для новых строк действуют исходные значения по умолчанию схемы; этот узкий refresh
не объявляет финансовые данные полными и не обновляет общий `sales_sync_state`.
Финансовую синхронизацию он не заменяет.

SQLite использует `BEGIN IMMEDIATE`, PostgreSQL — advisory transaction lock магазина
и площадки, общий с обычным upsert реестра. Итоги читаются внутри транзакции и далее
хранятся в памяти запуска: параллельная запись в БД не изменит уже проверенный результат.
Новый запуск выгрузки снова обращается к API; постоянного кеша полноты нет.

Один запуск `run_due` фиксирует московский период и переиспользует результат
магазина/площадки/окна для нескольких назначений. Ошибки тоже сохраняются до конца
запуска. Перед любыми Google-записями соответствующей публикации проверяются все
её магазины. При неуспехе возвращается ошибка с магазином, площадкой и периодом,
без тела ответа API или ключей; новая дата успешной выгрузки не записывается.
Ранее загруженный полный срез отдельного магазина может остаться в реестре,
если другой обязательный магазин объединённой публикации загрузить не удалось.

Если у ЯМ нет настроенного `business_id`, строгий путь требует единственный доступный
кабинет. При нескольких кабинетах он предлагает указать `business_id`. Поведение
legacy/backfill-разрешения кабинета не изменено. WB по-прежнему читает заказы и статусы
напрямую; выгрузка только остатков загрузку заказов не запускает. F10 и атомарность
Google `batchClear`/`batchUpdate` (F07) не входят в изменение.

Контракт ЯМ: [получение заказов](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/getBusinessOrders),
[пагинация](https://yandex.com/dev/market/partner-api/doc/ru/concepts/pagination).
30 дней и исключение конечной даты подтверждены официальной документацией.
Страница [Ozon Seller API](https://docs.ozon.ru/api/seller/#operation/PostingFbsList)
при проверке возвращала цикл перенаправлений; сохранён существующий адаптер v4,
его завершённость (`has_next`/`cursor`) проверена синтетическими ответами.

Проверки выполняются без `.env`, ключей и сети:

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests -p test_fbs_export.py -v
.venv/Scripts/ruff.exe check app/exports/stock_sheet.py app/stock/sales.py app/repositories/sales.py app/yandex/api.py app/ozon/api.py tests/test_fbs_export.py
```

Проверены пустой реестр, полное окно и его части, московские границы и переход через
полночь, статусы и количества, удалённые строки, повторный запуск, сохранение
непредоставленных полей, откат транзакции, объединение и companion stores,
повторное использование данных и ошибок, остановка до Google, полный пустой ответ,
WB и отдельная выгрузка остатков. SQL-ветка PostgreSQL и передача параметров advisory
lock проверены через подменённый драйвер; интеграционного запуска PostgreSQL и
реальных вызовов маркетплейсов/Google не было.
