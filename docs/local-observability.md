# Локальный просмотр логов в Grafana

Этот стенд запускает Grafana, Loki и Alloy в Docker Desktop. FastAPI остаётся
локальным процессом Windows и сохраняет логи в `data/logs/app.log` дополнительно
к выводу в терминал. Alloy читает файл через монтирование каталога; Docker socket
и сетевой порт Loki ему не нужны. Стенд не меняет серверный Compose.
Для Linux-сервера с приложением в Docker используйте [серверный Compose](server-observability.md).

## Запуск

Откройте Docker Desktop. Из корня репозитория в PowerShell выполните:

```powershell
docker compose -f deploy/observability/docker-compose.yml up -d
```

В другом терминале с активированным Python-окружением:

```powershell
$env:CHECKSTOCK_LOG_FILE = (Join-Path (Get-Location) 'data/logs/app.log')
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

Если нужен также локальный планировщик, откройте третий терминал с теми же
настройками БД и запустите:

```powershell
$env:CHECKSTOCK_LOG_FILE = (Join-Path (Get-Location) 'data/logs/scheduler.log')
python -m app.jobs.worker
```

При запуске через `python run.py` задайте `CHECKSTOCK_LOG_FILE` как путь к файлу
в нужном каталоге: дочерние процессы создадут рядом `app.log` и `scheduler.log`.
Для каждого файла появится также служебный каталог тегов `app.tags.log` или
`scheduler.tags.log`. Не запускайте второй планировщик рядом с уже работающим.

Откройте `http://127.0.0.1:3000`. При первом запуске войдите как `admin` с
паролем `admin`; если пароль уже меняли в интерфейсе, используйте новый.
Для другого начального пароля задайте `GRAFANA_ADMIN_PASSWORD` перед первым
запуском контейнера. Порт Grafana доступен только на `127.0.0.1`.

Grafana автоматически загружает дашборд **CheckStock — локальные логи** из
`deploy/observability/grafana-dashboard.json`. Это адаптация пользовательского
`fastapi-full-observability_rev4.json` к единственному источнику данных этого
стенда, `checkstock-loki`. В исходном дашборде остальные панели требуют
Prometheus/VictoriaMetrics, Tempo и Pyroscope, которые здесь не запущены.
Исходный файл в `Downloads` не изменяется. После изменения JSON запустите
`docker compose -f deploy/observability/docker-compose.yml up -d`; Grafana
проверяет файл каждые 30 секунд. Файл в репозитории — источник конфигурации
дашборда, поэтому изменения его панелей через UI не сохраняются.
Этот дашборд также назначен главной страницей Grafana: после входа нажмите
**Home** или откройте `http://127.0.0.1:3000/`. В обычном списке он находится
в **Dashboards**; блок главной страницы «Recently viewed dashboards» остаётся
пустым, пока вы не откроете дашборд впервые.

Отдельные страницы доступны по ссылкам сверху дашборда и в списке **Dashboards**:

- **Все логи** — фильтры «Сервис», «Уровень», «Модуль», «Теги», «Текст» и общий выбор времени Grafana.
- **HTTP-запросы** — фильтры «HTTP-статус», «Уровень», «Модуль», «Теги», «Текст» и время.
- **Фоновые задачи** — фильтры «Задача», «Уровень», «Модуль», «Теги», «Текст» и время.

Новые строки имеют формат `дата-время | уровень | полный Python-модуль |
[теги] | сообщение`; время содержит миллисекунды и смещение Москвы. Сегмент
тегов отсутствует, если тегов нет. Теги задаются кодом как список строк, а не
извлекаются из текста сообщения. Подходят устойчивые категории и названия
магазинов; идентификаторы запросов остаются в сообщении. Двойные кавычки,
обратная косая черта и управляющие символы в значении тега запрещены, чтобы
фильтрация по точному тегу оставалась однозначной.

Для нового модуля используйте `tagged_logger(__name__, "категория", "сценарий")`.
Дополнительные теги конкретного события передавайте через
`extra=log_tags(store_slug)`. Теги логгера и события объединяются; текст
сообщения не разбирается на теги автоматически.

Alloy добавляет к обычным записям Loki-метки `level`, `logger`, `http_status` и
`job`, когда соответствующее поле есть в строке. Из служебных файлов он
создаёт отдельные записи `record_type=tag_catalog` с меткой `tag`: одна запись
на каждый тег исходного лога. Панели считают только `record_type=log` и старые
записи без этой метки. Поэтому выпадающие списки
показывают только значения, уже встретившиеся в выбранном периоде. Старые
строки, загруженные до включения меток, остаются в общем потоке, но не
появляются в новых списках значений. Поля `http_status` нет у обычных логов,
а `job` — у сообщений планировщика без имени задачи. Страница фоновых задач
будет пустой, пока локальный планировщик не запущен с записью в
`data/logs/scheduler.log`.
Тег можно выбрать один или несколько; вариант **All** включает также записи
без тегов. В панелях логов выключен отдельный столбец времени Grafana: дата и
время уже стоят в начале каждой строки CheckStock, поэтому повтор не показывается.
При выборе **All** фильтр тегов не подсвечивает всю строку лога. При выборе
конкретного тега Grafana выделяет совпадение внутри сегмента тегов.
В журнале HTTP-запросов имя события `request_completed` используется для отбора
записей, но не подсвечивается как поисковый фрагмент. Введённый в поле «Текст»
поисковый фрагмент по-прежнему может подсвечиваться.

## Проверка и поиск

Отправьте запрос, который даст видимую запись уровня WARNING:

```powershell
curl.exe -i -X POST http://127.0.0.1:8000/api/agent/v1/unknown
```

В Grafana откройте **Explore → Loki**, выберите последние 15 минут и выполните:

```logql
{service_name="app"} |= "request_completed"
```

Можно искать по фрагменту `request_id=<id>` из логов FastAPI или выбрать
`{service_name="scheduler"}` для фоновых задач. При отсутствии записей проверьте
`data/logs/app.log` и `docker compose -f deploy/observability/docker-compose.yml logs alloy loki`.
Состояние источника Loki видно в **Connections → Data sources**.

Страница HTTP-запросов и обзор показывают среднее время **по каждой ручке с
запросами** за выбранный период, без ограничения «топ 10»; каждая строка
содержит HTTP-метод, маршрут и среднюю длительность в миллисекундах. График
времени показывает среднее по запросам в каждом интервале. Ручки без запросов
в выбранном периоде не отображаются. В строке запроса `path` сохраняет
фактический URL, а `route` содержит шаблон FastAPI: например,
`/items/{item_id}`. Панели объединяют запросы по HTTP-методу и шаблону; для
старых записей без `route` используют `path`. Обычные GET-запросы тоже пишутся
на уровне INFO; ответы 4xx и 5xx
сохраняют уровни WARNING и ERROR. Поле `slow=true` отмечает запросы дольше
`CHECKSTOCK_SLOW_REQUEST_THRESHOLD_MS`. Запросы `/healthz`, `/readyz` и `/static/`
не записываются. Если уровень логирования повышен выше INFO, часть успешных
запросов не попадёт в статистику. Это показатели по логам завершённых запросов,
а не замена Prometheus-метрикам. Панели трассировок, профилирования и текущих
активных запросов требуют отдельных источников данных.

Логи хранятся в Loki семь дней. Файлы `data/logs/*.log` не удаляются Loki и могут
расти; для локального теста их можно удалять после остановки FastAPI и Alloy.
Все файлы `data/logs/` исключены из Git. Не записывайте в логи токены, пароли
и персональные данные.

Остановите стенд командой:

```powershell
docker compose -f deploy/observability/docker-compose.yml down
```

Данные Grafana и Loki сохраняются в томах Docker. `down -v` удалит эти данные.
