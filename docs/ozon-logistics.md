# Логистика Ozon FBO за 30 завершённых дней

Ежедневный снимок служит входом будущего расчёта маржи. Калькулятор показывает
расходы на одну единицу, оставленную покупателем, и отдельную оценку по формуле
с выкупом. Полная прибыль Ozon этим изменением не подключается.

## Даты и источники

Для московской даты `D` окно равно `[D − 30 дней; D − 1 день]` включительно.
Например, снимок 19 октября использует 19 сентября — 18 октября. Выбор периода
таблицы экономики не меняет окно калькулятора. Сегодняшние начисления исключены.

Источники Seller API:

| Метод | Данные |
|---|---|
| `/v3/posting/fbo/list` | Все отправления FBO, принятые в обработку в окне; артикулы, SKU, количества и текущие статусы |
| `/v1/finance/accrual/types` | Соответствие числовых `type_id` именам услуг |
| `/v1/finance/accrual/postings` | Начисления по выбранным отправлениям, пакетами до 50; берутся только `accrual_date` внутри окна |
| `/v1/returns/list` | Возвраты FBO с полной последовательной пагинацией; затем отбор по выбранным отправлениям |
| `/v4/product/info/attributes` | Габариты упаковки; объём в литрах = ширина × высота × глубина в мм / 1 000 000 |

Это когорта отправлений окна, а не бухгалтерская сумма всех проводок магазина
за месяц: расходы по более старым отправлениям сюда не входят. Статусы получены
на `observed_at`; API списка не восстанавливает их состояние на вчерашнюю полночь.
Поздние начисления и возвраты ещё могут отсутствовать. Полученный снимок является
оценкой по доступным данным, даже когда загрузка полная.

Код источников: `app/ozon/async_logistics.py`; чистое преобразование:
`app/ozon/logistics_normalizer.py`; DTO: `app/dto/ozon_logistics.py`.

## Расходы, количества и формулы

Расход равен `−accrued.amount`. Кредитовые корректировки уменьшают расходы;
модуль суммы не берётся. Валюта — RUB. Сопоставление выполняется по отправлению
и SKU, затем по артикулу; количества учитывают несколько единиц в отправлении.
Платные отмены и невыкупы включаются. Отправления без учтённых расходов исключены
из знаменателя логистического выкупа.

| Составляющая | Имена услуг |
|---|---|
| Туда | `Logistic` |
| Обратно | `ReturnFlowLogistic` |
| Обработка | `PickUpPointReturnAcceptance` |
| До места выдачи | `LastMileCourier`, `DeliveryToHandoverPlaceByOzon` |
| Прочие расходы доставки | `PackageCost`, `PackingFee`, `ItemPacking`, `ItemSealing`, `CourierPickUpByOzon`, `CourierPickUpReinvoice`, `Cancellation`, `ClientReturn`, `PartialReturn` |

Список централизован в `OZON_LOGISTICS.accrual_parts`. Комиссия продажи,
эквайринг, реклама, хранение и поставки на склад сюда не добавляются.
Если услуга упаковки или другая дополнительная услуга относится ко всему
отправлению без SKU, её сумма распределяется между товарами пропорционально
количеству штук. Основная перевозка без SKU допустима только для одного SKU;
неоднозначная основная услуга прерывает сохранение магазина.

Количество оплаченных перевозок считается по товарным единицам с положительным
остатком расходов соответствующего типа. Корректировки одной услуги не создают
новую перевозку. Внутри отправления/SKU количество одного направления берётся
как максимум количеств его типов, затем суммируется по отправлениям.

Из полученных товаров вычитаются физические возвраты `ClientReturn` с
`logistic.return_date` не позже конца окна. Отмена до получения повторно не
вычитается. Возврат без даты фактического возвращения пока не вычитается.

```text
Оставлено = получено в платной когорте − возвращено после получения
Выкуп для логистики = оставлено / количество единиц с расходами × 100%
Туда = расходы туда / оплаченные единицы туда
Обратно = расходы обратно / оплаченные единицы обратно
Обработка = расходы обработки / оплаченные единицы обратно
До места выдачи = расходы Ozon и партнёров / оставлено
Прочие = дополнительные расходы доставки / оставлено

Основной итог = все перечисленные расходы / оставлено

Оценка по формуле =
  (туда + дополнительная наценка + обратно + обработка) / (выкуп / 100)
  − обратно − обработка + до места выдачи + прочие
```

Обработка не равна фиксированным 15 ₽ на каждый возврат. Например, при 64
начислениях по 15 ₽ и 88 обратных перевозках средняя обработка равна
`960 / 88 = 10,90909… ₽`. Сохраняются оба счётчика и сумма начислений.

Основной итог учитывает реально начисленные обратные расходы. Оценка по выкупу
может отличаться: она моделирует обратную перевозку для каждой неоставленной
единицы. Сохранённая оценка доступна только при полном совпадении оплаченной
когорты с единицами прямой перевозки. При 100% выкупа обратные составляющие
не требуются. При нулевом выкупе или отсутствии знаменателя расчёт — `null`.

Дополнительная наценка по умолчанию 0 ₽ и предназначена для сценария.
Стоимость маршрута уже содержится в начислениях `Logistic`. Доли нелокальных
доставок и их наценок не выводятся: эти расходы нельзя достоверно выделить из
используемых ответов. Исходный объём не заменяет фактическую стоимость. Его
изменение включает отдельную оценку по выбранному маршруту, описанную ниже.

## Сохранение и полнота

`OzonLogisticsService` использует порт `LogisticsUnitOfWork` и
`AsyncLogisticsRepository`. Новые таблицы создаёт обычный `init_db`:

- `ozon_logistics_daily`: ключ `(store_slug, day, article)`, окно, время и JSON
  типизированного снимка с версией формулы, суммами, количествами и состоянием.
- `ozon_logistics_runs`: ключ `(store_slug, day)`, время попытки, успешного
  завершения и код ошибки.

Все товары магазина и успешный статус записываются одной транзакцией.
Неоконченная пагинация, неизвестный тип начисления, несовпадение SKU, валюта,
неверное количество или ошибка API исключают новый снимок магазина. Предыдущий
снимок остаётся доступным с `stale` и ошибкой. Ошибка карточки габаритов исключает
только объём. Переход через московскую полночь во время загрузки отменяет снимок.

Успешный снимок дня неизменяемый; повторный запуск пропускает его. Исторические
пропуски не заполняются сегодняшним знанием задним числом. Для будущей маржи за
семь дней следует читать `history` по датам этих дней и отдельно учитывать
пропуски, а не подставлять сегодняшний снимок во всю неделю. Для текущего дня
используется его снимок; предыдущий доступный имеет явную пометку устаревания.

Состояния: `available` — вычислимый результат; `partial` — оплаченные отправления
ещё не завершены;
`insufficient` — нет оставленных единиц для распределения. Отсутствующий снимок
передаётся как `snapshot: null`. Неизвестное не превращается в ноль.

Отсутствие начисления прямой перевозки при успешно полученных данных отправления
не считается неполнотой: например, у отмены может быть только упаковка или
обратная логистика. Разница между количеством единиц с расходами и оплаченных
прямых перевозок не создаёт предупреждения `paid_without_full_forward`.
Фактические суммы, количества и ограничения оценки по формуле остаются прежними.
Ошибки загрузки, отсутствующие снимки и неизвестные исходные данные сохраняют
свои предупреждения. При обновлении старых данных удаляется только устаревшая
пометка; числовые значения и даты снимков не пересчитываются. У исторической
маржи пометка снимается только при подтверждении соответствующим снимком
логистики без других причин неполноты.

## Расписание и интерфейс

Задача `ozon_logistics_daily_sync` запускается общим worker после готовности
каталога, затем ежедневно в 05:00 МСК. Учитываются настройки магазинов и площадки
в интеграциях. На старте выполняется пропущенная загрузка текущего дня; успешные
магазины не перечитываются. Магазины выполняются через `TaskGroup`, ошибки
изолированы, страницы магазина последовательны. Межпроцессная блокировка
магазина предотвращает одновременные ручную и автоматическую загрузки.
Общие повторы планировщика — через 1, 5 и 15 минут; HTTP учитывает `Retry-After`.
При сохраняющемся 429 текущий пакет дополнительно ждёт 15, 30 и 60 секунд;
уже полученные в текущей попытке страницы не запрашиваются заново.
Пакет начислений содержит до 200 отправлений. Перед каждым запросом и повтором
действует [общий ограничитель Seller API](ozon-api-limits.md), учитывающий
Client ID, метод, `Retry-After` и `Ratelimit-Remaining`.
Пауза между пакетами задана `CHECKSTOCK_OZON_LOGISTICS_REQUEST_INTERVAL_SECONDS`
(по умолчанию 2 секунды). Обход возвратов ограничен 500 000 строк: превышение
прерывает загрузку, а не сохраняет обрезанные данные.

После обновления кода перезапустите уже работающий отдельный worker штатно.
Ручной запуск доступен в интеграциях; он не перезаписывает успешный снимок дня.

`GET /api/unit-economics-1c/ozon` читает только БД и добавляет `product.logistics`.
В подробном калькуляторе блок раскрывается по образцу Яндекса. Общий CSS блока
находится в `static/economics/shared/logistics.css`, Ozon-поля и обработчики —
в `static/economics/ozon/logistics.js`.
Блок Ozon сохраняет обычный фон при неполных данных и ошибках; пояснения остаются в тексте блока.

`POST /api/unit-economics-1c/ozon/logistics/calculate` принимает
`LogisticsScenario` и возвращает `LogisticsCalculation`. Нужны активная сессия
и доступ к preview экономики. Исходный итог берётся по фактическим расходам;
изменение составляющей включает оценку по формуле. Ручной итог, включая 0,
имеет приоритет. Сброс и закрытие карточки возвращают снимок. Правки сценария
не сохраняются в БД и не отправляются в Seller API.

## Сценарий объёма в подробном калькуляторе

С 23 октября 2026 из интерфейса удалены поля «Кластер отправки»,
«Кластер доставки» и «Кластер возврата». «Объём товара» остаётся справочным
полем только для чтения с подсказкой источника и даты снимка. Открытие карточки
не запрашивает тарифный справочник; ручные расходы отправляются в расчёт без
`volume`. Изменение цены не переключает логистику на оценку маршрута.
Средние начисления, редактирование составляющих, ручной итог и сброс сохранены.

Ниже описаны сохранённый серверный контракт и интерфейс до удаления кластеров.
Прежнее поле «Объём товара» редактировалось в литрах, включая дробные значения.
Исходное значение — `snapshot.volume_l` без округления до двух знаков.
Отсутствующий или неположительный исходный объём показан пустым: пользователь
может ввести положительное значение. Ноль, отрицательные, бесконечные значения
и неверные строки сервер отклоняет с 422. Пустое поле интерфейса возвращает
исходный объём; `volume_l: null` в запросе означает отсутствие объёма.

Для оценки нужны цена продавца с учётом акции и кластеры отправки и доставки.
Маршрут выбирается пользователем: дневной снимок содержит средние начисления
и не позволяет восстановить распределение маршрутов. Кластер возврата по
умолчанию совпадает с кластером доставки; его можно изменить. Это сценарий
одного маршрута FBO с возвратом на склад выбранного кластера, а не прогноз
среднего по всем заказам. Универсальный тариф не подставляется при неизвестном
маршруте: Ozon применяет его при собственном техническом сбое определения
кластеров, что не равнозначно отсутствию этих данных у CheckStock.

Источники проверены 20 октября 2026 года:

- [Доставка до покупателя, FBO, вкладка «С 10 сентября по 29 октября 2026 г.»](https://seller-edu.ozon.ru/libra/commissions-tariffs/commissions-tariffs-ozon/rashody-na-dostavku).
- [Официальный XLSX с тарифами с 28 августа 2026 года](https://cdn.ozone.ru/s3/ozon-disk-api/Seller-edu/files/commissions-tariffs/commissions/logistika-fbo-fbs-28082026_1784031962.xlsx):
  лист `Логистика РФ`, B4:F36467, 848 маршрутов × 43 диапазона.
  SHA-256: `9475b39b78410062820fb02e3d468e44a811c149894eb5d17d642ba2171a91a7`.
- [Возвраты FBO, вкладка «С 10 сентября по 30 ноября 2026 г.»](https://seller-edu.ozon.ru/libra/commissions-tariffs/commissions-tariffs-ozon/rashody-na-otmenu-vozvraty):
  обратная перевозка тарифицируется по направлению возврата; отдельная
  обработка партнёром не включается повторно в перевозку.
- [Объём и объёмный вес](https://seller-edu.ozon.ru/libra/commissions-tariffs/additional-information/obyom-i-obyomnyi-ves).

В репозитории сохранён типизированный снимок таблицы
`app/ozon/data/logistics-tariffs.json` с источником, хешем и сроком действия.
Используется колонка до 300 ₽ включительно либо свыше 300 ₽ по `seller_price`.
Дробные литры сравниваются через Decimal с верхними включительными границами
таблицы. До целого литра объём не округляется: 1,9 л входит в диапазон до 2 л,
2,1 л — до 3 л; значение чуть выше 2 л попадает в следующий диапазон.
Нижняя граница — предыдущая верхняя, не включительно. Погрешность float и
округление отображения поля не влияют на выбор диапазона.

```text
Туда = тариф(объём, цена, кластер отправки → кластер доставки)
Обратно = тариф(объём, цена, кластер доставки → кластер возврата)
Итог = (туда + наценка) / долю выкупа
       + (обратно + обработка) × (1 − доля выкупа) / долю выкупа
       + до места выдачи + прочие расходы
```

Выкуп остаётся отдельным логистическим выкупом из снимка или ручного сценария.
Обработка, последняя миля, дополнительные расходы, наценка, хранение, реклама
и налоги автоматически по литрам не масштабируются. При 100% выкупа данные
обратной перевозки и обработки не нужны. Неизвестные обязательные расходы и
нулевой выкуп дают неизвестный итог. Итог передаётся в существующий серверный
калькулятор, где обновляются прибыль и ROI.

Ручные суммы прямой/обратной перевозки имеют приоритет внутри сценария;
следующее изменение объёма или маршрута возвращает тарифный расчёт. Ручной
общий итог также имеет прежний приоритет, включая 0. Исходные начисления
и оценка дневного снимка показаны отдельно и не изменяются.

При неизвестной цене, объёме, маршруте, отсутствии строки тарифа или
недействующей редакции сервер возвращает смысловое состояние и `null`,
а интерфейс поясняет причину. Сетка ограничена 29 октября 2026 года:
опубликованные тарифы с 30 октября не применяются раньше срока, прежние
не выдаются за текущие после него. Для обновления нужно проверить новую
официальную таблицу и заменить снимок с датами и контрольной суммой.
Фиксация тарифов на 60 дней для конкретной поставки, льготы и специальные
программы здесь не восстанавливаются.

`GET /api/unit-economics-1c/ozon/logistics/tariffs` возвращает
`LogisticsTariffOptions` — списки кластеров, срок, источник и доступность.
Существующий POST дополнен необязательным `volume: LogisticsVolumeScenario`;
ответ содержит `volume: LogisticsVolumeEstimate` и рассчитанные `inputs`.
Прежние запросы без `volume` сохраняют поведение. Оба маршрута требуют preview.
DTO: `app/dto/ozon_logistics_volume.py`, расчёт:
`app/economics/ozon_logistics_volume.py`, чтение снимка справочника:
`app/infrastructure/ozon_logistics_tariffs.py`. Сетевых запросов, SQL и
изменений схемы БД при моделировании нет.

Сценарий сохраняется при переключении обычного и подробного режимов и
повторной отрисовке того же товара. Общий сброс возвращает исходный объём,
расходы и начисления; закрытие и смена товара удаляют сценарий. Устаревшие
ответы после сброса, новой правки или смены товара игнорируются.

Проверка 20 октября 2026 года: 13 временных серверных сценариев (включая
границы всех диапазонов, 2,1 → 1,9 л, порог цены 300 ₽, неизвестные данные,
ручные суммы, прибыль/ROI и HTTP-контракт), 41 существующий тест,
Ruff, mypy и синтаксис JavaScript. В браузере на синтетических данных
проверены ввод и очистка объёма, выбор маршрута, смена цены, ручной нулевой
итог, компактный режим, повторная отрисовка, сброс, закрытие и смена товара.
Проверка не отправляет изменения в Ozon и не изменяет исторические начисления.
