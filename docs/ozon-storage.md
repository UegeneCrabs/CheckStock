# Хранение Ozon FBO: дневные снимки за 30 дней

Для московского дня `D` расчёт использует `[D − 30; D − 1]` включительно.
Например, снимок 20 октября 2026 содержит 20 сентября — 19 октября.
Период таблицы экономики не меняет это окно.

```text
Хранение на штуку = расходы на размещение за 30 дней /
                   (продано FBO − возвращено FBO за те же 30 дней)
```

Итог округляется до копеек, исходные суммы сохраняются без округления.
Кредитовые корректировки уменьшают расходы. При знаменателе ≤ 0 итог — `null`,
а понесённые расходы и количества остаются в снимке. Нулевые подтверждённые
расходы при положительном знаменателе дают 0 ₽.

## Источники

- [Отчёт о размещении по товарам](https://docs.ozon.ru/api/seller/#operation/CreatePlacementByProductsReport):
  `POST /v1/report/placement/by-products/create`, `date_from`, `date_to`.
  Готовность и файл — `POST /v1/report/info` с `code`.
  В XLSX суммируется «Начисленная стоимость размещения» по «Артикул», «SKU»,
  «Дата» по всем складам и признакам товара. Это уже сумма строки, её не нужно
  умножать на остаток. Хранение возвратов FBS, доставка и реклама не добавляются.
- [Дневные начисления](https://docs.ozon.ru/api/seller/#operation/GetFinanceAccrualByDay):
  `POST /v1/finance/accrual/by-day`, все страницы каждого дня через `last_id`.
  Учитывается только `posting.delivery_schema = Fbo` и строки с `commission`.
  `commission.sale_amount.amount > 0` — продажа, `< 0` — обратная реализация;
  количество берётся из `posting.products[].quantity`, а не из числа отправлений.
  Нулевая сумма реализации с количеством отклоняется как неоднозначная.
  Валюта реализации — RUB. Отмена без реализации не увеличивает знаменатель.
- SKU связывается с артикулом из отчёта хранения. Отсутствующие в отчёте SKU
  запрашиваются через `/v3/product/info/list` существующим клиентом каталога.
  Если карточка больше не возвращается каталогом, артикул берётся из товара
  исходного отправления через `/v2/posting/fbo/get` по `unit_number` начисления.
  Пропущенная или неоднозначная связь не распределяется приблизительно.

Это расходы периода, распределённые на чистую реализацию того же периода,
а не расходы партии и не когорта заказов, созданных за 30 дней. Даты реализации —
даты финансовых начислений. Возвраты продаж более ранних периодов тоже вычитаются,
если обратная реализация начислена в рассматриваемом окне. Поздние начисления
попадут в следующие снимки, когда появятся в API. Снимок отражает сведения,
доступные на `observed_at`, а не окончательный бухгалтерский результат месяца.

## Хранение данных и повторы

Три новые таблицы создаются обычным `init_db` без изменения старых данных:

- `ozon_storage_daily`: `(store_slug, day, article)`, границы окна, время,
  типизированный JSON с версией формулы, расходами, продажами, возвратами,
  итогом на штуку, разбивкой по 30 дням и SHA-256 файла отчёта.
- `ozon_storage_runs`: попытка, успешное сохранение магазина и код ошибки.
- `ozon_storage_reports`: сохранённый код задания Ozon и число попыток создания
  за день. Ожидание/повтор загрузки использует тот же код, включая перезапуск worker.
  Максимум три попытки создания в день, чтобы не исчерпать лимит API 5 отчётов.
  Попытка записывается до запроса; неоднозначный сетевой исход тоже расходует её.

Все товары магазина записываются одной транзакцией. Успешный дневной снимок
не перезаписывается; второй запуск пропускает его. Ошибка HTTP, пагинации,
схемы файла, SKU или количества сохраняет ошибку попытки, но не заменяет
предыдущий снимок. Переход через московскую полночь отменяет сохранение.
Пропущенные исторические дни не заполняются сегодняшними данными задним числом.

Проверяется наличие всех 30 дат в отчёте размещения магазина. Если дат не хватает,
сохраняется снимок `partial` с доступными расходами, но `per_unit = null`.
Даже если причина — отсутствие остатков во всём магазине в конкретный день,
это не считается доказанным нулём. Такой снимок тоже фиксирует состояние дня;
следующий день пересчитывает окно заново. `insufficient` означает неположительную
чистую реализацию; `available` — вычислимую сумму. Отсутствующий снимок — `null`.

## Задача и калькулятор

`ozon_storage_daily_sync` входит в общий каталог `JOBS`, настройки интеграций
и асинхронный worker. Запуск ежедневно в **06:00 МСК**, после старта worker —
догрузка текущего дня, если его ещё нет. Общие повторы — через 1, 5 и 15 минут.
Магазины обрабатываются конкурентно с изоляцией ошибок, страницы последовательно,
с межпроцессной блокировкой магазина. `CHECKSTOCK_OZON_STORAGE_REQUEST_INTERVAL_SECONDS`
задаёт паузу между запросами начислений (по умолчанию 1 секунда).
После установки изменений уже запущенный worker нужно штатно перезапустить.

`GET /api/unit-economics-1c/ozon` читает только БД и передаёт `product.storage`:
`snapshot`, `stale`, `error`, `attempted_at`. Поле «Хранение, руб» калькулятора
берётся из `snapshot.per_unit`. Подсказка показывает период, расходы, продажи,
возвраты, формулу и свежесть. Ручные правки, включая ноль и кредитовую сумму,
действуют только в локальном сценарии; сброс возвращает снимок.

Для будущей маржи за текущий день используется снимок текущего дня; предыдущий
имеет явный `stale`. Для маржи прошлых семи дней `history` читает снимки каждого
дня отдельно: сегодняшнее окно нельзя подставлять во всю прошлую неделю.
Полная формула маржи этим изменением не подключается.

Модули: `app/dto/ozon_storage.py`, `app/ozon/{async_storage,storage_normalizer}.py`,
`app/application/ozon_storage.py`, `app/infrastructure/{async_storage_repository,ozon_storage_orm}.py`,
`app/jobs/ozon_storage.py`, `static/economics/ozon/calculator.js`.
