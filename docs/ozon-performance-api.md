# Реклама Ozon в юнит-экономике

Статус на 19 октября 2026 года: подробный асинхронный загрузчик подключён к
расписанию, ручному запуску и JSON API экономики. Старый
`ozon_unit_economics_advertising_sync` исключён из расписания;
[состояние объединения](architecture.md#состояние-объединения-19-октября-2026).

Для расходов, показов и кликов нужен отдельный доступ **Performance API** каждого кабинета. Ключ Seller API для рекламы не подходит. Создайте сервисный аккаунт и ключ на странице [Ozon → Настройки → API-ключи → Performance API](https://seller.ozon.ru/app/settings/api-keys?currentTab=performanceApi).

В `secrets/ozon_tokens.json` у каждого кабинета добавьте два поля:

```json
{
  "rimili": {
    "client_id": "seller-client-id",
    "api_key": "seller-api-key",
    "performance_client_id": "service-account@advertising.performance.ozon.ru",
    "performance_client_secret": "performance-secret"
  }
}
```

Секреты не добавляйте в Git. Автоматические выгрузки запускает отдельный процесс `app.jobs.worker`, а не вебовый lifespan.

## Существующие показатели

Единственный действующий загрузчик рекламы — `ozon_advertising_breakdown_sync`. Прежняя задача `ozon_unit_economics_advertising_sync` исключена из расписания и каталога запуска. Таблица затрат, совместимое поле `advertising.spend`, CTR, CPC, показы и клики используют дневные данные, описанные ниже. ДРР рассчитывается на сервере по согласованной формуле: расходы / ТО после отмен × доля выкупа × 100. `advertising.drr_basis` содержит использованные суммы, выкуп и покрытие; подробности — в [контракте выкупа](ozon-buyout.md).

## Дневные расходы по типам рекламы

`ozon_advertising_breakdown_sync` запускается после готовности каталога и затем каждый час. Вчерашний день закрывается на первом запуске после 04:30 МСК. Повторы после ошибок: через 1, 5 и 15 минут. Настройки магазинов и ручной запуск доступны в общем каталоге задач. До явного изменения нового переключателя наследуется соответствующий глобальный или магазинный переключатель старой задачи; сохранённые новые значения имеют приоритет. История старой задачи остаётся в БД.

Сценарий: `app/economics/ozon_advertising_breakdown.py` → `app/ozon/async_performance.py` → нормализация в `app/ozon/advertising_normalizer.py` → `app/infrastructure/async_advertising_repository.py`. Контракты находятся в `app/dto/ozon_advertising.py`. HTTP и БД асинхронные; магазины работают через `TaskGroup`, запросы одного магазина выполняются последовательно. Ошибка одного магазина или источника не отменяет остальные.

В первую очередь обновляются сегодняшние CPC и два источника CPO по Москве, затем закрывается вчерашний день и догружаются пропуски и ошибки последних семи завершённых дат. Успешные дни каждого источника, включая пустые ответы, повторно не запрашиваются. Соседние исторические пропуски объединяются в одно окно, чтобы не создавать отдельный отчёт на каждую дату. Незавершённое историческое окно продолжается с прежними границами, пока все его даты остаются пропусками текущего диапазона. Даты вне последних семи завершённых дней не инициируют новую историческую выгрузку. Поздние исправления Ozon за уже сохранённые дни автоматически не загружаются.

Для отчётов CPO передаются начало первого дня и `23:59:59` последнего дня с московским смещением. Проверка 14 октября 2026 года показала, что верхняя граница в полночь следующего дня включает строки следующей даты. Строки вне целевого периода не сохраняются: источник завершается ошибкой проверки.

| Тип | Источник |
|---|---|
| Оплата за клики за сегодня и вчера | `/api/client/statistics/products/sku`, `dateFrom = dateTo = нужный день`; пакеты по 10 кампаний |
| Пропущенные исторические дни CPC | `/api/client/statistics/json`, группировка `DATE`; ранее полученные пакеты используются повторно |
| Оплата за заказ: выбранные | `/api/client/statistic/orders/generate/json`, обычный источник заказов |
| Комбо: оплата за заказ | Тот же отчёт, источник «Кампания за клики»; стоимость кликов здесь не дублируется |
| Оплата за заказ: все товары | `/api/client/statistics/all_sku_promo/orders/generate/json` |
| Баннеры, видеобаннеры, брендовая полка | Дневные строки отчётов соответствующих кампаний |
| Блогеры, ВКонтакте, другие типы | Расходы, фактически возвращённые Performance API; неподтверждённые типы отмечаются недоступными |

Кампании читаются без фильтра по текущему состоянию. Поддерживаются `PaymentType` и `paymentType`, строка или массив `placement`; неизвестный тип сохраняется в исходном виде. Для вчерашнего CPC запрашиваются все кампании, включая остановленные и отсутствующие в дневном отчёте расходов: у них могут быть показы без кликов. Список кампаний для окна и результаты пакетов сохраняются в БД; порядок пакетов фиксирован сортировкой ID. Для остальных типов перечень подробных отчётов определяется дневной статистикой кампаний, CPC из него исключён. Внешние расходы площадок, отсутствующие в Performance API, не восстанавливаются предположениями. Надбавки вроде «Морковска» не вычисляются из сегодняшних ставок и не добавляются второй раз к готовой сумме CPO.

По [документации метода](https://docs.ozon.ru/api/performance/#operation/SearchPromoProductsSKUStatistics2) запрос статистики по SKU не расходует лимиты Performance API, но его начальная дата не может быть раньше вчерашней. Проверка на TRIS 15 октября 2026 года вернула дневные `views`, `clicks`, `expense`, `campaignId`, `sku`, `date` даже при исчерпанном лимите формирования отчётов. В запросах всегда явно передаётся дата; отсутствующие обязательные счётчики не считаются нулями.

При восстановлении исторических пропусков список CPC берётся из дневного отчёта за нужные даты: он содержит показы и клики, в том числе строки с нулевым расходом. Такие кампании сохраняются в выборке; фильтра по ненулевому расходу нет. Полностью отсутствующие в дневной статистике кампании не требуют отдельной исторической выгрузки. Уже начатые и готовые пакеты прежнего состава используются повторно. Проверка сохранённых ответов TRIS и ROCKKIDDO подтвердила наличие строк с показами без расходов; для этих данных требовалось существенно меньше кампаний, чем во всём каталоге.

В CPO расход принадлежит рекламируемому SKU (`advSku` / `adv_sku`), даже если купленный SKU другой. Поле готового расхода используется один раз, без дополнительного умножения на количество. SKU сопоставляется с каталогом своего магазина; неоднозначные и отсутствующие соответствия остаются нераспределёнными.

Баннерный отчёт может содержать только ID баннера. Для проверенной кампании метод списка объектов вернул ID баннера, а метод товаров кампании не предоставил SKU. Такие расходы сохраняются на уровне магазина. Состав покупателей после показа не заменяет состав кампании. Равное распределение допустимо только при подтверждённом составе товаров за дату расхода; текущий загрузчик не подменяет исторический состав сегодняшним и оставляет расходы без такого подтверждения нераспределёнными.

В таблице Ozon остаётся один столбец «Затраты, ₽»: сумма известных дневных расходов товара по всем типам за выбранный диапазон, по умолчанию семь завершённых дней. Десять отдельных столбцов удалены. Подсказка содержит семь строк с датами и расходами каждого типа: например, `07.10.2026 — За клики: 100 руб.; За заказ (выбранные): 150 руб.; Баннеры: нет данных`. Оплата за заказ выбранных товаров, всех товаров и Комбо остаются отдельными типами внутри подсказки.

Сводка вычисляется на backend через `Decimal`. Подтверждённое отсутствие расхода — ноль; неизвестное значение — `null`. Общая сумма включает известные расходы всех типов. Полнота и общий признак устаревания проверяются по CPC и всем частям CPO: выбранные товары, все товары и Комбо (`OZON_ADVERTISING.required_spend_kinds`). Если они подтверждены, отсутствие остальных типов, включая «Блогеры» и VK, не вызывает предупреждения или звёздочки. Исходные суммы и состояния остальных типов сохраняются в дневной разбивке. Нераспределённый расход CPC/CPO одного дня не делает неизвестными остальные дни того же типа. Если ни одного известного значения нет, столбец показывает «—». Предыдущий успешный снимок необходимого источника при ошибке обновления сопровождается общим признаком устаревания. Сортировка, фильтры и итоговая строка используют ту же сводку. Совместимое поле `advertising.spend` также заполняется из этой сводки. Историческая ошибка старого рекламного загрузчика не выдаётся за состояние новых дневных расходов.

Корректировки `totals.corrections`, не имеющие разбивки по дням, сохраняются отдельно по кампании и передаются в `advertising_unallocated`. Отдельная панель рекламы по магазинам в юнитке не отображается; ошибки Ozon показываются общими уведомлениями и пометками товаров. Суммы до корректировок могут отличаться от итогов кабинета. Поле `overExpenses` отчёта CPO сохраняется отдельно; при ненулевом значении полнота распределения CPO не подтверждается. Успешный пустой отчёт всех товаров может иметь вид `{}`; он означает подтверждённое отсутствие строк, но объект с ошибкой не считается пустым отчётом.

## CTR и CPC за выбранный период

Для вчерашнего дня сохраняются `views`, `clicks` и `expense` метода `/api/client/statistics/products/sku`. Для исторических пропусков используются `views`, `clicks` и `moneySpent` отчёта `/api/client/statistics/json` с `groupBy: DATE`. В историческом отчёте пропущенные нулевые поля трактуются как 0; явно переданный `null` остаётся неизвестным. Счётчики проверяются как неотрицательные целые числа. Старые сохранённые факты получают `null`, старые снимки — `traffic_collected: false`; они не подтверждают нулевые показатели. Поля дневных фактов сохраняются в совместимом JSON; для кэша и учёта обращений добавлены отдельные таблицы.

Новый источник `cpc` получает `traffic_collected: true` после чтения всех CPC-пакетов. Источник `campaigns` теперь содержит остальные типы и помечается `includes_cpc: false`. Старые объединённые снимки имеют `includes_cpc: true` по умолчанию; при чтении их факты и корректировки разделяются по источникам. Старый снимок без счётчиков подтверждает расход, но не полноту CTR/CPC. Для каждого дня выбирается последняя успешная версия, старые и новые расходы CPC не складываются повторно. Ошибка баннеров или CPO не скрывает сохранённый CPC.

CTR = сумма кликов / сумма показов × 100%; CPC = расходы на оплату кликов / клики. Расходы CPO, Комбо за заказ, баннеров и корректировки без даты исключены. Числитель и знаменатель собираются из одних строк с известными счётчиками; результат округляется на backend до двух знаков. При нулевом знаменателе возвращается `null`; показы без кликов дают CTR 0 и CPC `null`.

API заполняет существующие `advertising.ctr`, `cpc`, `impressions`, `clicks` и добавляет `click_spend`, `traffic_coverage`. Покрытие содержит даты, число дней, `missing_dates`, `partial_dates`, `complete` и `stale`. Несопоставленные CPC SKU с ненулевыми или неизвестными счётчиками делают день неполным; известная часть остаётся доступной. Ошибки CPO не скрывают CTR/CPC. Старые успешные данные при ошибке обновления показываются с пометкой устаревания, пересекающиеся выгрузки не удваиваются.

В таблице используются отдельные пометки полноты CTR/CPC и подсказки с формулами, счётчиками и пропусками. Итоги — отношение суммарных числителей и знаменателей; CPC использует `click_spend`, а не общие рекламные затраты. По умолчанию выбираются семь завершённых дней по Москве.

## Почасовое обновление и закрытие суток

Сегодняшние снимки CPC/CPO имеют `finalized: false` и `refresh_slot` с московским часом начала запуска. В следующем часу создаётся новый ключ запросов; внутри часа повтор использует готовые ответы и сохранённые UUID. Пропущенные часы не выгружаются отдельно: загружается текущий накопленный итог дня. Отчёты CPO формируются на кабинет, а не на каждый товар. Другие типы кампаний внутри дня не запрашиваются.

После полуночи предварительный снимок не подтверждает завершённый день. Финальная загрузка использует отдельный ключ без `refresh_slot`, поэтому сегодняшний кэш не замораживает вчерашние цифры. Старые исторические снимки совместимы: отсутствие `finalized` означает `true`; ключи прежних запросов не меняются. Успешные завершённые дни не опрашиваются повторно. При ошибке источника повторяются только его отсутствующие/ошибочные даты. Ранее начатый CPO-отчёт предыдущего часа сначала дочитывается по UUID; новый отчёт до этого не создаётся. Сохранённый запрет генерации после суточного 429 действует для всех часов.

Калькулятор использует `products[].calculator`: московский день, общий ТО после отмен и выкуп, отдельные `clicks`/`orders` с ДРР, покрытием и временем данных. `click_spend`/`order_spend` могут быть известны независимо от заказов. CPO включает выбранные товары, все товары и только заказную часть Комбо; клики в него не входят. Чтение карточки не запускает внешние запросы.

## Хранение и HTTP-контракт

Новые таблицы создаются штатным `init_db` для SQLite и PostgreSQL:

- `ozon_advertising_daily_facts`: дневные строки с исходными идентификаторами, суммой и способом распределения.
- `ozon_advertising_source_windows`: полнота источника за окно, последняя попытка и успешный снимок, включая корректировки.
- `ozon_advertising_reports`: UUID запросов и признак незавершённого получения отчёта.
- `ozon_advertising_responses`: параметры и содержимое готовых ответов, включая пакеты CPC, список кампаний и дневную статистику.
- `ozon_advertising_cooldowns`: срок запрета создания отчётов по кабинету после суточного лимита.
- `ozon_advertising_requests`: время, магазин, метод, путь, период, число кампаний, HTTP-результат, безопасный код ошибки и число единиц принятой генерации. Токены, ключи и тело авторизации не сохраняются.

Замена строк источника за период и успешного снимка выполняется одной транзакцией. Повтор не удваивает суммы; успешный пустой ответ удаляет прежние строки заменяемого периода. Ошибка сохраняет успешный снимок того же периода с признаком устаревания. После смены семидневного окна предыдущая неделя не выдаётся за текущую.

Запросы ограничены по частоте, обрабатываются `429`, `Retry-After`, обновление токена и отмена. UUID сохраняется сразу после получения, готовое содержимое — до завершения источника. Повтор сначала читает локальный ответ, затем ранее полученный UUID, и только при их отсутствии создаёт отчёт. Исчезнувший UUID удаляется после 404 и может быть создан заново следующей попыткой. Генерация не повторяется автоматически после неоднозначного сетевого сбоя; следующая попытка задачи может создать новый отчёт, если UUID получить не удалось.

По [лимитам Ozon](https://docs.ozon.ru/api/performance/#tag/Limits) одна кампания считается одной выгрузкой: пакет из 10 кампаний расходует 10 единиц. Общий лимит HTTP-запросов и лимит выгрузок различаются; ограничение выгрузок указано за 24 часа, сброс в полночь не предполагается. Журнал считает принятые API генерации, а не выдаёт локальную сумму за официальный остаток квоты; при сетевом сбое результат создания может быть неизвестен. Для CPO без списка кампаний журнал отмечает одну принятую генерацию; это не подтверждённая стоимость такого отчёта в квоте Ozon.

Тело ошибки 429 различает суточный лимит, лимит активных отчётов и временное ограничение частоты. Суточный лимит не повторяется: запрет генерации сохраняется до `Retry-After`, а без положительного срока — на 24 часа с момента ошибки. Он действует после перезапуска и проверяется до авторизации. Чтение сохранённых ответов/UUID и метод статистики по SKU продолжают работать. Остальные временные ошибки повторяются ограниченное число раз; очередная попытка задачи пропускает уже сохранённые дни и пакеты. Интервал проверки готовности отчёта растёт от 3 до 30 секунд; долгий `NOT_STARTED` не вызывает создание нового отчёта.

`GET /api/unit-economics-1c/ozon` сохраняет существующие поля. Дополнительно возвращает:

- `products[].advertising.breakdown[]`: тип, сумма, семь дневных значений, состояние, время обновления, исходные типы и способ распределения.
- `products[].advertising.spend_summary`: период, известная сумма, признаки `complete`/`stale` и семь элементов `days`. Каждый день содержит известную сумму, признаки полноты/устаревания и `breakdown[]` с типом, известной суммой, состоянием, исходными типами и признаком устаревания. Эта сводка используется в «Затраты, ₽»; прежняя разбивка сохраняется для совместимости.
- `advertising_unallocated[]`: период и нераспределённые расходы каждого доступного магазина, корректировки и перерасход CPO.

Деньги сериализуются десятичными строками, неизвестные суммы — `null`. Frontend форматирует деньги, даты и подсказки. Полный ноль показывается только после успешного отчёта. В старом `breakdown[].amount` неполный расход по-прежнему обозначается `null`; `spend_summary` дополнительно предоставляет известную часть с признаками неполноты. Сводка и разбивка относятся к диапазону HTTP-запроса. Чтение использует сохранённые дневные записи и пересекающиеся старые окна без сетевых запросов.

## Проверка

Использовать временные сценарии, без постоянных тестовых файлов: граница суток Москвы, разные рекламируемый/купленный SKU, разделение CPO/Комбо, повторы и удаление устаревших строк, пустые ответы, сохранение снимка при ошибке, `429`, обновление токена и продолжение по UUID. Проверять сумму семи дней, отдельные корректировки, единственный столбец затрат, сортировку, фильтры, итоговую строку, дневные подсказки и неизменность прежних показателей. Проверять отдельно подтверждённые нули, отсутствие всех данных, частичную известную сумму, нераспределённый расход только одного дня и устаревший снимок.

При реализации выполнена загрузка 7–13 октября 2026 года для четырёх настроенных кабинетов: все три источника завершились успешно, все рекламные SKU сопоставились с каталогом. Баннеры остались на уровне магазинов. PostgreSQL проверяется компиляцией DDL; подключение к живой PostgreSQL для этой проверки не использовалось.

## Чтение неполного диапазона

Для каждой пары «день / источник» выбирается последняя успешная версия из пересекающихся окон по `synced_at`. Дневные факты разных версий не складываются. Даты вне диапазона исключаются. Более поздняя ошибка не удаляет успешные данные: соответствующие дни получают `stale`.

`spend_summary.missing_dates` содержит даты без известных расходов, `partial_dates` — даты с известной частью, но без подтверждённой полноты CPC/CPO. Даже при отсутствии одного дня сумма остальных дней отображается со звёздочкой и выделением, как в WB/ЯМ. Подсказка перечисляет пропуски и частичные даты. Итоги, фильтры и сортировка используют эту же сумму. Подтверждённый ноль отличается от отсутствующего значения.

Нераспределённые расходы магазина также суммируются по доступным дням. Корректировки без даты и `over_expenses` не распределяются на пересечение диапазонов: дополнительное поле `advertising_unallocated[].adjustments[]` содержит исходный период, источник, время получения, корректировки и перерасход каждого использованного окна. Они сохраняются в API с периодом отчёта и не входят в сумму товара. Совместимые поля `corrections` и `over_expenses` содержат только окна, в точности совпадающие с запросом.
