# Цены Ozon и дневная история

Статус на 19 октября 2026 года: загрузчик подключён к расписанию и ручным запускам,
репозитории — к JSON API экономики, клиентские компоненты — к карточке товара Ozon.
[Состояние объединения](architecture.md#состояние-объединения-19-октября-2026).

Калькулятор Ozon показывает четыре цены из Seller API. Та же загрузка сохраняет комиссию за продажу FBO по каждому товару и дню. Асинхронная загрузка работает для включённых кабинетов с настроенными ключами, независимо от открытой страницы. Формула маржинальности, изменение цен в Ozon и интерфейс календаря в этот сценарий не входят.

## Источники и сопоставление

| Поле `product.price` | Источник Ozon | Значение |
|---|---|---|
| `black_price` | `website_prices.prices_by_schema.FBO.black_price`, при отсутствии — FBS | Цена с СПП |
| `green_price` | `website_prices.prices_by_schema.FBO.green_price`, при отсутствии — FBS | Цена с Кошельком |
| `base_price` | `price.price` | Цена поставщика |
| `seller_price` | `price.marketing_seller_price` | Цена с учетом акции; без дополнительной скидки Ozon |

Две цены продавца загружаются через [`/v5/product/info/prices`](https://docs.ozon.ru/api/seller/#operation/ProductAPI_GetProductInfoPrices), с `visibility=ALL` и обходом `cursor`. Витринные цены получаются из [`/v2/actions/products`](https://docs.ozon.ru/api/seller/#operation/ActionsProducts) по списку `/v1/actions`. Для товаров с недостающими витринными полями обходятся [`/v2/actions/candidates`](https://docs.ozon.ru/api/seller/#operation/ActionsCandidates). Обе выборки акций используют `last_id`; повтор курсора и превышение предела страниц считаются ошибкой неполной выгрузки. Контракты проверены живыми ответами API в октябре 2026 года. Поле `price.old_price` игнорируется на входе и не участвует в наблюдениях.

По каждому витринному полю сначала выбирается FBO, а при отсутствии значения FBO среди участников и кандидатов — FBS. Внутри выбранной схемы участники акций имеют приоритет над кандидатами. Различающиеся значения одного поля среди выбранных источников дают `conflict` и `amount=null`; одинаковые объединяются с сохранением идентификаторов акций. Конфликт FBO не маскируется значением FBS. Поле `scheme` сохраняет использованную схему; в прежних записях оно отсутствует и читается как `null`. При отсутствии обеих схем сохраняется `missing`. Полное покрытие всех товаров четырьмя ценами API не гарантирует.

Сопоставление выполняется по кабинету и `product_id`. `offer_id` сохраняется как артикул продавца; он не равен SKU. «Цена с СПП» и «Цена с Кошельком» — подписи исходных витринных полей выбранной схемы, без дополнительных расчётов. Значения API могут отличаться от цены конкретного покупателя на сайте.

## Хранение

`ozon_prices_current` хранит последнее состояние каждого товара. `ozon_prices_daily` имеет ключ `(store_slug, product_id, day)` и содержит первые и последние наблюдения каждого из четырёх полей, артикул, полноту и `closed_at`. Дата определяется по времени получения соответствующего ответа в Москве; метки времени сохраняются с часовым поясом. Полнота новых записей зависит только от этих четырёх цен.

При чтении сохранённого JSON репозиторий игнорирует только прежнее поле `old_price`; остальные поля проходят строгую проверку DTO. Новые записи и обновления текущих цен и открытой дневной истории не содержат зачёркнутую цену. Закрытые исторические записи физически не переписываются, включая прежний флаг полноты по пяти ценам. Поле `old_price` в API не возвращается. Изменение схемы таблиц и отдельная миграция данных не требуются.

Денежные значения валидируются как конечные неотрицательные `Decimal` и сохраняются точными строками в типизированном JSON. Отсутствие данных отличается от нуля. Для каждого поля сохраняются сумма, валюта, источник, идентификаторы акций, время получения и последней попытки, состояние. Первое наблюдение поля внутри дня не перезаписывается; последнее обновляется только более новым или равным по времени ответом.

При ошибке источника последние текущие значения и время их получения сохраняются, состояние становится `error`. Дневная запись продолжает содержать фактически полученные наблюдения. Успешный ответ без поля обновляет его на `missing`. Значения прошлых дней не копируются в новую дневную запись.

В 00:00 МСК закрытие фиксирует последние наблюдения прошедшего дня, выставляя `closed_at`. Закрытые записи становятся неизменяемой дневной историей. Если за день ответов не было, записи за него нет. Загрузка цен, закрытие дня и восстановление после простоя используют одну блокировку на кабинет; незакрытые прошлые дни закрываются из сохранённых наблюдений при следующем запуске. Запрос сегодняшних цен не восстанавливает прошлое. История автоматически не удаляется.

Таблицы регистрируются обычной инициализацией схемы; существующие таблицы WB/ЯМ не изменяются. Добавление схемы совместимо с SQLite и PostgreSQL. Перед запуском новой версии существующего приложения требуется штатная инициализация схемы.

## Задачи и JSON-контракт

### Комиссия за продажу FBO

Из тех же ответов `/v5/product/info/prices` читается `commissions.sales_percent_fbo`. Отдельные HTTP-запросы для комиссии не выполняются. Контракт проверен 15 октября 2026 года живыми ответами шести кабинетов: у всех 909 товаров поле было заполнено. Это процент комиссии по текущим условиям товара, а не фактическое удержание в рублях. Комиссии других схем, доставка и возвраты в этот показатель не входят.

Процент валидируется как конечный `Decimal` в диапазоне 0–100. Нулевой процент доступен; отсутствующее поле сохраняется как `percent=null`, `state=missing`. Для каждого наблюдения сохраняются источник, время получения и последней попытки. Пока успешного значения за текущий день нет, ошибка источника сохраняет предыдущий процент и время получения в текущей записи, меняет состояние на `error` и обновляет время попытки; дневная история не заменяется ошибкой. Уже полученная за сегодня комиссия, включая нулевую, не меняется при последующей ошибке почасовой загрузки цен.

`ozon_fbo_commissions_current` хранит последнее состояние по `(store_slug, product_id)`. `ozon_fbo_commissions_daily` хранит первое и последнее наблюдение по `(store_slug, product_id, day)`, артикул и `closed_at`. Дата наблюдения определяется по Москве. По каждому товару сохраняется первое успешное значение за день. После этого повторные ответы не меняют процент, времена получения и попытки или артикул ни в текущей записи, ни в дневной. До успеха можно догружать отсутствующие и ошибочные значения; более старый ответ не заменяет последнее наблюдение. Новые товары получают свой первый снимок при появлении в ответе. Существующая структура первых/последних наблюдений сохраняется для совместимости истории; при успешном первом ответе оба значения одинаковы. Данные комиссии хранятся отдельно от четырёх цен и не меняют полноту их исторических записей или текущий JSON-контракт калькулятора.

Комиссия сохраняется один раз за московский день при первом успешном ответе `ozon_prices_sync`. Сама загрузка цен остаётся почасовой; повторные ответы комиссии пропускаются без записи в БД. Если значения ещё нет, следующие запуски повторяют попытку. В 00:00 МСК `ozon_prices_daily_close` закрывает прошедшие дни цен и комиссий под общей блокировкой кабинета. При восстановлении после простоя закрываются также дни, в которых есть только комиссия, независимо от API-ключей. Закрытая история неизменяема. Пропущенные дни не заполняются текущей ставкой; первоначальная загрузка начинает историю с фактического дня получения ответа. Чтение текущих значений и диапазона дневной истории выполняется асинхронным `AsyncCommissionsRepository` без API-запросов.

Новые таблицы регистрируются в штатной инициализации схемы через `metadata.create_all`; изменение существующих таблиц и перенос старой истории цен не требуются. Схема поддерживает SQLite и PostgreSQL. Перед запуском обновлённого worker нужна штатная инициализация схемы. Названия задач и расписание сохраняются; их описания включают сохранение комиссии. Автоматическая история требует работающего worker и включённой задачи загрузки цен для кабинетов.

### Задачи и цены в API

- `ozon_prices_sync` — каждый час от начала предыдущего запуска, с ручным запуском и настройками кабинетов в разделе обновлений; обновляет цены и сохраняет комиссию FBO только при отсутствии успешного снимка товара за текущий день.
- `ozon_prices_daily_close` — ежедневно в 00:00 МСК, также запускается после старта для восстановления пропущенного закрытия. Закрывает сохранённые дни цен и комиссий независимо от наличия текущих API-ключей.
- Обе задачи используют `AsyncBackgroundJob`, `AsyncResources`, асинхронные HTTP/SQL и существующие блокировки. Кабинеты выполняются через `TaskGroup`; страницы внутри кабинета последовательно. Ошибки кабинетов изолированы. Повторы задач: 1, 5 и 15 минут; HTTP учитывает ограничения и `Retry-After` через общий клиент.
- Метаданные и расписания определены в `JOBS`, `JOB_SCHEDULE_RULES`, `OZON_PRICES`. Автоматическая работа требует запущенного штатного worker и включённых задач; веб-процесс сам расписание не запускает.

`GET /api/unit-economics-1c/ozon` в списке и карточке возвращает каждое новое поле цены объектом: `amount` (десятичная строка или `null`), `currency`, `received_at`, `attempted_at`, `source`, `action_ids`, `state`, `stale`. Состояния: `available`, `missing`, `conflict`, `error`. При чтении сохранённые данные старше двух часов или после ошибки источника помечаются устаревшими. Старые совместимые поля `current`, `with_spp`, `with_wallet` остаются пустыми: формула WB к Ozon не применяется.

GET только читает БД. Права и переключатель preview сохраняются. Отображение, подписи, формат денег и времени находятся в `static/economics/ozon/prices.js` и `prices.css`. В калькуляторе скрыты прежние строки цен WB; сохранение цен в маркетплейс остаётся недоступным.

## Проверка

Временные проверки покрывают пагинацию и зацикливание курсора, приоритет FBO и резервную цену FBS, кандидатов акций, совпадения и конфликты цен, нули, ошибки источников и независимость кабинетов. На временной SQLite проверены первые/последние наблюдения, переход через полночь, атомарный отказ изменения закрытого дня, повторное закрытие и восстановление без заполнения пропусков. При подключении проверены SQLite и отдельный PostgreSQL 17: запуск через планировщик, четыре цены, комиссия, закрытие истории и повтор без изменений. В Chrome проверены связанный пересчёт, подробный режим, сброс и закрытие карточки. Ответы Ozon в этих проверках подменены; это не проверка production API.

Для комиссии FBO дополнительно проверены границы процента, точность дробной ставки, различие нуля и отсутствия, порядок ответов, сохранение ставки при ошибке, закрытие дней без цен и отсутствие дополнительных HTTP-запросов. Ошибка витринных цен не мешает сохранять комиссию из ответа продавца. Первая фактическая загрузка 15 октября 2026 года записала 909 текущих и 909 дневных комиссий шести кабинетов; сохранённые записи прочитаны обратно через типизированный репозиторий. Для артикула продавца `1015852320` кабинета Toyka подтверждена ставка 51%.

Однократное дневное сохранение проверяется повторными почасовыми запусками с изменённой ставкой: цены обновляются, успешная комиссия и её временные метки остаются прежними. Проверяются повтор после отсутствующего поля, нулевая ставка, ошибки после успеха, новый московский день и сохранение первого значения после перезапуска процесса.

Проверяются Ruff, mypy, синтаксис JavaScript и калькулятор в браузере на отдельном проверочном сервере. Постоянные тестовые файлы в проект не добавляются.

Четыре цены размещены внутри списка полей калькулятора в порядке: «Цена поставщика», «Цена с учетом акции», «Цена с СПП», «Цена с Кошельком». Они используют общие строки и поля WB: подпись слева, числовое поле и валюта справа. Значения всех четырёх цен имеют обычный цвет текста; специальная окраска цены с Кошельком не применяется. Все четыре цены связаны через скидку акции продавца, СПП и скидку кошелька. Изменение любой цены пересчитывает остальные с сохранением текущих процентов скидок. После четырёх цен в обоих режимах размещены редактируемые «Скидка СПП, %» и «Скидка с Ozon Кошельком, %». Значения загружаются из сохранённых ответов API; локальные правки сохраняются при переключении вкладок и обновлении открытой карточки. Смена товара, закрытие карточки и кнопка «Сбросить» очищают правки. Они не записываются в БД, историю цен или Ozon. Время получения и состояние источника доступны в подсказке строки.

## Комиссия в расширенном калькуляторе

Только в расширенном режиме после цен отображаются «Комиссия Ozon FBO, %» и непосредственно под ней «Комиссия Ozon, руб». Ставка читается из сохранённой ежедневной комиссии по кабинету и `product_id`. Исходная сумма рассчитывается на сервере как `price.marketing_seller_price × percent / 100`, с округлением до копеек `ROUND_HALF_UP`. Это поле «Цена с учетом акции», до дополнительной скидки Ozon. Такая база соответствует цене без СПП в калькуляторе WB и цене продавца в калькуляторе Яндекса. Базовая цена до акций, цена с СПП и цена с Кошельком не используются. Пример: 1 769 ₽ × 51% = 902,19 ₽.

`OzonProduct.commission` содержит `percent`, `amount`, `price` (база расчёта), `state`, `source`, `received_at`, `attempted_at`, `stale`. Старый дневной снимок и ошибка источника отмечаются в подсказке; отсутствие ставки или базы не заменяется нулём. Подтверждённая нулевая ставка при известной цене даёт нулевую сумму.

Локальное редактирование цены с учётом акции или процента пересчитывает сумму. При редактировании суммы рассчитывается процент от той же цены. Интерфейс отправляет связанные изменения в `POST /api/unit-economics-1c/ozon/prices/calculate`, без записи в БД и без вызова Ozon. Отдельный `POST /api/unit-economics-1c/ozon/commission/calculate` (`OzonCommissionRequest` → `OzonCommissionCalculation`) сохраняется для независимого расчёта комиссии. Frontend отображает ответ, отменяет устаревшие запросы и хранит черновик в пределах открытого товара.

С 20 октября 2026 года изменение любой связанной цены автоматически выбирает
ставку по итоговой `seller_price`: `0 < цена <= 100` — 17%, `100 < цена <= 300` —
23%, с исключениями из [справочника категорий](ozon-tariffs.md). Для примера 299 ₽
нужно ввести 299 в **«Цену с учётом акции»**: комиссия будет 23% и 68,77 ₽.
Обычная ставка хранится отдельно и восстанавливается выше 300 ₽. Если исходный
товар уже был недорогим, для обычной ставки нужен сопоставленный тариф категории;
без него она остаётся неизвестной. Пустая цена остаётся `null`, некорректная
отклоняется. Ручной ввод комиссии действует до следующей правки цены/скидки
или выбора категории. Пересчёт не требует нажатия «По справочнику».

Новая сумма комиссии передаётся в [сценарий калькулятора](ozon-calculator.md),
который обновляет чистую прибыль и ROI. Сброс, закрытие карточки и смена товара
очищают локальные правки и заново применяют правило к исходным данным.
Обработчики формул WB к этим полям Ozon не применяются.


## Связь цен калькулятора

Типизированный `POST /api/unit-economics-1c/ozon/prices/calculate` принимает `OzonPriceCalculationRequest` (`values`, `initialize`, последовательность `edits`, необязательный `tariff_id`) и возвращает `OzonPriceCalculation`. При инициализации backend определяет текущие проценты из сохранённых цен. Последующие изменения применяются последовательно; frontend отменяет устаревшие ответы и сохраняет ещё не обработанные изменения нескольких полей. Расчёт выполняет `app/economics/ozon_price_calculator.py`, контракты находятся в `app/dto/ozon_price_calculator.py`. Доступ требует активной сессии и доступа к предварительной экономике Ozon. Расчёт не обращается к API Ozon и не записывает данные.

- Скидка акции = `(1 − цена с акциями / цена поставщика) × 100%`; она сохраняется для связи первых двух цен, отдельного поля в интерфейсе нет.
- СПП = `(1 − цена с СПП / цена с акциями) × 100%`.
- Скидка кошелька = `(1 − цена с кошельком / цена с СПП) × 100%`.
- Цена с акциями = `цена поставщика × (1 − скидка акции / 100)`.
- Цена с СПП = `цена с акциями × (1 − СПП / 100)`.
- Цена с кошельком = `цена с СПП × (1 − скидка кошелька / 100)`.

При изменении цены она становится опорной: верхние цены вычисляются делением на соответствующие коэффициенты, нижние — умножением. При редактировании СПП сохраняются цена поставщика и цена с акциями, пересчитываются цена с СПП и цена с кошельком. При редактировании скидки кошелька меняется цена с кошельком. Денежные результаты округляются до копеек `ROUND_HALF_UP`, проценты — до восьми десятичных знаков. В исходном примере 2 180 → 1 293 → 1 164 ₽ получаются СПП 40,68807339% и скидка кошелька 9,97679814%.

Отсутствующая цена или коэффициент не заменяются нулём. При нулевой исходной базе процент скидки неизвестен. Скидка 100% даёт нулевую следующую цену; обратное изменение этой нулевой цены сохраняет известные верхние цены, а положительная цена при скидке 100% отклоняется. Скидки выше 100%, отрицательные цены, нечисловые значения и комиссия в рублях больше цены с акциями отклоняются. Отрицательная скидка допустима, если следующая цена выше предыдущей, чтобы корректно представлять такие исходные данные API. Ошибка пересчёта отображается возле полей.

## Себестоимость и комиссия компании

Оба параметра загружаются из общей [Google-таблицы](https://docs.google.com/spreadsheets/d/1q0WL6OB3Edh2O1ogqx7CK3MAij3O6xjD6gE0i3q3qEY/edit), из листов, названия которых заканчиваются на `OZON`. `app/economics/sources/ozon.py` сопоставляет «Артикул ОЗОН» с `stock_items.mp_product_id`, колонку «Себес, руб» — с `purchase_price`, «ДРР %» — с `team_commission_percent`, «Проч.затр, руб» — с `fulfillment_cost`. Это комиссия компании, отдельная от рекламного ДРР Ozon и комиссии маркетплейса.

Задача `ozon_unit_economics_1c_source_sync` запускается ежедневно в час `CHECKSTOCK_UNIT_ECONOMICS_1C_SOURCE_SYNC_HOUR` (по умолчанию 02:00 МСК); действуют настройка включения задачи и повторы планировщика. При чтении карточки используются сохранённые `unit_economics_1c_source_values`, без запроса Google. В `product.details` передаются `purchase_cost`, `team_commission_percent`, название листа, номер строки и `source_synced_at`. Поля калькулятора закупки и комиссии компании заполняются из этих значений.

Сопоставление идентификатора ограничено магазинами из названия листа по общим правилам импорта 1С. Например, `TRIS OZON` применяется только к TRIS, а `SOKOLOFF и TRUSTHOME OZON` — к двум указанным магазинам. Идентификатор из листа другого магазина не переносит его себестоимость и не создаёт ложный конфликт. Листы без распознаваемого названия магазина сохраняют общую область поиска. Одинаковые дубли объединяются; несовпадающие данные одного товара внутри разрешённой области завершают загрузку ошибкой до записи. Прежние значения и дата их загрузки при ошибке сохраняются. Номер строки в сообщении о конфликте обозначает происхождение записи, а не величину себестоимости.


Редактирование выкупа, ТО, рекламы, расходов и налогов, связи с ценами и общий сброс описаны в [контракте калькулятора Ozon](ozon-calculator.md). Правки сценария не изменяют настройки кабинета или исходные выгрузки.
