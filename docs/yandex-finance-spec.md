# Функциональное ТЗ финансового отчёта Яндекс Маркета

Нужно добавить в CheckStock финансовый отчёт по магазинам Яндекс Маркета: от созданных заказов и состоявшихся продаж до расходов площадки, себестоимости и маржинальной прибыли. Каждый показатель должен иметь понятное основание, дату учёта и расшифровку. Пользователь должен видеть, какие данные загружены полностью, какие устарели и почему отдельную сумму пока нельзя посчитать.

Это проект требований для самостоятельной реализации от текущего кода. Предложенные ниже правила первой версии являются рабочей основой разработки; они не означают, что финансовые формулы уже реализованы. Код старой ветки переносить целиком не требуется.

Основание разработки: ветка `codex/yandex-finance`, созданная от `codex/analyzer`, коммит `48e536d`. Ревью относится к `feat/yandex-finance`, коммиту `030f43e`. Дата ТЗ: 7 октября 2026 года.

Реализация по последующему поручению ведётся от `master` (`f8b4a13`) в `codex/yandex-finance-implementation`. Текущий контракт, результаты проверок и оставшиеся условия пилота описаны в [инструкции реализации](yandex-finance.md). Этот документ сохраняет исходные требования, а не заменяет отчёт о проверенных возможностях.

## Результат первой версии

Пользователь открывает «Финансовые отчёты → Яндекс Маркет», выбирает магазин и период, получает финансовые показатели и может открыть их состав по дням и операциям. Программа использует уже загруженные локальные данные. Загрузка из Маркета выполняется отдельной фоновой задачей или ручным заданием администратора.

Первая версия включает:

- сводку по одному магазину и всем доступным магазинам;
- финансовый результат по реализации, отдельную воронку заказов и отдельный блок выплат;
- учёт нескольких кабинетов и кампаний в финансовом контуре;
- расходы, возвраты, корректировки и закупочную стоимость;
- подробности источников, полноты и времени обновления;
- ручную загрузку периода, ежедневное обновление и пересчёт из сохранённых источников;
- воспроизводимую сверку с официальными отчётами.

Банковская интеграция, налоги, внешний маркетинг, зарплаты и распределение общехозяйственных расходов не входят в формулу первой версии. Прибыль подписывается как маржинальная прибыль до налогов и внешних расходов. Автоматическое равенство показателей PiData не является критерием приёмки: сначала должны совпасть определения показателей и правила периодизации.

Экспорт в Excel, отдельный API для ИИ-агентов и финансовые отчёты по ограниченному набору товаров можно добавить следующей очередью. В первой версии проверка чисел обеспечивается расшифровкой на странице и сохранёнными исходными операциями.

## Пользовательские сценарии

### Просмотр отчёта

1. Пользователь открывает страницу `/finance-reports/yandex`.
2. По умолчанию выбран период последних семи завершённых дней по Москве и все разрешённые магазины.
3. Можно выбрать конкретный магазин и произвольный период до 366 календарных дней включительно.
4. Страница показывает выбранный период, состав магазинов, время последнего успешного обновления и состояние данных.
5. Смена фильтра читает локальную базу. Она не генерирует новые отчёты в Маркете и не запускает пересчёт истории.
6. Сводка раскрывается по дням. У суммы доступна детализация операций, из которых она получена.

Сегодняшний день допускается выбрать явно; он всегда помечается как незавершённый. Дата в будущем и перевёрнутый диапазон отклоняются. Начальная и конечная даты в интерфейсе включительны; внутренний полуоткрытый интервал должен покрывать их целиком.

### Детализация суммы

Для каждой операции показывать доступные пользователю поля: магазин, кабинет, кампания, дата события, тип, заказ, артикул, количество, сумма, валюта, статья расхода или дохода и источник. Рядом показывать время загрузки и признак корректировки. Сумма деталей должна объяснять итог строки с учётом указанного округления.

Отдельные фильтры по типу события и статье помогают объяснить расхождение. Отсутствие карточки товара в текущем каталоге не удаляет историческую операцию. Полный JSON ответа площадки и секреты через пользовательский API не выдаются.

### Неполные и устаревшие данные

Различать следующие состояния:

| Состояние | Что видит пользователь |
| --- | --- |
| Данные полные | Число, включая подтверждённый ноль. |
| Данные частичные | Пометку «Неполные данные», доступную часть и перечень отсутствующих источников или дат. |
| Данные не загружены | Прочерк и причину; отсутствие строк не превращается в ноль. |
| Последнее обновление завершилось ошибкой | Последний успешно опубликованный результат, его дату и заметное предупреждение об устаревании. |
| Расчёт невозможен | Прочерк у зависимого показателя и конкретную причину, например отсутствующую закупочную цену. |
| Идёт обновление | Старый результат остаётся доступным; статус задания показывается отдельно. |

Полнота и свежесть являются разными признаками. Полностью загруженный вчерашний снимок может устареть после неудачного сегодняшнего обновления. Он не должен смешиваться с половиной новой загрузки.

Частичный итог не выдаётся за итог всего периода. Для прибыли и её процента официальный итог остаётся неизвестным, если обязательные входные данные неполны; вычислимую часть можно показать отдельно и явно подписать.

## Права доступа

Добавить отдельное право раздела `FINANCE_YANDEX`. По умолчанию новый раздел доступен суперадминистратору; выдача остальным выполняется через существующее управление правами. Дополнительно всегда проверяются доступ к площадке Яндекс Маркет и разрешённые магазины.

Для сводки, детализации, списка фильтров и статуса загрузки действует одна область доступа. «Все магазины» означает только разрешённые магазины текущего пользователя. В запрос репозитория передаётся явный список разрешённых идентификаторов; пустой список даёт пустой результат, а не снимает фильтр.

Запрос конкретного недоступного магазина возвращает 404. Отсутствие права раздела возвращает 403. Проверка выполняется на сервере независимо от наличия ссылок в меню.

Первая версия представляет финансовый итог целого магазина. Пользователь, ограниченный отдельными товарами или менеджером, не получает через этот раздел общий итог магазина даже при доступе к юнит-экономике. До реализации полноценного товарного отчёта сервер отклоняет такой просмотр с понятным объяснением ограничения. Расходы всего кабинета нельзя раскрывать ему через итоги, статусы, фильтры или расшифровки.

Управление ключами, кабинетами и ручными заданиями доступно суперадминистратору. Просмотр отчёта не даёт права менять подключения. Финансовые ответы получают `Cache-Control: private, no-store`; общий кэш не смешивает пользователей и их области доступа.

## Подключения магазинов и кабинетов

Финансовое подключение описывает магазин CheckStock, Business ID, разрешённые Campaign ID и ссылку на секрет API. Один магазин может иметь несколько кабинетов. В интерфейсе администратора нужны список подключений, добавление, замена ключа, проверка доступа, выбор кампаний и отключение.

Обязательные правила:

- Старый формат с `api_key`, необязательным `business_id` и списком `campaigns` продолжает работать для существующих загрузчиков.
- Новый финансовый адаптер получает подключения явно. Добавление кабинета не заставляет старые загрузчики автоматически использовать первый ключ из нового списка.
- При неоднозначной старой привязке финансовое подключение получает состояние «Нужно выбрать кабинет». Действующий ключ не объявляется отсутствующим.
- Проверка подключения проверяет необходимые финансовые доступы, а не только присутствие кампании в списке кабинетов.
- При обновлении ключа отсутствие поля кампаний означает сохранение выбора. Пустой выбор и «все кампании» задаются явно разными состояниями.
- Выбор кампаний одинаков для заказов, реализации, услуг и платежей. В адаптерах используются фильтры конкретного метода API.
- Одна кампания за один исторический интервал принадлежит одному магазину CheckStock. Конфликт привязки отклоняется до загрузки.
- Отключение кампании прекращает будущие задания, но не удаляет её ранее загруженную историю. Переназначение магазина имеет дату действия и явный сценарий пересчёта.
- Секрет хранится отдельно от финансовых фактов. В журнал, детализацию и ошибки ключ не попадает.

Кабинетские расходы без кампании сохраняются один раз на кабинет. Число выбранных кампаний не является множителем расходов. Если расход нельзя отнести к конкретному магазину по подтверждённому правилу, он показывается как нераспределённый; полный результат затронутого магазина не объявляется достоверным. Пользователь с доступом лишь к части кабинета получает только факт невозможности полного расчёта, без чужой суммы.

## Источники и правила их использования

Внутренняя модель разделяет четыре назначения данных. Совпадающий заказ в нескольких отчётах не означает несколько продаж.

| Назначение | Источник и способ использования |
| --- | --- |
| Созданные заказы и их состав | Business Orders и операционный отчёт по заказам; использовать дату создания и исходную стоимость заказа. |
| Реализация и финансовые возвраты | Официальный отчёт по реализации как основной источник количества и финансовых событий; операционный отчёт помогает сопоставить строки. |
| Услуги и корректировки Маркета | Отчёт по стоимости услуг; каждая денежная операция учитывается в своей статье один раз. |
| Платежи и взаиморасчёты | Отчёт по платежам; отдельная денежная хронология с собственными идентификаторами транзакций. |

Для основной сводки выбирается учёт по событиям реализации, а не по строкам комиссии за перевод денег. Если в текущем месяце основной источник ещё не сформирован, соответствующий интервал остаётся предварительным или незагруженным. Оперативная оценка допустима только как отдельный явно обозначенный результат; она не подменяет подтверждённый итог.

Отчёт по реализации запрашивается по кампании и календарному периоду, предусмотренному методом. В нём есть отдельные листы доставленных и возвращённых товаров, а также поля количества. Адаптер должен различать структуры отчётов и значение SKU. Основание: [документация отчёта по реализации](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateGoodsRealizationReport).

Отчёт по услугам поддерживает `campaignIds`; максимальный период запроса ограничен тремя месяцами. `lateOrderExecutionFeeTariff` является процентным тарифом, а не денежным начислением. Эти особенности должны быть отражены в адаптере. Основание: [документация отчёта по стоимости услуг](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateUnitedMarketplaceServicesReport).

Для сопоставления заказов нужны строки конкретных товаров и финансовые признаки, а не один произвольно выбранный статус заказа. Поля и структура проверяются по [операционному отчёту по заказам](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateUnitedOrdersReport). Для денежного движения используются собственные даты и ID транзакций из [отчёта по платежам](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateUnitedNettingReport).

Перед реализацией каждого адаптера составить проверяемую таблицу соответствия: файл и поле источника → внутреннее поле → единица измерения → правило знака → дата учёта → обязательность. К ней приложить обезличенный пример реального формата и ожидаемые результаты. Документация API не заменяет проверку фактических выгрузок.

Если назначение поля, количество или дата неизвестны, адаптер фиксирует проблему качества. Запрещено автоматически считать такую строку одной штукой, принимать неизвестную сумму за ноль или определять вид операции по случайному фрагменту текста.

## Единая модель событий

### Идентичность товаров и операций

Связь товара с заказом должна включать кабинет, кампанию, заказ и товарную строку. Артикул добавляется как обязательное аналитическое измерение, но сам по себе не гарантирует уникальность строки. Один заказ может содержать разные SKU, несколько единиц одного SKU, частичный возврат и несколько финансовых операций.

У финансового события хранить тип, исходный ID операции, связанные заказ и товарную строку, количество, суммы, валюту, дату события, дату начисления, источник и версию загрузки. Если источник не предоставляет ID, правило составного ключа разрабатывается отдельно для этого типа отчёта и проверяется на повторных строках.

Хеш JSON подходит для контроля неизменности исходного содержимого. Он не является универсальным ключом операции: две одинаковые строки могут представлять две реальные единицы товара. Без доказательства уникальности такие строки нельзя схлопывать.

Исходные архивы или их точные строки сохраняются отдельно от нормализованных фактов. Повторная загрузка того же архива и перекрывающихся периодов не увеличивает результат. При этом законные одинаковые операции должны сохранять свою кратность.

### Даты

| Событие | Дата для основного отчёта |
| --- | --- |
| Заказ | Дата создания заказа. |
| Продажа | Подтверждённая дата реализации или доставки из принятого источника. |
| Возврат товара | Подтверждённая дата финансового возврата из принятого источника. |
| Услуга | Дата начисления или оказания услуги, выбранная для соответствующего поля адаптера. |
| Сторно услуги | Собственная дата корректировки в источнике. |
| Выплата | Дата платежной операции; отдельно от даты продажи. |

Все пользовательские периоды трактуются по `Europe/Moscow`. Временная метка с часовым поясом сначала переводится в Москву и только потом превращается в день. Для календарной даты без времени сохраняется смысл календарной даты источника.

Сопоставление заказа и оплаты не ограничивается совпадением календарных дней. Заказ, созданный до выбранного периода, может дать продажу внутри периода; продажа прошлого периода может дать возврат в текущем. Нужные связи извлекаются из сохранённой истории или отдельной загрузки источника.

### Возвраты и изменения состояния

Созданная заявка на возврат, перевозка и приёмка товара не считаются тремя возвратами. Для основной финансовой сводки нужен подтверждённый возврат и его количество. Смена логистического статуса сама по себе не переносит ранее признанный финансовый возврат на новую дату.

Частичный возврат уменьшает только количество и суммы соответствующей товарной строки. Отмена одного SKU не меняет статус соседних SKU заказа. Невыкуп товара без состоявшейся реализации не создаёт отрицательную продажу, хотя подтверждённые услуги по такому заказу могут остаться расходом.

Статусный снимок и поток операций обрабатываются по разным правилам. Новый снимок заменяет прежнюю версию состояния в той же области. Отдельная корректировка добавляется или обновляется по своему ID. Отсутствие строки в неполной загрузке не доказывает её отмену.

Возврат комиссии учитывается только по подтверждённой корректировке услуги. Нельзя автоматически возвращать всю комиссию заказа при возврате одного товара, брать максимальную старую комиссию или повторно начислять сторно при каждой смене статуса.

## Показатели и формулы

Все суммы ниже выражены в рублях. Денежные расчёты выполняются в `Decimal` или целых минимальных денежных единицах с явной точностью источника. Округление выполняется по одному правилу на границе показателя; бинарные погрешности `float` не должны накапливаться.

Обозначения для выбранного периода и разрешённой области:

- `Q_sale`, `Q_return` — количество реализованных и возвращённых единиц;
- `S_sale`, `S_return` — стоимость тех же единиц в принятой цене селлера;
- `B_sale`, `B_return` — фактическая оплата покупателя по тем же единицам;
- `C_sale`, `C_return` — закупочная стоимость этих единиц;
- `E` — подтверждённые расходы Маркета после сторно;
- `I` — прочие подтверждённые денежные начисления, ещё не включённые в выручку.

Количество, суммы в двух ценах и закупочная стоимость должны описывать один и тот же набор товарных событий. При отсутствии соответствия нельзя дополнять одну метрику посторонними заказами или делить сумму заказа поровну между SKU.

| Строка на странице | Правило |
| --- | --- |
| Оборот созданных заказов | Исходная стоимость всех товарных единиц заказов, созданных в периоде, до последующих отмен. Не вычислять добавлением текущих отмен к неизвестной исходной базе. |
| Реализовано, шт. | `Q_sale`. |
| Возвращено, шт. | `Q_return`; отдельная видимая строка. |
| Выкупы за вычетом возвратов, шт. | `Q_sale - Q_return`. Отрицательное значение допустимо. |
| Оборот реализации за вычетом возвратов в цене селлера | `S_sale - S_return`. Основа — денежная выручка селлера принятого источника, с явно описанным учётом скидок и субсидий. |
| Оборот реализации за вычетом возвратов в цене покупателя | `B_sale - B_return`. Баллы, субсидии и компенсации не добавляются второй раз. |
| Комиссия | Денежные начисления комиссии минус подтверждённые сторно. |
| Эквайринг и перевод платежей | Отдельная сумма соответствующих услуг после корректировок. |
| Логистика | Сумма согласованных статей доставки и связанных операций после корректировок. |
| Хранение | Фактические услуги хранения после корректировок. При отсутствии загрузки — неизвестно. |
| Реклама | Денежные начисления рекламных услуг. Одна услуга не дублируется между статистикой рекламы и финансовым отчётом. |
| Прочие расходы | Все остальные классифицированные денежные расходы; доступна расшифровка. |
| Прочие начисления | Подтверждённые денежные доходы и компенсации вне уже учтённой выручки. |
| Всего расходов Маркета | `E`, сумма расходных статей с учётом сторно. |
| Расчётный результат расчётов с Маркетом за период | `(S_sale - S_return) - E + I`. Это показатель по начислениям, без входящего сальдо и графика выплат. |
| Закупочная стоимость реализованных товаров | `C_sale`. |
| Восстановленная закупочная стоимость возвратов | `C_return`; требуется связь с исходной продажей. |
| Закупочная стоимость за вычетом возвратов | `C_sale - C_return`. |
| Маржинальная прибыль до налогов и внешних расходов | `(S_sale - S_return) - E + I - (C_sale - C_return)`. |
| Маржинальность от оборота в цене покупателя | При положительном полном `B_sale - B_return`: прибыль / этот оборот × 100. При нуле, отрицательной или неизвестной базе — прочерк с причиной. |

Расходы учитываются по своей дате и не исчезают из периода из-за отсутствия продажи того же заказа в тот же день. Такую сводку нельзя подписывать как прибыль только по заказам, созданным за выбранный период.

У каждой услуги должен быть ровно один денежный эффект в формуле. Например, эквайринг не вычитается одновременно отдельной строкой и внутри «Прочих расходов». Тарифы в процентах, база тарифа и итоговое начисление хранятся раздельно. Для расхода берётся подтверждённая денежная сумма, а не сумма процентов.

Знак операции определяется контрактом источника. Нельзя применять `abs()` ко всем расходам: это превращает возврат платы в новый расход. Также нельзя второй раз менять знак уже отрицательной корректировки. Неизвестный тип или знак сохраняется как проблема разбора и делает зависимый итог неполным.

Технически незнакомые денежные операции показываются в расшифровке «Не классифицировано». Если их денежный эффект однозначно известен, он может участвовать в общем сальдо один раз с отметкой неполноты классификации. Если неизвестны эффект или назначение, полный финансовый результат не публикуется.

### Выплаты

Отдельный блок называется «Выплаты по данным Маркета». Он показывает подтверждённые переводы и связанные удержания по их собственным датам. Детали одного платежа не суммируются повторно вместе с его итоговой строкой.

Платёжный статус площадки не подтверждает поступление в банковской выписке. Без банковского источника на странице не должно быть строки «Фактически поступило на расчётный счёт».

Выплаты могут относиться к продажам другого периода. Для объяснения разницы нужны входящее сальдо, начисления, удержания, переводы и исходящее сальдо, если источник их предоставляет. Без этих данных показывать наблюдаемую разницу и её неполноту, а не искусственно подгонять финансовую формулу под платёж.

### Числовой пример

За день реализованы 2 единицы товара: цена селлера 1 000 рублей за единицу, оплата покупателя 900 рублей, закупка 400 рублей. На следующий день подтверждён возврат одной единицы. Комиссия за два дня после сторно — 100 рублей, логистика — 50, эквайринг — 20, реклама — 30; остальные обязательные источники подтверждают ноль.

За два дня результат должен быть следующим:

| Показатель | Значение |
| --- | ---: |
| Реализовано | 2 шт. |
| Возвращено | 1 шт. |
| Выкупы за вычетом возвратов | 1 шт. |
| Оборот в цене селлера | 1 000 ₽ |
| Оборот в цене покупателя | 900 ₽ |
| Всего расходов Маркета | 200 ₽ |
| Расчётный результат расчётов с Маркетом | 800 ₽ |
| Закупочная стоимость за вычетом возвратов | 400 ₽ |
| Маржинальная прибыль | 400 ₽ |
| Маржинальность | 44,44% |

Во второй день количество нетто равно −1. Если в этот день не было продажи, отрицательное количество всё равно участвует в сумме периода. Выплата Маркета на 700 рублей в тот же период отражается отдельно и не меняет приведённую прибыль.

## Себестоимость и исторические цены

Сохранить действующий импорт листа `YM`, который обновляет привязки товаров к магазинам и остальные данные 1С. Новый финансовый отчёт использует его как существующий источник закупочной цены; подключение другого листа является отдельной задачей со своим маппингом и миграцией.

Для финансового события сохранять использованную закупочную цену, её источник и период применимости. Новая цена сегодня не переписывает автоматически прибыль старой продажи. Для возврата использовать закупочную цену возвращаемых единиц исходной продажи; сегодняшнюю цену вместо неё не подставлять.

Если исторической цены нет, разрешён отдельный режим оценки по текущей цене с заметной пометкой. Такой результат не получает статус подтверждённого исторического расчёта. Основной показатель остаётся неизвестным до появления достаточного основания.

Финансовая ручная корректировка цены хранится отдельным слоем со временем действия, автором и причиной. Обычная синхронизация её не стирает. Применение новой исходной цены поверх корректировки требует явного правила приоритета и записи изменения.

Если цену не удалось определить хотя бы для одной реализованной или возвращённой позиции, неизвестны полный итог закупочной стоимости и зависимая прибыль. Расшифровка показывает проблемные SKU и количества. Если подтверждено, что продаж и возвратов нет, закупочная стоимость равна нулю независимо от наличия цен в справочнике.

## Загрузка и хранение

### Публикация согласованного результата

1. Зафиксировать область загрузки: магазин, кабинет, кампании, источник и период, включая версию настроек подключения.
2. Получить все необходимые страницы и части отчёта во временную область. Сохранить ID задания Маркета, чтобы продолжить ожидание после перезапуска.
3. Проверить структуру, обязательные поля, валюту, даты, количества, кампании, повторные страницы и состав частей.
4. Нормализовать факты, разрешить идентичность операций и подготовить расчёт в той же версии источников.
5. В одной транзакции опубликовать полный снимок соответствующей области, его дневные результаты и маркеры полноты.
6. Только после успешной транзакции сделать новую версию доступной читателям.

Ошибка скачивания, страницы, разбора, кабинета или вставки не удаляет последний успешный результат этой области. Удаление старого снимка и вставка нового не фиксируются раздельными транзакциями. Операция повторяемая: повтор после обрыва не добавляет второй экземпляр финансового события.

Единица атомарности — кабинет, набор кампаний и загружаемое окно обязательных источников финансового результата. Воронка заказов и платежный блок могут обновляться независимо с собственными статусами. При ошибке одного кабинета успешный кабинет не откатывается, но общий итог честно отражает неполноту или устаревание.

Для перекрывающихся окон хранить версии и явно определять действующий полный снимок каждого участка. Нельзя просто сложить два месячных архива с одинаковыми операциями. Пересчёт интервала должен использовать согласованную версию, а не случайный набор «последних строк» разных импортов.

Маркеры покрытия хранятся по магазину, кабинету, области кампаний, источнику и дню. Полный пустой ответ подтверждает ноль. Отсутствующий лист, незавершённый архив или ошибка источника не подтверждают ноль. Проверка полноты периода охватывает все запрошенные дни и все входящие в него подключения.

### Расписание и ручные операции

Рабочие настройки первой версии:

- отдельная задача `yandex_financial_reports_sync` с настройками по магазинам;
- ежедневный запуск в 05:00 по Москве;
- переобработка последних 90 завершённых дней: для даты запуска D интервал D−90 … D−1;
- текущий день — отдельное предварительное окно, если соответствующий источник уже доступен;
- длинные периоды делятся по ограничениям каждого метода; месячный источник запрашивается календарными месяцами;
- поздние возвраты и корректировки за пределами окна учитываются при обнаружении нового события и через ручную загрузку старого периода;
- для источника, допускающего произвольные исправления старых дат, предусмотрена периодическая сверка закрытых месяцев; одно окно в 90 дней не считается гарантией полноты всей истории.

Квоты и блокировки должны быть общими с существующими загрузчиками отчётов для того же кабинета. Генерация, ожидание и скачивание используют ограниченные повторы, серверные сроки повторов и сохранённое состояние задания. Одновременные ручной и фоновый запуски не публикуют конфликтующие версии.

В админке доступны действия «Загрузить период», «Повторить неудачное окно» и «Пересчитать по сохранённым данным». Последнее не обращается к внешнему API и сохраняет исходные операции. Задание работает в фоне; HTTP возвращает его ID и состояние, а не держит соединение до завершения всех отчётов.

Во время первой поставки функциональности финансовая задача по умолчанию выключена. Глобальное отключение фоновых задач отключает и её. Ручной запуск при отключённом расписании допускается только как явно выбранное действие администратора в существующем механизме заданий.

### Журнал

Для задания сохранять область, этап, число полученных и опубликованных операций, покрытые даты, пропущенные участки, время последнего успеха, ошибку и версию расчёта. Ошибка включает безопасное описание без ключей и персональных данных покупателей.

Историческая версия показателя должна объясняться исходными строками и версией формулы. Изменение классификатора расходов или формулы запускает отдельный пересчёт; исходные архивы остаются доступными для сверки. Хранение старых архивов и резервных копий имеет настраиваемый срок, а не бесконечное ежедневное размножение одинаковых окон.

## Контракт страницы и API

Предлагаемый состав маршрутов:

| Маршрут | Назначение |
| --- | --- |
| `GET /finance-reports/yandex` | Страница финансового отчёта. |
| `GET /api/finance-reports/yandex/stores` | Только разрешённые магазины и доступные финансовые подключения. |
| `GET /api/finance-reports/yandex` | Сводка выбранного периода. |
| `GET /api/finance-reports/yandex/days` | Дневная расшифровка той же сводки. |
| `GET /api/finance-reports/yandex/operations` | Постраничные операции выбранного показателя. |

Административные запуски подключаются к существующему API заданий. Отдельный обход этого механизма не нужен.

Общие параметры чтения: `date_from`, `date_to`, необязательный `store_slug`. Кабинет и кампания, если доступны как дополнительные фильтры, обязательно проверяются внутри уже разрешённого магазина. Для деталей используются ограниченный размер страницы и стабильный порядок.

Ответ содержит выбранную область, фактически доступный период, версию расчёта, суммы и состояния каждого показателя, отдельные статусы основных источников, пропущенные дни и время последнего успеха. Деньги передаются точными десятичными строками или целыми копейками по единому контракту. `null` означает неизвестное значение; полный известный ноль передаётся как ноль.

При частичной сумме различать `value` полного показателя и `known_value` вычислимой части. При невозможности полного расчёта `value=null`; клиент не подменяет его `known_value` без подписи «частично». Процент вычисляется из сумм числителя и знаменателя на одинаковой области, а не усреднением дневных процентов.

Детализация и сводка должны ссылаться на одну версию опубликованных данных. Если версия уже недоступна после обновления, клиенту предлагается перечитать отчёт; тихо показывать детали другой суммы нельзя.

Быстрая смена периода или магазина отменяет устаревший запрос либо игнорирует его ответ. На ошибке загрузки выбранного фильтра интерфейс не оставляет старые цифры под новой подписью магазина. Сообщение об ошибке видно на странице, а не только в консоли браузера.

## Устройство реализации

Ориентироваться на [архитектуру проекта](architecture.md). Новые финансовые сценарии реализовать отдельным предметным модулем:

- DTO запросов, результатов, покрытия и операций — в `app/dto`;
- сценарии чтения, загрузки, публикации и пересчёта — в `app/application`;
- чистые функции финансовых расчётов и классификации — в отдельном модуле финансовой предметной области;
- адаптеры Яндекс API — в `app/yandex`;
- SQLAlchemy-модели, репозитории и Unit of Work — в `app/infrastructure`;
- HTTP-валидация и авторизация — в `app/web/routers`;
- регистрация задания — в `app/jobs`;
- интерфейс — в `templates/finance` и `static/finance`.

Точные имена новых файлов можно выбрать при реализации. Существенно разделение ответственности: расчёт получает нормализованные события и не делает HTTP-запросов; маршрут не содержит финансовые формулы; загрузчик не выдаёт доступ к данным; репозиторий требует явную область магазина.

Существующий `app.repositories` остаётся совместимым слоем старых модулей. Новые финансовые записи не стоит добавлять туда как ещё один монолит. Повторяющиеся механизмы генерации отчётов можно вынести в общий адаптер с сохранением поведения текущих загрузчиков.

Для модели хранения нужны сущности подключений и их истории, заданий загрузки, исходных архивов или строк, нормализованных событий, цен себестоимости, покрытия и версий расчёта. Производные дневные итоги являются кэшем: их можно воспроизвести из фактов. Отдельно хранится привязка опубликованного снимка к исходным версиям.

## Очередность разработки

| Этап | Что реализовать | Проверяемый результат |
| --- | --- | --- |
| 1. Семантика и примеры | Словарь показателей, таблицы маппинга, обезличенные архивы продаж, возвратов, услуг и платежей. | Каждое поле имеет единицы, знак, дату и ожидаемый результат; спорные поля не замаскированы догадками. |
| 2. Подключения и доступы | Отдельное право, область магазинов, безопасный адаптер старых ключей, выбор кампаний. | Пользователь не видит чужие суммы; старые подключения продолжают работать. |
| 3. Хранилище и импорт | Миграции, сохранение источников, идентичность, версии, покрытие и атомарная публикация. | Повторная и оборванная загрузки не меняют корректные данные. |
| 4. Чистый расчёт | Продажи, возвраты, услуги, сторно, закупка, полнота, дневные и периодные итоги. | Проходят числовые примеры и сверка суммы дней. |
| 5. Чтение и интерфейс | Сводка, даты, магазины, статусы, детали операций и ошибок. | Цифры, подписи фильтров и расшифровки всегда относятся к одной версии и области. |
| 6. Задания и история | Ручные запуски, расписание, ограничения API, продолжение после сбоя и пересчёт. | Нет параллельных конфликтующих публикаций и зависимости чтения от внешнего API. |
| 7. Пилот | Один явно включённый магазин, закрытый месяц и период с возвратами, затем несколько кабинетов. | Каждое расхождение объясняется источником, датой, классификацией или полнотой. |
| 8. Включение | Исправления пилота, проверка совместимости и постепенное включение магазинов. | Стабильный отчёт при неизменном поведении остальных разделов. |

Изменения оформлять небольшими самостоятельными коммитами. Переключение источника 1С, миграция общих ключей заказов и переработка складских загрузчиков не входят в скрытые зависимости финансовой страницы.

## Проверки приёмки

Проверки используют синтетические данные и обезличенные архивы. Ни одна из них не обращается к рабочей базе, реальным секретам или внешнему API. Проверки транзакций выполняются на SQLite и PostgreSQL, поскольку обе БД поддерживаются приложением.

| Код | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| A01 | Доступен только магазин с оборотом 100, у недоступного оборот 900. | «Все магазины» возвращает 100; чужой магазин не попадает ни в детали, ни в фильтры. |
| A02 | Список разрешённых магазинов пуст. | Пустая область; запрос без ограничения магазинов не выполняется. |
| A03 | Пользователь ограничен товарами менеджера. | Полный финансовый итог магазина недоступен в первой версии. |
| A04 | Нет права финансового раздела, но известен URL API. | Сервер возвращает отказ. |
| I01 | Вторая страница или второй источник окна завершились ошибкой. | Прежний опубликованный снимок цел; окно не помечено полным. |
| I02 | Ошибка вставки после подготовки замены данных. | Откатывается вся публикация, включая маркеры покрытия. |
| I03 | Тот же архив загружен дважды и ещё раз в перекрывающемся периоде. | Количество и деньги не изменились. |
| I04 | Две одинаковые исходные строки являются разными реальными операциями. | Сохраняется их кратность, если источник её подтверждает. |
| I05 | Изменение источника добавило корректировку существующего события. | Событие обновлено или дополнено по правилам типа; второй продажи нет. |
| I06 | Ручная и фоновая загрузки одного кабинета запущены одновременно. | Нет смешанной версии; поведение блокировки и повторов определено. |
| I07 | Один кабинет обновлён, второй завершился ошибкой. | Успешный результат сохранён, общий отчёт помечен неполным или устаревшим. |
| I08 | Финансовая загрузка работает рядом со старой синхронизацией продаж. | Количество и ключи строк `sales_order_lines` не меняются от финансовой загрузки. |
| C01 | Старый конфиг содержит только API-ключ. | Старое чтение ключа работает; финансовый адаптер разрешает кабинет либо сообщает о неоднозначности. |
| C02 | Один магазин содержит два кабинета с одинаковыми внешними номерами заказов. | Заказы не сталкиваются и не смешиваются. |
| C03 | Выбрана одна из двух кампаний кабинета. | Все товарные источники ограничены этой кампанией; общие расходы не приписаны ей целиком по умолчанию. |
| C04 | Ключ обновлён без изменения кампаний. | Выбор кампаний сохранён. |
| C05 | Кампания отключена после закрытия месяца. | Ранее опубликованная история не удалена. |
| C06 | Общий расход кабинета 1 000 и три кампании. | Расход кабинета всего 1 000; не 3 000. |
| F01 | Одна продажа вчера и полный возврат сегодня. | За два дня количество и товарный оборот нетто равны нулю; сегодня количество −1. |
| F02 | Доставленный и отменённый SKU в одном заказе, строки меняют порядок. | Доставленный SKU остаётся в реализации; порядок строк не влияет. |
| F03 | Реализованы 3 единицы SKU, возвращена одна. | Нетто 2; возвращается цена и закупка именно одной единицы. |
| F04 | Доставка и перевод платежа в разные дни. | Цена покупателя не пропадает; финансовая реализация и выплата имеют собственные даты. |
| F05 | Возврат последовательно проходит три логистических статуса. | Один финансовый возврат, одна исходная дата события. |
| F06 | Услуга +100 и подтверждённое сторно −100. | Чистый расход 0; не 200. |
| F07 | Источник содержит процентный тариф 5 и денежное начисление 150. | В расходы попадает 150 по маппингу, а не 5 и не 155. |
| F08 | Услуга начислена в день без продажи. | Услуга учитывается и видна в расшифровке. |
| F09 | У одного из двух выкупов отсутствует оплата покупателя. | Полный оборот покупателя неизвестен; известная часть подписана как частичная. |
| F10 | Товар снят с продажи после реализации. | Историческая продажа остаётся в отчёте. |
| F11 | Изменилась закупочная цена после продажи. | Сохранённая подтверждённая закупка продажи и её возврата не меняется автоматически. |
| F12 | Есть ручная корректировка цены, товар отсутствует в новой выгрузке. | Корректировка сохранена; её приоритет и период действия видны. |
| F13 | Нет цены у одного реализованного SKU. | Нет полного итога закупки и прибыли; список проблемных SKU доступен. |
| F14 | Полные источники подтверждают отсутствие продаж и возвратов. | Количество и закупка равны нулю; фактическая реклама остаётся расходом. |
| F15 | Разные периоды, включая один день, конец месяца и границу суток МСК. | Нет пропущенного последнего дня и двойного учёта граничных событий. |
| F16 | Сумма дневных итогов сравнивается с итогом периода на одной версии данных. | Равенство денежных и количественных аддитивных показателей; проценты пересчитаны из общих сумм. |
| F17 | Фактическая выплата по данным Маркета отличается от расчёта по начислениям. | Обе суммы показаны отдельно; прибыль не подгоняется под выплату. |
| F18 | Неизвестный тип услуги или изменённая структура файла. | Видимая ошибка качества; неизвестное не становится нулём или лишним расходом. |
| U01 | Медленный ответ по первому магазину приходит после ответа по второму. | На странице остаётся результат второго магазина. |
| U02 | Запрос нового периода завершился ошибкой. | Старые цифры не выглядят отчётом нового периода; ошибка видна пользователю. |
| U03 | Между сводкой и открытием деталей опубликована новая версия. | Детали объясняют выбранную версию или явно требуют обновить сводку. |
| U04 | Просмотр страницы при недоступном внешнем API. | Локальные данные доступны; чтение не обращается к Маркету. |
| R01 | Финансовые задачи выключены. | Они не запускаются автоматически и не влияют на существующие задания. |

Для каждой из десяти категорий ошибок ревью есть защитный сценарий: доступы — A01; частичная и неатомарная запись — I01/I02; смена ключей заказов — I08; кампании — C03/C04; несколько SKU — F02; отрицательное количество возвратов — F01; разные даты — F04; проценты вместо рублей — F07; закупочные цены — F11/F12/F13; старые ключи — C01.

Дополнительно проверить существующие тесты продаж, доступов, ЯМ и дневной экономики, Ruff и форматирование по правилам репозитория. Для новой страницы нужны проверки поведения JavaScript и визуальная проверка длинных сумм, ошибок, пустых состояний и узкого окна.

## Условия готовности

Функциональность готова к включению, когда выполнены следующие условия:

- каждый показатель имеет закреплённые источник, единицы, дату, знак и формулу;
- все проверки приёмки проходят, включая ошибки транзакций и повторные импорты;
- выбранный закрытый период сверяется с официальными источниками до установленной точности округления;
- необъяснённая разница не спрятана в нуле, модуле суммы или множителе кампаний;
- права проверены на сводке, деталях, фильтрах и статусах;
- отчёт воспроизводится из сохранённых источников без внешнего API;
- существующие подключения, импорт `YM`, общие продажи и аналитика сохраняют поведение;
- отключение новой задачи прекращает обновления и оставляет возможность прочитать последний успешный результат;
- миграция, резервное копирование, включение по магазинам и откат описаны в инструкции эксплуатации.

Начинать реализацию следует с этапа 1: точного состава событий и контрольных примеров. Страница и расписание подключаются после того, как расчёт и публикация выдерживают частичные загрузки, возвраты и повторное получение тех же данных.
