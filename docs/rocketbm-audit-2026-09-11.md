# RocketBM: проверка кода и серверных данных

Проверка переписки с 4 сентября и актуальных данных — 11 сентября 2026 года.
Код изменён локально в ветке `codex/rocketbm-stock-audit`. Рабочая база и рабочий код сервера не изменялись.
Запросы к PostgreSQL выполнялись в транзакциях `read_only`; ответы маркетплейсов читались через действующие серверные подключения.

## Как устроен учёт

`ff_stock` хранит свободный, ещё не распределённый остаток, а не весь физический остаток склада.
Это подтверждено журналом: обычные отгрузки с пометкой «на ФБС» уменьшали эту величину.
Поэтому повторно вычитать текущий FBS из всей таблицы `ff_stock` нельзя.

Правильная последовательность:

1. Приход увеличивает свободный остаток.
2. Распределение на FBS уменьшает свободный остаток. Товар физически остаётся на том же ФФ.
3. API показывает текущий остаток, выставленный на FBS. Продажа уменьшает этот остаток и не возвращает проданное в свободный запас.
4. FBO-отгрузка уменьшает свободный остаток; остаток FBO появляется из API маркетплейса после приёмки.
5. Перемещение между ФФ или площадками проходит через «В пути» до подтверждения получения.

TOTAL складывает свободный остаток, товары в пути между ФФ и остатки маркетплейсов. Это оперативный показатель, а не сверка бухгалтерского физического наличия: отдельно нужно учитывать резервы заказов, товары в пути на FBO и задержки приёмки API.

Найденная ошибка нового действия «Перемещение на FBS»: оно только проверяло наличие, но не уменьшало свободный остаток. Исправлено списание из свободного остатка в транзакции. На момент проверки операций нового типа `fbs_transfer` на сервере не было, поэтому массовая корректировка исторических остатков по этой причине не требуется.

## Исправления кода

| Область | Изменение |
|---|---|
| Импорт приходов | Явный артикул имеет приоритет. Неоднозначный штрихкод и конфликт известных артикула/штрихкода останавливают импорт до записи. |
| Файлы перемещений | Если присутствуют артикул и штрихкод, используется артикул. Перемещение по неоднозначному штрихкоду не выбирает случайную карточку. |
| Штрихкоды | Сохраняются все штрихкоды WB/Ozon/ЯМ и прежний основной код. Поиск, ручной ввод и импорт поддерживают дополнительные коды и начальные нули. |
| Смена артикула | Прежний и новый артикулы сопоставляются только при единственном текущем предложении с тем же ID товара Ozon или SKU ЯМ и совпадающим штрихкодом. Две действующие карточки не объединяются. |
| Сохранность данных при смене артикула | Объединяются свободные остатки, мусорка и снимки импортов; сохраняются связи перемещений и приёмок. История операций остаётся с исходными артикулами. Отдельная таблица хранит связь старого и нового артикула. |
| TOTAL | По последнему уточнению пользователя карточки объединяются по артикулу между магазинами и площадками, даже при разных штрихкодах. Остатки суммируются, ЗЦ выбирается максимальная. Формула свободного остатка сохраняется. |
| Ozon FBS/rFBS | Загружается детализация по складам продавца. Общая сумма FBS и детализация формируются из одного набора данных. Фильтр отдельно обновляет FBS и rFBS. |
| Названия ФФ | Для ЯМ и Ozon добавлены точные соответствия Afflatus/Аффлатус, ФуллСервис, Казань Царицыно и Екатеринбург справочнику сайта. Неизвестное название не угадывается. |
| ЯМ, отключённая кампания | Недоступный дубликат кампании того же ФФ не прерывает обработку работающей кампании. При иной ошибке сохраняется прежний снимок проблемной схемы, а полностью полученная схема обновляется. Ошибка частичного обновления остаётся видимой. |
| WB FBS | Вместо устаревшего запроса по `skus` используется актуальный `chrtIds`. Несколько штрихкодов одного размера не удваивают остаток. |
| WB, ошибка склада | Если хотя бы один склад не ответил, прежний FBS-снимок сохраняется целиком. Ранее такой склад мог превратиться в ноль. |
| Запись API-снимков | Общие суммы и детализация схемы заменяются одной транзакцией. Ошибка записи откатывает оба представления. |
| Параллельные перемещения | Чтение изменяемых строк остатка блокирует их в PostgreSQL; проверка нескольких артикулов берёт блокировки в стабильном порядке. |
| Фильтр в интерфейсе | Ошибки HTTP и некорректный ответ не подменяются нулевыми остатками. Поиск учитывает скрытые дополнительные штрихкоды. |

Текущий контракт WB проверен по [официальной документации остатков](https://dev.wildberries.ru/openapi/work-with-products) и [инструкции WB](https://dev.wildberries.ru/en/news/101). `chrtId` идентифицирует размер, а дополнительные штрихкоды служат его альтернативными кодами.

### Видеоняни: почему 40 + 5 не означают нынешние 45

- №955/956: по 40 перемещены с WB на ЯМ и получены.
- №1114/1117 и №1118/1119: дополнительно по 5 перемещены и получены.
- №1120/1121: по 5 распределены на FBS; в примечаниях прямо указано «Отгрузка на ФБС 02.09.26». Свободный остаток уменьшен.
- №1411: по 35 отгружены на FBO, примечание «Видеоняни Яндекс фбо ВРЦ-9762241 Аффлатус».
- Итого по журналу осталось по 5 свободных единиц; они висят на прежних текстовых артикулах. Текущий FBS из API — 2 и 3. Это даёт соответственно 7 и 8 единиц свободного и выставленного FBS вместе, без ещё не отражённого FBO и резервов.

## Что требует отдельной сверки

1. Фактическая приёмка 35 видеонянь каждого вида на FBO по ВРЦ-9762241. В проверенном ответе остатков ЯМ по нынешним артикулам FBO нет; нужны статус поставки и акт приёмки.
2. Начальные остатки и повторные ручные добавления `1464129897`: №555 и №556 по 50, отгрузка №625, повторный приход №872, отгрузка №963 и восстановление №1461. Одной фразы «куплено 50, продано 4» недостаточно для исправления обеих площадок.
3. Финальная инвентаризация GOGOL. Сопоставить поартикульно исходные 6000, все приходы/переносы/списания, принятые FBO-поставки, заказы и резервы. Установка TOTAL ровно 6000 не является исправлением кода.
4. Правила исключения складов из WB FBO: в исходном коде жёстко исключены семь складов, включая Электросталь и Краснодар. Правило сохранено; нужно подтвердить, что это действующее бизнес-требование.
5. Резервы и статусы площадок: ЯМ использует `AVAILABLE`, Ozon FBS — `free_stock`. Эти величины нельзя безоговорочно назвать всем физическим товаром. Для физической инвентаризации нужен отдельный учёт резервов и поставок в пути на FBO.

## Проверки и выпуск

### Дополнение: общий TOTAL по артикулу

По запросу пользователя изменены глобальная таблица и XLSX: после текущей ЗЦ добавлена колонка «Магазины / площадки», например `ROCKKIDDO OZON, TOYKA WB`. В ней перечисляются пары с ненулевыми остатками. Одинаковые артикулы объединяются между магазинами и площадками независимо от штрихкодов; разные артикулы с общим штрихкодом остаются отдельными строками. Остатки суммируются по каждой схеме и площадке. Строки без остатков во всех магазинах исключаются; отсутствие штрихкода не мешает объединению по артикулу.

ЗЦ выбирается из текущих значений источника 1С для всех карточек артикула в доступных пользователю магазинах; по явному ответу пользователя при нескольких значениях берётся максимальное. Нулевой складской остаток не мешает использовать заполненную ЗЦ. Если ни одна доступная карточка не имеет цены, сохраняется «—». Фильтр магазина пересчитывает количества только по выбранному магазину, сохраняя общую ЗЦ. Это же правило действует во встроенном TOTAL магазина. Поиск учитывает все связанные артикулы и штрихкоды.

Импорт ЗЦ расширен с WB на Ozon и ЯМ: цена сопоставляется по артикулу для магазинов, указанных в названии листа. Комиссии и прочие параметры WB не копируются на другие площадки. Выполнена загрузка в настоящую локальную базу: 2539 заполненных ЗЦ, включая `303077583` с ценой 848,59 ₽ на всех трёх площадках. Серверная база не менялась. Подробности, девять максимальных цен и 40 несопоставленных строк источника приведены в [отчёте загрузки](purchase-price-sync-2026-09-11.md).

Проверено на изолированной тестовой базе: объединение 412 + 106 = 518, фильтр ROCKKIDDO = 106 с сохранением ЗЦ 400 ₽, совпадение HTML/XLSX/встроенного TOTAL, исключение нулевых строк, дополнительные штрихкоды и ограничения доступа. Общий запуск unit-тестов дал 592 успешных проверки и одно замечание архитектурного теста о комментариях в Python; комментарии удалены, повторный запуск 14 затронутых и архитектурных тестов прошёл. В браузере проверены таблица, фильтр магазина, поиск по магазину и пересчёт итогов. Новое объединение на рабочий сервер пока не установлено.

Проверены регрессии импорта, смены артикула и сохранения количества, штрихкодов, TOTAL, распределения на FBS, частичных сбоев API и отката транзакций.
Результат: 586 unit-тестов пройдены; 106 интеграционных, HTTP end-to-end и отдельных тестов каталога пройдены с обновлением ожидаемого остатка после распределения на FBS. `ruff check` и `git diff --check` проходят.

Общий порог `coverage-unit` не пройден: 82% при требовании 90%. Общая проверка форматирования также не проходит на множестве файлов проекта; массовое переформатирование посторонних модулей не выполнялось. Следовательно, весь `make check` нельзя считать зелёным, несмотря на успешные функциональные проверки.

Новый запрос WB дополнительно проверен на живом кабинете RIMILI с заблокированной записью: 1100 карточек, 154 товара с ненулевым FBS; контрольные `949725484`, `949563410`, `949558341` дали соответственно 189, 79 и 78. Дополнительные штрихкоды не удвоили суммы.
Повторяемый smoke-тест `scripts/check_stock_audit_postgres.py` запускается только против отдельной базы с именем `rocketbm_stock_audit`; на другой базе он отказывается работать.
На изолированной PostgreSQL 17 подтверждены создание схемы, смена артикула, дополнительные штрихкоды, распределение FBS, TOTAL и полный откат неудачного снимка.

Перед выпуском: проверить актуальный серверный commit, сделать резервную копию, применить согласованный код и новые таблицы, затем обновить каталоги и остатки и сверить указанные контрольные товары. Смена артикула переносит текущие остатки и связи, поэтому откат требует учитывать изменения данных, а не только возврат версии приложения.

Полная гарантия «ошибок больше нет» невозможна по одной переписке и набору тестов. Три голосовых сообщения не расшифрованы; документы поставок и физическая инвентаризация не заменены предположениями.
