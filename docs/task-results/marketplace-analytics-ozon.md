# Ozon: три инструмента аналитики и исправления полноты

На 30.10.2026 выполнены реализация первой попытки и адресные backend-исправления второй. Кандидат ещё требует совместной заморозки Ozon/ЯМ и новых независимых проверок; это не сообщение о завершённой приёмке. Контракт страниц и данных — [аналитика Ozon](../ozon-analytics.md).

## Запрос и решения

Пользователь поручил перенести три инструмента меню WB — «Анализатор», «Эфемериды», «Продажи по API» — на Ozon и Яндекс Маркет с теми же возможностями, логикой и дизайном, адаптируя источники. Рейтинг товаров в задачу не входит. Два направления имеют собственные author/reviewer/coder и независимые панели из Astra/Sol/Terra: сначала три initial, затем обсуждение и три final. Голосование 2/3 не применяется; итоговые проверки относятся к единому совместному дереву. Push, релиз и деплой исключены.

Четыре решения человека сохранены:

1. У каждой площадки собственные 24 nullable коэффициента D по московским часам, без копирования WB. Пустое поле неизвестно, явный 0 сохраняется. Без D прогноз и зависимые отклонения неизвестны.
2. Колонки WB сохраняются; недостоверные значения — null/«—» с объяснением, неизвестное не подменяется 0.
3. Корзины Ozon сохраняются за UTC source_day, в интерфейсе/подсказках/CSV явно указан интервал «03:00–03:00 МСК». Заказы и реклама остаются МСК.
4. Для ЯМ сохраняется дата собственного отчёта при неподтверждённых часовых границах. Это не разрешение подставлять Ozon UTC-интервал в ЯМ.

Отдельного решения о нулевом ДРР Ozon человек не принимал. Узкое фактическое уточнение второй попытки устранило внутреннее противоречие ТЗ с исходной логикой WB: пригодные известные согласованные пары с суммами 0/0 дают ДРР 0; пустое множество, отсутствующая часть пары и положительный расход при нулевой базе дают null. Partial/stale сохраняются отдельно от числа. ROI/CTR и другие отношения исключения 0/0 не получают. fullArticle определяет только идентичность товара.

## Итоговое содержание ТЗ

Четыре URL Ozon: анализатор, эфемериды, история weekly comments и продажи. Анализатор переносит поиск, сегменты/цвет, сортировку/column filters до итогов и пагинации 20/50/100, группы/скрытие колонок, compact/separate product, закрепление, сводку, drawer, копирование и заметки. Эфемериды сравнивают две недели, сохраняют competitor/decision/next и историю 12 недель. Продажи показывают gross-заказы FBO+FBS и отдельные отмены за 1–366 дней, с началом не ранее 01.01.2000. Полный offer_id с ` / ` не сокращается; магазины независимы.

Текущие ТО и ROI не зависят от выбранной недели. Предыдущая цена — отношение согласованных сумм/количеств предыдущей выбранной недели. ДРР аналитики = 100×Σрекламы/Σ(gross-ТО дня×датированный эффективный выкуп/100); отмены повторно не вычитаются. Итоги процентов — отношение сумм пригодных пар, не среднее процентов. Юниточная формула [Ozon](../ozon-buyout.md) не меняется. Недельный ROI использует дневные inputs существующего margin calculation; прошлые цены/цели не подменяются сегодняшними.

Сток анализатора — FBO+FBS. Дни запаса требуют полного покрытия предыдущей завершённой календарной недели относительно сегодня и положительного среднего gross-количества за семь дней. Неполный или нулевой знаменатель даёт null. Известная часть остатка сохраняется с partial. Сток эфемерид — неизменяемый снимок понедельника 00:05 МСК с FBO/FBS/возвратами/ФФ, без вторничного backfill. Daily reference накапливается проспективно; историческая цена должна принадлежать нужной неделе, product_id и собственному received_at.

GET читает сохранённые источники без API/снимков/записи. Доступ — активному пользователю, при записи и чтении ревизий проверяется точный товар Ozon. Notes только сегодня МСК, trim 1..4000, CAS по previous_note и атомарная ревизия. Weekly comments допускают пустой текст, сохраняют точные пробелы, CAS по версии и атомарную ревизию; decision редактируется только в текущую московскую неделю, с повторной проверкой при save. Автосохранение сохраняет draft при конфликте, вводе во время PUT и смене часа.

Корзины запрашиваются по одному UTC-дню, sku/hits_tocart, последовательно по offset/1000, через staging/checkpoint и атомарную публикацию дня. Короткая страница не доказывает ноль пропущенного SKU. Persisted бюджет 40 попыток/24 часа по Client-ID, методный интервал минимум 60 секунд каждой попытки; run максимум 8 попыток/10 минут, страница максимум 3 попытки поколения. Просроченный lease не меняет нового владельца; поколение старше 72 часов начинается заново. Магазины конкурентны через TaskGroup с изоляцией отказов. Источники целей/возвратов не ждут корзин.

R1 был отклонён: три Ozon final — defects_found. Подтверждены F1: потеря confirmed-empty в границах продаж; F2: known partial ошибочно complete; F3: семь partial дней принимались за полный denominator; F4: качество частичной рекламы терялось у ДРР; F5: stockPartial скрывался основной таблицей. Общая заморозка была снята только для точных исправлений. Исторические R1 снимки и отчёты не заменены новым baseline.

Вторая попытка изменила только четыре backend-пути после предметного расширения lease:

- [ozon_analytics_repository.py](../../app/infrastructure/ozon_analytics_repository.py): SQL min/max объединяет saved rows с допустимыми пустыми днями. Две схемы должны иметь listed/ok и finalized в прошлом; сегодня допустимо полное перечисление. Legacy source=orders применяется только при отсутствии native-состояния конкретной схемы. Неуспех, половина схем, историческая нефинализированность и будущие даты не создают полноту или нулевые продажи. Тот же набор дней очищает analytics eligible/confirmed; raw rows остаются известной частичной частью. Shared turnover repository не менялся.
- [analytics_normalizer.py](../../app/ozon/analytics_normalizer.py): исправлены complete продаж, семидневного stock denominator и качество предыдущей цены при семи partial днях; известные 10/2 и partial zero сохранены. ДРР сохраняет пригодные пары/weights, отмечает partial/stale у периода, вчера и обеих недель. Для ДРР введён отдельный известный 0/0, без изменения generic ratio/юнитки. - [ozon_analytics.py](../../app/dto/ozon_analytics.py): именованный OzonAnalyticsMetricQuality и optional mapping quality на строках/периодах. Поля complete/stale, machine reasons, expected_dates/known_dates сериализуются ISO. Known dates отражают численную пригодность, не полноту. Существующие coverage/weights/field_issues и provisional/source_day метаданные сохранены.

- [ozon_analytics.py](../../app/application/ozon_analytics.py): после отдельного расширения scope минимально ограничено начало периода по умолчанию 01.01.2000; обычные семь дней, явный диапазон, 366 и неизвестный последний день сохраняются.

Shared frontend исправил отдельный разработчик ЯМ, ACTUAL v1 передан с девятью стабильными хешами. Ozon coder самостоятельно проверил actual DTO→shared функции и реальный Chrome в своей fixture: stock markers, partial/stale summary и три скачанных CSV. Это самопроверка разработчика, не независимый R2. Пустой quality mapping сохраняет legacy fallback WB/ЯМ; конкурирующие drrComplete/drrStale flags не добавлены.

# Известные ограничения при немедленной передаче

Независимые ревью остановлены по прямому запросу пользователя 30 октября 2026 года. Полная финальная приёмка не завершена.

В первом независимом отчёте Яндекс Маркета зафиксированы следующие воспроизводимые случаи, которые не исправлялись после остановки:

- Окно почасовых коэффициентов D (общий интерфейс Ozon/ЯМ) может потерять несохранённый ввод при закрытии/повторном открытии и допускает повторное открытие во время запроса сохранения. До исправления вводите значения, нажимайте «Сохранить» и дожидайтесь завершения запроса; не закрывайте окно и не продолжайте редактирование во время сохранения.
- Агрегация сохраняет числовой результат, partial/stale и причины, но теряет expected_dates/known_dates/complete в метаданных итогов. Даты происхождения качества в агрегированных данных требуют доработки.
- У Яндекс Маркета период по умолчанию может начинаться в декабре 1999 года, если единственная подтверждённая дата — 1 января 2000 года. Обычные современные периоды этим случаем не затронуты; явная нижняя граница валидируется.

Эти находки ещё не прошли обсуждение трёх проверяющих и не являются завершённым итогом панели. Источник: отдельный immutable INITIAL Astra R2. Физическое переключение существующей вкладки hidden→visible не проверялось по согласованному с пользователем ограничению; логические обработчики проверялись отдельно. Живые API кабинетов и production не проверялись.


## Надёжность части доказательств проверки

После остановки выявлено: один тестовый harness Ozon с неверно закреплённым рабочим каталогом перезаписал семь служебных файлов результатов разработчика (fresh-bootstrap, PostgreSQL compatibility payload/results и четыре HTML-снимка). Их текущую целостность нельзя считать подтверждённой; они не служат основанием для заявления о завершённой приёмке. По известным путям записи затронуты validation outputs, не исходники продукта. Исходники при передаче совпали с зафиксированными SHA. Подробный перечень и реальные журналы сохранены в state направления Ozon; восстановление доказательств не выдумывалось.
