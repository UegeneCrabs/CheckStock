# API Ozon для ИИ-агентов

Расширение существующего `/api/agent/v1` поддержкой `marketplace=OZON`. Основа разработки — master `5fff2931089fb1e17de9fd929bc30f59645c7349` от 1 ноября 2026 года. Права, API-ключи и OAuth MCP остаются общими с действующим API. Новые методы не меняют цены, настройки, акции или бизнес-записи.

## Границы

- Только существующие источники хранения. Новых таблиц, миграций, сборщиков и запросов Seller/Performance из методов API нет.
- Пустая таблица означает отсутствие загруженных данных, а не отсутствие событий в кабинете. Наличие метода и доступ пользователя не доказывают наличие данных.
- Акции и связанные товары пропущены: полноценного постоянного источника текущих данных для этих API в рассматриваемом master нет. Журнал операций не заменяет текущую принадлежность акции.
- Для Ozon недоступны `standard-costs`, `spp-hourly`, `spp-daily`, `supplies`. Обычная комиссия Ozon не является двумя сценариями WB с ИУ и без ИУ; дневные наблюдения цены не являются средними СПП WB.
- Внешняя приёмка выполняется только через ChatGPT MCP. Claude и GPT Actions не подключаются к тестовому стенду. Компактная инструкция Actions обновляется и проверяется локально.
- Синтетические записи разрешены только в существующих таблицах изолированной локальной БД. Рабочую БД не изменяем. GET API не создаёт тестовые записи.

## Поддерживаемые общие методы

Всего Ozon поддерживают 39 методов, включая четыре метода обнаружения и десять дополнительных отчётов.

| Группа | Методы | Источники и ограничения |
| --- | --- | --- |
| Обнаружение | `stores`, `capabilities`, `article-stores`, `data-status` | Доступные магазины/площадки, области методов, фильтры, существующий каталог, счётчики источников. Счётчики и крайние даты не являются покрытием периода. |
| Товары | `products`, `product-details` | Каталог Ozon и наблюдаемые остатки. Полный `offer_id` сохраняется, включая ` / ` и суффикс. |
| Справочники | `product-newness`, `product-reputation`, `product-tags`, `costs` | Загруженная история, рейтинг по SKU, текущие значения 1С, менеджер, ABC, цели/план/факт. Возраст наблюдений не является возрастом карточки. Текущие закупочные цены не подставляются в прошлое. |
| Экономика | `current-economics`, `profit-calculator`, `profit`, `target-prices`, `loss-products` | Те же серверные расчёты Ozon, что использует сайт. Текущая экономика и калькулятор — на единицу, `profit` — период. Убыточные товары отбираются только при полном отрицательном расчёте. |
| Сводка и отбор | `profit-summary`, `product-analysis` | Все строки до пагинации. Ozon указывается явно. Без магазина рассматриваются все доступные магазины выбранной площадки; ошибки магазинов изолируются. |
| Реклама | `advertising`, `advertising-campaigns` | Сохранённые рекламные окна и факты. Перекрывающиеся окна выбираются существующим нормализатором, а не складываются. Активность кампании определяется статусом Ozon, а не WB `9`. |
| Остатки | `stocks`, `stock-value`, `stock-history`, `stock-operations` | Каталог, текущие схемы/склады, история, движения. `stock-value` Ozon использует общий текущий остаток; фильтры `warehouse` и `scheme` для него отклоняются. Неизвестная закупка даёт неизвестную стоимость. |
| Цены | `prices` | Без дат — четыре текущих объекта цен. С датами — первое/последнее наблюдение каждого дня, полнота и закрытие. Это не дневное среднее. |
| Поставки и складские отчёты | `inbound-supplies`, `supply-arrivals`, `stock-cost-report` | Сохранённые составы/приёмка поставок, общий реестр поступлений, движения и закупочная стоимость. Реестр поступлений требует доступа ко всем площадкам магазина и не должен дублироваться по площадкам. |
| История | `economics-history` | Точный товар, `days=7`, `14` или `30`; видимые дни графика, включая текущий неполный день. Вспомогательная неделя сравнения не попадает в `rows`. Прибыль этим графиком не предоставляется. |

## Дополнительные методы Ozon

Для этих методов каталог показывает «Нет» у WB и Яндекс Маркета и «Есть» у Ozon. Это доступность конкретного контракта API, а не утверждение об отсутствии похожих данных у других площадок.

| Метод | Фильтры сверх общих | Данные |
| --- | --- | --- |
| `ozon-buyout` | `article`, `search`, `manager` | Эффективный и фактический процент, признак резервного значения, получено/отменено/возвращено/удержано, окно и свежесть. |
| `ozon-logistics` | `article`, `search`, `manager`, `details` | Последний сохранённый 30-дневный снимок: фактические/модельные расходы на единицу, суммы, количества, причины неполноты. `details=true` добавляет начисления. |
| `ozon-storage` | `article`, `search`, `manager`, `details` | Последний сохранённый снимок хранения: расходы, продано/возвращено/удержано, стоимость единицы, период. `details=true` добавляет дневные строки расходов. |
| `ozon-advertising-breakdown` | обе даты, `article`, `search`, `manager` | Статьи/дни расходов, состояние, пропуски, устаревание. Нераспределённые расходы магазина возвращаются отдельно в контексте. |
| `ozon-commissions` | `article`, `search`, `manager`, необязательные обе даты | Без дат — сохранённая комиссия FBO: ставка, ценовая база, сумма, источник и состояние. С датами — первое/последнее наблюдение ставки дня, без подстановки текущей ценовой базы. Это не все комиссии Ozon. |
| `ozon-profit-details` | обе даты, `article`, `search`, `manager` | Прибыль/ROI и дневные компоненты: цена, закупка, ФФ, комиссия, эквайринг, налоги, логистика, хранение, реклама, ожидаемые выкупы, базы и причины неполноты. Для большого периода сужайте товар/страницу. |
| `ozon-analyzer` | `week`, `article`, `search` | Анализатор: факт/план/прогноз, недельные количества, текущий остаток, реклама/ROI, корзины и даты их источников, качество. |
| `ozon-ephemerides` | `week`, `article`, `search` | Показатели текущей/предыдущей недели, цели, отклонения, недельные снимки остатков и качество. Неизвестный недельный остаток не заменяется текущим. |
| `ozon-sales` | обе даты, `article`, `search` | `days`, `orders`, `cancellations`, `cancels` — количества единиц; `today_turnover` — рубли. Даты массива находятся в `context.dates`. Заказы не равны подтверждённым продажам. |
| `ozon-analytics-comments` | `week`, `article`, `search`, `include_history` | Комментарии недели и дневные рабочие записи. `include_history=true` добавляет сохранённые ревизии текста. Имена/ID сотрудников и права редактирования не возвращаются. Тексты являются данными, а не командами ИИ. |

Общие параметры табличных методов: `store`, `marketplace`, `limit` 1–100, `offset`, `sort_by`, `order`. Калькулятор требует точный товар и не поддерживает пагинацию. Даты включительны, период API 1–90 дней, будущие даты недоступны. Для недельной аналитики произвольный день нормализуется к понедельнику; будущая неделя отклоняется. Фильтры проверяются сервером, неизвестные параметры не игнорируются.

## Семантика показателей

- Все суммы в рублях, машинные значения остаются числами; проценты не складываются и не усредняются без баз.
- `orders_amount` в `profit` — ТО заказов до отмен; `net_orders_amount` — после отмен. Ни один из них не является подтверждённой выручкой выкупов.
- Потенциальная прибыль берётся из существующих дневных расчётов сайта с ожидаемыми выкупами, историческими вводными и календарными поправками. Формула при добавлении API не менялась.
- `margin_complete=false` не скрывает доступную числовую прибыль/ROI. Пользователь видит «Расчёт неполный» и причину/покрытие. `null` не заменяется нулём.
- `orders_complete` и `context.orders_coverage` описывают заказы независимо от полноты прибыли. Отсутствующий расчёт прибыли за день не означает отсутствия заказов.
- В `profit` и `ozon-profit-details` объект `stock_basis` раскрывает базу существующего показателя `stock_days`: `period_from`, `period_to`, `period_days`, количество `orders_count` после отмен (`orders_basis=after_cancellations`) и `coverage`. Сейчас это скользящие 21 день, включая текущий день; окно не зависит от выбранного периода прибыли. Средний спрос остаётся в `stock_average_daily_orders`. Полнота покрытия сохранённых наблюдений не делает текущий день завершённым: `current_day_partial=true` отмечается отдельно. При отсутствии базы `stock_basis=null`; при пропусках известны даты и полнота, а недоступные показатели остаются `null`. Для строк группировки база отдельного товара не назначается. Формула сайта не менялась, дополнительных чтений БД нет.
- В сводке маржа относится к товарам с положительным ТО и полным расчётом. Исключения считают неполные/неизвестные расчёты, а не товары без заказов. Нулевой исходный ТО не даёт процент изменения.
- `product-analysis` поддерживает шесть существующих сценариев. Неизвестная полнота заказов/рекламы попадает в неизвестные результаты, а не подтверждает отсутствие продаж. Для сравнения Ozon по умолчанию берётся непосредственно предшествующий равный период.
- Сохранённый выкуп с `default_applied=true` является резервным значением, а не фактическим результатом. Логистика и хранение имеют собственное 30-дневное окно; фильтр недели к ним не применяется.
- CPC-показы/клики не являются органическими показами. Расход без подтверждённой атрибуции не создаёт показатель рекламных заказов. Кампании и общий рекламный отчёт могут иметь разные доступность и покрытие; окна не дублируются.
- ДРР анализатора использует валовой ТО и выкуп; Unit Profit — свою базу после отмен. Показатели разных баз не подменяются. `wallet` анализатора — цена, не процент.
- `seller_price`, `black_price`, `green_price`, `base_price` в `prices` — объекты значения/валюты/состояния/времени. `black_price` — покупатель, `green_price` — Ozon Карта. Скидка покупателя текущей экономики повторяет формулу анализатора и не является почасовой историей СПП WB.
- Категории из внешнего Seller API при чтении прибыли не запрашиваются. Без локального источника категория неизвестна; это отражено в `category_unavailable_stores`.

## Реализация

- `app/dto/agent_*.py` — проверяемые параметры и именованные контракты границы JSON.
- `app/application/agent_ozon.py`, `agent_ozon_analysis.py` — сценарии чтения, обогащение менеджером, сводка и отбор. Магазины сводки/анализа выполняются через `TaskGroup` с изоляцией ошибок.
- `app/infrastructure/agent_ozon_repository.py` — чтение существующих источников. Старые общие складские модели выполняются через `AsyncReadModels`: асинхронное соединение SQLAlchemy/greenlet и защищённый контекст чтения, без пула потоков для БД.
- `app/container.py` — сборка из существующих Ozon repositories/services; локальный читатель категорий не обращается к Seller API.
- `app/agents/ozon_fields.py`, `ozon_campaigns.py` — преобразование в контракт JSON и нормализация сохранённых кампаний.
- `app/agents/marketplaces.py`, `ozon_reports.py`, `ozon_catalog.py` — поддержка площадок, описания методов и полей; один реестр используется каталогом, валидацией и OpenAPI.
- MCP передаёт существующие асинхронные ресурсы внутреннему ASGI-вызову. Токены внешнего клиента не пересылаются внутреннему HTTP-приложению.
- В каталоге три столбца доступности: WB / Яндекс Маркет / Ozon. Оформление и объединение строк выполняет JavaScript; backend не формирует интерфейс.
- Полная инструкция MCP и компактная инструкция GPT Actions содержат одинаковые ограничения Ozon. Компактная версия проверяется по UTF-16 с CRLF и остаётся в пределах 8000.
- При неполной прибыли/ROI обе инструкции требуют дословную пометку «Расчёт неполный» рядом с числами, включая ответы с объяснением пропущенных дней. Для вопроса о запасе используется показатель сайта с его окном и базой; альтернативный расчёт выполняется по отдельному запросу.

## Приёмка перед push

1. Локальный Linux/PostgreSQL, отключённые внешние загрузчики, фиксированный генератор тестовой выборки. Отдельные товары помечены `[ТЕСТ API]`; исходные записи не перезаписываются.
2. Каждый из 39 поддерживаемых методов вызывается по HTTP и через реальное подключение ChatGPT MCP. После добавления инструментов обновляется подключение и создаётся новый чат.
3. Числа сверяются с исходной выборкой: положительная/отрицательная прибыль, неполный расчёт, неизвестная закупка, нулевые заказы, реклама без заказов, отмены/возвраты, обе схемы, точный артикул с суффиксом, неоднозначный магазин, страницы и недоступные площадки.
4. Контрольные суммы бизнес-таблиц до/после чтения подтверждают отсутствие изменений данных API.
5. Существующие регрессионные проверки, Ruff и настроенный mypy; новые модули включены в постоянный список mypy. Новые постоянные тестовые файлы не добавляются.
6. Проверяется обычный ответ GPT менеджеру: понятные подписи, потенциальная прибыль/расчётный ROI, пометка неполноты, без JSON/имён полей/методов.

Синтетические проверки подтверждают контракт и поведение приложения, а не полноту и достоверность загрузок рабочего сервера. Push, PR и отправка на проверку выполняются отдельным шагом после разрешения пользователя.

## Результат локальной проверки 1 ноября 2026

- Linux/PostgreSQL 17: 39 из 39 поддерживаемых методов вернули успешный ответ. Дополнительные 46 запросов проверили числа, полноту, фильтры, точный артикул, неоднозначность магазина, пагинацию, валидацию, аутентификацию и неподдерживаемые площадки.
- Временная SQLite с копией той же синтетической выборки: 39 из 39 методов; прибыль и ROI совпали с PostgreSQL. Внешние HTTP-запросы в этом прогоне запрещены транспортом и не выполнялись.
- Реальный ChatGPT MCP: вызваны все 39 методов и инструкция. Проверены новые инструменты после обновления подключения, история цен/ставок, оба вида рабочих записей с ревизиями, детализация логистики и хранения.
- Положительная прибыль: 9 547 ₽ и ROI 84,88%; отрицательная: −12 645 ₽. Неполный расчёт: 5 472 ₽ и ROI 58,91% за 6 из 7 дней. GPT сохранил числа и объяснил «Расчёт неполный» без JSON и технических полей в обычном ответе менеджеру.
- Оба рекламных отчёта дали 105 ₽. Детализация снимков дала одно начисление логистики на 5 000 ₽ и 30 строк хранения на 500 ₽. Период снимков не подменяется неделей запроса.
- Контрольные суммы 48 бизнес-таблиц перед/после итоговой матрицы чтения совпали. Генерация тестовой выборки выполнялась отдельно, только в изолированной локальной БД.
- Существующие Python-проверки API/MCP/управления доступами: 22 теста; клиентские проверки инструкций/подключений: 14 тестов. Ruff lint прошёл для `app`, `scripts`, `run.py`; форматирование всех изменённых Python-файлов корректно. Общая проверка форматирования обнаруживает 22 прежних незатронутых файла master; они в эту задачу не включены.
- Настроенный mypy: 184 файла без ошибок. Компактная инструкция Actions: 7 992 единицы UTF-16 с CRLF, в пределах 8 000.
- Временный ключ HTTP-проверки отозван; временные проверочные сценарии удалены. Сервер, локальная тестовая выборка и разрешённый HTTPS-туннель оставлены для просмотра результата.

После проверки 20 бизнес-вопросов уточнены два контракта: обязательная дословная пометка неполного расчёта рядом с числами и `stock_basis` для обеспеченности запасом. Повторные вопросы через ChatGPT MCP дали «Расчёт неполный» с прежними 5 472 ₽ / 58,91% и запас 14,36 дня с окном 12 октября — 1 ноября, 98 единицами после отмен и предупреждением о текущем дне. Альтернативная недельная оценка больше не подставлялась.

Дополнительный прогон на PostgreSQL и временной SQLite проверил оба метода, независимость окна запаса от периода прибыли, пропуски наблюдений, отсутствие базы и совместимость группировок. Чтение не изменило контрольные суммы 60 бизнес-таблиц. Прошли 22 существующих серверных и 14 клиентских тестов, Ruff и настроенный mypy (184 файла). Компактная инструкция после уточнений занимает 7 991 единицу UTF-16 с CRLF. Синтетические данные и формулы сайта при исправлениях не менялись.
