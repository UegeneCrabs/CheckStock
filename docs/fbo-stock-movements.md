# Поставки FBO: выбор одного ФФ и ручное проведение

С 23 октября 2026 года поставки WB, Ozon и Яндекс Маркета учитываются в блоке
«Сток → Движение товаров» по данным `inbound_supply_snapshots`.

## Списание и нехватка

Для WB, Ozon и Яндекс Маркета загрузка поставок из API не списывает остатки.
Новая поставка необработанная, пока сотрудник не выбрал один ФФ. Выпадающий список
содержит все названия из справочника БД `fulfillments`. После выбора сервер проверяет
весь состав в пределах магазина, площадки и выбранного ФФ. Остатки других ФФ
и других площадок не суммируются. Повторяющиеся артикулы в составе объединяются.
Успешный выбор сохраняется в БД и делает поставку обработанной, но ещё не проведённой.

Перед проведением проверяется весь состав поставки. Нехватка хотя бы одного артикула
не допускает частичного списания. Внутри карточки, в таблице товаров, столбец
«Не хватает, шт.» показывает недостающее количество; вся строка такого товара красная.
При достатке показан 0, до выбора ФФ — прочерк. При нехватке выбор ФФ сбрасывается,
кнопки «Провести» нет; внутри поставки перечислены товары и количество недостающих
единиц. Последний проверенный ФФ сохраняется отдельно для пояснения ошибок и фильтра
«Только с нехваткой». Пользователь может выбрать ФФ заново. «Провести» появляется
после успешной проверки при подтверждённом составе и доступном для проведения статусе.
Перед списанием сервер повторно проверяет остатки под блокировкой; если между выбором
и проведением сток уменьшился, операция не списывает ни одной позиции и сбрасывает
выбор непроведённой поставки. Пополнение, синхронизация и перезапуск не проводят
поставку автоматически. Выбор ФФ сам по себе не резервирует остатки.

Уже проведённая поставка сохраняет ФФ списания; менять его нельзя. Изменение состава
не корректирует остатки автоматически: новое ручное проведение изменяет только разницу
на том же ФФ. До него сохраняется ранее проведённое количество. Старые поставки,
ранее проведённые с нескольких ФФ, сохраняют свои распределения и не списываются
повторно; новый сценарий не перераспределяет их между складами.

## Статусы

| Площадка | Полное учтённое количество остаётся в пути | Закрытие пути |
| --- | --- | --- |
| WB | `2`, `3`, `4`, `6`: запланировано, отгрузка разрешена, идёт приёмка, отгружено на воротах | `5` — принято, независимо от готовности к продаже и расхождений |
| Ozon | `READY_TO_SUPPLY`, `ACCEPTED_AT_SUPPLY_WAREHOUSE`, `IN_TRANSIT`, `ACCEPTANCE_AT_STORAGE_WAREHOUSE`, `REPORTS_CONFIRMATION_AWAITING`, `REPORT_REJECTED` | `COMPLETED` |
| Яндекс Маркет | `ACCEPTED_BY_WAREHOUSE_SYSTEM`, `REGISTERED_IN_ELECTRONIC_QUEUE`, `ARRIVED_TO_SERVICE`, `ARRIVED_TO_XDOC_SERVICE`, `SHIPPED_TO_SERVICE`, `WAREHOUSE_HANDLING`, `WAREHOUSE_SIGNED_ACT` | `FINISHED` |

Черновики и ещё не согласованные заявки не списываются. Частичная фактическая приёмка
не уменьшает путь до итогового статуса. Закрытие пути не возвращает товар на ФФ и не
начисляет FBO: остатки маркетплейса продолжают загружаться отдельными отчётами.
Кнопки ручной приёмки и возврата приёмки FBO удалены; сервер также запрещает эти действия.
Приёмка перемещений между ФФ сохраняется.

При неподтверждённых данных, неизвестном статусе, ошибке или устаревшем снимке новые
списания запрещены, ранее учтённые количества сохраняются. При отмене площадкой
списанное количество не возвращается автоматически. После фактического возврата
сотрудник может нажать «Товар вернулся — вернуть на ФФ»; сервер проверяет подтверждённую
отмену и возвращает количество на исходные ФФ.

## Переход и хранение

`fbo_supply_movements` хранит последнее учётное состояние, распределение, снимки цен
и алерты по ключу магазин / площадка / поставка. `fbo_supply_batches` связывает поставку
с партиями `ff_transit_batches` типа `fbo_shipment` по ФФ. Обе новые таблицы создаёт
обычный `init_db`, без пересоздания существующих таблиц. DDL поддерживает SQLite/PostgreSQL.
Выбранный `fulfillment` и последний `checked_fulfillment` хранятся в существующем
`payload_json`; новая миграция схемы не нужна. Старые JSON читаются с пустыми значениями.
Если старая проведённая поставка имеет ровно один источник, ФФ определяется из её
распределения. `processed` вычисляется по выбранному ФФ или прежнему распределению.

После успешного сохранения снимка выполняется асинхронная сверка складского учёта.
При старте сайта сверяются сохранённые снимки; ни свежие, ни устаревшие не создают новых списаний.
Сверка читает актуальный снимок под блокировкой, поэтому поздний обработчик не применяет
устаревший состав. Списание ФФ, партии, операции, журнал и учётное состояние фиксируются
одной транзакцией. Ошибка откатывает все изменения. Сохранение API-снимка и складская
сверка — отдельные транзакции; прерванная сверка повторяется при следующем обновлении
или старте сайта, без повторного списания уже проведённых поставок.

Впервые обнаруженные завершённые поставки сохраняются как история без списания текущего
ФФ. При пересечении открытой поставки со старыми ручными FBO-отгрузками автоматическое
списание блокируется. Сотрудник выбирает соответствующие отгрузки в карточке; сервер
требует точного совпадения суммарного состава и проверяет магазин, площадку и отсутствие
другой связи. Привязка не списывает ФФ повторно. Связанные партии показываются одной
карточкой поставки с разбивкой по ФФ. Новые ручные FBO-отгрузки через старую форму
запрещены; повтор уже зафиксированного запроса с прежним ключом сохраняется.

Если уже списанная родительская заявка Яндекса заменяется дочерними, новые списания
детей блокируются до сверки распределения. Это предотвращает повторное списание;
автоматическое разделение прежней отгрузки между дочерними заявками не выполняется.

## HTTP, отображение и экспорт

- `GET /stock/{slug}/fbo-stock?mp=...` возвращает типизированный `FboStockReport`.
- `POST /stock/{slug}/fbo-stock` принимает `marketplace`, `supply_key`, `action`
  (`select_fulfillment`, `post`, `link`, `return`), `fulfillment` для выбора/проведения
  и `batch_ids` для привязки. Пустой ФФ при выборе очищает выбор. При проведении ФФ
  запроса должен совпадать с сохранённым; справочник проверяется сервером.
- Отчёт включает `fulfillments`; движение — `fulfillment`, `checked_fulfillment`,
  `processed`, `stock_checked`, `can_select_fulfillment` и `can_post`. Возможность
  проведения вычисляется на сервере и повторно проверяется при POST.
- POST требует `Idempotency-Key` и активного пользователя с доступом к магазину.
  Результат сохраняется вместе с изменением. Повтор возвращает прежний результат;
  другой состав с тем же ключом отклоняется. Обработанная нехватка возвращает состояние
  с алертом, поэтому после пополнения пользователь создаёт новую попытку проведения.
- Frontend формирует подписи, нехватку по товарам, кнопку проведения и разбивку по ФФ.
  Активные движения и алерты показываются в «В пути», завершённые — в «Истории».
- Карточки используют оформление страницы «Поставки FBO»: в шапке остаются номер,
  площадка, маршрут, статус и итоговые количества. Нажатие на шапку раскрывает или
  скрывает таблицу товаров. Все поставки изначально свёрнуты; выбранное состояние
  сохраняется при обновлении данных и переключении вкладок до перезагрузки страницы,
  отдельно для магазина, площадки и поставки. Таблица строится при первом раскрытии,
  имеет ограниченную высоту и закреплённые заголовки. Строки одного артикула объединяются,
  чтобы распределение по ФФ и количество в пути не дублировались. Неизвестная приёмка
  показана прочерком. Нехватка, сообщения и действия находятся внутри раскрытого состава;
  при свёрнутой карточке в шапке остаётся только отметка «Требует внимания».
  Кнопки «Развернуть все» и «Свернуть все» над списком меняют состояние только
  показанных поставок с учётом текущей вкладки и фильтров. Скрытые фильтрами поставки
  сохраняют прежнее состояние. При загрузке и отсутствии показанных поставок кнопки
  недоступны; перемещения между ФФ они не затрагивают.
  В каждом из восьми столбцов товаров подключён `CheckStockTableFilter` — тот же
  компонент, что в юнит-экономике: поиск значений, множественный выбор и сортировка.
  Фильтры независимы для каждой поставки и сохраняются при обновлении списка до
  перезагрузки страницы. Общие фильтры поставок не изменяют фильтры товаров.

Сначала показаны необработанные поставки, затем обработанные. Внутри каждой группы
первой идёт ближайшая к текущему московскому дню плановая дата отгрузки (по модулю
разницы дат); поставки без даты — последними. При одинаковом расстоянии используется
сама дата, затем ключ поставки. Состояние обработки показано в шапке отдельно от
статуса маркетплейса и отметки проведения.

В отчёте нехватка каждой проверенной незавершённой поставки пересчитывается при чтении
по текущим остаткам выбранного/последнего проверенного ФФ с добавлением уже списанного
для этой поставки на том же ФФ количества.
Используется та же формула, что при проведении; повторяющиеся артикулы суммируются.
GET не списывает товар и не снимает ожидание ручного проведения. После пополнения
столбец показывает 0, но сброшенный ФФ нужно выбрать заново, затем явно нажать «Провести».
Это проверка одной поставки,
а не резервирование товара сразу для всех ожидающих поставок.
Неподтверждённое состояние, устаревший снимок и необходимость связать старые отгрузки
не скрывают расчёт: он использует сохранённый состав. Исходные `issue`, состояние
учёта, распределение и запрет проведения сохраняются, предупреждение показано внутри
карточки. Несвязанные старые отгрузки не прибавляются к доступному количеству.
Завершённые, исторические и возвращённые поставки не требуют пополнения; при наличии
ранее проверенного ФФ показан 0, без проверки — прочерк;
если уже принятой поставке не проведено увеличение количества, её нехватка рассчитывается.
Прочерк в столбце нехватки означает, что ФФ ещё не проверялся; неподтверждённый
статус сам по себе не скрывает результат последней проверки ФФ.

Над списком есть совместные фильтры по диапазону дат включительно, части номера
отправления, складу назначения и точному статусу площадки. Номер ищется также по ID
поставки и заявки. Дата — плановая, при её отсутствии — дата создания; для перемещений
между ФФ — дата отправки. Даты с временем приводятся к Москве, поставки без даты
исключаются при заданном диапазоне. Фильтры действуют в текущей вкладке «В пути»
или «История», сохраняются при переключении вкладок и обновлении, сбрасываются кнопкой.
Показан счётчик найденных движений; при пустой выдаче и обратном диапазоне дат есть пояснение.
Флажок «Только с нехваткой» по умолчанию выключен. При включении остаются только
поставки, у которых хотя бы один элемент `shortages` содержит `missing > 0`,
независимо от кода ошибки поставки. Пустой или отсутствующий расчёт, нулевая нехватка
и перемещения между ФФ в такую выдачу не входят. Флажок сочетается с остальными
фильтрами, сохраняется при обновлении и смене вкладки и выключается при сбросе фильтров.

В блоке «Движение товаров» для WB выводятся только поставки со статусами `2`
«Запланировано», `3` «Отгрузка разрешена», `4` «Идёт приёмка», `6` «Отгружено на воротах».
Ограничение применяется перед выбором вкладки, подсчётом карточек и построением
вариантов фильтров. Остальные статусы WB, включая принятое и неизвестное состояние,
в этом блоке не показываются. Ozon, Яндекс Маркет и перемещения между ФФ сохраняют
свои правила отображения. Ограничение только клиентское: снимки, отчёт API, учёт,
закрытие пути и страница «Поставки FBO» не отфильтровываются.

Обычная таблица стока, детализация ФФ и ТОТАЛ используют существующие транзитные партии.
Google-выгрузка стоков получает J только из перемещений между ФФ, K — из учтённых
FBO-партий. API-количества к K повторно не добавляются. Непроведённая поставка не
попадает в K; её товар ещё находится в доступном ФФ. Принятая поставка даёт ноль в пути.
Выгрузка только читает учёт, не проводит поставки и не требует свежего ответа API.
Аналитические оценки страницы «Поставки FBO» и юнит-экономики остаются отдельным контрактом.

Основные модули: `app/application/fbo_stock.py`, `app/dto/fbo_stock.py`,
`app/infrastructure/fbo_stock_{repository,orm}.py`, `app/stock/fbo_sync.py`,
`app/web/routers/fbo_stock.py`, `app/stock/fbo_availability.py`,
`static/stock/transit.js`, `static/stock/fbo-stock.css`.

## Проверка

Сценарий выбора одного ФФ проверен на временной SQLite-базе для трёх площадок:
отсутствие списаний при синхронизации/выборе, нехватка на одном ФФ при достаточном
суммарном стоке, сброс выбора, уменьшение стока между выбором и проведением,
параллельный повтор POST, полный откат ошибки после записи, ручная корректировка
состава и закрытие пути по принятому статусу. Проверены сортировка необработанных,
пустые даты, общий фильтр нехватки, независимые фильтры восьми столбцов и сохранение
их выбора после изменения ФФ. Реальный PostgreSQL в этой проверке не запускался.

Временные SQLite-сценарии проверяют три площадки, выбор и распределение ФФ, нехватку
в составе из нескольких товаров, ручное проведение после пополнения, параллельные
повторы, конфликт ключей, откат до commit, изменение количества, отмену, связывание
старой отгрузки, исторические и неподтверждённые поставки, HTTP-доступ, выгрузку и
сохранение приёмки между ФФ. Клиентский сценарий проверяет красные строки нехватки, отсутствие
приёмки FBO, явное проведение, распределение и переход в историю. Проверки не оставляют
постоянных тестовых файлов. DDL проверяется для обеих СУБД; реальная конкуренция
PostgreSQL и живые API требуют отдельного интеграционного окружения.

Карточки проверены в браузере на временных данных: сворачивание с мыши и клавиатуры,
ленивое раскрытие 40 позиций, сохранение состояния при обновлении и переходе в историю,
нулевой путь принятой поставки, проведение внутри раскрытого состава, объединение
повторяющихся артикулов и вёрстка на ширине 390 px и в узком рабочем блоке.

Проверки фильтров покрывают совместный отбор, московские границы дат включительно,
отсутствующую дату, пустую выдачу, обратный диапазон и сохранение выбора при обновлении.
Проверка отчёта подтверждает пересчёт нехватки после пополнения без изменения сохранённого
состояния, автоматического проведения и повторного списания.
