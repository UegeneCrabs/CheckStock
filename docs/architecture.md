# Архитектура CheckStock

`app.main` — только composition root: создаёт FastAPI-приложение, контейнер зависимостей, middleware и подключает предметные роутеры.

- `app.dto` — неизменяемые Pydantic-модели границ HTTP, прикладных сервисов и инфраструктуры.
- `app.application` — бизнес-сценарии и порты репозиториев. Этот слой не импортирует FastAPI, SQLAlchemy или `app.db`.
- `app.infrastructure` — SQLAlchemy 2.x модели, репозитории, Unit of Work и проверки готовности БД.
- `app.container` — явная сборка зависимостей; FastAPI-зависимости получают сервисы из контейнера приложения.
- `app.web.routers` — HTTP-валидация, авторизация, преобразование DTO и кодов ошибок; блокирующая работа отправляется в thread pool.
- `app.wb`, `app.ozon`, `app.yandex` — внешние API-клиенты и синхронизация маркетплейсов.
- `app.ff_import` — парсеры табличных файлов; изменение складских остатков выполняет прикладной сервис.
- `app.config` — единый источник путей, интервалов, лимитов, retry и timeout.
- `app.core.logging_config`, `app.jobs.scheduling`, `app.jobs.background` — структурный контекст запросов, жизненный цикл и фоновые задачи.
- `app.stock` — TOTAL, идентификация товаров, поставки, история и складские отчёты.
- `app.economics` — расчёты и отчёты WB/ЯМ; исходные данные и ЗЦ находятся в `sources`.
- `app.access` и `app.agents` — доступы пользователей и API ИИ-агентов.
- `app.jobs` — расписания, настройки, блокировки и ручные запуски синхронизаций.
- `app.exports` и `app.integrations` — выгрузки и общие внешние подключения.

Основной поток зависимости:

```text
FastAPI route -> Pydantic DTO -> application service -> repository Protocol
                                                    -> SQLAlchemy Unit of Work -> SQLite/PostgreSQL
```

Через этот контур работают аутентификация и складские перемещения. Шаблоны страниц обрабатываются через `string.Template`.

Синхронные SQLite, HTTP-клиенты, PBKDF2 и OpenPyXL не выполняются в event loop: асинхронные маршруты передают их в thread pool. Отдельный process pool сейчас не нужен: длительных вычислительных задач в профиле приложения нет; его следует добавлять только по результатам измерений.

`app.repositories` и `app.db` остаются compatibility-слоем для крупных аналитических read-моделей и синхронизаторов. Новые сценарии и изменения состояния не должны добавляться в этот слой; он мигрируется предметными срезами в SQLAlchemy-репозитории.

`templates` и `static` разделены на `stock`, `economics`, `admin`, `integrations`, `agents`. Общие шаблоны находятся в `templates/layout`, общие CSS и JavaScript — в `static/common`.

На странице `/analytics/analyzer` сводка товарооборота по магазинам отображается без подписи над таблицей и без внутренней прокрутки: высота определяется всеми строками, текст в ячейках переносится по ширине. Сводка выровнена по правому краю верхнего блока и учитывает фильтры основной таблицы товаров.
Анализатор, эфемериды и продажи по API по умолчанию сортируют товары по сегодняшнему
`wb_funnel_daily_orders.orders_amount` по убыванию (день определяется по Москве).
Выбранный период меняет показатели отчёта, но не день ранжирования. Неизвестные
значения идут последними; отмены и процент выкупа из ТО не вычитаются.
В продажах поле `today_turnover` загружается отдельно за один день, если сегодня
не входит в выбранный период; пропущенные дни между периодом и сегодня не читаются.
Проверки этого контракта и общего чтения эфемерид: `tests/test_analytics_today.py`,
`tests/test_analytics_today.cjs`.
Оформление анализатора согласовано с эфемеридами: поиск и переключатели «Все товары»,
«В минус», «Новинки» находятся в одном ряду у нижнего края верхнего блока.
Кнопка в заголовке «Магазин» переключает отдельные магазины и одну строку общего итога;
состояние сохраняется в настройках вида. Итоги используют общий расчёт без повторов размеров,
неизвестные значения не становятся нулями, звёздочки в сводке не показываются.
Столбец товара имеет ширину 160 px, остальные столбцы также уплотнены.
Шапка закрепляется целиком: группы — 24 px, названия — от 56 px, итоги — 24 px.
Навигация учитывает фактическую ширину закреплённых столбцов товара и кода.
Нижняя информационная подпись убрана, освобождая место для строк таблицы.
В заказах по дням плашка сравнивает факт с дневной целью: невыполненная доля
цели подсвечена красным, доля заказов сверх цели — зелёным. Например, 8 из 10
дают 20% красного, 12 из 10 — 2/12 зелёного. Выполненная часть сохраняет
нейтральный фон, точное выполнение не выделяется. Без положительной дневной
цели и при отсутствии факта цветового сравнения нет. Подсказка содержит цель
и недостающее количество либо перевыполнение; плашка видна и в плотном режиме.

Блок «Рекламная воронка · 4 дня» содержит рекламные показы и CTR, а «Корзины» —
все добавления товара за день, включая органические. Синхронизация воронки сохраняет
`statistic.selected.cartCount` в nullable-поле `wb_funnel_daily_orders.cart_count`.
Анализатор предпочитает этот счётчик старому `rnp_daily_metrics.traffic_carts`.
Старые записи без счётчика остаются неизвестными до обновления источника; ноль
показывается при полученном нулевом значении. Итог корзин не повторяет размеры
одного артикула WB и разделяет одинаковые артикулы разных магазинов.

В `scripts` команды разделены на `ops`, `sync`, `imports`, `exports`, `diagnostics` и `parsers`. Предпочтительный запуск — `python -m scripts.<раздел>.<имя>` из корня проекта.

Локальная БД — `data/checkstock.db`; в Docker используется именованный том PostgreSQL. Резервные копии находятся в `data/backups`, состояние браузерного парсера — в `data/yandex-storefront`. Эти данные не входят в Git.
