# WB: расходы без ИУ за неделю

Третий отчёт WB: `/sales/unit-economics-1c/reports/standard-costs`. Чтение не вызывает API. Расходы калькулятора дополняют стандартные расходы WB для расчёта чистой прибыли и ROI. Синтетические данные не используются.

Источники: официальные [тарифы](https://dev.wildberries.ru/docs/openapi/rates), [хранение](https://dev.wildberries.ru/docs/openapi/reports), [реализация](https://dev.wildberries.ru/docs/openapi/documents-and-accounting). Проверено 19.10.2026.

- Детализация реализации `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed`, `period=daily`: все страницы до пустого ответа, уникальный `rrdId`, отбор по `rrDate`. База комиссии — операции «Продажа» минус «Возврат», `retailPriceWithDisc × quantity`. Корректировки и прочие операции в базу не включены, их счётчики сохранены.
- Хранение `GET /api/v1/paid_storage`, status, download на seller-analytics-api: `barcodesCount` и `volume` по каждому дню и складу. Строки «скидка по спецусловиям» не являются остатками и исключены.
- Короба `GET /api/v1/tariffs/box?date=...`: отдельный архивный снимок для каждого из семи дней. В реальном ответе за 12–13 октября 2026 нет «Склад WB РФ», поэтому показатель логистики одной доставки явно использует тариф на конец недели; исторический недельный итог логистики не рассчитывается. Стоимость = первый литр + max(литры − 1, 0) × дополнительный литр. Коэффициенты уже включены. Паллеты, штрафные типы хранения, неизвестные ставки не подменяются нулями.
- Комиссия `GET /api/v1/tariffs/commission?locale=ru`: `paidStorageKgvp` для FBW, `kgvpMarketplace` для FBS; предмет из карточки. **Это текущая ставка на дату загрузки**, не архивная комиссия недели: endpoint не принимает дату.

Логистика в таблице — **рубли на одну доставку**, тариф на конец недели, взвешенный по количеству товара в ежедневных остатках недели и историческому объёму. При отсутствии остатков — средняя по складам продаж и текущему объёму карточки, что указано в деталях. Для FBS используются поля `boxDeliveryMarketplaceBase/Liter`. Это не фактическая сумма поездок за неделю; Это базовая прямая доставка; в итоговом сравнении к ней добавляются возвраты и повторные отправки (см. ниже). Дополнительные услуги не включены. Логистика не суммируется с недельными затратами.

Хранение — сумма базовых начислений `warehousePrice` до скидки по спецусловиям. Строки скидок исключены, положительная сумма не заменяется нулём. Сохраняется фиксированный тариф поставки. При ненулевой `loyaltyDiscount` сумма считается неизвестной. Ставка в деталях = начисление / `barcodesCount`. Комиссия — сумма базы продаж/возвратов × ставка схемы. Схемы одного артикула отображаются отдельно. Неизвестные расходы имеют null; итоговые карточки показывают число исключённых позиций.

Явные псевдонимы API: «Склад WB» → «Склад WB РФ»; «Склад поставщика - везу на склад WB» → FBS, тариф «Свой склад РФ». Неизвестные схемы/склады не сопоставляются приблизительно.

В `wb_standard_costs_snapshots` хранится последний расчёт каждого магазина, даты и источники. В `wb_standard_costs_sources` — реальные исходные ответы API для повторной проверки; в веб-ответ они не включаются. Запись источников и расчёта атомарна с commit. Доступ к странице и данным через существующий контроль секции отчётов WB. Хранение относится к строке FBW, другие схемы того же товара его не дублируют.

## Отображение на единицу товара

Версия 3: таблица показывает только расходы на 1 шт. Логистика — одна доставка. `storage_unit_day` = базовое хранение / сумма дневных остатков; ₽/шт./день, точность до 6 знаков. `unit_price` = сумма только продаж / проданные штуки, без возвратов; `commission_unit` = эта средняя цена × ставка. При отсутствии продаж цена и комиссия на штуку неизвестны. При отсутствии остатков хранение на штуку неизвестно, для FBS хранение на складе WB равно 0. Суммы недели остаются внутренними основаниями и доступны в объяснении формулы, но не выводятся как расходы в таблице или итоговых карточках.


## Сравнение на единицу

Отчёт использует `load_wb_calculator_products` — общий с калькулятором загрузчик локальной БД. Он выделен из существующего обработчика без изменения его расчётов. Магазины ограничиваются правами пользователя; нет HTTP-запросов к другому кабинету или синхронизации при чтении. Сопоставление по магазину и nmId; несколько размеров без однозначного соответствия не объединяются.

`standard_profit.compare` воспроизводит входы `databaseCalculatorValues` и вызывает общий Decimal-калькулятор для обоих сценариев. Одинаковы цена калькулятора, закупка, ФФ, реклама, эквайринг, комиссия компании, НДС и УСН/ОСНО. Для варианта без ИУ заменяются только комиссия WB (цена калькулятора × стандартная ставка), логистика и хранение (базовые расходы недели / продажи той же схемы). Для рекламы применяется правило основного калькулятора: отсутствующий `spend_per_order` заменяется на 0 ₽ в обоих сценариях; известная сумма сохраняется. Неполное покрытие периода рекламы само по себе не блокирует итог. Остальные неизвестные расходы и несохранённые настройки кабинета по-прежнему блокируют итог; отдельные допущения хранения описаны ниже.

Прибыль = цена − расходы. ROI = прибыль / закупка × 100%; это показатель калькулятора, не ROE капитала. Разница = без ИУ − с ИУ; разница ROI измеряется в процентных пунктах. Это сценарное сравнение: текущая цена калькулятора и расходы вместе с указанными датами тарифов и неделей хранения, а не фактическая прибыль финансового отчёта.

Ввод со скриншотов удалён, `calculator_inputs` не используется и не возвращается. Данные реальной БД применяются ко всем артикулам. Изображение берётся из каталога калькулятора или сохранённых карточек официального API. Нет фото — заглушка. По умолчанию отображаются фото, артикул со схемой и шесть итоговых показателей. Кнопка «+» вверху раскрывает все статьи расходов. Кнопка строки открывает сравнение статей и причины неполноты. Старый URL conditions-comparison перенаправляется на standard-costs.

## Логистика с возвратами (2026-10-19)
В сравнении без ИУ итоговая логистика = D + (D + R) × (1 − p) / p.
D — ранее рассчитанная прямая доставка с ИЛ=1; R = 46 + max(V−1, 0) × 14.
46/14 ₽ — согласованный пользователем тариф по умолчанию, не результат API.
V — объём карточки WB (литры), до 1 л минимум 46 ₽; складской коэффициент и ИЛ к R не применяются.
p — details.buyout_percent общего загрузчика калькулятора /100 (в том числе его настроенный fallback).
Модель распределяет неудачные доставки и возвраты на выкупленные единицы, допускает повторные невыкупы.
Нулевой/отсутствующий/некорректный выкуп или отсутствующая прямая ставка дают None; неизвестный объём также блокирует итог при выкупе ниже 100%.
Сценарий с ИУ остаётся из калькулятора. Поле row.logistics остаётся прямой доставкой; profit.logistics — итог с возвратами. logistics_returns содержит составляющие и причины отсутствия расчёта.
Новые загрузки API и изменения БД не требуются. UI показывает формулу, составляющие и источник тарифов.


## Штатная загрузка и публикация
`app/economics/wb/standard_sync.py`, задача `wb_standard_costs_sync` — общий загрузчик для ручного запуска и scheduler. Период вычисляется в Москве: вчера и шесть предыдущих дней. Загрузка читает все страницы реализации и карточек, ожидает готовность задания хранения (до 30 проверок), загружает тарифы за каждый день и текущую комиссию. Неполная пагинация, неверный формат ответа и ошибки WB прерывают публикацию для магазина; исходные ответы и расчёт сохраняются одной транзакцией только после успешной проверки. Подтверждённый пустой ответ допустим для магазина без операций.

Первое появление задачи: через 60 секунд после старта worker; далее каждые 4 часа после завершения. После ошибки два повтора через 5 и 15 минут; затем обычный интервал. Расписание, история и межпроцессная блокировка — общие `app.jobs.scheduling`/`tracking`. Ошибка одного магазина не блокирует остальные. Магазины без токенов отмечаются пропущенными; выключенные магазины не загружаются.

В «API и интеграции» → штатные загрузки появляется «WB: сравнение ИУ и без ИУ»: ручной запуск, настройки магазинов, история результата. Ручной запуск использует ту же блокировку и не меняет срок планового запуска. Загрузчик не требует локальных скриптов `work/`, Windows-путей, фиксированных дат или переноса локальной БД.

Для сервера: опубликовать все новые модули, шаблон и статику; стандартная инициализация схемы создаёт обе таблицы. Запустить/обновить сервис `scheduler` вместе с вебом (в docker-compose он уже есть), включить общую фоновую синхронизацию и новую задачу/нужные магазины. Настроить штатные WB-токены с доступом к контенту, аналитике, финансовым отчётам и тарифам. В ходе локальной проверки общий worker не запускается; проверяется отдельный ручной запуск TRIS. Для автоматических загрузок необходим работающий worker.

Задача обновляет только источники нового отчёта. Закупку, ФФ, налоги, рекламу, цены и процент выкупа обеспечивает существующая синхронизация калькулятора; отсутствие этих данных по-прежнему отображается прочерком. Копирование локальной БД не требуется. Проверка на сервере выполняется отдельно по статусу первого запуска и датам снимка.


## Разделение модулей

Версия 5: базовые строки `паллеты: основные` учитываются наряду с коробами. `warehousePrice` уже является суммой строки; её не умножают на число паллет или товаров повторно. Скидки по спецусловиям исключаются. При отсутствии базовых строк хранения в API для FBW принимается условный ноль (`basis=missing_api_zero`), отмеченный знаком † и пояснением в интерфейсе и Excel. Некорректные начисления не заменяются нулём. Для FBS сохраняется согласованное правило модели: 0 руб. хранения, в том числе при отсутствии продаж. Для FBW с продажами недельная сумма хранения делится на число проданных единиц. Старые снимки пересчитываются из исходников при чтении. Для товаров FBW с нулём продаж и известной дневной ставкой по согласованию пользователя применяется оценка: storage_unit_day × 90 дней. Она явно обозначена в подсказке и деталях, поле storage_calculation содержит basis=estimate_90_days. Если ставка неизвестна и оснований для условного нуля нет, расчёт остаётся неполным.


Снимки версии 4 сохраняют точность чисел до отображения: объём и промежуточные расходы не округляются перед вычислением обратной логистики. Старые снимки при чтении пересчитываются из сохранённых исходных ответов API без сетевых запросов и записи в БД. Если исходников нет, требуется штатная повторная загрузка магазина.

Чтение отчётов изолирует ошибки по магазинам. API возвращает `report: null` и безопасное поле `error` для проблемного магазина, остальные отчёты доступны. Интерфейс перечисляет недоступные магазины; диагностическое исключение остаётся в серверном журнале.

Для полной прибыли нужны данные штатной загрузки «Данные 1С» (`app/economics/sources/purchase_prices.py`, Google Sheets, колонки себестоимости и прочих затрат) и заполненные настройки кабинета WB. Загрузчик тарифов WB эти источники не заменяет. Локальная проверка 19.10.2026: сервисный аккаунт Google недоступен, закупка и ФФ отсутствуют во всех 517 справочных строках TRIS, кабинет не настроен. До подключения источника и настроек проверка прибыли на реальных данных остаётся незавершённой.

`app/wb/standard_costs.fetch_sources` собирает исходные документы без записи в БД; `sync_store` рассчитывает и публикует снимок. Пагинация и ожидание хранения имеют именованные лимиты. `standard_logistics.py` содержит независимую формулу возвратов и согласованные константы 46/14; `standard_profit.py` объединяет её с расходами калькулятора. Публичные поля отчёта и расписание сохранены. Результаты сверены целиком на 467 строках TRIS до и после рефакторинга.

Числа интерфейса округляются до целых; точность исходных расчётов и сортировки сохраняется. Отрицательная прибыль и соответствующий ROI выделяются красным в обоих сценариях.

Рефакторинг: `standard_storage.storage_per_unit` — чистая функция распределения хранения, возвращает метаданные и причины отсутствия расчёта. `NO_SALES_STORAGE_DAYS = 90` — согласованный срок оценки. `standard_profit.calculate_scenario` — единая функция расчёта прибыли/ROI и полноты для обоих сценариев. `compare` объединяет исходные расходы, логистику, хранение и разницу результатов. Контракт API сохранён; проверено точное совпадение всех 1606 строк до/после, 29 тестов прошли.
# Выгрузка Excel

Кнопка «Скачать Excel» выгружает все строки текущей выборки, включая остальные страницы,
в порядке сортировки таблицы. Фильтры магазина, поиска, схемы, активности, предмета и
менеджера учитываются через список выбранных строк. Сервер повторно читает значения из БД
и проверяет доступ к магазинам. При изменении состава данных требуется обновить отчёт.
Файл содержит период, оборот, оба сценария, разницы, подробные расходы и причины пропусков.
Числа сохраняют точность, но отображаются без дробной части; отсутствующие значения пустые.
Убытки и отрицательные разницы выделяются красным, положительные разницы — зелёным.
Маршрут: `POST /api/unit-economics-1c/reports/standard-costs.xlsx`.

При отсутствии базовых строк хранения в API WB для FBW принимается условный ноль (`missing_api_zero`). Он отмечается знаком † в таблице, пояснением в подсказках и примечанием в Excel; прибыль рассчитывается с этим допущением. Некорректные начисления не заменяются нулём. Если дневная ставка известна и продаж нет, сохраняется оценка на 90 дней.

Проверка локальных доработок: экспорт проверяет период каждой выбранной строки и отклоняет устаревшую выборку (409). Загрузка и экспорт ограничены ожиданием 120 секунд; после ошибки загрузку можно повторить. При истечении сессии показывается сообщение входа вместо скачивания HTML. Некорректные начисления хранения, даже без детализации, остаются неизвестными. Отображение округлённых чисел исключает «−0» без изменения исходных значений.


## Типизированные контракты отчёта

Снимки, строки, расходы сценариев, результаты логистики/хранения и запрос Excel описаны именованными моделями в `app/dto/wb_standard_costs.py` на базе `DtoModel`. Расчёт передаёт между функциями эти модели; XLSX получает `ExportItem` с типизированной строкой и контекстом магазина/периода. Завершённые DTO неизменяемы; коллекции строк и причин представлены кортежами. Изменяемые `RowDraft` и `RowAccumulator` из `standard_working.py` используются только при сборке. Результат сравнения — неизменяемый `Comparison`; сравнение не изменяет входную строку.

`standard_sources.calculator_product` адаптирует существующий JSON-контракт каталога калькулятора один раз при входе в отчёт. Исходный JSON WB сохраняется без потери дополнительных полей в `SourceBundle` для повторного расчёта и аудита. Сериализация моделей выполняется на границах хранения JSON, HTTP и интерфейса планировщика (`sync_job_payload`). Внутренние индексы по артикулам/магазинам не являются записями с неявными полями.

Формулы, версия снимка 5, схема БД и JSON-формат ответа сайта не изменены. Проверки охватывают точность и неизвестные значения, чтение старых снимков, сохранение/чтение SQLite, экспорт, HTTP-сериализацию и распознавание ошибок загрузки планировщиком.

API-пагинация и ожидание хранения находятся в `app/wb/standard_costs.py`, нормализация внешних ответов в именованные записи — в `app/wb/standard_costs_sources.py`. `standard_sync.py` управляет периодом, сборкой и сохранением. Технические лимиты и расписание задаются через `settings.wb_standard_costs`; бизнес-допущения ИЛ=1 и обратный тариф 46/14 оставлены в формулах. Запрос Excel валидирует схему FBW/FBS, даты и порядок границ периода.

Согласованное правило рекламы: отчёт повторяет `databaseCalculatorValues()` основного калькулятора — отсутствующая сумма рекламы считается нулём, неполное покрытие периода не блокирует расчёт. Для остальных неизвестных затрат сохраняется строгое поведение; исключения хранения описаны выше. Общий загрузчик калькулятора перенесён в `app/economics/wb/catalogue.py`; HTTP-роутер и отчёт используют его независимо друг от друга. Существующий JSON-контракт каталога сохранён, на входе отчёта он преобразуется в типизированные модели.

Обычные текст, фон, границы и фокус используют общие переменные из `static/common/base.css`, который не менялся. Контрастные цвета финансовых показателей сохранены в локальных `--sc-negative` (#b42318), `--sc-positive` (#137333) и `--sc-loss-bg` (#fff0ee). Прибыль с убытком и её ROI выделяются красным, знаки разниц определяют красный/зелёный; нули и неизвестные разницы нейтральны. Это оформление, формулы и значения не меняются.

Регрессионные проверки `tests/test_wb_standard_loader.py` вызывают настоящий `load_wb_calculator_products` и `enrich`; подменены только источники данных и часы. Проверено, что возврат прежнего поведения любого из двух фильтров вызывает падение тестов.


## Публикация снимка и общий загрузчик

`standard_sync.py` получает и проверяет все источники, собирает снимок и передаёт `PublishSnapshot` сервису `WbStandardCostsService` из `app/application/wb_standard_costs.py`. Зависимости собираются в `ApplicationContainer`; порты описаны в `app/application/ports.py`. Сервис открывает Unit of Work, сохраняет снимок и исходники и только затем вызывает commit. Реализация в `app/infrastructure/wb_standard_costs_repository.py` использует транзакцию SQLAlchemy и не делает самостоятельный commit. При ошибке записи источников обновление снимка также откатывается. Схема таблиц и JSON не изменены; `app/repositories/wb_standard_costs.py` оставлен для чтения.

Загрузчик `load_wb_calculator_products` и его вспомогательные функции находятся в `app/economics/wb/catalogue.py`, без зависимости от HTTP-роутера. При переносе тела всех десяти функций сверены по AST без изменений. Проверка до/после дала точное совпадение 1662 строк семи магазинов; повторная сборка семи наборов API и Excel (1453 строки × 43 колонки) также сохранили значения. Финансовые формулы не менялись.

Проверки транзакций используют временную SQLite: успешное сохранение и замена обеих записей, сохранность другого магазина, откат при ошибке второй записи и отсутствие commit внутри репозитория. Реальный PostgreSQL в этом окружении не проверялся.


Проверка согласованного поведения рекламы использует общий набор `tests/fixtures/wb_advertising_parity.json`: отсутствующий блок, отсутствующее поле, null, ноль, положительная сумма и неполное покрытие с отсутствующей либо известной суммой. Python-тест вызывает `compare`, а `tests/wb_advertising_parity.cjs` выполняет настоящие функции `databaseCalculatorValues` и `calculatePrice` из основного интерфейса. Проверяются сумма рекламы, прибыль и ROI. Это согласованное изменение входного значения по умолчанию после архитектурного рефакторинга; прежнее точное сравнение 1662 строк относится к рефакторингу до изменения правила рекламы.
