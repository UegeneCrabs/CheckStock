# Статус загрузки цены WB Кошелька

## Почасовая история витрины WB

Фоновая задача «Почасовые цены витрины WB» запускается отдельным планировщиком
`python -m app.jobs.worker` через 60 секунд после его первого старта и
повторяется через час после завершения предыдущего прохода. Посещение сайта для
запуска не требуется. Она работает отдельно от текущих задач цен для
юнит-экономики и WB Кошелька. По умолчанию включена; настройки
`CHECKSTOCK_WB_HOURLY_PRICES_ENABLED` и
`CHECKSTOCK_WB_HOURLY_PRICES_INTERVAL_SECONDS` задают включение и интервал.
Задачу и отдельные магазины можно выключить в настройках фоновых выгрузок.
Кнопка ручного запуска использует тот же сборщик и сохраняет результат в истории запусков.

Задача один раз запрашивает карточки уникальных nmID всех выбранных магазинов
через общий клиент витрины WB. Для каждого артикула и размера с фактической ценой
сохраняется запись в `wb_hourly_prices`: час и время наблюдения UTC, цена с СПП,
фактический процент СПП (`spp_percent`), исходные поля `price` карточки,
условия продажи и, при доступной скидке,
рассчитанная цена WB Кошелька. Ключ записи — магазин, артикул и час UTC;
повтор в течение часа обновляет запись. Если карточка или цена недоступна, новая
запись не создаётся и предыдущая история сохраняется. Расчёт по последней СПП
для этой истории не применяется. Дневные цены юнит-экономики продолжают
заполняться прежними задачами.
Товары без актуальной цены, в том числе без остатка на витрине, учитываются как
неполный результат задачи; сохранённые цены остальных товаров не теряются.
В ту же запись попадает доступный на момент сбора дневной оборот заказов из
воронки WB (`orders_turnover_rub` = сумма заказов минус отмены) и время последнего
обновления этих данных (`orders_turnover_updated_at`). Оборот относится к карточке
`nmID`, поэтому у размеров одной карточки он одинаков. День определяется по МСК.
Если загрузка воронки за этот день ещё не дала строку товара, оборот остаётся
пустым, а не превращается в ноль. Новые загрузки воронки не изменяют прежние
почасовые снимки.
Процент вычисляется для того же `nmID` и размера по актуальной цене продавца
`discountedPrice`: `(discountedPrice − цена с СПП) / discountedPrice × 100`.
Если цена продавца недоступна или размер нельзя сопоставить, `spp_percent`
остаётся пустым; цена витрины при этом сохраняется. Старые записи не пересчитываются.
В журнале почасового сбора видны загрузка каталогов, запрос витрины, получение цен
продавца, число сохранённых записей и записей с процентом СПП по каждому магазину,
а также ошибки отдельных этапов и общая длительность прохода.

Отдельная задача «Дневные цены витрины WB» в 00:05 МСК закрывает все завершённые
дни. Для каждого магазина и артикула она сохраняет одну строку в
`wb_daily_prices`. Цены, суммы в копейках и проценты усредняются с весом
`orders_turnover_rub` каждого почасового снимка. Пустые и неположительные веса
не участвуют; если положительных весов нет, берётся обычное среднее доступных
значений. Остальные поля берутся из последнего снимка дня. В дневной таблице
нет поля `orders_turnover_rub`. После успешного сохранения удаляются только
почасовые строки закрытых дней; запись после московской полуночи не затрагивается.
Сохранение и удаление выполняются одной транзакцией. При ошибке почасовые строки
сохраняются для повторного запуска задачи. Если запоздавшая почасовая запись
попытается изменить уже закрытый день, она отклоняется с ошибкой в журнале сбора.

## Отчёт по СПП

В разделе «Отчёты» доступна вкладка «WB · Отчёт по СПП».
Для выбранных дат включительно она сравнивает средневзвешенный фактический
`spp_percent` каждого товара со значением за непосредственно предшествующий
период той же длины. Например, 1–30 сентября сравнивается с 2–31 августа.
Для завершённых дней используются значения `wb_daily_prices`, а весом дня служит
сохранённый в воронке WB оборот заказов минус отмены по `nmID`. Дни с пустым или
неположительным ТО не получают веса; если положительных весов нет, берётся
обычное среднее доступных дневных СПП. Оборот размеров относится к общей карточке
`nmID`. Даты определяются по Москве.
Если в многодневном диапазоне есть почасовые записи неполного дня, этот день
не участвует в сравнении и обороте; введённые границы периода сохраняются, а
страница показывает уведомление. Чтобы посмотреть данные за сегодня, нужно
указать сегодняшнюю дату в обоих полях периода. При выборе только сегодняшнего
дня СПП и цена с СПП усредняются по почасовым снимкам с весом
`orders_turnover_rub`.
Снижение СПП получает статус «Требует внимания», равенство или рост —
«Без проблем». Если одного из замеров нет, статус — «Нет данных»; такие товары
не входят в процент здоровья. Расчётный СПП из дневных цен не подставляется.
Ползунок «Допустимое снижение СПП» задаёт порог от 0 до 100 процентных пунктов
с шагом 0,5; числовое поле также допускает значения больше 100. Товар требует
внимания только при снижении больше порога.
Порог применяется к статусам и сводке через параметр API `tolerance` (по умолчанию 0).
При открытии страницы обе даты равны сегодняшнему дню по Москве; выбранный период
сохраняется при переходах между вкладками в рамках браузерной сессии.
Поля дат отображаются в формате `ДД.ММ.ГГГГ`, API получает даты ISO.
Кнопка рядом с артикулом раскрывает два графика независимо от периода сравнения
отчёта. Дневной график показывает сохранённые СПП закрытых дней за последние
7 или 30 дней, 6 календарных месяцев либо год; неполный день остаётся
пропуском. Почасовой график показывает записи выбранного московского дня из
`wb_hourly_prices`, по умолчанию сегодняшнего. После ночной очистки прошлые дни
обычно не имеют почасовых точек. Подсказки обоих графиков показывают СПП, цену
с СПП и доступный ТО; почасовой график также показывает средневзвешенные итоги дня.
После закрытия день считается одним замером. Весь выбранный срок помещается в
ширину панели.
При движении курсора по графику или использовании стрелок с клавиатуры
показываются дата, среднее значение и число замеров. Временную ось можно
масштабировать колесом мыши над графиком, перетаскиванием оси дат вправо
или влево с непрерывным изменением диапазона относительно его середины,
или кнопками `+`/`−`; увеличенный график непрерывно сдвигается при зажатой
кнопке мыши и перетаскивании области точек.
Кнопка «Весь период» возвращает полный диапазон. История
загружается по запросу через
`/api/unit-economics-1c/reports/spp/history` с параметром `period` (`7d`,
`30d`, `6m`, `1y`) и проверкой доступа к магазину и товару. Для прежних
клиентов маршрут также принимает пару `date_from`/`date_to`. Почасовые точки
загружаются через `/api/unit-economics-1c/reports/spp/hourly-history` с
параметром `day` и той же проверкой доступа.

Торговый оборот в таблице — сумма заказов за включённые дни выбранного периода
за вычетом отмен по сохранённой воронке WB. При отсутствии исходных строк оборот
неизвестен. Бренд для фильтра берётся из синхронизированных карточек WB;
после добавления поля существующие карточки запрашиваются повторно при
следующей синхронизации категорий.
Заголовки таблицы переключают сортировку всей выборки между убыванием и
возрастанием до разбиения на страницы. API принимает `sort_by` (`article`,
`name`, `turnover`, `current_spp`, `previous_spp`, `status`) и `sort_order`
(`asc` или `desc`); по умолчанию товары упорядочены по обороту по убыванию.

## Локальная полная выгрузка

Из корня проекта, в окружении с установленным Playwright и Яндекс Браузером или Chromium Playwright:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-parser.txt
.\.venv\Scripts\python.exe -m playwright install chromium
```

После установки запустите синхронизацию:

```powershell
.\.venv\Scripts\python.exe -m scripts.sync.sync_unit_economics_1c_prices
```

Команда обрабатывает все кабинеты из каталога. При необходимости она обновляет
анонимный сеанс WB в отдельном профиле, получает цены с СПП, обновляет цену продавца через API
кабинета и сохраняет цены с WB Кошельком в настроенную БД. Юнитка WB читает эти
дневные записи; после выгрузки обновите страницу. Запуск виден в истории
«Цены для юнит-экономики 1С». `--store tris` ограничивает кабинет,
`--storefront-only` оставляет только СПП и кошелёк. Копия БД этой командой
автоматически не создаётся.

Текущий сайт WB использует маршрут
`https://www.wildberries.ru/__internal/u-card/cards/v4/detail`.
Запросам нужны анонимная cookie `x_wbaas_token`, версия сайта, `DeviceId` и
`X-Requested-With`. Токен продавца в эти запросы не передаётся.
Версия и cookie считываются из отдельного браузерного профиля; личный профиль
пользователя не используется. Сеанс хранится в игнорируемом Git файле
`secrets/wb_storefront_session.json`. При каждой подготовке создаётся отдельный
временный профиль в `data/wb-storefront/`, который удаляется после закрытия браузера.
Профиль с отклонённой cookie и старой открытой вкладкой не восстанавливается.
Путь файла можно изменить через `CHECKSTOCK_WB_STOREFRONT_SESSION_PATH`.

WB может отклонить сеанс значительно раньше срока cookie. При проверке
последовательные запросы с сохранённым сеансом вскоре начинали возвращать 498.
Теперь общий сборщик автоматически обновляет отсутствующий/истёкший сеанс,
а также сеанс, отклонённый с HTTP 401/403/498, и повторяет ту же пачку.
Это действует для CLI, кнопок ручной выгрузки и плановых задач цен/кошелька.
Уже полученные пачки не запрашиваются заново. Рабочий сеанс используется без
запуска браузера. `--prepare-session` остаётся необязательной принудительной
подготовкой перед запуском.

Весь процесс использует одну межпроцессную блокировку подготовки: ожидающая
задача переиспользует сеанс, уже обновлённый другой задачей. На пачку допускается
один повтор после обновления, на полный проход — максимум два обновления.
После неудачной подготовки действует пауза 120 секунд, чтобы параллельные
выгрузки не запускали браузер снова. Если новый сеанс тоже отклонён, ошибка
попадает в историю запуска, а ранее сохранённые данные остаются доступны.
Сеанс перезаписывается только после проверочного HTTP-запроса. При автоматическом
восстановлении проверяется именно отклонённая пачка со всеми исходными параметрами,
а не только один артикул: успешная одиночная проверка не гарантирует приём пачки.

Открытая страница сама по себе не подтверждает работоспособность cookie.
При HTTP 401/403/498 во время подготовки очищается
только `x_wbaas_token` этого домена/пути и страница перезагружается. Подготовка
ждёт отличающуюся cookie и проверяет её запросом карточки; старую cookie
повторно рабочей не объявляет. На подготовку допускается одна такая очистка,
повторный отказ нового сеанса останавливает обновление с ошибкой.

Автовосстановление включено по умолчанию:
`CHECKSTOCK_WB_STOREFRONT_AUTO_REFRESH=1`. Значение `0` отключает его для
диагностики. Локально нужны Playwright и Яндекс Браузер либо Chromium Playwright;
нестандартный путь задаётся `CHECKSTOCK_WB_BROWSER_PATH`. На Windows сначала
ищется Chromium Playwright, затем Яндекс Браузер. Используется отдельный
профиль, браузер по умолчанию запускается без окна. Для диагностики добавьте
`CHECKSTOCK_WB_BROWSER_HEADLESS=0` в `.env` и перезапустите приложение;
`1` возвращает фоновый режим. Проверка WB ожидается автоматически; CAPTCHA не решается.
При перенаправлении карточки на страницу проверки используется открытая вкладка.
Если Chromium не смог загрузить сайт, выводится его сетевой код ошибки сразу;
при незавершённой проверке выводится адрес страницы без параметров запроса.
Если Chromium завершается до подключения Playwright (например, из-за отказа в запуске
GPU-процесса в ограниченном окружении), можно явно включить
`CHECKSTOCK_WB_BROWSER_NO_SANDBOX=1`. Эта настройка отключает песочницу процессов
Chromium для отдельного профиля WB; по умолчанию она выключена.
В Docker используется установленный Chromium Playwright с виртуальным дисплеем
Xvfb и `CHECKSTOCK_WB_BROWSER_HEADLESS=0` по умолчанию. На сервере WB может
оставлять headless-браузер на странице «Подозрительная активность», хотя обычный
режим на том же IP успешно получает проверенный сеанс. Compose передаёт настройку
из `.env` и сайту, и планировщику; после изменения их необходимо пересоздать.
Браузер работает от пользователя приложения с включённой песочницей.
Отдельный том `wb-storefront-data` хранит `session.json` между пересозданиями
контейнера и рабочие временные профили; каталог `secrets` остаётся доступным только для чтения.
Сеанс создаётся на самом сервере, локальные cookie переносить не нужно.

Цены запрашиваются пачками до 1000 артикулов с паузой в секунду. Значение
по умолчанию 1000 одинаково в приложении и Docker Compose: короткий проход
уменьшает число запросов до истечения служебного сеанса WB. Цена с СПП
берётся из ответа карточки, процент WB Кошелька — из публичных настроек оплаты;
округление цены кошелька осталось прежним. Если свежей цены нет, применяется
существующий расчёт по последней СПП, когда для него есть данные. Отсутствие
цены не заменяется нулём. В отчёте разделены свежие цены и число расчётов по
последней СПП; отсутствие карточек и цены продавца остаётся видимым.

Проверка отдельных артикулов без записи в БД:

```powershell
.\.venv\Scripts\python.exe -m scripts.diagnostics.check_wb_storefront 153985484
```

## Оценка результата обновления кошелька

Отсутствие цены на витрине не считается ошибкой загрузки WB Кошелька, если у
товара нет ТО за последние семь завершённых дней и за сегодня, а остатки
FBS/FBO в БД нулевые. ТО берётся из сохранённой воронки WB как сумма заказов
минус отмены. Артикулы с размерами объединяются по nmID: остаток любого размера
не позволяет исключить товар из ошибок. Остаток ФФ не относится к остаткам WB.

Для исключения нужна история воронки за все семь завершённых дней хотя бы по
товарам магазина и известный остаток в БД или явный ноль `totalQuantity` витрины.
Положительный остаток из свежего ответа витрины отменяет исключение. Пустая или
неполная история не трактуется как подтверждённое отсутствие ТО.

Правило применяется к товарам без цены и к карточкам, не возвращённым в успешном
ответе витрины. Ошибки HTTP, сети и формата ответа для не загруженных пачек не
скрываются. Число исключённых товаров возвращается в
`storefront_ignored_inactive_products`; в тексте ошибки учитываются только
остальные проблемные товары.

Правило исключения меняет только оценку результата загрузки WB Кошелька.
Формулы, сохранение истории и загрузка цены продавца не зависят от него. Старые записи
истории запусков не переоцениваются; правило действует при новых загрузках.
