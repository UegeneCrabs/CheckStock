# Ozon: анализатор, эфемериды и продажи по API

Документ соответствует кандидату от 30 октября 2026 года. Проверки разработчика описаны в [результате задачи](task-results/marketplace-analytics-ozon.md); итоговые независимые проверки выполняются после общей заморозки Ozon и ЯМ.

## Страницы и API

- `/analytics/ozon/analyzer` — анализатор с недельными заказами, текущими показателями, четырьмя днями рекламы и корзин, прогнозом и записями.
- `/analytics/ozon/ephemerides` — сравнение двух недель и недельные комментарии.
- `/analytics/ozon/ephemerides/comments` — история трёх видов комментариев за 12 недель.
- `/analytics/ozon/sales-api` — gross-заказы FBO + FBS, отдельные отмены и дневная детализация; интервал 1–366 дней, начало не ранее 01.01.2000.

Читающие JSON-маршруты имеют префикс `/api/analytics/ozon`: `/analyzer`, `/ephemerides`, `/ephemerides/comments`, `/sales-api`. В этих GET отчётах `week` допускает любую дату внутри выбранной недели и нормализуется к её понедельнику; начало недели не ранее 03.01.2000. `date_from`/`date_to` продаж задают включительный период. История комментариев не загружает экономические источники. Для ключа weekly comment при записи и чтении его ревизий требуется сама дата понедельника; не-понедельник отклоняется с 422.

`GET /api/analytics/ozon/settings/{store}` читает собственные коэффициенты кабинета, `PUT` по тому же URL принимает `{hourly_d_coefficients:[{hour:0,value:null},…,{hour:23,value:null}],revision:0}`. Ровно 24 уникальных целых часа 0–23; значение null или конечное число 0–1000000. Это проекция секции `forecast` существующего Ozon cabinet, с той же атомарной revision: конфликт даёт 409, остальные секции сохраняются. Диалог анализатора и кабинетная форма меняют одну запись, чужие коэффициенты не используются.

Записи используют POST `/analyzer/notes`, PUT `/analyzer/notes/{id}` с `note`/`previous_note` и GET `/analyzer/notes/{id}/revisions`. Weekly PUT `/ephemerides/comments` принимает `store`, полный `article`, понедельник `week`, `kind`, `text`, `version`; GET `/ephemerides/comments/revisions` — тот же ключ без текста и версии. Невалидные DTO дают 422, отсутствующий товар/запись — 404, конфликт сохранения — 409. Production middleware отвечает 401 для JSON и записей без активной сессии, браузерный GET перенаправляет на login; дополнительная проверка active-only внутри Ozon маршрута отвечает 403. JSON отдаёт машинные `field_issues` с точным ключом поля, причиной, датой и временем наблюдения/следующей попытки; русские пояснения выбирает frontend.

## Источники и вычисления

Три страницы используют сохранённые источники Ozon. Открытие страницы и чтение JSON не вызывают Seller API и не создают снимков. Любой активный пользователь видит настроенные магазины. Для записей, ревизий и комментариев дополнительно проверяется точный товар Ozon; совпадающий артикул WB или ЯМ доступа к объекту не создаёт.

Строка принадлежит одному магазину и полному offer_id, включая ` / ` внутри него. Заказы и сегодняшний товарооборот имеют gross-смысл. Отмены показаны отдельно; факт завершённой недели эфемерид net. Известная часть данных сохраняется с покрытием, неизвестное не превращается в ноль. Смена выбранной недели не меняет сегодняшний ТО и текущий ROI.

ДРР = 100 × сумма рекламных расходов / сумма(gross-ТО дня × датированный эффективный выкуп / 100), только по согласованным парам дней. Пример: gross 1000, отмены 200, реклама 80, выкуп 80% дают 10%. Юниточная формула Ozon не меняется. Недельный ROI использует существующий Ozon margin calculation и сохранённые дневные inputs; текущий ROI использует текущую юниточную прибыль и закупку. Итоги процентов используют отношение сумм тех же баз.


Доступные границы продаж включают сохранённые строки заказов и достоверно подтверждённые пустые дни, не позже сегодня. Для нового состояния требуются обе схемы FBO/FBS: listed/ok и finalized для прошлых дней; сегодня допустимо полное текущее перечисление. Старый маркер source=orders используется только при отсутствии нового состояния конкретной схемы. Явное неуспешное или незавершённое историческое состояние не становится нулём из-за старого маркера. Без указанного периода конец выбирается по последнему доступному дню, начало семидневного окна ограничено 01.01.2000. Известные частичные количества и отмены сохраняются; complete=false и причины отличают их от полной загрузки и подтверждённого нуля.

Сток анализатора равен FBO+FBS. FBO20/FBSnull даёт известные20 с stockPartial и quality; FBO20/FBS0 даёт полные20. Дни запаса требуют полного покрытия семи дней предыдущей завершённой календарной недели относительно сегодняшнего дня. Семь известных частичных строк недостаточны. Неполный или нулевой знаменатель оставляет stockDays неизвестным; известный частичный числитель может дать число с признаком неполноты.

Типизированный quality[field] содержит complete, stale, reasons, expected_dates и known_dates. Даты сериализуются ISO; known_dates обозначают пригодные численные значения/пары, а не полноту источника. stale независим от известности и полноты: полное сохранённое покрытие при более поздней ошибке имеет complete=true/stale=true. Исходные coverage, weights и field_issues сохранены. Качество ДРР передаётся отдельно для периода, вчера и обеих недель эфемерид; известная часть рекламных расходов не выдаётся за полную.

Нулевой ДРР соответствует исходной логике WB: при хотя бы одной пригодной согласованной паре и известных суммах0/0 результат0, в том числе с partial/stale. Пустое множество, отсутствующая часть пары и положительный расход при нулевой базе дают null. Для ROI/CTR и других отношений исключение0/0 не применяется. fullArticle определяет идентичность товара, арифметика от него не зависит. Это исправление внутреннего уточнения ТЗ, отдельного выбора человека об иной нулевой политике Ozon не было.
Собственные настройки D находятся в параметрах кабинета Ozon: 24 московских часа, пустое поле не задано, ноль задан явно. Прогноз = сегодняшний gross-ТО × D текущего часа. Без D прогноз, разница и отклонение неизвестны. Коэффициенты WB не используются. Изменение секции использует CAS revision существующих настроек; сохранение целей или расходов не стирает прогноз, а изменение прогноза сохраняет расходы.

Текущий ROI берётся из действующей экономики Ozon с календарными поправками, включая кабинетный `unallocated_percent` от цены продавца. Выбор исторической недели не меняет текущий ROI. Старые настройки без этого поля читаются с0%. В изолированном свежем процессе проверены оба SQL-движка и реальные API: цена100, закупка40, реклама80, gross10 и выкуп80% дают прибыль50/ROI125% при0%; при10% прочих нераспределённых расходов сумма расхода10, прибыль40 и ROI100%. Обновления расходов и прогноза через общий revision сохраняют24 коэффициента, null и явный0.

Корзины Seller API сохраняются за source_day UTC. Дата D означает с 03:00 D до 03:00 D+1 по Москве; подпись интерфейса и CSV — «03:00–03:00 МСК». Заказы и реклама остаются в московских сутках. Сумма не сдвигается на соседний день и не распределяется по часам. В Москве до 03:00 сегодняшняя UTC-корзина ещё не началась. Данные текущего UTC-дня предварительные; исторические наблюдения не объявляются финализированными.

Адаптер `/v1/analytics/data` запрашивает один день, dimension sku и hits_tocart, последовательно по offset/1000. Короткая страница завершает обход, но не доказывает ноль пропущенных SKU. Явный ноль относится к указанному SKU. Нулевой итог товара требует подтверждённого полного набора SKU; неполный набор остаётся неизвестным/частичным. Неизвестный SKU разрешается только в том же магазине через product info; конфликт не публикуется, raw payload сохраняется в состоянии поколения для диагностики.

Промежуточные страницы пишутся в staging; публикация всего дня и complete checkpoint атомарны. Ошибка второй страницы сохраняет предыдущую публикацию. Повтор зафиксированной страницы идемпотентен. Deferred checkpoint возобновляется; поколение старше 72 часов начинается заново. Успешный sparse refresh заменяет текущий набор: отсутствующий ранее известный SKU становится missing_source, а не старым текущим значением.

У корзин общий persisted бюджет 40 попыток в скользящие 24 часа по SHA-256 Client-ID. Методный persisted limiter сохраняет минимум 60 секунд каждой HTTP-попытке даже при смене Api-Key/процесса. Один run — максимум 8 попыток на аккаунт и 10 минут; каждая страница максимум 3 попытки поколения. Суточная квота и доказанный отказ подписки откладывают аккаунт минимум на сутки, неизвестный 403 обозначает access_denied. Работа возвратов и снимка целей не ожидает корзин. Подписка реальных кабинетов не проверяется fixtures и автоматически не покупается.

Недельный stock хранится неизменно на понедельник, с компонентами FBO/FBS/в пути от клиента/ФФ и временем фиксации. Повтор не заменяет снимок, вторник не восстанавливает пропущенный понедельник. Исторические цели копятся ежедневно только на будущее; внутри недели берётся последний снимок, прошлое не заполняется сегодняшними целями. ФФ суммирует все склады точного магазина/площадки/offer_id. Отсутствующий компонент помечает stock partial.

Notes отдельны от weekly comments. Notes разрешены только за сегодняшний московский день, trim/1..4000, сравнение предыдущего текста и revision атомарны. Weekly comments независимы по competitor/decision/next; пустое значение создаёт ревизию. CAS защищает первую конкурентную запись и изменения; decision редактируется только в текущую московскую неделю с повторной проверкой при save. История за 12 недель читает каталог/комментарии без экономического расчёта.

Восстановление после неудачного внедрения — отключение новых routes/jobs с сохранением новых таблиц и пользовательских данных. SQLite и PostgreSQL создают добавочные таблицы через существующий create_all. Никакие ключи или строки WB не мигрируются.

## Хранение и фоновая работа

Новые таблицы: `ozon_analytics_comments`, `ozon_analytics_comment_revisions`, `ozon_analytics_stock_snapshots`, `ozon_analytics_reference_daily`, `ozon_analytics_transit`, `ozon_analytics_source_status`, `ozon_analytics_funnel_daily`, `ozon_analytics_funnel_runs`, `ozon_analytics_funnel_staging`, `ozon_analytics_attempts`, `ozon_analytics_accounts`. Account row сериализует бюджет, очередь и lease; интервалы HTTP остаются в существующем DB-backed limiter. Старый истёкший lease не может менять retry/status нового владельца. Статус попытки корзин привязан к исходному дню; отказ backfill другой даты не помечает свежую публикацию устаревшей.

`ozon_analytics_sources_sync` выполняется каждый час, независимо сохраняет сегодняшние цели, получает возвраты и обходит корзины с ограниченным бюджетом. `ozon_ephemerides_stock_snapshot` запускается по понедельникам в 00:05 МСК; старт в понедельник после этого времени разрешает текущую фиксацию, во вторник backfill не выполняется. Магазины конкурентны, страницы одного аккаунта последовательны, ошибка магазина изолирована.

В ответах `/v1/analytics/stocks` идентификатор склада может быть отрицательным: это подписанный ненулевой integer либо его строгая десятичная строка, нормализуемая в integer для проверки повторов SKU/склад. Положительность SKU и неотрицательность количества остаются обязательными. Снимок публикуется после проверки всех страниц и пакетов; ошибка не заменяет последний успех частичными данными.

Запросы возвратов повторяют временные транспортные ошибки, HTTP 5xx и обычный 429 с учётом `Retry-After` и общего устойчивого ограничителя. Для аналитики остатков применяется существующий предел восьми попыток; для каталога остатков — настройки попыток Ozon. Суточная квота, отказ подписки, права и невалидный источник не повторяются внутри запроса. Загрузчик корзин сохраняет одну HTTP-попытку на единицу собственного бюджета. Итог ошибки магазина содержит reason и HTTP-статус, если он известен; срок `Retry-After` также попадает в статус источника возвратов.

Общие шаблоны и CSS WB переиспользуются через include. Площадочные API, полный ключ товара, preferences, CSV и подписи передаются frontend-конфигурацией. Сохраняются фильтры до итогов/пагинации, сортировка, группы колонок, compact/separate product, drawer и копирование. Анализатор и продажи выгружают все колонки отфильтрованного набора независимо от скрытых дневных колонок; эфемериды — только видимые колонки. CSV содержит BOM UTF-8, разделитель `;`, корректное quoting и защиту строк от формул. Числовые значения сохраняются числовыми, null экспортируется пустым.


Для Ozon CSV сохраняет исходные числовые колонки и добавляет пары «· качество»/«· причины» только к выгружаемым числовым полям с неполным, устаревшим или неизвестным значением. Например, рядом с «ДРР» идут «ДРР · качество» и «ДРР · причины»; известный0 остаётся0, состояние может быть partial|stale, причины — машинные коды. У продаж применяются «Итого заказы · качество»/«Итого заказы · причины», отдельно для отмен и ISO-дней. В эфемеридах такие пары соответствуют видимым числовым колонкам конкретной недели. Тексты, фото, комментарии и корзины дополнительных колонок качества не получают; подписи UTC-корзин сохраняются. Эта возможность задаётся явным qualityExport: для WB исходный CSV сохранён, для Ozon/ЯМ включены поля качества. Проверены реальные скачанные байты всех трёх Ozon CSV; подробности и границы проверки — в результате задачи.
Новые цели и недельные снимки появляются только после начала сбора. Текущая цель эфемерид берётся из текущего справочника даже до первого daily reference; для прошлой недели требуется последний снимок внутри неё. Историческая цена проверяет product_id текущего соответствия, собственные `received_at` и дату снимка; конфликт или неверный день оставляет поле неизвестным.
