# Табло поставок

Страница `/supply-schedule` (совместимый адрес `/stock/arrivals`) показывает грузы из Google Таблицы
«Поставки ВСЕ ПРОЕКТЫ NEW», лист с `gid=582873931`.
Исходная таблица не изменяется. Это отдельный реестр прибытия грузов, без изменения
складских остатков или планов в разделе «Поставки».

## Источник и обновление

Используется существующий ключ `CHECKSTOCK_GOOGLE_SERVICE_ACCOUNT_PATH`; сервисному
аккаунту нужен доступ «Читатель» к таблице. Запросы выполняются с read-only scope.
Настройки передаются также в Docker Compose:

- `CHECKSTOCK_SUPPLY_ARRIVALS_SPREADSHEET_ID` — по умолчанию `16yqGq_tIuhtjgDG55QrF8asiAPIMFNq1zrqOdBEPBoc`.
- `CHECKSTOCK_SUPPLY_ARRIVALS_SHEET_GID` — по умолчанию `582873931`.
- `CHECKSTOCK_SUPPLY_ARRIVALS_SYNC_INTERVAL_SECONDS` — 900 секунд, минимум 300.

Задание `supply_arrivals_sync` входит в обычный планировщик приложения: первый запуск
через 20 секунд после старта, затем каждые 15 минут. Его можно отключить и запустить
в «Интеграции и выгрузки». Общий `CHECKSTOCK_DISABLE_BACKGROUND_SYNC` отключает
автоматические загрузки. Отдельный cron не нужен. Кнопка на странице запускает то же
чтение в фоне; повторный запуск в течение минуты пропускается. Общая блокировка
заданий работает между процессами для SQLite и PostgreSQL.

Однократное заполнение локальной или серверной БД:

```powershell
.\.venv\Scripts\python.exe .\scripts\sync\sync_supply_arrivals.py
```

В работающем Docker Compose:

```sh
docker compose --env-file .env -f deploy/docker-compose.yml exec app python scripts/sync/sync_supply_arrivals.py
```

Новая таблица `supply_arrivals_snapshots` создаётся штатно при старте приложения.
CLI создаёт только эту таблицу, без запуска остальных миграций. Полный ответ Google
не сохраняется: в БД попадают только поля реестра. Снимок привязан к ID таблицы и gid.
Успешная загрузка заменяет его одной транзакцией. Ошибка сохраняет прошлые данные,
дату успешной загрузки и сообщение. Старые данные отмечаются после двух интервалов.
Страница читает снимок из БД раз в минуту, при ручном обновлении — раз в 2 секунды
до завершения задания; эти запросы не обращаются к Google.

## Сопоставление

Лист выбирается по gid, поэтому его переименование допустимо. Заголовок ищется
в первых 20 строках по названиям колонок; порядок колонок можно менять. Обязательны:
«Проект», «Номер заказа», «Группа», «Ссылка на файл заказа», «Категория», «Склад ФФ»,
«Статус поставки», «Факт даты прихода на ФФ» (прежнее имя «Факт даты прихода в МСК» также поддерживается), «Способ», а также «Обьем», «Вес», «Коробки»
с суффиксами «(поставщик)» и «(перевозчик)». «Объём» и «Объем» также распознаются.
Обрабатываются все строки с номером заказа, включая скрытые фильтром Google.

Числа берутся из effectiveValue (запятая и пробелы в текстовых значениях поддерживаются).
Приоритет — перевозчик; пустое значение заменяется данными поставщика. Ноль сохраняется.
Ошибка формулы или некорректное число дают null и замечание к строке. Для дат
поддерживаются серийные числа Google Sheets, ДД.ММ.ГГГГ и ISO. Поле «План прихода»
и неделя прихода берутся из «Факт даты прихода на ФФ». Если фактическая дата
пуста, поставка отображается без даты и недели; плановая дата её не заменяет.
Это календарная дата Москвы; часовой пояс документа её не сдвигает. Ссылки читаются также из hyperlink;
в интерфейс допускаются только HTTP(S).

Все активные пользователи имеют доступ к табло, ручному обновлению и отметкам стока.
Прежняя матрица разделов и магазинов удалена; описание её настроек больше не действует
([текущий контракт учётных записей](authentication.md)). Доступ без активной сессии запрещён.
Сохраняются маршруты `/supply-schedule` и `/stock/arrivals`, включая `/data` и `/sync`.
TRIS → tris, RockKiddo → rockkiddo, Sokoloff → sokoloff, ХОЧУШАР → rimili,
BTH → trusthome, Гоголь и Ракета → gogol. Привязка «Ракета» подтверждена владельцем.
Новые неизвестные проекты видны активным пользователям с замечанием; добавить
псевдоним можно в `app/integrations/supply_arrivals_sheet.py`.

## Интерфейс

- Поиск по заказу, группе, проекту и категории; фильтры проекта, склада, статусов, недель.
- По умолчанию «В пути из китая», текущая и следующая недели. Недели по умолчанию
  сдвигаются вместе с датой. В ручном выборе недели сохраняются как выбраны.
- Доступные недели зависят от статуса; пустой выбор означает все значения.
- Группа — точное непустое значение `Группа.trim()`, с учётом регистра. Две и более
  выбранные поставки объединяются; внутри доступны отдельные файлы и значения.
- Карточка текущей недели учитывает остальные фильтры, но не фильтр недель.
  Объём, вес и короба суммируются по всем выбранным строкам, без двойного счёта групп.
  Пропуски отмечаются, полностью неизвестная сумма отображается как «—».
- Даты и ISO-недели рассчитываются по Москве; прошедший план у груза в пути
  отмечается «ОПАЗДЫВАЕТ». Есть подсветка сегодня/завтра, следующей недели, поздних дат.
- Фильтры сохраняются отдельно для каждого пользователя. Табло использует светлый
  дизайн сайта. Данные поставок и Google-ключ в localStorage не записываются.

## Отметка «Поставлена на сток»

Реализована по ТЗ RBM с уточнением владельца от 20 октября 2026 года: пока без
индивидуальных прав, отмечать и снимать могут все активные пользователи.
Ограничение на четырёх сотрудников из PDF в эту версию не включено.

Последняя колонка после «Способ доставки» содержит чекбокс «Отметить» / «На стоке».
Под активной отметкой отображаются серверное время в формате `ДД.ММ.ГГГГ ЧЧ:ММ`
в `Europe/Moscow` и полное имя пользователя из сессии. При снятии оба поля исчезают;
повторная установка фиксирует новые время и автора. В свёрнутой группе показаны
отдельные отметки каждого заказа; массового изменения группы нет.

Состояние хранится отдельно от снимка Google в `supply_arrival_stock`. Таблица
создаётся штатным `OrmBase.metadata.create_all()` при старте, без изменения прежних
таблиц и пересчёта остатков. Работает для SQLite и PostgreSQL. Обновление реестра
каждые 15 минут, перезапуск приложения и фильтры не удаляют отметки. Другие браузеры
видят их при очередном чтении `/data` (раз в минуту), возвращении на вкладку или перезагрузке.

`supply_id` — SHA-256 от JSON-кортежа `(source_key, project_key, order)`. `source_key`
включает ID Google Таблицы и gid; `project_key` — сопоставленный `store_slug`, а для
неизвестного проекта — его имя в нижнем регистре с нормализованными пробелами.
Номер заказа берётся из проверенного DTO без краевых пробелов. Номер строки,
дата, склад, группа, доставка, объём и статус не входят в ID. Перестановка строк
или изменение этих полей сохраняет отметку.

Проект и номер заказа являются бизнес-идентичностью поставки: их переименование
создаёт другой ID. Номера должны быть уникальны в проекте и не переиспользоваться
для новых поставок; полностью одинаковые проект и номер нельзя автоматически
различить по имеющимся данным источника. При дублях чекбоксы заблокированы, API
отвечает 409. До исправления дублей существующая отметка сохраняется. Записи
исчезнувших из снимка поставок не удаляются; вернуть тот же заказ можно с его отметкой.

### API и атомарность

`GET /supply-schedule/data` сохраняет прежние поля и числовые значения, добавляет
`can_edit_stock`, а каждой строке — `supply_id`, `stock_editable` и `stock`:
`{supply_id, checked, version, marked_at, marked_by}`. Даты передаются в ISO 8601,
представление по Москве выбирает браузер.

`PUT /supply-schedule/{supply_id}/stock` принимает строго
`{"checked": true, "expected_version": 0}`. Автор и дата не принимаются от клиента.
Успех возвращает `stock`; 401 означает отсутствие активной сессии, 404 — отсутствие
поставки в текущем снимке, 409 — конфликт версии или неоднозначный ID, 422 — неверный DTO.
Совместимый PUT доступен также по `/stock/arrivals/{supply_id}/stock`.

Запись выполняется асинхронно через прикладной сервис и инфраструктурный Unit of Work.
SQLite использует `BEGIN IMMEDIATE`, PostgreSQL — блокировку строки снимка `FOR UPDATE`.
Сравнение версии, сохранение состояния и запись `activity_log` фиксируются одной
транзакцией. События `supply_arrival_stock_mark` / `supply_arrival_stock_unmark` содержат
автора, время, идентификатор, проект, номер заказа, прежнее и новое состояния.
Ошибка журнала откатывает отметку. Удаление/переименование сотрудника не меняет
сохранённое имя автора.

Это отметка реестра, а не складское движение: количества не изменяются. Отдельный
`Idempotency-Key` не нужен: запрос задаёт состояние и ожидаемую версию. Повтор со
старой версией получает 409, повтор текущего состояния с актуальной версией ничего
не записывает и не обновляет автора/время. Одновременные запросы не перезаписывают
изменения незаметно. Интерфейс сохраняет прежнюю галочку до ответа, блокирует повторное
нажатие на время записи и показывает ошибку, если успех не подтверждён; затем
перечитывает данные. Старый ответ фонового чтения не заменяет состояние с новой версией.

### Локальная проверка

Временные проверки на SQLite охватывают установку/снятие/повторную установку,
смену автора, журнал и его отказ, конкурирующие соединения, неверные DTO, активность
сессии, дубли и отсутствие поставки, обновление снимка штатным импортом и повторное
чтение из нового соединения. При подготовке выпуска 21 октября 2026
на временных SQLite и PostgreSQL 17 проверены HTTP-контракт, конкуренция
соединений, конфликт версии, откат при ошибке журнала и сохранение отметки
после обновления снимка. Рабочие базы не использовались.
В браузере проверены оба состояния, подпись по Москве, перезагрузка, поиск,
независимость отметок в группе и HTTP 500 без ложного подтверждения. Ruff,
проверка синтаксиса JavaScript и mypy проходят. Временный стенд и сценарии удалены.
