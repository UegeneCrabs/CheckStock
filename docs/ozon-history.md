# Динамика Ozon за 14 дней

Карточка товара использует общий график WB/ЯМ с переключателями рядов,
подсказками и сравнением заказов с предыдущей неделей. Видимы 14 московских
дней, включая сегодня. Сервер возвращает 21 день: дополнительные 7 нужны для
сравнения каждой даты с датой на неделю раньше. Период таблицы не меняет это
окно. Сегодняшние показатели предварительные.

`GET /api/unit-economics-1c/ozon/history?store=trusthome&article=140729397`
проверяет активную сессию, preview экономики и доступ к кабинету. Чужой кабинет
даёт 403, отсутствующий товар — 404, неполный запрос — 422. Ответ `OzonHistory`
содержит `today`, видимые `period_from`/`period_to` и 21 элемент `days`.
В каждом элементе есть дата, числовые значения либо `null`, а также
`partial_fields` и `stale_fields`. Подписи дат и пояснения формирует frontend.

| Ряд | Источник и правила |
| --- | --- |
| Заказы | `sales_order_lines`: сумма `quantity - cancelled_quantity` по исходному дню заказа, FBO + FBS. Известные строки неполного дня показываются с пометкой. Без строк ноль допустим только при подтверждении загрузки дня; иначе `null`. |
| Реклама | Сохранённые окна `ozon_advertising_source_windows`, общий нормализатор `source_days` / `spend_summary`. Сумма известных распределённых на товар расходов всех типов. Корректировки без привязки к товару не распределяются графиком. Неполнота и устаревание сохраняются. |
| ДРР с выкупом | Существующий `app/ozon/drr.py::metrics` отдельно за каждый день: расходы / ТО после отмен × фактическая доля выкупа дня × 100. Даты заказов и рекламы совпадают, неподтверждённые источники блокируют расчёт. Текущая настройка выкупа кабинета не подставляется в прошлые даты. |
| Остатки | `marketplace_stock_daily_history` (FBO + FBS) и `fulfillment_stock_daily_history`. Сумма известных составляющих, при отсутствии одной — пометка неполноты. Текущие остатки не переносятся в прошлые дни. |
| Цена с СПП | Последнее сохранённое `black_price` соответствующего дня из `ozon_prices_daily`, по кабинету, текущему product ID и артикулу. Время получения должно относиться к той же московской дате; конфликтная цена неизвестна. Исторические пробелы сегодняшней ценой не заполняются. |
| Прибыль | Пока `null` в API графика: [дневной расчёт маржи](ozon-margin.md) подключён в таблицу и калькулятор. Переключатель графика недоступен, рядом указана причина. |

Ноль и отсутствие данных различаются, в том числе в полоске заказов под
графиком. Линии Ozon разрываются на пропусках всех рядов. Доступны только ряды,
где есть значения в видимых 14 днях. Подсказки показывают неполноту и
неподтверждённые обновления. Сравнение доступно, если есть хотя бы одна пара
известных значений заказов. Высота столбиков заказов масштабирована ×10,
подсказки и подписи сохраняют фактическое количество.

История загружается отдельно при открытии карточки, только из БД, без вызова
API Ozon и без записи снимков. При смене товара или закрытии запрос отменяется,
поздний ответ не заменяет график другого товара. Перерисовка той же карточки
сохраняет загруженные ряды; после ошибки есть кнопка повтора. Повторное открытие
карточки заново читает актуальную историю.

## Модули и проверка

- DTO: `app/dto/ozon_history.py`.
- Сценарий: `app/application/ozon_history.py`, порт `OzonHistoryReader`.
- Асинхронное чтение: `app/infrastructure/ozon_history_repository.py`.
- Нормализация: `app/ozon/history_normalizer.py`; существующие нормализаторы ТО и рекламы.
- Frontend: `static/economics/ozon/history.js` и общий график `static/economics/shared/dashboard.js`.

Проверены временные сценарии: пропуски и подтверждённые нули, отмены,
отрицательные рекламные корректировки, ошибки источников, московская дата цены,
изоляция магазинов и площадок, доступ к HTTP, отсутствие записей при GET,
21-дневное окно, отмена запросов и повтор. SQL-запросы выполнялись на временной
SQLite и компилировались диалектом PostgreSQL; живой PostgreSQL не проверялся.
Проверены общий график WB/ЯМ, разрывы линий и переключатели Ozon.
