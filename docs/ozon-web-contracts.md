# Интерфейс Ozon и общие страницы

Поле «Новинка» с 20 октября использует историю заказов и положительных остатков
с порогом 21 день; список и карточка возвращают `newness`, `is_new`, `sales_days`.
[Источники и ограничения возраста](ozon-newness.md).

Статус на 23 октября 2026 года: подключены клиентские страницы экономики Ozon,
склада и интеграций, общий контекст и статические шаблоны. Чтение данных,
настройки Google и управление ключами используют типизированные JSON-контракты.
Складские операции и XLSX сохраняют существующие прикладные сценарии.

В `product.price` передаются четыре типизированных объекта цен с состоянием и временем получения. Калькулятор форматирует их на frontend; GET читает только БД. [Поля цен, источники и дневная история](ozon-prices.md).

Страница отдаёт статическую оболочку из `templates/layout/client-page.html`.
`static/common/client-page.js` получает контекст пользователя и данные страницы,
строит интерфейс и подключает обработчики. Python не собирает таблицу и
калькулятор этой страницы. Общая страница интеграций использует ту же оболочку.
Правила слоя — в [скилле проекта](../.agents/skills/checkstock-task-guide/SKILL.md).

Страница экономики Ozon задаёт `alertMarketplace: 'OZON'`. Общий клиентский рендерер отбирает уведомления `UiContext.alerts` по точному совпадению `marketplace` до построения баннера, его индикаторов и переключения сообщений. Ошибки загрузок, доступа и ключей других площадок на этой странице не показываются. При пустом результате баннер отсутствует. Исходный контекст не изменяется; страницы без `alertMarketplace` сохраняют общий список. Ошибки данных товаров Ozon из `data_issues` отображаются независимо от баннера.

После получения контекста пользователя страница Ozon строит панель управления и шапку таблицы с пустым списком товаров и `productsLoaded: false`. Общий загрузчик таблицы получает товары отдельно: при ожидании показывает индикатор, после ответа — строки или пустое состояние, при ошибке — стандартное сообщение с повторной попыткой. Подготовка страницы не ждёт API товаров.

Необязательный параметр frontend-конфигурации `initialProductsUrl` сохраняет исходные `period_days`, `date_from` и `date_to` в первом запросе и повторных попытках до успешной загрузки. Неизвестные даты до ответа остаются пустыми, управление периодом недоступно. После успеха период, границы дат и последующие запросы используют значения ответа сервера. Ошибочные даты проверяет backend; новый HTTP-контракт не требуется. Страницы без этого параметра сохраняют прежнее формирование запросов.

Отдельная панель рекламы по магазинам не выводится. `advertising_unallocated` остаётся в JSON-контракте для совместимости; нераспределённые расходы и корректировки магазина не включаются в сумму товара. Ошибки Ozon показываются общим баннером и пометками товаров, частичные показатели сохраняют подсказки полноты.

Ограничение подписки метода отзывов Ozon (`not available with existing subscription`)
не выводится в ошибках товара и общем баннере для всех магазинов. История задачи
отзывов сохраняет причину отказа и код `ozon_review_subscription_required`.
Сохранённые оценки и отзывы остаются доступными, отсутствующие значения остаются
неизвестными. Остальные ошибки отзывов, включая обычный отказ в доступе 403,
продолжают отображаться; отсутствие данных без подтверждённого ограничения
подписки по-прежнему считается неполнотой.

Подключены экономика Ozon, цены, комиссии, оборот, выкуп, реклама, логистика,
хранение, маржа, история и расчёт запаса по заказам FBO/FBS. Запуск, настройки,
история и состояния асинхронных задач Ozon проходят через `IntegrationViews`.
WB и Яндекс сохраняют существующие загрузчики и обработчики задач.
Клиентские складские страницы получают данные через `stock_read.py` и
`inbound_supplies.py`; серверная проверка сессии и доступных магазинов сохраняется.

Фрагменты интеграций находятся в `templates/integrations/client/render.html`.
Они загружаются общим API шаблонов и используются через `ui.render`.
Настройки кабинетов Ozon подгружаются только при доступном preview экономики.

На страницах раздела «Сток» общий баннер предупреждений временно отключён:
`static/stock/page-render.js` задаёт `showAlerts: false` для всех своих маршрутов.
Общий клиентский рендерер в этом случае не создаёт баннер. Остальные страницы
сохраняют прежнее отображение; данные `UiContext.alerts`, состояния загрузок
и фоновые задачи не изменяются.

Меню «Отчёты» в клиентской шапке `templates/layout/client-header.html` и обычной
шапке `templates/layout/header.html` содержит одинаковые восемь ссылок: четыре
отчёта WB (юниточная прибыль, целевая цена, расходы без ИУ, СПП), два отчёта ЯМ
и два отчёта Ozon (юниточная прибыль и целевая цена). При добавлении отчёта обновляются оба шаблона,
чтобы ссылки сохранялись на складе, в интеграциях и экономике Ozon.
Пункты отчётов Ozon используют голубой фон и тёмный текст в обеих шапках;
при наведении и для активного пункта фон становится светлее.

DTO находятся в `app/dto/{integrations,ui,ozon_economics}.py`. В общем ответе
состояний новые DTO Ozon соседствуют с прежними состояниями остальных задач;
контракты истории, запуска и настроек в таблице относятся к задачам из `app/jobs/ozon.py`.
`ozon_reputation_sync` временно удалена из каталога и расписания. Общие API
каталога и состояний её не возвращают, а запросы запуска, настроек и истории
по этому имени возвращают `404`. История запусков и сохранённые рейтинги
остаются в БД. Карточки Ozon используют сохранённые значения без предупреждений
об отсутствии отзывов или ошибках отключённой загрузки.
Старый `?data=1` страницы Ozon направляется в тот же обработчик JSON.
Период выбирается через `period_days` либо пару `date_from`/`date_to`: до 366
завершённых дней, начало не позже конца. Магазин проверяется по доступам;
`article` требует явного `store`. Ошибочные параметры возвращают `422`, чужой
магазин — `403`, отсутствующий товар — `404`.

Backend сохраняет числовые значения, ISO-даты, признаки отсутствующих данных
и смысловые коды. В экономике это `data_issues` и `stock.inbound_state`.
Тексты, валютные обозначения, даты для показа, цвета и доступность кнопок
определяются в `static/economics/ozon`, `static/integrations` и
`static/stock/page-render.js`. Данные вставляются с экранированием.
Метаданные задач берутся из `JOBS`; `JOB_SCHEDULE_RULES` и текущие настройки
преобразуются в `JobScheduleView`, который frontend форматирует самостоятельно.

Маршруты контекста и экономики не возвращают ключи. `CredentialUpdate` проверяет запись ключей, а
`IntegrationRoute` исключает секретные входные значения из ошибок валидации.
Новые ошибки Ozon передают смысловой код в `detail`; диагностические сообщения
загрузчиков могут оставаться данными истории. Доступ проверяется сервером:
сессия, активность учётной записи, допустимые цели и флаг preview экономики.

## Чтение и запись БД

Репозитории новых JSON-маршрутов используют общую `AsyncDatabase` из ресурсов
веб-приложения. Драйверы — `asyncpg` и `aiosqlite`. Настройки задач, история,
аудит и снимки поставок экономики Ozon используют
асинхронные SQLAlchemy-запросы.

Для существующих складских и экономических расчётов `AsyncReadModels`
сохраняет старые SQL-запросы и формулы, но выполняет их внутри
`AsyncConnection.run_sync`. Это адаптация через greenlet: SQL ожидает
асинхронный драйвер; синхронное соединение и пул потоков не создаются.
`read_context` подменяет соединение только в пределах текущего чтения и
сбрасывается при ошибке. SQLAlchemy-транзакция принадлежит внешнему вызову.
Запись запрещена в адаптере и на уровне транзакции PostgreSQL либо
`PRAGMA query_only` SQLite. Асинхронные снимки поставок передаются в расчёт
Ozon явно, без вложенного синхронного ORM-запроса.

Общая Google-выгрузка, складские перемещения, классификация отгрузки и XLSX
сохраняют существующие прикладные сценарии и маршруты.

Перенос интерфейса не переписывает общую выгрузку остатков и заказов в Google, синхронизатор
поставок, остальные старые фоновые загрузчики и синхронные XLSX-экспорты.
Они пока исполняются прежними обработчиками. Синхронная работа с локальными
файлами ключей также сохраняет блокировки файлов. Асинхронная загрузка
заказов Ozon описана отдельно в [контракте планировщика](background-jobs.md).

Недельная Google-выгрузка использует отдельный асинхронный JSON-контракт
`/api/admin/google-weeks` для трёх площадок. Сервер возвращает настройки, времена,
коды ошибок и структурированные отчёты; карточки и сообщения строит
`static/integrations/google-week-update.js`. Сохранение WB совместимо с прежними
таблицами состояния через однократный перенос в профиль WB. Общая выгрузка
«Все проекты на каждой площадке» сохраняет прежний сценарий записи в Google;
его настройки читаются и сохраняются через новый JSON API.
[Недельный контракт](google-week-update.md).

## Проверка изменений

Проверять пустые и заполненные данные, отсутствие ключей, неполные данные
экономики, недоступную сессию и preview, ошибочные периоды и цели, отсутствие
секретов в успешных ответах и ошибках валидации. Для задач — настройки целей,
прерванный запуск, `202`, повторный `409`, завершение и историю. Для склада —
фильтры, TOTAL, детали, классификацию отгрузки и XLSX. В браузере проверять
экранирование названий товаров и отсутствие ошибок JavaScript.

Чтение проверяется на SQLite и PostgreSQL; отдельно — конкурентные обращения
к разным БД, сброс контекста после исключения, запрет записи через модель чтения
и совместимость блокировок. Использовать временную БД и подменённые загрузчики;
проверка кнопок не должна отправлять фиктивные данные во внешние сервисы.

## Частичные показатели Ozon

`product.logistics` содержит последний успешный дневной снимок FBO за 30 полных дней до вчера включительно, признаки устаревания и ошибки. Подробный калькулятор показывает исходные расходы, количества и отдельную оценку по формуле; редактирование локальное. Неизвестный расход остаётся `null`. POST дополнен необязательным `volume: LogisticsVolumeScenario`: объём, цена и кластеры для оценки перевозок. Ответ содержит смысловое состояние `volume` и рассчитанные составляющие `inputs`; неизвестный или недействующий тариф не подменяется фактической суммой. [Источники, формулы и ограничения](ozon-logistics.md).

`product.cabinet` содержит эффективные цели ДРР/ROI, расходы кабинета и отдельный
выкуп за настраиваемый период. `product.calculator.buyout` передаёт те же эффективные данные с возвратами, периодом и источником подстановки; `calculator.buyout_percent` и ДРР CPC/CPO используют этот процент. `GET/PUT /api/unit-economics-1c/ozon/cabinets`
обслуживает три формы Ozon в параметрах кабинетов; PUT адресуется `/{store}`.
`GET /api/unit-economics-1c/ozon/cabinets/{store}` возвращает актуальные настройки
одного доступного кабинета для обновления эквайринга, НДС и УСН в калькуляторе.
Сохраняется один раздел с проверкой `revision`; устаревшая версия возвращает 409.
[Поля, права, состояния и ограничения](ozon-cabinet-settings.md).

CTR и CPC читаются из дневных фактов кампаний «Оплата за клик». В `advertising` добавлены `click_spend` и `traffic_coverage`; существующие `ctr`, `cpc`, `impressions`, `clicks` относятся к известным дням выбранного периода. Общие расходы сохраняют отдельное покрытие. Значение при нулевом знаменателе — `null`, неполные и устаревшие показатели сопровождаются пометкой. [Загрузка и формулы](ozon-performance-api.md#ctr-и-cpc-за-выбранный-период).

Карточка товара Ozon располагается ниже фиксированной навигации: верхний отступ равен `--app-header-height`, высота занимает оставшуюся часть окна. Используется общая адаптивная высота шапки; заголовок и кнопка закрытия остаются доступны, содержимое карточки прокручивается внутри неё.

GET экономики использует `AsyncTurnoverRepository` и пересекающиеся сохранённые окна рекламы за запрошенные даты. Существующие поля сумм и URL сохраняются; в покрытие ТО добавлены `partial_dates` и `stale`, в `advertising.spend_summary` — `missing_dates` и `partial_dates`. Периоды корректировок магазина передаются в `advertising_unallocated[].adjustments`. Отсутствующие значения остаются `null`, известная часть сопровождается данными полноты. Подробности: [полнота экономики](f05-economics-completeness.md#то-и-рекламные-расходы-ozon).

Четыре цены оформлены редактируемыми полями калькулятора: `black_price` — «Цена с СПП», `green_price` — «Цена с Кошельком», `base_price` — «Цена поставщика», `seller_price` — «Цена с учетом акции». `old_price` исключено из JSON-ответа и новых сохранений. Редактирование локальное, запросов записи в Ozon не создаёт; сброс и завершение работы с карточкой возвращают значения БД. `advertising.drr` и `drr_coverage` рассчитываются по совпадающим доступным дням заказов и рекламы; неизвестный ДРР остаётся `null`. Маржа подключена в текущую экономику, сумму за диапазон и локальный калькулятор: [формула, дневные параметры и полнота](ozon-margin.md). [График истории Ozon](ozon-history.md) принимает `days=7|14|30` через `GET /api/unit-economics-1c/ozon/history` и показывает выбранное окно со сравнением с прошлой неделей; ответ содержит ещё 7 дней для сравнения, по умолчанию выбрано 14; неизвестные значения не заменяются нулями.


Редактирование выкупа, ТО, рекламы, расходов и налогов, связи с ценами и общий сброс описаны в [контракте калькулятора Ozon](ozon-calculator.md). Правки сценария не изменяют настройки кабинета или исходные выгрузки.

## Хранение Ozon

Товар в `GET /api/unit-economics-1c/ozon` дополнен `storage: StorageData` (`snapshot`, `stale`, `error`, `attempted_at`). Снимок содержит `expenses`, `sold_units`, `returned_units`, `retained_units`, `per_unit`, период, время, состояние и дневную разбивку. GET читает только БД. Калькулятор подставляет `per_unit`, допускает локальную правку и показывает формулу при наведении. [Полный контракт хранения](ozon-storage.md).

`current_economics.calculation` содержит слагаемые, прибыль дня, ожидаемые выкупы, `missing` и `issues`. `economics_7d.daily` содержит расчёты каждой даты; `margin_coverage`/`roi_coverage` описывают включённые дни. `calculator` дополнен `orders_count` до отмен и `other_spend`; ответ калькулятора — `advertising_amount` и `result` с маржой, ROI и отсутствующими полями.
