# Финансовый отчёт Яндекс Маркета

Локальная реализация [технического задания](yandex-finance-spec.md). Страница — `/finance-reports/yandex`, версия расчёта — `yandex-finance-1`. Автоматическое обновление по умолчанию выключено. Закрытый месяц нужно сверить с конкретным кабинетом до включения расписания: синтетические тесты не подтверждают соответствие всем вариантам реальных архивов Маркета.

## Пользовательский сценарий

Пользователь выбирает один доступный магазин или все доступные магазины и период от 1 до 366 дней включительно. По умолчанию выбраны семь завершённых дней по Москве. Будущие даты запрещены; текущий месяц предварительный. Страница читает опубликованные локальные данные даже при недоступном API Маркета.

На странице есть итоговые карточки, полный состав показателей, таблица по дням и состояние каждого источника по магазину и кабинету. Нажатие на денежную сумму или количество открывает операции с фильтрами по типу и статье и постраничным просмотром. Детали содержат вклад операции, заказ, артикул, кабинет, кампанию, источник, время загрузки, происхождение закупочной цены и причины отсутствующих данных.

Полная сумма отсутствует, если не хватает обязательного источника, цены или классификации. API возвращает `value: null`, `known_value` и `reasons`; интерфейс показывает прочерк и известную часть. Подтверждённый ноль остаётся нулём. Признак неполноты независим от ошибки последнего обновления: старый полный снимок после неудачной загрузки остаётся полным, но помечается устаревшим.

Сводка и все её дни вычисляются из одних идентификаторов снимков. Запрос деталей передаёт `version`; изменение версии даёт HTTP 409 с предложением обновить сводку. При смене фильтра старые запросы отменяются, а их запоздавшие ответы игнорируются. Ошибка не оставляет прежние цифры под новым периодом.

## Показатели и источники

Все суммы в рублях. Денежные поля читаются как `Decimal`. Каждый денежный вклад операции округляется до копеек `ROUND_HALF_UP` перед суммированием. Поэтому сумма отображённых дней и деталей равна итогу периода. Количество возвратного дня может быть отрицательным. Проценты считаются из общих числителя и знаменателя.

| Показатель | Правило |
| --- | --- |
| Оборот созданных заказов | Сумма `prices.payment`, `subsidy`, `cashback` строк BusinessOrders по дате создания. Это суммы всех единиц строки; повторно умножать на количество нельзя. Отмены не превращают этот показатель в реализацию. |
| Реализовано / возвращено / количество нетто | Количества финансового отчёта реализации; нетто = реализовано − возвращено. |
| Оборот селлера нетто | Стоимость реализации с компенсациями из goods-realization минус соответствующая стоимость возвратов. |
| Оборот покупателя нетто | Однозначная `billingPrice` из united-orders × количество реализации / возврата. Связь по кабинету, кампании, заказу и SKU, без равенства дат платежа и доставки. |
| Расходы | Фактические денежные начисления услуг с исходным знаком; отрицательное сторно уменьшает расход. Проценты и тарифы не суммируются. |
| Прочие начисления | Отдельный вид финансового события. Неизвестный источник взаиморасчётов блокирует полный итог, а не превращается в ноль или выручку. Граница текущего маппинга описана ниже. |
| Результат по начислениям | Оборот селлера нетто − расходы + прочие начисления. |
| Закупка нетто | Закупочная стоимость реализации − восстановленная закупка возвратов. |
| Маржинальная прибыль | Результат по начислениям − закупка нетто, до налогов и внешних расходов. |
| Маржинальность | Прибыль / оборот покупателя нетто × 100, только при полных данных и положительном знаменателе. |
| Выплаты | Оплаченные транзакции united-netting по дате платёжного поручения. Это данные Маркета, а не подтверждение банка. |

Маппинг закреплён в `app/yandex/finance_mapping.py`:

- Реализация: `delivered` / `returned`, `yourSku`, `deliveredCount` / `returnedCount`, `deliveryDate` / `returnWarehouseOrScAcceptDate`, `deliveredPriceSumWithVatAndDiscounts` / `returnPriceSumWithVatAndDiscounts`. `shopSku` этого отчёта не используется как артикул продавца. Невыкуп и логистические статусы не создают повторный финансовый возврат.
- Услуги: таблица `SERVICE_FIELDS` выбирает конкретную денежную колонку и дату каждого листа. В частности, комиссия — `totalAmount`, большинство услуг — `servicePrice`, новое хранение — `paidStorage`. Неизвестный непустой лист создаёт признак качества и неизвестную операцию. Неоднозначный положительный «возврат/сторно» не меняет знак по догадке.
- Платежи: `transaction_date`, `transactionId`, `transactionSum`, `paymentStatus`, `bankOrderDate`. Повтор ID в одном снимке удаляется только при одинаковой сигнатуре; конфликт завершает загрузку ошибкой. `bankSum` не складывается по товарным строкам. Факты включаются только в месяц даты поручения, даже если попали в два исходных отчёта. Неизвестный тип/статус и положительное удержание требуют сверки, не дают подтверждённого полного итога.

Поля проверялись 7 октября 2026 года по официальным описаниям: [реализация](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateGoodsRealizationReport), [услуги](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateUnitedMarketplaceServicesReport), [заказы и товары](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateUnitedOrdersReport), [платежи](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateUnitedNettingReport), [BusinessOrders](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/getBusinessOrders). Смена схемы требует новой проверки адаптера, а не добавления произвольных числовых колонок в сумму.

### Что требует проверки на пилоте

Сейчас подтверждённые названия платежей покупателя и компенсаций скидок/бонусов распознаются как уже учтённые в реализации. Они не создают второй доход. Для иных источников взаиморасчётов нет универсальной автоматической классификации: нормализованная операция начисления остаётся с неизвестной суммой, причины видны в деталях, полный итог прибыли блокируется. Перед поддержкой конкретной компенсации необходимы образец строки, дата признания, знак и доказательство отсутствия двойного учёта с реализацией/услугами.

Если операционный отчёт не содержит однозначную цену старого возвращённого заказа, оборот покупателя неполный. Если продажа принадлежала предыдущей привязке кампании к другому магазину, её закупочная цена не переносится в новый магазин автоматически: такой возврат требует отдельной сверки. Общие расходы без кампании не распределяются произвольно. Эти ограничения отображаются как отсутствие полного итога и не скрываются под подтверждённым нулём.

## Доступ и подключения

Отдельное право `FINANCE_YANDEX` по умолчанию есть только у суперадминистратора. Его можно выдать на чтение через управление пользователями. Все читающие endpoints проверяют это право, доступ к Яндекс Маркету и магазинам. Пользователь с ограничением по товарам менеджера не получает итог целого магазина. Пустая область не выполняет запрос ко всем магазинам. Ответы, включая отказы, имеют `Cache-Control: private, no-store`.

Настройка, ключи, цены, нераспределённые операции и запуски доступны только суперадминистратору. Подключение содержит магазин, Business ID, непустой список Campaign ID и исторический интервал. Один магазин может содержать несколько кабинетов. Пересекающиеся интервалы одной кампании одного кабинета запрещены, в том числе у отключённых подключений.

Кнопка поиска кабинетов читает метаданные по ключу; она не подтверждает права на финансовые отчёты. Кнопка проверки финансового доступа запускает задание на четыре источника за предыдущий закрытый месяц, без публикации фактов. Реальная загрузка также проверяет доступ каждым вызовом.

Новые ключи хранятся в отдельных UUID-файлах каталога `yandex-finance` рядом с настроенным файлом токенов ЯМ. В таблицах и HTTP-ответах ключей нет. При отсутствии отдельного ключа адаптер читает старый ключ магазина через существующий `tokens.get_api_key`; старый конфиг не переписывается. Business ID и кампании выбираются явно, даже если старый конфиг содержал только ключ. Замена ключа не меняет выбор кампаний.

Отключение закрывает интервал и исключает подключение из расписания. Оно не удаляет историю. Дата не может отрезать уже записанные операции. Ручная повторная загрузка и пересчёт старого интервала остаются возможны. Перенос кампании выполняется новым непересекающимся интервалом.

## Хранилище и задания

Новые таблицы имеют префикс `finance_yandex_`: `connections`, `snapshots`, `heads`, `operations`, `attempts`, `report_tickets`, `costs`, `unallocated`. Схема добавляется штатным `create_all` при инициализации приложения; существующие таблицы не изменяются. SQLAlchemy использует ту же настроенную БД, но отдельные таблицы. Загрузчик не пишет в `sales_order_lines` и не меняет ключи общих продаж.

Единица публикации — календарный месяц подключения и группа источников. Реализация вместе с услугами публикуется одной транзакцией после полной загрузки обоих источников. Заказы и платежи имеют независимое покрытие. Сначала создаются неизменяемые снимки и операции, затем в той же транзакции переключаются `heads` и успешные отметки покрытия. Ошибка вставки откатывает всё. Ошибка одного кабинета не отменяет завершённый другой кабинет.

Ключи строк месячных архивов используют кампанию/лист/порядковый номер. Кратность одинаковых строк сохраняется; повторная загрузка заменяет активную версию месяца и не добавляет вторую продажу. История версий остаётся. Снимок сохраняет исходный JSON, ID отчётов, время, автора и версию расчёта. Публикация с более коротким покрытием уже загруженного месяца запрещена. Факты вне исторического интервала подключения исключаются до расчёта закупки.

Нераспределённые расходы сохраняются один раз на кабинет, источник и месяц; суммы не выдаются через доступ к отдельному магазину и не умножаются на кампании. Суперадминистратор видит их отдельно. Архивы исходных снимков сохраняют доказательства прежних версий.

Ручные import/retry/recalculate возвращают HTTP 202 и `run_id`, работают через существующую очередь и журнал `sync_job_runs`. Ручной и фоновый запуск используют одну межпроцессную блокировку `yandex_finance_sync`; второй запуск получает 409. Генерация отчётов использует существующие бизнес-блокировки `yandex-reports:{business}` и таблицу квот. Сохранённый report ID позволяет продолжить опрос после таймаута. Повтор загрузки обрабатывает выбранные месяцы заново, возобновляя незавершённые отчёты; успешно опубликованные месяцы остаются идемпотентными.

Расписание — 05:00 МСК, последние 90 завершённых дней с расширением до календарных месяцев. Публикация текущего месяца обрезается вчерашним днём; ручной запрос до сегодняшнего дня может включить его как предварительный. При включённой настройке сверки первое число месяца дополнительно захватывает старые закрытые месяцы. Глобальное отключение фоновых задач имеет приоритет.

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `CHECKSTOCK_YANDEX_FINANCE_ENABLED` | `0` | Разрешение автоматического финансового задания. |
| `CHECKSTOCK_YANDEX_FINANCE_RAW_RETENTION_DAYS` | `365` | Срок хранения исходного JSON устаревших версий, минимум 90 дней. |
| `CHECKSTOCK_YANDEX_FINANCE_RECONCILE_MONTHS` | `0` | Дополнительная глубина сверки на первое число месяца, 0–12. |

Очистка удаляет только старый raw у вытесненных снимков и старые билеты генерации. Нормализованные факты, аудит и raw всех текущих опубликованных версий сохраняются. Поэтому последняя версия воспроизводима. Чтение не запускает загрузку или очистку.

## Себестоимость

Импорт исходных значений `YM` остаётся без изменений. Финансовое задание архивирует наблюдения закупочной цены из существующего хранилища с датой `synced_at` по Москве. Текущая выгрузка не доказывает цену в прошлом и не распространяется задним числом.

Ручная цена имеет артикул, период, автора, время и обязательное основание. Она приоритетнее наблюдения `YM`; среди действующих ручных цен выбирается запись с более поздним началом периода, затем более поздним ID. Ручные записи не удаляются, если товар пропал из выгрузки. Явный ноль допустим; отсутствующая цена неизвестна.

При обычной загрузке сохраняется уже установленная закупка исходной продажи. Возврат восстанавливает её цену за единицу при однозначной связи с продажей. Изменение цены требует отдельного пересчёта. Для корректировки продажи и её более поздних возвратов пересчитывайте период начиная с месяца продажи и заканчивая месяцем возврата. Пересчёт читает сохранённые исходники и не обращается к API.

## HTTP API

Общий читающий префикс — `/api/finance-reports/yandex`. Параметры: `store` (пусто — все доступные), `date_from`, `date_to` в ISO-формате.

| Метод и путь | Назначение |
| --- | --- |
| `GET /` или `/summary` | Сводка, дни, версия и состояния источников. |
| `GET /filters` | Только доступные магазины, период по умолчанию и текущая дата МСК. |
| `GET /status` | Версия и состояния источников. |
| `GET /details` | Обязательные `version`, `metric`; необязательные `day`, `kind`, `category`, `page`, `page_size` (1–100). |

Административный префикс — `/api/admin/integrations/yandex-finance`:

| Метод и путь | Назначение |
| --- | --- |
| `GET/POST /connections` | Список / добавление подключения. |
| `PUT /connections/{id}/key` | Смена отдельного ключа с сохранением области. |
| `POST /connections/{id}/disable` | Завершение интервала (`effective_to`). |
| `POST /connections/{id}/check` | Фоновая проверка финансовых источников, 202 + `run_id`. |
| `POST /discover` | Доступные кабинеты и кампании ключа. |
| `GET/POST /runs` | Последние 30 заданий / запуск import, retry, recalculate. |
| `GET/POST /costs` | История цен магазина / новая ручная цена. |
| `GET /unallocated` | До 1 000 последних нераспределённых операций кабинетов, только суперадминистратор. |

## Локальная проверка и пилот

Синтетический пример — `tests/fixtures/yandex_finance/month.json`. Три продажи по 1 000, возврат одной единицы, цена покупателя 900, закупка 400, комиссия 150, платёжная услуга +100/−100, реклама 80. Ожидается: оборот селлера 2 000, покупателя 1 800, закупка 800, расходы 230, прибыль 970, выплата 1 600. Выплата не подгоняется под результат начислений.

```shell
python -m unittest discover -s tests -p "test_yandex_finance*.py" -v
node --test tests/test_yandex_finance_ui.cjs
python -m scripts.diagnostics.reconcile_yandex_finance tests/fixtures/yandex_finance/month.json --output work/finance-reconciliation.json
python tests/preview_yandex_finance.py
```

Последняя команда запускает изолированное демо на `http://127.0.0.1:8875/finance-reports/yandex`. Выберите RIMILI, 1–31 августа 2026. TRIS в том же месяце содержит искусственно большую сумму для проверки вёрстки; остальные магазины показывают отсутствие источников. Демо использует SQLite в памяти, синтетические данные, запрещает изменяющие HTTP-запросы и не запускает жизненный цикл основного приложения. Остановить — Ctrl+C.

Команда сверки тоже использует БД в памяти и не обращается к API или рабочей БД. В bundle находятся `connection`, `period`, датированные `costs`, `expected` и четыре словаря исходников. Реальные обезличенные архивы преобразуются в эту же структуру. Код выхода 1 означает расхождение или неполноту; файл результата содержит дни и причины. Для возврата из другого месяца однократный bundle может не содержать исходную продажу: используйте полную историю в приложении, а не подставляйте сегодняшнюю закупочную цену.

Для транзакционных тестов PostgreSQL задайте **отдельный тестовый** `CHECKSTOCK_TEST_POSTGRES_URL` и запустите `test_yandex_finance_postgresql.py`. Тесты создают и удаляют только уникальные схемы `finance_test_*`; URL приложения не используется. Без этого параметра проверки явно пропускаются. Генерация DDL для PostgreSQL проверяется и без сервера, но не заменяет проверку транзакций.

Порядок пилота:

1. Выбрать магазин, кабинет, конкретные кампании и закрытый месяц с возвратами. Зафиксировать модель работы и доступные финансовые отчёты.
2. Сделать резервную копию БД и каталога финансовых ключей. Создать подключение с правильным историческим началом; оставить расписание выключенным.
3. Загрузить период вручную; при возвратах прошлых продаж также загрузить их месяцы. Проверить результат задания и покрытие каждого источника.
4. Зафиксировать подтверждённые исторические закупочные цены и основания. Выполнить пересчёт от месяца продажи до месяца возврата.

После пилота установите `CHECKSTOCK_YANDEX_FINANCE_ENABLED=1`, перезапустите приложение и выберите разрешённые магазины в `/admin/integrations`. Ручной запуск доступен и при выключенном расписании. Глобальное отключение фоновых загрузок продолжает действовать. Проверяйте журнал задания и дату успешного снимка, а не только наличие процесса.

Чтение опубликованной истории продолжает работать. Для отката к прежнему коду остановите приложение, верните предыдущую ревизию и запустите её; новые таблицы и отдельные ключи можно оставить.
