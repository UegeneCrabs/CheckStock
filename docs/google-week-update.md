# Автообновление недели в Google Таблицах

В разделе «Интеграции и выгрузки → Google Таблицы» находятся три одинаковых
независимых блока: WB, Ozon и Яндекс Маркет. У каждого свои ссылка на таблицу,
лист заказов, ячейки номера недели, лист остатков, расписание, флажки действий,
список листов для фиксации и результаты запусков. Доступ соответствует разделу
интеграций: требуется активная учётная запись.

Блок «Выгрузка остатков и заказов / Все проекты на каждой площадке» использует
прежние настройки `project_sheet_export_*` и прежний обработчик. Недельные
действия не меняют его настройки, расписание и результаты.

## Настройки и совместимость WB

Профили хранятся в таблице `google_week_marketplaces`, ключ — `marketplace`.
Таблица создаётся обычной инициализацией схемы; отдельная команда миграции не нужна.
Пока профиль WB отсутствует, репозиторий читает прежние таблицы
`google_week_update_settings`, `google_week_search_state`, `google_week_sales_state`,
`google_week_stock_state`, `google_week_freeze_state` и `google_sheet_catalog`.
Сохраняются URL, листы, ячейки, расписание, включённые действия, выбор листов,
последние попытки, успешные периоды и отчёты. Первое сохранение или действие
записывает новый профиль; старые записи остаются. Уже сохранённый новый профиль
имеет приоритет. Простое чтение API не переносит и не изменяет данные.

Ozon и Яндекс Маркет изначально имеют пустую ссылку и выключенное расписание.
По умолчанию используются лист «2. Факт продаж», ячейка `F4`, понедельник, 00:05
по Москве. Имена листов остатков: «Сток на складах Ozon» и «Сток на складах ЯМ».
Перед первым действием нужно указать собственную таблицу и сохранить настройки.
Названия, время и ячейки можно изменить независимо от WB.

Сохранение проверяет ссылку, названия листов, отдельные A1-адреса, время и выбор
листов, но не обращается к Google. Несохранённые изменения блокируют ручные
действия только в редактируемом блоке. После изменения файла сбрасываются кеш
листов, выбор для фиксации и её флажок; новый список загружается отдельно.
Время и день общие для действий внутри одной площадки.

## Действия и расписание

1. **Номер недели** записывает последнюю полностью завершённую ISO-неделю в
   формате `W41 2026` в выбранные ячейки. Расчёт использует московскую дату.
2. **Заказы** записывают количество заказанных товаров по всем найденным
   завершённым неделям. WB и Яндекс Маркет вычитают отменённые единицы; Ozon
   суммирует полное количество FBO/FBS по дате «Принят», исключая только
   отправления со статусом `cancelled`.
3. **Остатки** записывают снимок за воскресенье выбранной недели на отдельный
   лист: FBO у WB/Ozon, FBY у Яндекс Маркета.
4. **Проверить недели и ячейки** показывает найденные недельные заголовки и
   столбцы сопоставления без записи в Google.
5. **Фиксация** заменяет формулы прошлых недель рассчитанными значениями на
   выбранных листах. Предварительная проверка ничего не записывает в Google.

Каждый флажок включает действие по расписанию своей площадки. Ручной запуск
использует сохранённые настройки и доступен при выключенном флажке. Три фоновые
задачи определены в `JOBS.google_weeks`: `google_week_update` (WB),
`google_week_update_ozon`, `google_week_update_yandex`. Требуются работающий
фоновый worker и `BACKGROUND_SYNC_ENABLED`; опрос выполняется раз в минуту.

При совместном запуске номер недели обновляется первым. Пока его включённое
действие не завершилось успешно для текущего периода расписания, остальные
действия ожидают. Ошибка заказов не мешает выгрузке остатков и проверке недель.
Автоматическая фиксация ждёт полного успешного результата включённых выгрузок
заказов и остатков. Ошибка отдельной проверки недель ей не мешает.

Успешные действия в одном периоде повторно не запускаются. Ошибка или неполный
результат повторяются не раньше чем через пять минут; успешные зависимости
сохраняются. Повторное сохранение тех же настроек не отменяет ожидающий повтор.
Изменение расписания, назначения данных или включение действия активирует его
для следующего наступившего периода. Неполный ручной повтор снимает прежнюю
отметку успешного периода, чтобы не подавлять автоматическое восстановление.

Настройки, ручной запуск и worker используют общую блокировку внутри площадки.
Дополнительная блокировка по ID документа не даёт двум недельным действиям
одновременно писать в один файл даже при одинаковых ссылках разных площадок.
Остальные площадки могут работать параллельно.

## Недельные заголовки и сопоставление

Источники недель читаются из настроенных ячеек листа заказов. Поиск сравнивает
текст недель с нормализацией пробелов. Для заказов от совпадения просматриваются
непрерывные недельные заголовки влево до первой пустой ячейки или другого формата.
Для остатков выбирается только столбец совпавшей недели. Выгрузка требует
однозначную строку с единственными заголовками `ARTICLE` и `Проект`.

Настроенная исходная ячейка может сама быть недельным заголовком, например
`AI10` при настройке `F4, AI10`: наличие в её строке `ARTICLE` и `Проект`
позволяет использовать её для поиска. Исходная ячейка над товарной таблицей
сама по себе не становится строкой выгрузки. Несколько исходных ячеек,
ссылающихся на одну шапку, не дублируют запись.

Товары сопоставляются по `ARTICLE + Проект` только внутри выбранного
маркетплейса. Используются каталог `stock_items`, псевдонимы
`catalog_article_aliases` и общие псевдонимы проектов `PROJECT_STORE_ALIASES`.
Неизвестные проекты, отсутствующие или неоднозначные товары и повторные строки
одного товара пропускаются с замечаниями. Данные семи проектов берутся по строкам
таблицы; отдельный файл на проект не требуется.

## Источники заказов и остатков

| Площадка | Заказы | Подтверждение полноты дня |
| --- | --- | --- |
| WB | `wb_funnel_daily_orders`: `orders_count - cancel_count`, версия источника от 3 | Версия от 4 или `economics_source_days` с `source=orders` |
| Ozon | `sales_order_lines`: сумма `quantity` для FBO/FBS, кроме статуса `cancelled`, по `raw_json.in_process_at` («Принят») в МСК | `economics_source_days`; при наличии `ozon_order_days` обе схемы FBO/FBS должны иметь `listed`, `finalized`, `ok` |
| Яндекс Маркет | `sales_order_lines`: сумма `quantity - cancelled_quantity` по дате заказа, все схемы | `unit_economics_yandex_loaded_days` с `source=orders` |

Выгрузка читает уже загруженные данные БД и не инициирует загрузку заказов из API
маркетплейса. В Ozon состояние неполной новой загрузки дня отменяет старую
отметку полноты. Магазины читаются конкурентно через `asyncio.TaskGroup`, ошибка
одного магазина изолируется: его строки не перезаписываются нулями.

Только действие «Заказы Ozon» использует дату `in_process_at` из сохранённого
ответа API. Время переводится в московский часовой пояс до определения дня и
недели. `ordered_at` и `created_at` не подставляются вместо даты «Принят».
Выборка не ограничивается старым `ordered_at`: отправление, созданное раньше
выбранной недели, учитывается в неделе принятия в обработку. Полное `quantity`
учитывается для любого другого статуса, включая доставленные, доставляемые,
ожидающие в ПВЗ и неизвестные новые статусы. `cancelled_quantity`, причины отмены
и сведения о возврате не уменьшают этот показатель. Статус `cancelled`
проверяется без учёта регистра и пробелов по краям.

Некорректная или отсутствующая дата «Принят» у неотменённой строки делает
источник магазина недоступным для этого запуска: его ячейки не перезаписываются.
Схема БД и общая нормализация заказов не меняются. Маркеры полноты остаются
привязаны к исходным датам загрузки; для известных отправлений, перемещённых
между датами, дополнительно требуется полнота исходного дня. Эти маркеры не
заменяют повторную сверку с API по дате принятия. Остальные выгрузки и расчёты
экономики сохраняют прежние правила дат и отмен.

Неделя — понедельник–воскресенье ISO-календаря. Незавершённые недели не
перезаписываются. Известные количества суммируются; отсутствующие данные
учитываются нулём с явным неполным результатом и перечнем дат. Отсутствующий
товар в подтверждённом дне заказов означает ноль. Исторические факты WB версии
3 используются как в прежней выгрузке; отсутствие неподтверждённого дня остаётся
замечанием. Неполный результат препятствует автоматической фиксации.

Остатки всех площадок читаются из `marketplace_stock_daily_history` строго по
площадке, проекту, артикулу, `scheme=fbo` и воскресенью нужной недели. Общая
схема хранения `fbo` для Яндекс Маркета отображается как FBY. Соседний день,
текущий остаток и другая площадка не подставляются. При отсутствии снимка
записывается ноль и замечание; в отчёте есть время использованных снимков.

## Фиксация формул

Список листов каждой таблицы обновляется ежедневно и кнопкой «Обновить список».
Выбор хранится по `sheetId`, поэтому переименование его сохраняет. Удалённые
листы остаются видимыми как недоступные до снятия выбора. При первой успешной
загрузке выбираются существующие листы из `GOOGLE_WEEK.default_freeze_sheets`;
пользовательский выбор, в том числе пустой, далее сохраняется. Добавление или
удаление пункта меняет только список обработки, сами листы не удаляются.

На каждом выбранном листе алгоритм:

1. Находит строки с обоими заголовками `ARTICLE` и `BARCODE`.
2. Только в этих строках, начиная со столбца I, ищет точный текст последней
   завершённой недели — тот же расчёт, что в действии «Номер недели».
3. Двигается влево по непрерывным заголовкам `W(номер) (ISO-год)`, проверяя
   существование ISO-недели и строгое убывание дат, включая смену года.
4. Фиксирует прошлые столбцы ниже шапки до конца листа. Столбец найденной недели,
   сама шапка и строки выше сохраняются. Для W39 фиксируются W38 и более ранние.

Повторные шапки с одинаковыми недельными границами сохраняются: диапазоны
заканчиваются перед ними и продолжаются со следующей строки. Пересекающиеся
границы и разные недели в одинаковых столбцах считаются неоднозначными.

Проверяются исходные ячейки номера недели, более поздние недели внутри диапазона,
объединения, защищённые области и исключения защиты, ошибки и нерассчитанные
формулы, сводные таблицы, внешние источники и возможный вывод массивов.
Небезопасный лист пропускается с причиной; другие проверенные листы могут
обработаться. Защита с предупреждением или разрешённым редактированием не мешает.

Для безопасных диапазонов используется `copyPaste / PASTE_VALUES` в тот же
диапазон; оформление сохраняется. Диапазоны без формул повторно не записываются.
Предварительная проверка не создаёт резервную копию и не заменяет последний
сохранённый результат фиксации.

## Google API и защита записи

Клиент использует существующий сервисный аккаунт, локально подписывает JWT и
получает токен через асинхронный HTTP. Для чтения запрашивается scope readonly,
для записи — spreadsheets. Сетевые операции Google и обращения к БД выполняются
через асинхронные клиенты; синхронные потоки не используются.

Заказы и остатки записываются числами через `values:batchUpdate` с `RAW`.
Большой набор изменений делится на последовательные пакеты: сериализованный
JSON каждого не превышает `GOOGLE_WEEK.max_payload_bytes` (1 800 000 байт).
Размер всего набора не является причиной отказа. Если в лимит не помещается
одна ячейка, ошибка содержит её адрес. Порядок и значения ячеек сохраняются.
Уже совпадающие числовые ячейки не записываются. Перед записью повторно читаются
структура листа, заголовки, исходные ячейки и ключи товаров; изменение останавливает
запись. Для фиксации аналогично перепроверяются структура, диапазоны и формулы.

Перед изменением заказов, остатков или формул создаётся JSON-копия прежних
значений/формул рядом с БД: `backups/google-week-marketplaces/<площадка>/<действие>/`.
Файл сбрасывается на диск до Google-запроса. Ошибка создания копии останавливает
запись. Обновление номера недели, как и прежде, отдельную копию не создаёт.
Сетевой клиент не повторяет запись вслепую после ошибки. Следующая попытка
заново читает документ. Пакеты не составляют единую транзакцию: при сбое позднего
пакета уже записанные значения остаются, а повтор пропускает совпадающие ячейки.
Резервная копия охватывает весь набор до первого пакета. Проверки не блокируют
параллельные правки людей в Google.

Контракты Google: [service account OAuth](https://developers.google.com/identity/protocols/oauth2/service-account),
[values.batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchUpdate),
[пакетное обновление](https://developers.google.com/workspace/sheets/api/guides/batchupdate).

## API и карта реализации

Новый JSON API:

- `GET /api/admin/google-weeks` — три профиля и состояния.
- `GET /api/admin/google-weeks/{marketplace}` — состояние одной площадки.
- `PUT /api/admin/google-weeks/{marketplace}` — сохранение `WeekSettings`.
- `POST /api/admin/google-weeks/{marketplace}/catalog` — обновление списка листов.
- `POST /api/admin/google-weeks/{marketplace}/{action}` — действие
  `number`, `sales`, `stock`, `search`, `freeze`.
- `POST /api/admin/google-weeks/{marketplace}/freeze?preview=true` — проверка фиксации.

Площадки: `WB`, `OZON`, `YANDEX MARKET` (пробел кодируется в URL).
Ошибки валидации возвращают 422, занятость площадки — 409, ошибки сценария — 400
с машинным кодом. Старые HTTP-обработчики `/admin/google-week-update/*` удалены;
после обновления приложения старую открытую вкладку нужно перезагрузить.

- DTO: `app/dto/google_week.py`; константы и метаданные: `app/core/constants.py`.
- Сценарии: `app/application/google_weeks.py`.
- Хранение и источники: `app/infrastructure/google_week_repository.py`,
  `app/infrastructure/google_week_orm.py`.
- Протокол Google: `app/integrations/google_week_client.py`.
- Чистые расчёты и планы: `app/integrations/google_week_plans.py`.
- Маршруты: `app/web/routers/google_weeks.py`; worker: `app/jobs/google_weeks.py`.
- Интерфейс: `templates/integrations/google-week-update.html`,
  `static/integrations/google-week-update.js`; оформление сохраняет существующий CSS.

При локальной приёмке используются временная SQLite, имитация Google API,
HTTP-проверки маршрутов и браузер с синтетическими профилями. Они проверяют
изоляцию площадок, перенос WB, расчёты, повторы, зависимость фиксации, резервные
копии и независимое редактирование форм. Реальная запись в Google и подключение
к рабочему PostgreSQL не входят в эти проверки.

Для правил «Заказы Ozon» временный сценарий проверяет FBO/FBS, границы недели
в МСК, перенос между датами создания и принятия, исключение только `cancelled`,
полное количество при остальных статусах, изоляцию ошибочной даты и маркеры
полноты. Отдельная сверка в режиме только чтения сравнивает результат с
независимым пересчётом сохранённых ответов API.
