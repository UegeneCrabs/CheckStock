# Аналитика Яндекс Маркета

Для Яндекс Маркета доступны три самостоятельные страницы в меню «Аналитика»: Анализатор, Эфемериды и Продажи по API. Они используют сохранённые данные ЯМ и общий интерфейс отчётов WB. Рейтинг товаров в эти страницы не входит. Каждый активный пользователь видит настроенные магазины. Недельные и дневные записи ЯМ, настройки вида и коэффициенты прогноза изолированы от WB и Ozon.

Товар определяется магазином и полным артикулом продавца: `001 / x` и `001` различаются. Пробелы, ведущие нули и разделитель ` / ` сохраняются. FBY и FBS объединяются для одной такой пары. Данные другой площадки или другого магазина с таким же артикулом не подставляются.

## Анализатор

Страница `/analytics/yandex-market/analyzer` показывает полный сохранённый каталог: поиск, отбор по магазину и ответственному, сегменты, фильтры значений и цвета, сортировку, скрытие блоков/столбцов, плотность, пагинацию, карточку товара и CSV. Строки по умолчанию ранжируются по валовой сумме заказов сегодня, даже при выборе прошлой недели. Подтверждённый ноль располагается перед неизвестным значением.

Семь дневных столбцов относятся к выбранной московской неделе, будущие дни неизвестны. Четыре дня рекламы и CTR заканчиваются на `min(сегодня, воскресенье выбранной недели)`; «вчера» отсчитывается от этой даты. Рекламный CTR — сумма кликов / сумма рекламных показов ×100%, с совпадающим покрытием. Органические показы из отчёта корзин не подменяют рекламные показатели.

Средняя цена предыдущей недели — сумма валовых сумм заказов / сумма количества заказов по известным парам дат. Сток анализатора — FBS+FBY, с признаком отсутствующих компонентов. Дни запаса доступны при полном покрытии спроса предыдущей завершённой календарной недели и положительном среднем спросе. ФФ сюда не прибавляется.

Цель дня берётся из текущего справочника ЯМ; при отсутствии дневной цели используется недельная /7. Цель оборота — цель дня × средняя цена предыдущей выбранной недели. Факт оборота — валовая сумма заказов сегодня. Прогноз = факт × собственный D магазина для текущего часа Москвы; разница = прогноз − цель; отклонение = разница / цель ×100%. При нулевой или неизвестной цели отклонение отсутствует.

Кнопка «Коэффициенты D» открывает 24 nullable значения по часам Москвы отдельно для каждого магазина. Пустое значение оставляет прогноз, разницу и отклонение неизвестными; коэффициенты WB не копируются. Явный нулевой D допустим. Сохранение требует ревизию и отклоняет устаревшую версию HTTP 409. После смены часа открытый анализатор обновляет коэффициент.

Дневные заметки сохраняются только за сегодня, с полным артикулом и защитой от конкурентной правки. В карточке доступны прежние и новые тексты редакций с автором и временем. История берётся из сохранённых revisions.

## Эфемериды и комментарии

Страница `/analytics/yandex-market/ephemerides` сравнивает выбранную и предыдущую ISO-неделю. Текущая неделя показывает валовые заказы по сегодня, завершённая — `max(заказы − отмены,0)` по подтверждённым дням. Это правило факта не изменяет формулу аналитического ДРР. ТО эфемериды по цели = цель недели × цена продавца этой недели; известная цель 0 даёт ТО 0.

Исторические цены берутся из сохранённых снимков внутри соответствующей недели. Историческая цель берётся из `economics_daily.source.raw.source_1c.goal_week`; сегодняшний справочник допустим только для текущей недели. Текущие цены и цели не заполняют прошлые недели. Старые снимки без цели остаются неизвестными. Сводка магазинов над таблицей показывает сегодняшние валовые суммы независимо от выбранной недели.

Недельный сток — неизменяемый снимок четырёх компонентов: FBS, FBY, ФФ и возвраты от клиента. Итог суммирует известные компоненты и передаёт признак частичных данных. В подсказках указаны неделя и время фиксации. Текущие остатки не подмешиваются в пропущенный снимок.

Комментарии имеют ключ `(магазин, полный артикул, понедельник, вид)`. Виды `competitor`, `decision`, `next` независимы. Решения можно создавать, менять и очищать только за текущую московскую неделю; сервер перепроверяет это при каждой записи, в том числе после смены недели в открытой вкладке. Конкуренты и планы следующей недели допускают прошлые недели. Текст до 4000 символов, пустой текст означает аудируемую очистку.

Шесть недель решений на основной странице и двенадцать недель на `/analytics/yandex-market/ephemerides/comments` доступны для чтения; можно выбрать более раннюю неделю. Запись решения выполняется в основной зоне текущей недели или карточке. Автосохранение работает через 5 секунд, при выходе из поля и переходах. Ответ старого запроса не стирает более новый ввод; черновики не попадают в общий localStorage. При HTTP 409 интерфейс предлагает сравнение с сохранённой версией. Основной текст и ревизия фиксируются одной транзакцией.

## Продажи по API

Страница `/analytics/yandex-market/sales-api` показывает заказы, отмены отдельно и дневную детализацию; это не отчёт о реализованных продажах. Полный каталог дополняется историческими артикулами, которые уже вышли из каталога. FBY/FBS одной пары магазин+артикул не дублируются.

Период —1–366 дней, начиная с 2000-01-01 и не позже сегодняшнего московского дня. Начальная и конечная даты задаются вместе. По умолчанию открываются 7 дней до последнего доступного дня; без истории окно заканчивается сегодня с неизвестными значениями. «Весь период» ограничен последними 366 днями и сообщает об ограничении. Границы включают успешно загруженные пустые дни.

Отсутствующая строка товара даёт 0 только при подтверждённой полной загрузке заказов магазина за день; иначе значение неизвестно. Частичные итоги суммируют известные дни и обозначают неполноту. Ранжирование использует сегодняшний валовый ТО независимо от выбранного периода. Ошибка запроса сохраняет прежний результат; старый ответ не заменяет новый.

## Экономика, ДРР и неизвестные значения

Текущий ROI рассчитывается действующей юнит-экономикой ЯМ по сегодняшним сохранённым ценам, расходам и настройкам. Периодные прибыль и ROI используют дневные inputs, применимые ручные overrides и сохранённую версию формулы ЯМ. Существующие формулы юнитки не меняются. COMMON FBY/FBS не складывается повторно с исходными схемами.

Аналитический ДРР повторяет базу аналитики WB: `сумма расходов / сумма(валовая сумма заказов × датированный выкуп /100) ×100%`. Участвуют только даты, в которых известны все три исходных значения. Отмены повторно не вычитаются; сегодняшний или периодный выкуп не заполняет неизвестную историческую дату. При пустом пересечении числитель, знаменатель и ДРР неизвестны. При нулевых числителе и знаменателе ДРР 0; при положительных расходах и нулевом знаменателе — неизвестен. Вчерашний и накопительный интервалы имеют самостоятельные weights и coverage. Итоги после frontend-фильтрации складывают согласованные числители и знаменатели, а не усредняют проценты.

Например, валовые заказы 1000₽, отмены 300₽, датированный выкуп 50%, реклама 100₽ дают аналитический ДРР 20%. Полная отмена текущего заказа не меняет эту формулу. Второй товар с валовой суммой 2000₽, выкупом 25% и рекламой 50₽ даёт 10%; совместный итог —150/1000×100=15%.

Качество передаётся отдельно от числа в optional quality: complete, stale, reasons, expected_dates, known_dates. Известные пригодные веса сохраняются, даже если источник неполон или устарел. known_dates обозначают пригодные части, а не доказанную полноту. Для заказов и рекламы отдельно проверяются подтверждения загруженных дней: одинаковая известная строка без подтверждения остаётся числом с partial, а не становится полной. Семь известных строк без всех семи подтверждений недостаточны для дней запаса. Полный, но устаревший снимок может иметь complete=true и stale=true. Строки, оба недельных периода и отфильтрованные weighted итоги сохраняют эти признаки. При отсутствии нового поля действуют совместимые coverage/field_issues/stockPartial.

Все исходные колонки WB сохраняются. `—` означает неизвестное значение; подтверждённый 0 остаётся 0. Расчётные и устаревшие цены отмечаются данными источника. Неизвестные корзины не заменяются рекламными корзинами, текущие остатки — недельными, и данные WB — совпавшим артикулом ЯМ.

## Корзины и возвраты

Корзины загружаются отдельным отчётом `shows-sales`, `grouping=OFFERS`, `dateFrom=dateTo`; используется именно `toCart`. Исходная дата отчёта и timezone=`unknown` сохраняются отдельно от московского календаря заказов. Пользователь выбрал показывать достоверный toCart за исходную дату с пояснением «дата отчёта Маркета; границы суток не подтверждены». Пересчёта в московские сутки нет. Данные могут запаздывать и оставаться предварительными; DONE означает готовность файла, а не полноту суток. NO_DATA, отсутствие колонки, explicitnull, ошибка или пропавшая строка не подтверждают 0. Известный toCart=0 сохраняется.

Возвраты FBY читаются для всех собственных кампаний и всех страниц API returns. Неизвестный или отсутствующий общий/per-instance статус, повтор идентификатора возврата, повтор токена страницы, неполные instances и неверное количество отклоняют новый снимок. Учитываются RECEIVED/IN_TRANSIT, fastReturn исключается. Успешный пустой снимок подтверждает 0; до успеха значение неизвестно. Ошибка сохраняет последний успех с отметкой ошибки; для недельного стока используются только свежие подтверждённые возвраты.

Официальные источники: [shows-sales](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateShowsSalesReport), [returns](https://yandex.ru/dev/market/partner-api/doc/ru/reference/returns/getReturns). Для первого нужен доступ финансовой отчётности или all-methods; для returns достаточно inventory-and-order-processing/read-only либо all-methods/read-only. Права конкретного кабинета и подписка проверяются API, покупка подписки в задачу не входит.

## API, хранение и фоновые задачи

Общий корень API `/api/analytics/yandex-market`:

| Метод и суффикс | Результат |
|---|---|
| GET `/analyzer?week=YYYY-MM-DD` | Выбранная неделя, сегодняшний оборот/ROI и записи |
| POST `/analyzer/notes` | Запись за сегодня: store/article/day/note |
| PUT `/analyzer/notes/{id}` | Правка сегодняшней записи с previous_note для CAS |
| GET `/ephemerides?week=...` | Две недели и комментарии |
| GET `/ephemerides/comments?week=...` | Каталог и 12 недель комментариев, без расчёта экономики |
| PUT `/ephemerides/comments` | store/article/week/kind/text/version |
| GET `/ephemerides/comments/revisions` | Ревизии того же ключа |
| GET `/sales-api?date_from=...&date_to=...` | Заказы и отдельные отмены |
| GET/PUT `/settings/{store}` | hourly_d_coefficients и revision |

GET не вызывает API площадки и не пишет историю. Новые записи проходят application service, порт и infrastructure Unit of Work. Дневные заметки используют marketplace-aware rnp_action_log/revisions. Остальные таблицы собственные: yandex_analytics_comments/revisions, settings, customer_transit, stock_snapshots и funnel_days. Funnel-показатели также сохраняются в существующие daily_metrics/loaded_days с source=funnel; raw метаданные не означают полную московскую дату. Схема добавляется повторяемым create_all для SQLite и PostgreSQL без destructive миграции старых данных.

Задачи доступны в общей панели интеграций с выбором магазинов и ручным запуском:

- `yandex_analytics_funnel_sync`: интервал после завершения 15 минут, today первым, затем отсутствующие/устаревшие source-days в окне D−7…D. Исторический refresh по умолчанию 4 часа, конфигурируется `CHECKSTOCK_YANDEX_ANALYTICS_FUNNEL_HISTORY_REFRESH_SECONDS`. Метаданные freshness сохраняются. Существующий устойчивый limiter shows-sales общий с выкупом: без подписки не чаще 1 генерации/10 минут на business; polling использует тот же reportId. Магазины обрабатываются независимо конкурентно; частичный день не публикуется.
- `yandex_customer_transit_sync`: каждые 4 часа и вручную; снимок заменяется атомарно после полной проверки всех кампаний.
- `yandex_ephemerides_stock_snapshot`: понедельник после 00:05 МСК, три повтора по общему правилу эфемерид. Первый успех immutable; во вторник пропущенный понедельник не создаётся.

Интервалы новых задач и startup-delay задаются `CHECKSTOCK_YANDEX_ANALYTICS_FUNNEL_INTERVAL_SECONDS`, `CHECKSTOCK_YANDEX_ANALYTICS_TRANSIT_INTERVAL_SECONDS`, `CHECKSTOCK_YANDEX_ANALYTICS_STARTUP_DELAY_SECONDS`. Общий каталог и persisted scheduler сохраняются. Ошибка одного магазина не стирает результаты другого.

CSV анализатора сохраняет исходный набор колонок и все отфильтрованные товары; эфемериды экспортируют только видимые колонки; Продажи по API всегда экспортируют стандартные отдельные реквизиты и все дни, даже скрытые в интерфейсе. Все три экспорта сохраняют числовые значения таблицы и экранируют формулы Excel в текстовых полях. Исходные числовые колонки остаются числовыми. Для неполных, устаревших и неизвестных числовых показателей Ozon/ЯМ добавляются колонки «качество» и «причины» с машинными кодами: full, partial, stale, unknown могут различаться независимо от числа. У эфемерид эти колонки относятся только к экспортируемым видимым полям. Новый quality-export включён явным параметром страницы для Ozon/ЯМ; по умолчанию WB сохраняет прежние CSV байты, фото/тексты не получают metadata. Календарные подписи корзин сохраняются; новый обязательный динамический marker или metadata-колонки корзин не вводятся.

## Проверка исходной даты отчёта

Загрузчик формирует типизированный подтверждённый однодневный запрос dateFrom=dateTo с OFFERS. Нормализатор без этого provenance либо с многодневным запросом отклоняет снимок. Совместимость адаптера явно поддерживает строгие формы day: YYYY-MM-DD, DD.MM.YYYY, DD-MM-YYYY и строковый D/DD. Это поддерживаемая grammar, а не утверждение официально гарантированного формата строки отчёта. Все присутствующие month (числовая строка M/MM или M/MM-YYYY) и year (строгий integer) проверяются против запроса даже при полной дате day. Отсутствующие компоненты разрешаются только единственным днём запроса; explicit null/empty и неизвестные формы отклоняются. Timestamp, slash-date, boolean, дроби, невозможная дата и конфликт любого SKU отклоняют весь снимок. Строгий analytics consumer сохраняет каждую строку листа до валидации: malformed строка без offerId не отбрасывается legacy extractor. Mixed ответ не публикует valid subset; предыдущие A/B значения, received_at и last_success сохраняются, ошибка добавляется отдельно. Старые потребители выкупа, репутации и рекламы используют прежний режим извлечения.

Исходные day/month/year и флаги присутствия, режим разбора и происхождение сохраняются рядом с нормализованной date-only датой. В HTTP cartSources сохраняются source_date/source_scope=report_date/timezone=unknown/received_at/provisional=true/complete=false/known/stale/reason и provenance. known означает валидное наблюдение счётчика, а не окончательные сутки. Старые counters без подтверждённого date provenance остаются неизвестными до обновления. Датированные JSON экономики читаются потоково и разбираются один раз; архив economics_daily_events не читается. Ревизии заметок загружаются пакетно.

При диагностике 30.10.2026 реальный отчёт вернул day=`30-10-2026`, month=`10-2026`, year=`2026`. Адаптер дополнительно принимает строгие DD-MM-YYYY и M/MM-YYYY, проверяя год и месяц против единственного дня запроса и полной даты day. Режим day сохраняется как `local_dash_date`; исходные компоненты сохраняются без изменений. Прежние ISO, дата с точками и число дня продолжают поддерживаться. Неизвестные формы и конфликты компонентов отклоняют весь снимок; fuzzy-разбор не применяется. Ошибка неизвестного формата содержит имя поля и ограниченное диагностическое значение без ключей доступа.

Общий shipmentStatus и instances.status проверяются разными наборами значений API. Общий `FULFILMENT_RECEIVED` и поштучный `RECEIVED_ON_FULFILLMENT` допустимы, но не относятся к движению от клиента; учитываются только RECEIVED/IN_TRANSIT. Неизвестный статус сохраняет ошибку источника и прошлый успешный снимок. Магазин без ключа получает `credentials_missing` без traceback; его можно отключить в настройках конкретной задачи, сохранив остальные интеграции магазина.

## Проверки и ограничения

Первые самопроверки предшествовали R1, где три проверяющих подтвердили дефекты итогового 0/0 ДРР, качества итогов/CSV, mixed malformed funnel и скрытой истории редакций. Исправления второй попытки проверены отдельным разработчиком: шесть integration методов на каждой из SQLite и PostgreSQL ym_coder2, actual Node models/renderers и Chrome fixture UI с настоящими CSV. Это самопроверка, отдельная R2 панель ещё требуется. Полный scoped mypy включает унаследованные ошибки legacy unit_economics_sync; новый типизированный контур проходит отдельно.
