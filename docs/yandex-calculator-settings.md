# Калькулятор и постоянные параметры Яндекс Маркета

## Тарифы по фактической кампании от 21.09.2026

Логистика, приём платежа и эквайринг загружаются через `/v2/tariffs/calculate`
с `campaignId` магазина нужной модели FBY/FBS. Кампании проверяются через API
на принадлежность кабинету. При нескольких кампаниях одной модели требуется
явный выбор; произвольная кампания не подставляется. График выплат и валюту
берёт сам Маркет из настроек кампании. Старые локальные `frequency` и
`payment_delay_weeks` не отправляются и больше не редактируются на странице.

Отсутствие `PAYMENT_TRANSFER` является неполным ответом, а не нулевой ставкой.
Если API возвращает процент в параметрах услуги, сохраняется этот процент,
без погрешности от деления округлённой суммы на цену. Явный нулевой тариф
в ответе допускается. Ручная ставка товара сохраняет прежний приоритет.
Старые тарифы без подтверждённого эквайринга не используются до обновления;
история закрытых дней не переписывается. Пропуски тарифов теперь отражаются
в результате фонового задания с причиной и примерами артикулов.

## Актуальные изменения от 18.09.2026 (формула версии 7)

- Затраты на ФФ, хранение за день, период хранения и прочие фиксированные расходы
  исключены из калькулятора, настроек и текущих формул. Старые значения в БД
  игнорируются, включая прежний общий `tax_percent`.
- Два отдельных параметра: `vat_percent` (НДС) и `usn_percent` (УСН).
  Как в WB: НДС = цена с СПП × ставка НДС / (100 + ставка НДС);
  УСН = (цена с СПП − НДС) × ставка УСН / 100. Оба расхода вычитаются из прибыли.
  Эти же формулы используются для ROI, текущей экономики и цены без убытка.
  Ставки задаются в настройках YM и для кабинета общие у FBY/FBS;
  без ставки показывается недостающий параметр,
  явный ноль допускается. Старый общий налог автоматически не разделяется.
- История закрытых дней сохраняет формулу и параметры соответствующего дня.
  Новые дневные снимки используют версию 7.
- Товар виден при ненулевом ТО за выбранный период либо положительном остатке
  FBS, FBO, ФФ или «В пути на склады FBO», включая утверждённые заявки.
  Сборщик цен использует этот же отбор за последние семь завершённых дней,
  исключает архив и не зависит от статического списка артикулов.

## Изменения от 17.09.2026 (предыдущая формула версии 6)

- Стоимость капитала и оборачиваемость исключены из входов и расчёта прибыли.
  Старые поля `capital_percent`, `turnover_days`, `other_percent` игнорируются.
- Комиссия компании `company_commission_percent` задаётся в параметрах кабинета
  и едина для FBY/FBS. Расход = цена продавца × процент / 100, как у WB.
  При первом запуске переносится прежнее значение комиссии кабинета; последующие
  импорты 1С его не читают и не перезаписывают. Нулевой процент допускается.
- Хранение = явно заданные `storage_per_day` × `storage_days` (по умолчанию 30).
  Старые сохранённые суммы хранения остаются входными данными. Нет ставки —
  нет расчёта, с указанием причины. Зависимости от оборачиваемости больше нет.
- Сохранённые расчёты закрытых дней не пересчитываются по новой формуле.

Проверка публичного API на 17.09.2026: `offer-mappings` с `archived=true`
позволяет исключать архив. В [официальной OpenAPI-спецификации](https://github.com/yandex-market/yandex-market-partner-api)
не найдены готовые поля прогноза хранения на остаток месяца и количества/дат
перехода на платное хранение. Эти показатели доступны в кабинете и его
[логистических отчётах](https://yandex.ru/support/marketplace/ru/storage/logistics).
`reports/goods-turnover/generate` и финансовый отчёт по услугам дают другие,
исторические показатели; они не подставляются вместо такого прогноза.

Разделы с проверками и формулами за 15–16 сентября ниже описывают прежние версии;
их зависимости от оборачиваемости и капитала заменены правилами версии 6 выше.

Карточка ЯМ использует общие с WB стили калькулятора `ue1c-calculator`: компактные строки,
переключатель подробного расчёта и результат справа. Формулы остаются в `app/yandex/economics_calculation.py`.
Расчётные формулы WB не меняются.

- В карточке один редактируемый **расчёт чистой прибыли**, без переключения между текущей
  экономикой и калькулятором. При открытии он сразу показывает значения и результат сценария
  (`calculator_values`, `calculator_origins`, `calculator_result`), согласованные между собой.
  Изменения полей пересчитываются через `POST /calculate/…`, без сохранения.
  «Сбросить» заново загружает исходные параметры; FBY/FBS выбирает модель работы.
  «Цена без убытка» подставляет расчётную цену продавца. По умолчанию реклама считается по ДРР за последние 7 завершённых
  дней. Выбора режима рекламы нет: рядом с ДРР сразу показана сумма рекламы за эти дни.
  Процент можно отредактировать прямо в поле, как у WB; очистка возвращает недельное значение.
- Экономика в списке товаров и снимках использует заказы и рекламу за сегодня (МСК).
  При пропуске цены применяются последние СПП и скидка Пэй; происхождение цены сохраняется
  в снимке. Пробные значения из открытой карточки в список и снимки не попадают.
- При изменении цены продавца калькулятор пересчитывает цену с СПП и цену с картой Пэй
  по последним наблюдённым скидкам, если эти цены не заданы вручную.
  Скидки и времена их получения показаны под ценой Пэй. Цена Пэй справочная:
  в формулах прибыли и маржинальности по-прежнему участвует цена покупателя без Пэй.
- **За 7 дней**: отдельный результат по накопленным снимкам завершённых дней, не зависит от сценария.
  Для каждого дня используются сохранённые параметры, его заказы и расходы на рекламу:
  маржа дня = прибыль единицы без рекламы × заказы × выкуп / 100 − реклама дня.
  Маржа периода — сумма дневных результатов; ROI = эта сумма / суммарная закупочная
  стоимость ожидаемых выкупов за те же дни × 100. Дневные ROI не усредняются.
  Если из последних 7 завершённых дней известна только часть, считаются только эти дни:
  ячейки маржи и ROI подсвечиваются, при наведении перечислены даты, как у WB.
  Во вкладке «Параметры» также показаны число дней и все использованные даты.
  Без истории — прочерк; сегодняшними параметрами пропуски не заполняются.
  Снимки входных параметров сохраняются часовой выгрузкой экономики, завершённый день
  закрывается после загрузки его заказов и рекламы. Закрытые дни не перезаписываются.

Постоянный ввод перенесён в **API-ключи и фоновые выгрузки → Ввод данных по кабинетам →
Экономика Яндекс Маркета · закупка и расходы**. Ссылка из карточки выбирает кабинет, артикул и FBY/FBS.
Доступ соответствует разделу интеграций: суперадминистратор с доступом к кабинету и юнит-экономике.

Общие расходы, налоги, оборачиваемость, стоимость капитала и расписание выплат можно задать для кабинета.
Закупка задаётся для отдельного товара; индивидуальные значения имеют приоритет перед общими.
Ручные замены тарифов, категории, габаритов и выкупа находятся в раскрывающемся блоке. Они имеют
приоритет перед API, пока пользователь не вернёт источник кнопкой ↺. Пустое поле снимает ручное
значение, ноль сохраняется как явное значение. Сохраняются только отредактированные поля.

`GET/PUT /api/unit-economics-1c/yandex-market/settings/{store}?article=…&scheme=FBY` использует
существующую таблицу настроек, журнал изменений и проверку ревизии. Пустой артикул означает
настройки кабинета. Цены и план рекламы этот endpoint не сохраняет. Миграции БД не нужны.

Ранее тестами проверены наследование, нулевое значение, сброс, ревизии, доступ, разделение FBY/FBS,
сохранение и получение параметров расчётом, формулы ЯМ и интеграции. Набор тестов удалён из проекта.
В браузере проверены компактный/подробный режимы, сценарный пересчёт и сохранение закупки
с повторным открытием карточки. Проверки проводятся на отдельной локальной базе.

## Формулы и сверка с листом «ДЛЯ ЖЕНИ»

### ДРР калькулятора за завершённую неделю

Берутся ровно семь календарных дней до сегодняшнего дня по Москве, независимо от выбранного
периода таблицы. ДРР = сумма рекламы / (сумма оборота заказов × выкуп / 100) × 100, как в
недельном расчёте WB. Это отношение сумм, а не среднее арифметическое дневных процентов.
Используются только совпадающие дни, за которые полностью загружены и реклама, и заказы.
Успешно загруженный пустой день учитывается как нулевой; отсутствующий день не подменяется нулём.
Реклама и оборот берутся по товару во всех схемах, поскольку реклама ЯМ не разделена на FBY/FBS.

При наличии 1–6 дней ДРР считается по ним, поле выделяется жёлтым и показывает «Данные за N из 7
дней», даты периода и пропущенные дни в подсказке. Если совместных дней нет либо реклама есть,
а оборота нет, процент и прибыль не выдумываются: отображается причина. При нулевой рекламе за
известные дни ДРР равен 0%. Процент может превышать 100% и не ограничивается этим значением.

Рекламный расход калькулятора = цена продавца × ДРР / 100. Сегодняшние рекламные расходы на
этот сценарий не влияют. Ручной ДРР действует до сброса/очистки поля и не сохраняется.
Список текущей экономики и исторические снимки продолжают использовать фактическую рекламу.
Ответ калькулятора содержит `calculator_advertising` с охватом дней, суммами и исходным ДРР.

В компактном и подробном видах рядом показаны «ДРР с выкупом за 7 дней» и «Расходы на рекламу
за 7 дней». Сумма расходов — отдельный справочный показатель, не редактируется и не меняется
при ручном вводе ДРР. `advertising_spend` включает все загруженные дни рекламы за этот период,
даже если за часть дней ещё нет заказов. `spend` остаётся суммой только совместных дней для
формулы ДРР. Полноту суммы показывают `advertising_days`/`advertising_complete`; при неполной
истории строка выделяется жёлтым. Без данных показан прочерк, загруженный нулевой расход — 0 ₽.

Проверены 310 сценариев активного ассортимента (155 товаров × FBY/FBS), совпадение недельного
ДРР с WB, неполные/пустые дни, несовпадающее покрытие заказов и рекламы, исключение сегодняшнего
дня, отсутствие оборота при расходах, ДРР выше 100%, ручное значение и обновление тарифа API.
В браузере на временном сервере с доступом к БД только для чтения проверены подсветка «2 из 7 дней»,
ручной ввод и возвращение к автоматическому значению. Тестовые данные в БД не записывались.

Итоговая арифметика версии 3 сверена 16 сентября 2026 года с
[исходным листом](https://docs.google.com/spreadsheets/d/1UH3ank5iAEreLNgFGLs6I7Jfq0TXeKSV4hpfgBxLPEk/edit?gid=1565890225#gid=1565890225).
При одинаковых входных параметрах совпали прибыль, ROI, маржинальность и все статьи расходов
для 161 строки. В строке 79 (`TRIS / 153985484001`) исходная таблица возвращает `#N/A`;
её результат не заменяется нулём. Через обработчик `POST /calculate/…` отдельно проверены
310 сценариев: 155 действующих товаров в двух схемах. Доступ к локальной БД при этой проверке
ограничен `PRAGMA query_only=ON`; исходные значения не переносились и не заменялись.

- Прибыль (`AH`) = цена продавца − все расходы. Промежуточные расходы до суммирования не округляются.
- ROI (`BB`) = прибыль / закупка × 100. При нулевой закупке показатель не определён.
- Маржинальность (`AI`) = прибыль / цена покупателя × 100; при нулевой цене — 0, как в `IFERROR` листа.
- Комиссия, перевод платежа, процентные прочие расходы и потери считаются от цены продавца.
  Налог всегда считается от цены покупателя с СПП, без скидки Пэй.
- Капитал (`AG`) = закупка × годовая ставка / 100 × оборачиваемость / 365.
- Возвраты (`AS`) = (средняя миля по формуле `AP` + 15 ₽) × (1 − выкуп / 100).
  Утилизация (`AX`) использует такую же долю невыкупа. Эти две статьи не делятся на выкуп.
- Хранение (`AO`) = ставка по оборачиваемости × объём в литрах × 30 дней.
  Приём платежа, успешная доставка, транзит,
  закупка, фулфилмент и фиксированные прочие расходы входят готовыми суммами.
- Плановая реклама (`W`) = цена продавца × ДРР / 100. Такой сценарий определён и при выкупе 0%.
  Фактическая реклама распределяется на ожидаемые выкупленные единицы:
  расходы / заказы / (выкуп / 100). Для этого режима нулевой выкуп по-прежнему блокирует расчёт.

Денежный вывод убирает остаточную погрешность чисел с плавающей точкой до 15 значащих цифр,
затем округляет до копеек по `ROUND_HALF_UP`. Например, комиссия для `401818217`
отображается как 2876,04 ₽, совпадая с форматом Google Sheets. Проверены также нулевые
цены, отсутствие закупки, выкуп 0% и 100%, срок хранения и распределение фактической рекламы.

### Автоматические хранение и возвраты (версия 4)

Объём `V` = длина × ширина × высота упаковки в сантиметрах / 1000. Используются действующие
габариты товара из каталога или ручной настройки; объём не округляется до целых литров.
Без положительных габаритов нужно вручную задать объём либо расходы на невыкуп и хранение.

Ставка хранения в ₽/л/день выбирается по оборачиваемости: до 120 дней включительно — 0;
до 180 — 0,75; до 300 — 1; до 450 — 1,25; свыше 450 — 1,75. Период расчёта по умолчанию 30 дней,
как в `AO`. Оборачиваемость одновременно продолжает участвовать в стоимости капитала.

Средняя миля для возвратов (`AP`) ограничена сверху 5500 ₽:

- `V ≤ 1`: 80 ₽;
- `1 < V ≤ 30`: `80 + (V − 1) × 9`;
- `30 < V ≤ 200`: `80 + 29 × 9 + (V − 30) × 7`;
- `V > 200`: `80 + 29 × 9 + 170 × 7 + (V − 200) × 5`.

После ограничения добавляются 15 ₽, затем сумма умножается на долю невыкупа.
Расчёт применяется к обеим схемам калькулятора по запросу пользователя. Это формулы исходного
листа FBY, а не подтверждение фактических тарифов хранения и возвратов для FBS.
Все входные поля калькулятора редактируются: в том числе ДРР, цена Пэй, объём, средняя миля,
стоимость одного невыкупа, хранение и его срок, габариты, категория и параметры выплат.
Ручные значения действуют только в сценарии, до очистки поля, сброса или закрытия карточки.
Очистка возвращает значение из исходных данных или формулы. Заданный вручную объём участвует
в расчёте средней мили и хранения; ручная средняя миля — в расходе на один невыкуп.
Явно заданный зависимый расход имеет приоритет и сохраняется при изменении исходных параметров
и пересчёте тарифа API. Нулевые значения также считаются явным вводом.
Ввод ДРР сразу включает ручной режим, очистка возвращает недельный расчёт и его подсветку.
Цена Пэй остаётся справочной и не меняет формулу прибыли. Ручная цена покупателя сохраняется
при изменении цены продавца; без ручного значения действует расчёт по последнему СПП.
Старые сохранённые `return_cost`, `storage_per_day`, `storage_days` игнорируются автоматической
базой; их можно переопределить в сценарии. API постоянных настроек эти поля не сохраняет.
Закрытые исторические дни не пересчитываются.

Версия 4 проверена на 161 корректной строке листа уже с расчётом возвратов и хранения из
габаритов и оборачиваемости: прибыль, ROI, маржинальность и все расходы совпали. Проверены
310 сценариев через обработчик калькулятора (155 активных товаров × две схемы), границы
ставок хранения, объёмы 1/30/200 л и лимит 5500 ₽, отсутствие габаритов, выкуп 0/100%,
приоритет формул над старыми ручными суммами и повторный расчёт тарифа API. У 155 активных
локальных товаров габариты заполнены. При исходных данных строки `153985484` и изменении
оборачиваемости на 150 дней хранение равно 49,61 ₽, прибыль — 162,00 ₽.

Успешная доставка остаётся суммой услуг из
[`POST /v2/tariffs/calculate`](https://yandex.ru/dev/market/partner-api/doc/ru/reference/tariffs/calculateTariffs)
или ручной настройки; она не заменяется суммой `AP + AQ`. Для возвратов используется отдельная
средняя миля по формуле таблицы, а не составляющая API-доставки. Совпадение формул не означает
совпадения итогов при разных исходных данных или при сравнении фактической рекламы с плановым ДРР.

Проверка редактирования 16 сентября 2026: все 36 полей проходят через обработчик в FBY и FBS
(72 сценария); сброс проверен на 310 конфигурациях активного ассортимента. Проверены приоритет
ручных расходов, нулевые значения, пересчёт зависимостей, сохранение при обновлении тарифа и
неизменность базы после сценариев. В браузере подтверждены ввод, очистка, недельный ДРР
и полный сброс. Проверки выполнялись с `PRAGMA query_only=ON`.

### Фиксированная база налога (версия 5)

Поле «База налога» удалено из калькулятора, параметров и постоянных настроек ЯМ.
Налог = цена покупателя с СПП, без скидки Пэй × налоговая ставка / 100.
Старые значения `tax_base` в БД игнорируются, API больше не принимает этот параметр.
Без цены покупателя расчёт сообщает о недостающих данных; при цене 0 налог равен 0.
Закрытые исторические дни не пересчитываются.

### Цена без убытка

Внизу калькулятора осталась кнопка «Цена без убытка»; кнопки пересчёта тарифа API и перехода
к закупке/расходам удалены. Постоянные настройки доступны через вкладку параметров и интеграции.
Кнопка использует действующие входные данные и ручные правки, недельный либо ручной ДРР,
сохраняет соотношения цен покупателя и Пэй к цене продавца и округляет цену продавца вверх
до 10 ₽, как WB. Налог по-прежнему считается от новой цены покупателя без Пэй.

Подбор использует ту же функцию расчёта прибыли, с неокруглённой прибылью: округлённый ноль
не должен скрывать доли копейки убытка. Проценты расходов фиксируются, суммы успешной доставки
и остальных услуг берутся из текущего расчёта. При обычном изменении только цены продавца
калькулятор использует последний сохранённый тариф как оценку, даже после истечения срока свежести витринных цен; остальные
параметры его запроса должны совпадать. Фактическая экономика и снимки по-прежнему требуют
совпадения цены. Нового запроса тарифа или отправки цены в Маркет кнопка не делает.

Если исходных данных нет, процентные расходы не оставляют положительной доли выручки либо
цена выходит за лимит калькулятора, отображается причина, введённые значения сохраняются.
Сброс убирает весь сценарий. API: `POST /calculate/{store}/{article}` с `break_even: true`
возвращает результат и `break_even_scenario` для дальнейших пересчётов.

Проверка на локальной БД только для чтения: из 310 конфигураций (FBY/FBS) в 148 цена найдена
и неокруглённая прибыль неотрицательна; для остальных исходных данных недостаточно либо
условия безубыточности невыполнимы. Отдельно проверены ручные расходы и ДРР, нулевые/пропущенные
цены, доли копейки, предельные проценты, повторный пересчёт и отсутствие вызовов API Маркета.
В браузере проверены обе схемы, подстановка цен, ручной ДРР, ошибка недостижимости и сброс.

### Сохранённые тарифы в плановом расчёте

Срок свежести витринной цены не удаляет тарифы из калькулятора. Последние известные приём
платежа, перевод платежа, доставка и прочие услуги продолжают использоваться до новой выгрузки.
Источник отмечается как «Последний загруженный тариф API»; `tariff.stale` показывает использование
сохранённого тарифа после срока свежести. Ручные значения, включая 0, сохраняют приоритет.
Действующая комиссия категории имеет приоритет над комиссией из резервного тарифа.
Цена может отличаться, остальные параметры запроса тарифа и схема должны совпадать.
Отсутствующие в БД компоненты не заменяются нулём. Правила текущей экономики и истории не меняются.

### Выбор категории в калькуляторе

В подробном расчёте вместо ID и текстового названия категории расположен поиск по полному
справочнику ЯМ и последовательный выбор уровней. При смене родителя прежние дочерние поля
удаляются. Конечная категория завершает ветку; промежуточная раскрывает следующий уровень.
Поиск поддерживает несколько слов из пути. Подсказки ограничены первыми 60 совпадениями.

Полное публичное дерево `/v2/categories/tree` хранится в `yandex_economics_sources` как
`category_tree` с пустыми магазином и артикулом, отдельно от товарных данных. Его обновляет
еженедельная выгрузка категорий, а при отсутствии актуального дерева — первое открытие
справочника. При ошибке API доступен последний сохранённый справочник с предупреждением.

`GET /categories/{store}` возвращает дерево доступного пользователю кабинета.
`POST /category-tariff/{store}/{article}` принимает только калькуляторный сценарий,
проверяет конечную категорию и запрашивает `/v2/tariffs/calculate` для выбранной модели,
цены, габаритов, веса и условий выплат. Комиссия выбранной категории имеет приоритет
над прежней комиссией товара. Ручные суммы остальных услуг, в том числе 0, сохраняются;
не заданные вручную компоненты обновляются из API. Ответ возвращает `category_scenario`,
который используется при дальнейших пересчётах и подборе цены без убытка.

До завершения ветки или получения комиссии старый результат скрыт. Устаревшие ответы
на быстрые изменения не применяются. После выбора категории изменения цены, габаритов
или условий тарифа вызывают новый запрос. Комиссию по-прежнему можно переопределить
вручную; выбор другой категории снова подставляет ставку API. Очистка поля услуги
восстанавливает тариф выбранной категории. Сброс возвращает исходную категорию товара.
Эти действия не меняют категорию/цены в Маркете и постоянные настройки товара в БД.

«Кампания магазина» — технический ID магазина для запроса тарифа (не реклама). При единственной
настроенной кампании нужной модели она выбирается автоматически. «Выплаты» и «Отсрочка» —
параметры тарифного API `frequency` и `paymentDelayWeeks`; отсрочка 0/1/2/4 недели допустима
только с еженедельным графиком. Сами настройки выплат в кабинете Маркета здесь не меняются.

Поля кампании, выплат и отсрочки убраны из калькулятора. Они доступны в постоянных настройках
кабинета/товара, откуда продолжают подставляться в запрос тарифа; при единственной подходящей
кампании сохраняется автоматический выбор.

Проверка 16 сентября 2026: загружены 11 026 узлов справочника; реальные запросы FBY/FBS
подтвердили комиссии выбранных категорий, сохранение ручных расходов и нулей, повторный
расчёт и подбор цены без убытка. В браузере проверены поиск по нескольким словам,
добавление/удаление уровней, ошибка кампании, сброс, смена схемы и восстановление ставки
API после очистки ручного значения. Проверочный процесс работал с БД только для чтения.
