# Учётные записи без матрицы доступа

С 10 октября 2026 года блок учётных записей хранит только `users`, `sessions` и
`activity_log`. Остальные бизнес-таблицы каталогов, остатков, операций, экономики,
синхронизаций и интеграций сохраняются.

У всех активных пользователей одинаковый доступ ко всем настроенным магазинам,
маркетплейсам, реализованным разделам и административным действиям. Полей роли,
профиля и индивидуальных разрешений больше нет. Автоматическое ограничение товаров
по совпадению ФИО с менеджером удалено; выбранный пользователем фильтр менеджера работает.

Вход по логину/паролю, проверка активности и срока сессии, выход и отзыв сессий
сохранены. Блокировка и смена пароля отзывают все сессии учётной записи.
Админ-панель позволяет создавать, блокировать, удалять сотрудников, менять пароль
и читать журнал с выгрузкой операций. Удаление и блокировка самого себя запрещены.
Защита последнего активного пользователя выполняется внутри транзакции: SQLite
использует `BEGIN IMMEDIATE`, PostgreSQL — блокировку строк пользователей.
Первый пользователь создаётся из прежнего файла `admin_seed_path`, без назначения роли.

API агентов остаётся только для чтения. Личные ключи и OAuth принадлежат владельцу:
чужие ключи нельзя получить или отозвать. Отключение пользователя прекращает доступ
по ключам. Проверки Origin, срока действия, поддерживаемых отчётов и площадок сохраняются.
Идемпотентность, бизнес-проверки складских операций, ограничения фоновых заданий и
проверки полноты экономики не изменяются.

`CHECKSTOCK_ECONOMICS_PREVIEW_ENABLED=1` открывает календарь и новую таблицу Ozon всем
активным пользователям, `0` выключает функцию. Если новая переменная отсутствует,
положительный прежний `CHECKSTOCK_ECONOMICS_PREVIEW_USER_ID` означает включение для всех.
Это общий переключатель функции, а не разрешение учётной записи.

Порядок и видимость колонок юнит-экономики сохраняются только в `localStorage`
браузера. Между устройствами эти настройки не синхронизируются. Endpoint
`PUT /api/unit-economics-1c/preferences/columns` удалён. Также удалены изменения
ролей, кабинетов и разделов пользователя, заявки и временные разрешения, уведомления
об этих заявках и неиспользуемые настройки SMTP.

## Миграция и выкладка

Миграция `app/repositories/identity_migration.py` запускается из `init_db()` **до**
`metadata.create_all()`. ORM, legacy SQL, сервисы, CLI и интерфейс больше не создают
и не читают удалённые таблицы. Миграция повторяема и выполняется одной транзакцией.

Удаляются `temporary_access_grants`, `access_requests`, `user_access_profiles`,
`user_marketplace_access`, `user_store_access`, `user_section_access`,
`user_ui_preferences`, `user_section_usage`, `user_usage_sessions` и поля
`users.role`, `users.can_edit_stock`, `users.can_manage_users`.
Идентификаторы, имена, логины, хеши паролей, активность, даты создания, сессии и журнал
сохраняются. `CASCADE` не используется; неожиданная зависимость прерывает миграцию.

1. Остановить приложение, фоновые процессы и другие записи в эту БД.
2. Сохранить текущую версию кода/образа и резервную копию БД. Для PostgreSQL использовать
   `pg_dump -Fc` и проверить архив через `pg_restore --list`.
3. Проверить новую версию на копии БД. Для SQLite команда ниже без `--apply` только
   показывает объём изменений; с `--apply` создаёт новый backup, проверяет его,
   применяет миграцию и сравнивает схемы/число строк оставшихся таблиц и содержимое
   пользователей, сессий и журнала:

   ```shell
   python -m scripts.ops.retire_account_acl --database data/checkstock.db
   python -m scripts.ops.retire_account_acl --database data/checkstock.db --apply
   ```

4. Обновить код и схему вместе. При PostgreSQL миграция выполнится при старте новой
   версии, после внешнего резервного копирования. Для старой SQLite требуется версия
   с поддержкой `ALTER TABLE DROP COLUMN` (3.35+).
5. Проверить вход, админ-панель, журнал, каталоги, операции, отчёты и личные ключи.
   Проверки: `python -m unittest discover -s tests -v`, существующие Node-тесты,
   линтер и форматирование изменённых Python-файлов.
6. Для отката остановить новую версию, восстановить **и прежний код, и backup**.
   Сначала сохранить новую БД отдельно: восстановление старого backup теряет записи,
   сделанные после него. Старый код с новой схемой несовместим.

## Следующая задача: матрица ролей и доступов

Спроектировать отдельно: перечень действий, чтение/изменение, охват магазинов и
маркетплейсов, управление сотрудниками и интеграциями, правила собственника ключей,
наследование и приоритет запретов, аудит изменений и миграция текущих пользователей.
Реализовать единый серверный механизм проверки и тесты каждого сочетания роли,
ресурса и действия; интерфейс должен отражать результат этих проверок. До этой задачи
индивидуальных исключений и скрытых проверок ФИО/ID нет.
