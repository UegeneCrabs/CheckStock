# Поставки на склады маркетплейсов

Страница `/stock/inbound` находится в меню «Сток → Поставки FBO» и открывается также из карточки магазина. Поддерживает WB (FBW), Ozon (FBO) и Яндекс Маркет (FBY) для всех магазинов из `app.core.stores.STORES`. Права на просмотр применяются к каждой паре «магазин — маркетплейс», включая запросы обновления. Магазины FBY Яндекса разрешаются через существующие настройки кампаний; при отсутствии явного списка используются кампании из API.

Фильтры: магазин, площадка, этап, поиск по артикулу/баркоду/названию/номеру, показ завершённых и отменённых поставок. Карточка раскрывает состав, плановое количество, приёмку и расхождения. Идентификаторы остаются строками, включая ведущие нули; апострофы не добавляются.

## Обновление

- Фоновая задача `inbound_supplies_sync` запускается через 90 секунд после старта приложения, затем каждые 30 минут после окончания предыдущего цикла.
- Интервал задаётся `CHECKSTOCK_INBOUND_SYNC_INTERVAL_SECONDS` (по умолчанию 1800, минимум 300).
- Задача включается существующим флагом фоновых обновлений. В разделе API можно включать и выключать её по магазинам и площадкам.
- Кнопка «Обновить поставки» запускает чтение API для выбранных доступных пользователю подключений. Раздел с правом только чтения эту кнопку не показывает.
- Повторный ручной запуск одного подключения ограничен одной минутой. Сохранённый в БД идентификатор запуска и двухчасовая аренда защищают от одновременной записи нескольких процессов. Просроченный процесс не может перезаписать результат нового.
- Три рабочих потока обрабатывают независимые подключения. Сбой одного магазина не останавливает остальные.
- WB использует общий существующий ограничитель API поставок. Все запросы `supply-order` Ozon используют общий адаптивный ограничитель. Для `/v1/supply-order/act/product/get` дополнительно сохраняется отдельная адаптивная пауза: успешные запросы списка и состава поставок не уменьшают задержку, вызванную ограничением актов. При недоступности/ограничении актов Ozon остальные акты в этом цикле не запрашиваются, состав поставок остаётся доступным.

## Хранение и учёт

Добавлена только таблица `inbound_supply_snapshots` в общей SQLAlchemy metadata. Создаётся при обычном запуске приложения; SQL совместим с SQLite и PostgreSQL. Таблицы каталога, ФФ, остатков маркетплейсов и перемещений новой функцией не изменяются. Каталог читается для дополнения названий и баркодов в пределах одного магазина и площадки.

В таблице хранится последний полный нормализованный снимок по каждой паре, даты попытки и успешного получения, ошибка и идентификатор выполняющегося обновления. Состав и статусы заменяются в одной транзакции. Ключи API и необработанные ответы площадок в снимок не попадают.

Если список или состав получен не полностью, повторяется страница или ответ не соответствует схеме, прошлый снимок сохраняется. Поставка, пропавшая из ответа без подтверждённого завершения, остаётся с пометкой о неподтверждённых данных. Она не считается достоверным количеством в карточках этапов. Отсутствие ключа показано отдельно от пустого списка поставок.

Успешное получение снимка может сопровождаться замечаниями к отдельным поставкам. Карточка подключения показывает их число и причины. Для недоступных актов Ozon различаются ограничение частоты (429), отсутствие доступа (401/403) и ошибка сервиса (5xx). Дата успешной загрузки снимка не означает, что фактическая приёмка подтверждена по всем поставкам.

Начальная загрузка читает открытые поставки без ограничения по возрасту; для завершённых загружает подробности за последние 90 дней. Ранее известные незавершённые поставки проверяются и вне этого окна. Уже загруженная история сохраняется. Пропавшие известные открытые поставки дополнительно запрашиваются по идентификаторам.

Если WB явно отвечает «поставка удалена» (HTTP 400) для ранее сохранённой поставки, отсутствующей в текущем списке, она сохраняется в истории со статусом «Удалена» и этапом «Отменено». Её состав остаётся доступным, незавершённое количество становится нулевым, повторные запросы этой поставки прекращаются. Остальные ошибки 400 прерывают обновление с сохранением прежнего снимка.

## Значение количеств

«В заявке» — заявленное количество, не фактический остаток в продаже. Карточки этапов суммируют заявленные количества соответствующих поставок; устаревшие и неподтверждённые данные исключены из суммы и явно отмечены. «Не завершено» — вспомогательная оценка:

- В планах: заявленное количество. Оно не считается отправленным.
- В транзите: заявленное количество, для WB за вычетом уже готового к продаже. Приёмка на промежуточной площадке не обнуляет товары, которые ещё перевозятся.
- На приёмке: положительная разница между заявленным и принятым по каждому товару. Если фактическое количество неизвестно, показывается «—».
- При размещении WB: разница между заявленным и готовым к продаже.
- При завершении/отмене: ноль; при споре или неподтверждённом статусе: «—».

Эти вспомогательные количества страницы FBO не меняют ТОТАЛ в блоке остатков, не списывают товары с ФФ и не выполняют приёмку во внутренних перемещениях. Для Google-выгрузки применяется отдельный потоварный расчёт, описанный ниже. Даты показаны в МСК.

## Особенности источников

**WB.** `/api/v1/supplies`, `/api/v1/supplies/{ID}`, `/api/v1/supplies/{ID}/goods`. Для черновиков используется `preorderID` с `isPreorderID=true`; связь сохраняется после появления номера поставки. Статус 6 трактуется с учётом транзитного склада. Статус 5 не означает автоматическую доступность всего товара: учитываются `acceptedQuantity` и `readyForSaleQuantity`. Приёмка в СЦ может предшествовать дальнейшей перевозке. Для привязки артикула к каталогу сначала используется однозначный баркод в текущем магазине WB.

**Ozon.** `/v3/supply-order/list` с обязательным фильтром всех поддерживаемых статусов; `/v3/supply-order/get`; `/v1/supply-order/bundle` отдельно для каждого `bundle_id`. Статус берётся у отдельной поставки внутри заявки. Факт приёмки — `/v1/supply-order/act/product/get` с числовым `supply_id`. Конфликтующие значения в нескольких актах не суммируются: показывается предупреждение и неподтверждённое количество. Недоступность актов не обнуляет план поставок. Черновик с незаполненным составом может быть пустым.

**Яндекс Маркет.** `/v2/campaigns/{campaignId}/supply-requests` и `/items`. Читаются входящие поставки, в том числе транзитные и дочерние. Вывоз, утилизация, инвентаризации и внутренние межскладские движения исключаются. Родительская мультипоставка не суммируется с дочерними; появившиеся дочерние заменяют ранее показанную общую заявку. `ACCEPTED_BY_WAREHOUSE_SYSTEM` — согласование заявки, а `TRANSIT_MOVING` — перемещение на склад вывоза, не входящий транзит. Баркод берётся из каталога по артикулу текущего магазина.

Документация источников: [WB FBW](https://dev.wildberries.ru/docs/openapi/orders-fbw), [статусы WB](https://seller.wildberries.ru/instructions/ru/ru/material/statuses-for-fbw-shipment), [Ozon](https://docs.ozon.ru/api/seller/#operation/SupplyOrderList), [Яндекс Маркет](https://yandex.ru/dev/market/partner-api/doc/ru/reference/supply-requests/getSupplyRequests).

## Проверка

Автоматические тесты удалены вместе с прежним набором тестов проекта.

`python scripts/diagnostics/check_inbound_access.py` проверяет небольшую выборку реальных API по сохранённым ключам каждого магазина. Скрипт не открывает БД и не печатает ключи или товарные строки; для Ozon дополнительно проверяет акт завершённой поставки. Это проверка подключений и формы ответов, не полная синхронизация.

Перед обновлением работающего сервера следует сделать согласованный бэкап его БД обычным способом (для PostgreSQL — `pg_dump`). Для этой функции не требуется переносить или заменять файл БД и не требуется очищать существующие таблицы.

## Выгрузка в Google Таблицы

В разделе `/admin/integrations?tab=google` [общая выгрузка семи проектов](project-sheet-export.md) записывает КЛЮЧ в формате «ПРОЕКТ БАРКОД» в A, проект в B, артикул, штрихкод и название в C:E, основные количества в F:K и разбивку нераспределённых остатков по ФФ начиная с L. F (ТОТАЛ) равен сумме G:K: ФФ + FBS + FBO + в пути между ФФ + в пути на склады МП. J — «В ПУТИ МЕЖДУ ФФ», K — «В ПУТИ НА СКЛАДЫ МП». Шапка находится в строке 2, товары начинаются со строки 3. В строке 1 записываются дата выгрузки в A1:B1 и формулы суммы от F1 (ТОТАЛ) до последнего выгружаемого столбца; C1:E1 очищаются. Формулы суммируют товары с третьей строки, например `=SUM(F3:F)`. Значения, включая ТОТАЛ, записываются числами (`RAW`), пересчитываются при каждой выгрузке.

Каждый ФФ получает колонку «ДОСТУПНО ФФ ДЛЯ РАСПРЕДЕЛЕНИЯ — название ФФ». Включаются все ФФ из справочника, а также названия, встречающиеся в остатках семи проектов выбранной площадки; порядок алфавитный, пустые остатки записываются нулями. Разбивка и сумма G рассчитываются из одного чтения `ff_stock` для каждого магазина с тем же сопоставлением артикулов, что и остальные показатели. Одинаковые артикулы разных проектов остаются отдельными строками. Детализация раскрывает G и не добавляется к ТОТАЛ повторно.

После успешной записи данных на каждом затронутом листе стоков и FBS-заказов в A1 появляется «Выгрузка (МСК)», в B1 — фиксированная дата и время по Москве в формате `dd.mm.yyyy hh:mm:ss`. B1 хранит числовую дату Google Sheets, а не текст или формулу `NOW()`. Значения A1:B1, формулы сумм первой строки остатков и формат даты B1 записываются одним запросом после товарных данных; остальное оформление не меняется. Время относится к записи этого листа, а не запуску общей задачи или синхронизации API площадок. При ошибке записи данных новая отметка успеха не записывается; отключённые и невыбранные листы не затрагиваются. Успешная запись с предупреждением о давности или неполноте поставок также получает отметку времени. Подтверждённые сохранённые значения остаются в K/ТОТАЛ; при отсутствии подтверждённых количеств эти ячейки остаются пустыми.

Кнопки «Выгрузить остатки» и «Выгрузить заказы» также сохраняют дату успешной
общей выгрузки в БД: используется время фактической записи листа. Дата сразу
показывается в результате и сохраняется после перезагрузки страницы. Отдельная
ручная выгрузка не меняет время попытки полной выгрузки, поэтому не откладывает
её расписание. Ошибка или пропуск записи не обновляют дату успеха.

После успешной записи, в том числе отдельной выгрузки стоков или FBS-заказов, старая ошибка сбрасывается. Уже сохранённая историческая ошибка не показывается на странице, если дата успеха не раньше неудачной попытки. Более новая ошибка сохраняется; неуспешная или пропущенная запись её не сбрасывает. Время попытки полной выгрузки при отдельном запуске не меняется, чтобы не откладывать расписание. Ошибка загрузки заказов указывает проект и площадку, а ошибка назначения — проблемный лист.

Клиент Google использует тайм-аут 120 секунд и до двух повторов запроса при временных ошибках, поддерживаемых библиотекой Google API. Повторяется тот же запрос с теми же значениями; очистка, запись и форматирование идемпотентны. Если после записи товарных данных не удалось подтвердить запрос отметки времени, ошибка явно сообщает об этом: товары уже записаны, но успешное завершение всей операции не подтверждено.

На листе остатков прежние значения и формулы, в том числе A1:B1, не проверяются и не блокируют выгрузку: лист полностью перезаписывается. Объединения снимаются автоматически. На листе FBS-заказов сохраняется проверка A1:B1: разрешены пустые ячейки или собственная прежняя отметка; чужие данные, формулы и объединения останавливают запись. Формат числовой даты описан в [документации Google Sheets](https://developers.google.com/workspace/sheets/api/guides/formats).

J получает сумму `sent_quantity - received_quantity - cancelled_quantity` по активным перемещениям ФФ. Используются магазин, маркетплейс и артикул назначения, чтобы перенос между площадками не учитывался дважды. K получает незавершённое количество из сохранённых поставок МП в транзите, на приёмке и размещении. Черновики и отменённые поставки исключены.

В WB расчёт выполняется отдельно по каждому товару. После завершённой приёмки (`statusID=5`) K равен `max(acceptedQuantity - readyForSaleQuantity, 0)`: недостача не является товаром в пути, а готовые к продаже единицы исключаются. Это применяется и к поставкам с общим статусом «Расхождения». При продолжающейся приёмке используется `max(quantity - readyForSaleQuantity, 0)`, чтобы принятые, но ещё не готовые к продаже товары не терялись. При неизвестном необходимом счётчике значение остаётся неподтверждённым только для соответствующего артикула. Значения и статусы API описаны в [документации WB](https://dev.wildberries.ru/openapi/orders-fbw).

Для Ozon `COMPLETED` и Яндекс Маркета `FINISHED` количество в пути равно нулю, даже если завершённая поставка отмечена расхождением по недостаче, излишкам или браку. Незавершённые споры и неизвестные статусы не подменяются нулём. Для открытых поставок Ozon и Яндекса сохраняется расчёт: в транзите — заявленное количество, на приёмке — положительная разница между заявленным и принятым. Принятое на транзитной площадке не считается окончательно доставленным на склад хранения.

Условие учёта: отправка должна быть отражена обычной отгрузкой с ФФ, которая уже уменьшает его остаток. Внутреннее перемещение также сразу списывает товар с исходного ФФ; приёмка увеличивает остаток назначения и уменьшает J. Связи внешней поставки МП с конкретным списанием ФФ в данных нет: выгрузка не пытается повторно списывать товар или угадывать неоформленные отгрузки. Независимые снимки FBO-остатков и поставок могут обновляться в разное время; автоматической сверки исторических расхождений этот расчёт не выполняет.

Google-выгрузка только читает эти данные из БД: не запускает приёмку, не списывает остатки и не обращается к API площадок за поставками. Поставки обновляются отдельной задачей, описанной выше. Если сохранённый подтверждённый снимок устарел или последняя синхронизация завершилась ошибкой, выгрузка использует последние корректно сохранённые значения и сообщает о давности данных в предупреждении. Срок актуальности — два интервала синхронизации, но не меньше часа; его превышение само по себе не обнуляет количества и не делает K и F (ТОТАЛ) пустыми. Если подтверждённого снимка нет либо количество неизвестно для отдельного артикула, K и F соответствующих товаров остаются пустыми. Подтверждённое отсутствие незавершённых поставок даёт числовой 0 и позволяет рассчитать полный ТОТАЛ.

Все семь проектов записываются на общий лист выбранной площадки с колонкой КЛЮЧ в A и ПРОЕКТ в B. ROCKKIDDO и TOYKA остаются отдельными проектами, совпадающие артикулы между ними не суммируются. Возраст и ошибки снимка одного проекта не отменяют подтверждённые значения остальных. При отсутствии подтверждённых данных K и ТОТАЛ остаются пустыми только в затронутых строках. Предупреждения возвращаются в отчёте выгрузки и показываются после ручного запуска. Товар в активной поставке или перемещении не теряется, даже если его уже нет в текущем каталоге; закрытые нулевые позиции не добавляются из истории поставок.

При каждой выгрузке стоков весь выбранный лист очищается от значений и формул, включая первую строку и старые колонки за пределами новой выгрузки. Затем записываются текущая шапка, товары, дата и формулы сумм. Все объединения на этом листе снимаются; оформление сохраняется, кроме штатного формата даты B1. При необходимости строки и колонки добавляются до очистки. Даже при пустом каталоге остаются минимум три строки, чтобы формулы сумм возвращали 0. Лист FBS-заказов заменяет A2:C, включая ПРОЕКТ в A. Порядок перехода на общую конфигурацию описан в [project-sheet-export.md](project-sheet-export.md).
