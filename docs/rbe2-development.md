# RBE 2: локальная разработка и сверка

Состояние на 19 октября 2026 года: отдельная вкладка, операционная корзина,
расчёт полных расходов, диагностика и тесты реализованы локально.
Публикации, push, изменения production-БД и перезапуска сервера нет.
Полное совпадение прибыли с Pidata пока не подтверждено.
По решению пользователя считаем только прибыль до налогов.

## Изоляция

Финансовый RBE, его /api/report и реестр первой финансовой даты возврата
не меняются. Запись только в rbe2_snapshots и rbe2_runs.
Исходная БД CheckStock открывается через mode=ro и PRAGMA query_only=ON.
Старые P&L-итоги не используются в новых формулах.
Себестоимость — только магазинная, на конкретную дату, без общей цены.

Автообновления RBE 2 нет. GET читает снимки, загрузку запускает администратор.
Общая блокировка с финансовой загрузкой, пауза между кабинетами 125 секунд.
Окно до 7 дней, не старше 90 дней, без будущих дат; возвраты от свежих к старым.
Пропущенная страница операционных данных не заменяет прежний снимок.
Ошибка расходов сохраняет успешно полученные выкупы, но запуск становится
частичным, а расходы/прибыль — неполными. Старое перекрывающееся окно расходов
не маскирует последнюю неудачную проверку зелёным статусом.

## Корзина

- POST /v2/reports/united-orders/generate: выкупы по deliveryDate и статусу
  доставки. Позднейший возврат не удаляет исходный валовый выкуп.
- POST /v2/campaigns/{campaignId}/stats/orders с updateFrom/updateTo,
  а недостающие первоначальные товары возвратов — по явным ID заказов.
- GET /v2/campaigns/{campaignId}/returns: type=RETURN, fromDate=toDate=день,
  все статусы и страницы. Дата — принадлежность дневной выборке API, не банк.
  После обновления Яндекса старый состав выборки может измениться.
  Это отличается от фиксированной финансовой даты исходного RBE.
- REFUND_IN_PROGRESS признаётся после передачи товара (RECEIVED, IN_TRANSIT,
  FULFILMENT_RECEIVED и последующие состояния). Пустой статус/CREATED —
  pending_returns, без уменьшения продаж. REFUNDED, REFUNDED_WITH_BONUSES,
  REFUNDED_BY_SHOP допускаются без физической отправки.
  Отменённые/отклонённые заявки, CANCELLED/EXPIRED исключены.
  Правило проверено на контрольной неподтверждённой заявке; это не утверждение
  о наличии опубликованной спецификации внутреннего алгоритма Pidata.
- Идентичность возврата: магазин + бизнес + кампания + return ID.
  Дубли страниц и пересечения снимков не удваивают количество.
  Превышение исходного купленного количества блокирует итог, а не обрезается.
  Новая отмена исключает заявку, успешный пустой ответ заменяет старый день.
  Дневной набор сверяется с недельным; несовместимый снимок не сохраняется.
- Отмены отделены от возвратов: полная/частичная отмена заказов, созданных
  в выбранный период, исходное количество initialCount.

## Полные расходы

summaryCommission/saleCommission по заказам могут быть уменьшены баллами.
Они оставлены только в диагностическом order_report_expenses и не используются
для прибыли с полным оборотом продавца.

При ручной загрузке отдельно запрашивается свежий отчёт стоимости услуг:
POST /v2/reports/united-marketplace-services/generate.
Он не определяет корзину выкупов; отчёт платежей и старый финансовый P&L
не запрашиваются. Исходные исторические комиссии читаются из архива
CheckStock без записи и без запросов периодов старше 90 дней.

- Комиссия: placement.amountWithoutBonuses / count исходного заказа + SKU
  × количество выкупов минус та же исходная комиссия × количество возвратов.
  Технический отрицательный totalAmount не вычитается повторно.
  Нет исходной комиссии — есть подтверждённый подытог, но нет полного итога.
- Логистика: delivery.servicePrice; crossregional_delivery.servicePrice
  + netting, транзит и другие явно классифицированные услуги.
  Сторно сохраняет знак, баллы не прибавляются второй раз.
- Реклама: буст postpaid, показы/полки/баннеры payment.
  Предоплата и бонусная оплата требуют отдельной сверки.
  Общая реклама учитывается один раз, не умножается на число магазинов.
  Рекламный campaignId не является ID магазина.
  Без доказанной привязки к выбранному складу расход остаётся unallocated,
  а не распределяется произвольно.
- Эквайринг, обработка возвратов, утилизация и другие расходы — один раз
  по дате начисления. Неизвестный лист/отсутствующая сумма — не нулевая услуга.
- Выручка = продажи минус возвраты − комиссия − логистика.
  Расчётное перечисление = выручка − реклама − эквайринг и прочие услуги.
  Прибыль до налогов = перечисление − магазинная себестоимость.
  Фактическая выплата банка и прибыль после налогов — другие показатели.
  При недостающих обязательных входах итог null, подтверждённые части
  видны отдельно и не получают зелёный статус.

## Проверки

tests/test_rbe2.py и tests/test_rbe2_expenses.py: даты, отмены, ожидающие
заявки, дубли, магазинные цены, полные комиссии, сторно, нулевой успешный
отчёт и ошибка API, однократная реклама кабинета, ограничение кампаний,
перекрытия версий, инвалидация расходов после неудачной загрузки,
неизменность исходной БД. tests/test_rbe2_ui.cjs: отдельные URL, права,
безопасный текст, подтверждённая часть без ложного зелёного статуса,
локальный предпросмотр без запросов. Регрессия исходного RBE отдельно.
Личные выгрузки, реальные заказы и ключи не включаются в Git.
