# Выпуск CheckStock на сервер

`master` — ветка разработки. `dev-release` указывает на подготовленную к выпуску
версию. Обновление `dev-release` не запускает деплой. Деплой запускает только
новый тег вида `vMAJOR.MINOR.PATCH` на коммите `dev-release`. Все три компонента
номера — неотрицательные целые без ведущих нулей; номер должен быть строго
больше каждого ранее опубликованного корректного релизного тега.

## Однократная настройка

1. Убедитесь, что работающий Compose-проект и Git checkout находятся в
   `/home/checkstock`, сервис `db` здоров, `.env` и `secrets/` находятся на сервере.
   После выпуска команды Compose выполняются из корня репозитория с
   `--env-file .env -f deploy/docker-compose.yml`.
   Относительные пути в Compose-файле, включая профиль seccomp, отсчитываются
   от каталога `deploy/`.
   Сценарий не создаёт новый сервер и не переносит данные.
   Если текущий checkout ещё содержит корневой `docker-compose.yml`, первый
   выпуск использует его для проверки и резервного копирования БД, а после
   переключения коммита — `deploy/docker-compose.yml`.
2. Создайте `/home/bd_backup` с доступом на запись для пользователя деплоя.
   Выделите место как минимум для трёх полных дампов. Желательно дополнительно
   копировать их на другой сервер или диск.
3. Создайте отдельного SSH-пользователя для деплоя. Ему нужны права на Git checkout,
   Docker Compose и каталог бэкапов. Дайте серверу доступ на чтение GitHub-репозитория.
   Сохраните приватный ключ для доступа Actions к серверу только в GitHub Secrets.
4. В GitHub задайте Secrets `DEV_DEPLOY_HOST`, `DEV_DEPLOY_USER`,
   `DEV_DEPLOY_SSH_KEY`, `DEV_DEPLOY_KNOWN_HOSTS` и, если SSH использует
   нестандартный порт, Variable `DEPLOY_PORT`. Значение `DEV_DEPLOY_KNOWN_HOSTS`
   получите после проверки отпечатка ключа сервера, например через
   `ssh-keyscan -H SERVER`; не отключайте проверку
   ключа. Разрешите Actions и ограничьте обновление `dev-release` и тегов `v*`.
5. Для первого выпуска убедитесь, что существующий checkout не имеет изменений
   отслеживаемых файлов. Если прежних релизных тегов нет, выбранный тег становится
   начальным. На сервере тег нового выпуска также сравнивается с тегом текущего
   коммита, если такой тег есть. Теги для текущего коммита должны быть доступны
   в серверном checkout; для первого выпуска из checkout без тегов дополнительное
   сравнение на сервере не выполняется.

## Выпуск версии

Работайте в чистом локальном checkout. Замените `0.2.0` выбранным номером,
который строго больше всех прежних тегов вида `vMAJOR.MINOR.PATCH`:

```bash
git switch master
git pull --ff-only origin master
git fetch --tags origin
# Если в master есть ещё не отправленные коммиты:
git push origin master

git switch dev-release
git pull --ff-only origin dev-release
git merge --ff-only master
git push origin dev-release
```

Если `dev-release` ещё не создана, вместо `git switch dev-release` выполните
`git switch -c dev-release master`, затем `git push -u origin dev-release`.
При обычном выпуске `dev-release` должен продвигаться до выбранного коммита
`master` без дополнительных коммитов.

После отправки `dev-release` создайте тег на этом коммите и отправьте его:

```bash
git tag v0.2.0
git push origin v0.2.0
```

Дождитесь результата **Deploy CheckStock release** в Actions. Не повторяйте
старый тег для повторной установки: выпуск новой версии требует нового номера.
Тег с неверным форматом, не возрастающим номером или коммитом вне `dev-release`
будет отклонён до подключения к серверу.

## Что делает деплой

Workflow проверяет формат и рост тега относительно ранее опубликованных релизных
тегов, присутствие коммита в `dev-release`, Ruff и сборку Docker-образа. Далее
сценарий на сервере проверяет чистоту checkout, рост тега относительно текущего
развёрнутого тега (если он есть) и здоровую БД. Он создаёт дамп PostgreSQL в
`/home/bd_backup/checkstock-YYYYMMDD-HHMMSS-vX.Y.Z.dump` (время UTC) и проверяет
его через `pg_restore -l`. SSH-клиент отправляет keepalive каждые 30 секунд,
чтобы соединение не простаивало во время длительного дампа. Только после бэкапа
скрипт переключает checkout на коммит тега, собирает образ и обновляет `app`,
`scheduler`, `watchdog`.
Сервис `db` и Docker volumes не удаляются. Успех требует здорового `app` (его
healthcheck обращается к `/readyz`), здорового `scheduler` и работающего
`watchdog`. После этих проверок сценарий оставляет три последних успешных дампа
CheckStock. Временные и посторонние файлы не удаляются.
Во время проверки сценарий сообщает состояние каждого сервиса. Если сервис не
прошёл проверку, журнал Actions содержит состояние контейнера, последние
результаты healthcheck и 40 последних строк его логов перед откатом.
Журнал также показывает этапы переключения кода, проверки Compose, сборки образа
и запуска контейнеров; при ошибке перед откатом указывает этап и код выхода.
Ошибка создания или проверки дампа останавливает выпуск до смены кода.

При неуспехе после переключения кода сценарий возвращает прежний коммит,
пересобирает прежний образ, запускает сервисы и проверяет их здоровье. Если
восстановить здоровые сервисы не удалось, журнал явно сообщает об этом. Проверьте
журнал Actions и состояние сервера; если новая версия успела изменить схему БД,
откат одного кода может быть недостаточен.

## Проверка и восстановление БД

Список дампов: `ls -lh /home/bd_backup/checkstock-*.dump`. Проверка структуры:

```bash
cd /home/checkstock
docker compose --env-file .env -f deploy/docker-compose.yml exec -T db pg_restore -l \
  < /home/bd_backup/checkstock-YYYYMMDD-HHMMSS-vX.Y.Z.dump > /dev/null
```

Для восстановления сначала остановите `app`, `scheduler` и `watchdog`, чтобы
они не меняли данные. Сохраните отдельную копию текущей БД, даже если она
неработоспособна. Затем восстановите выбранный дамп:

```bash
cd /home/checkstock
docker compose --env-file .env -f deploy/docker-compose.yml stop app scheduler watchdog
docker compose --env-file .env -f deploy/docker-compose.yml exec -T db sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > /home/bd_backup/emergency-before-restore.dump
docker compose --env-file .env -f deploy/docker-compose.yml exec -T db sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" exec pg_restore --clean --if-exists --create --exit-on-error -U "$POSTGRES_USER" -d postgres' \
  < /home/bd_backup/checkstock-YYYYMMDD-HHMMSS-vX.Y.Z.dump
```

Проверьте журнал восстановления, верните соответствующую версию кода и запустите
сервисы через `docker compose --env-file .env -f deploy/docker-compose.yml up -d app scheduler watchdog`. Восстановление
удаляет изменения данных после даты дампа, поэтому его выполняют вручную после
оценки последствий. Перед первым рабочим релизом проверьте эту процедуру на
отдельной тестовой БД.
