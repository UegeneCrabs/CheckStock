# Автоматические загрузки и восстановление расписания

Статус на 19 октября 2026 года: `app/jobs/background.py` регистрирует четыре
асинхронные задачи из `app/jobs/ozon.py`: заказы, цены с комиссией FBO, закрытие
дневной истории и подробную рекламу. Прежние загрузчики заказов и рекламы Ozon
исключены из расписания; [состояние объединения](architecture.md#состояние-объединения-19-октября-2026).

Цены Ozon: `ozon_prices_sync` асинхронно обновляет четыре цены каждый час, `ozon_prices_daily_close` закрывает дневную историю в 00:00 МСК. Обе задачи поддерживают ручной запуск и общую блокировку на кабинет. [Источники, хранение и восстановление](ozon-prices.md).

Веб-приложение и автоматические загрузки работают отдельными процессами.
`app.jobs.background` содержит описания задач и общую инициализацию;
`app.jobs.worker` запускает автоматические циклы. `lifespan` веб-приложения
не создаёт задач расписания. Ручные загрузки продолжают работать через HTTP
и используют те же обработчики и блокировки.

## Запуск

Для локальной работы из корня проекта с активированным окружением выполните одну команду:

```shell
python run.py
```

Она запускает сайт на `http://127.0.0.1:8000` с перезагрузкой при изменениях Python-файлов
в `app/` и отдельный планировщик. Оба процесса используют интерпретатор текущего окружения,
корень проекта как рабочий каталог и выводят логи в текущий терминал. Перезагрузка сайта
не перезапускает планировщик. Перед запуском проверяется доступность порта 8000;
если он занят, планировщик не запускается.

`Ctrl+C` передаёт обоим процессам сигнал штатного завершения. Через 60 секунд
оставшиеся процессы этого запуска завершаются принудительно. Неожиданное завершение
любой службы останавливает другую и возвращает ненулевой код. Команда не останавливает
процессы, запущенные отдельно в других терминалах.

Оркестрация и слежение за Python-файлами через `watchfiles` находятся в `app/development.py`.
Перезагрузкой управляет эта команда; встроенный `uvicorn --reload` не используется,
чтобы сигналы перезагрузки на Windows не конфликтовали с управлением двумя службами.
На Windows каждая служба до старта включается в отдельный Job Object
(`app/infrastructure/process_job.py`), чтобы при завершении запуска или перезагрузке
сайта не оставались дочерние процессы. На POSIX используются отдельные группы процессов.
Параметры локального запуска и ожидания завершения собраны в `DEVELOPMENT`
в `app/core/constants.py`. Команды Docker и серверного запуска не меняются.

Для раздельного запуска используйте два терминала:

```shell
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
python -m app.jobs.worker
```

Доступны также `make run` и `make scheduler`. Процессы должны использовать
одинаковые настройки, доступы и БД. Для SQLite это один абсолютный путь
`CHECKSTOCK_DB_PATH` и общий каталог файловых блокировок; для PostgreSQL —
одинаковая целевая БД. При одновременном старте инициализация схемы и начальных
настроек сериализуется блокировкой `application_initialization`.

В Docker сервисы `app` и `scheduler` используют один образ, общие настройки
и необходимые тома. Обычный запуск:

```shell
docker compose up --build -d
docker compose logs --follow app scheduler
```

При первом переходе на отдельный планировщик остановите старый `app` со
встроенными задачами, затем пересоберите и запустите новую версию и `scheduler`.
Нельзя оставлять старый планировщик работающим рядом с новой версией: старый код
не проверяет сохранённое расписание. Перезапуск нового `app` не перезапускает
автоматические загрузки.

Существующие переключатели сохраняются: `CHECKSTOCK_DISABLE_BACKGROUND_SYNC`,
отдельные флаги воронки и цен 1С, настройки задач, магазинов и маркетплейсов.
Флаги воронки и цен 1С по-прежнему могут включать свои группы при отключённой
общей фоновой синхронизации. Эти параметры теперь применяет worker.

## Сохранённое расписание

Таблица `sync_job_schedules` содержит имя задачи, следующий срок в UTC,
номер попытки текущего цикла, идентификатор незавершённого запуска и время
обновления. Таблица создаётся существующим механизмом схемы без удаления
истории или настроек.

При первом появлении задачи используется прежний `sync_job_states.next_run_at`,
если он заполнен корректно; иначе действуют существующие стартовые задержки.
После этого расписание читается из `sync_job_schedules`, включая после
перезапуска процесса. Изменённые интервалы применяются при расчёте следующего
срока, уже сохранённый срок при старте не пересчитывается.

Перед запуском исполнитель берёт общую блокировку задачи и повторно проверяет
срок в БД. Начало попытки и её запись в `sync_job_runs` сохраняются до вызова
загрузчика. Завершение, следующий срок, счётчик повторов и отображаемый статус
фиксируются одной транзакцией. Блокировка удерживается до завершения записи.
Второй процесс после получения блокировки увидит новый срок и не повторит
завершённую плановую попытку. Ручной запуск использует ту же блокировку.

В PostgreSQL соединения, удерживающие блокировки на время загрузки, отсоединены
от общего пула. Поэтому длительные задачи не занимают слоты, необходимые
загрузчикам для чтения и записи данных; после освобождения блокировки такое
соединение закрывается.

После простоя выполняется **одна актуальная загрузка** по просроченной задаче.
Каждый пропущенный интервал не воспроизводится. Обработчики сохраняют свои
проверки актуальности, времени работы и необходимости загрузки, включая FTP.

Если свободная блокировка сопровождается незавершённым запуском в расписании,
предыдущая попытка отмечается ошибкой. Для Ozon она расходует одну попытку
текущего цикла и далее действует политика повторов. Для задач без такой политики
планируется один восстановительный запуск. После аварийного обрыва загрузка
может выполняться повторно: это не гарантия однократного внешнего действия.
Заказы сохраняются через upsert по существующим ключам строк.

Зависимые задачи ждут `catalog_ready`. Если сохранённый срок каталога ещё не
наступил, проверка расписания освобождает сигнал; если просрочен — сначала
проходит попытка каталога. Ошибка самой загрузки или отключение каталога также
освобождают сигнал, как раньше: сигнал не является подтверждением полноты данных.

## Ошибки и повторы

Ошибка проверки настроек, доступа к расписанию или обработчика завершения
логируется; цикл повторяет проверку через 60 секунд. Ошибка одной задачи
не завершает другие. Если начало попытки не удалось записать в БД,
загрузчик не вызывается. Занятая блокировка не расходует попытки.

Для синхронных задач `resource_locks` задаёт дополнительные общие блокировки.
Они берутся вместе с блокировкой задачи до чтения расписания и регистрации попытки;
при занятости любой из них уже взятые блокировки освобождаются.

Недельные Google-выгрузки работают отдельными асинхронными задачами
`google_week_update` (WB), `google_week_update_ozon` и `google_week_update_yandex`.
Метаданные находятся в `JOBS.google_weeks`, действия и расписания — в независимых
профилях площадок. Каждая задача раз в минуту проверяет своё расписание и ежедневное
обновление списка листов. Прежняя отдельная задача `google_sheet_catalog` больше
не запускается. Сохранение настроек, обновление списка и ручные действия используют
блокировку своей площадки; операции с одним Google-документом дополнительно
сериализуются. [Контракт трёх недельных блоков](google-week-update.md).

Ответ Ozon `403` с причиной `not available with existing subscription` отображается
как ограничение текущей подписки. Он не означает, что API-ключ отозван. Загрузка отзывов
при такой ошибке сохраняет предыдущий снимок, а очередная попытка остаётся в обычном
суточном расписании. Остальные задачи Ozon продолжают работать.

Для `ozon_unit_economics_turnover_sync` действуют почасовое расписание
и три повтора: через **60, 300 и 900 секунд после завершения предыдущей
неудачной попытки**. Всего — максимум четыре попытки за цикл. Ошибкой считаются
исключение и частичный результат с `ok=False` или `status="error"`, включая
вложенные результаты магазинов.

Каждая попытка заново выбирает включённые магазины с доступами и вызывает обычную
загрузку заказов за последние 21 календарный день. Повторяются все выбранные
магазины. После успеха или исчерпания попыток счётчик сбрасывается и назначается
следующий часовой запуск. Отключение задачи отменяет ожидающие повторы при ближайшей
проверке, не позднее обычного интервала опроса в 60 секунд.

Повторы применяются к четырём асинхронным задачам Ozon. Остальные интервалы, отсчёт
от начала выполнения и собственные правила FTP сохраняются. При успехе FTP
следующий срок относится к следующему окну, даже если результат текущей попытки
ещё не записан. Ручной FTP-запуск обновляет сохранённый срок; остальные ручные
запуски, включая Ozon, автоматическое расписание не сдвигают.

## Асинхронные заказы Ozon

`ozon_unit_economics_turnover_sync` описана как `AsyncBackgroundJob`.
Worker выполняет её через `await`; ручная кнопка использует тот же обработчик.
Цепочка загрузки:

```text
worker / HTTP → async_scheduling / async_tracking
  → jobs.ozon.run
  → orders.ozon_async.sync_configured_store → sync_store
  → ozon.async_api.AsyncSellerApi → каталог по SKU при отсутствии артикула
  → OzonPosting.prepare → orders.normalizers.ozon.normalize_postings
  → AsyncOrdersRepository.save
```

`jobs.ozon.run` один раз определяет общий период в 21 календарный день по Москве,
убирает повторяющиеся магазины и запускает все выбранные магазины с доступами
как задачи `asyncio.TaskGroup`. Ограничения на три магазина нет. Внутри магазина
страницы API и схемы FBO/FBS обходятся последовательно; ожидание сети одного
магазина позволяет продолжать работу остальных. Результаты возвращаются в
порядке входного списка. Ошибка магазина сохраняется в его результате и не
прерывает другие магазины; отмена всей загрузки распространяется на дочерние задачи.

Доступы проверяются внутри задачи магазина. Исключение на этом этапе сохраняется
через пустой `OrderSaveBatch`: `sales_sync_state` и `sync_health` получают ошибку
и время попытки в одной транзакции. Старые заказы и `last_success_at` сохраняются.
Если запись ошибки тоже не удалась, отчёт содержит причины `CREDENTIALS` и `SAVE`.
Магазины без настроенных доступов по-прежнему пропускаются.

`AsyncResources` создаётся отдельно в каждом веб-процессе и worker и владеет
одним `httpx.AsyncClient`, асинхронными подключениями БД и ручными задачами.
Ключи передаются в заголовках отдельного запроса. Контекст магазина в логах
хранится в `ContextVar`. HTTP-повторы при сетевых ошибках, 429 и 5xx используют
`asyncio.sleep`, учитывают `Retry-After` и действующие настройки Ozon.
FBS использует `/v4/posting/fbs/list`, FBO — `/v3/posting/fbo/list`, оба с cursor; повтор курсора, неполный обход
и некорректная страница не считаются успешной загрузкой.

Для PostgreSQL применяется SQLAlchemy `AsyncEngine` с `asyncpg`, для SQLite —
с `aiosqlite`. В прежней БД штатная инициализация создаёт совместимую таблицу `ozon_order_days`; старые подтверждения загрузки читаются без перезаписи заказов.
Оба PostgreSQL-движка используют `PostgresConnectionOptions`: `connect_timeout`
преобразуется в `timeout`, `application_name` — в `server_settings`, остальные
параметры передаются в нормализованном DSN. SSL-настройки и сертификаты разбирает
сам драйвер. Подробности — в [настройках PostgreSQL](postgresql-migration.md#async-order-connections).
Настройки задач, расписание, история и заказы в этом пути читаются и записываются
через асинхронные репозитории. Каждая загруженная схема/дата получает отдельную транзакцию: строки заказов, дневное состояние, `sales_sync_state` и `sync_health` сохраняются атомарно. При обновлении нескольких пакетов незавершённых отправлений полнота дня подтверждается после всех пакетов.
При частичной ошибке FBO/FBS сохраняются доступные строки и статус ошибки.

SQLite допускает одного писателя: записи сериализуются через `asyncio.Lock`
и `BEGIN IMMEDIATE`, не останавливая event loop. Сам драйвер `aiosqlite`
использует внутренний поток для SQLite; HTTP-запросы выполняются нативно
асинхронно. PostgreSQL удерживает блокировку задачи на отдельном соединении
`NullPool`, не занимая пул чтения и записи. Имена блокировок совместимы с
прежними синхронными загрузчиками и ручными запусками.

При штатной остановке процесс ждёт активные задачи и запись их результатов,
затем закрывает HTTP-клиент и БД. Отмена ручной задачи, включая отмену до её
первого шага, записывается как ошибка; блокировка освобождается после финализации.
Прерванная автоматическая попытка восстанавливается по сохранённому расписанию.

Для запуска нужны обновлённые `requirements.txt` (`sqlalchemy[asyncio]`,
`asyncpg`, `aiosqlite`). Общий HTTP-транспорт, ресурсы и тип асинхронной задачи
можно использовать для следующих загрузчиков. Команды загрузки
истории и строгая FBS-выгрузка в Google Таблицы имеют отдельные сценарии. Реклама юнит-экономики использует асинхронный дневной загрузчик, описанный в [контракте Performance API](ozon-performance-api.md).

Заказы и реклама Ozon запускаются каждый час. Сохранённое прежнее ежедневное расписание, отложенное более чем на час, при первом проходе worker переводится на текущий запуск. Повторы ошибок — через 1, 5 и 15 минут, далее очередной час. Полный список заказов сегодня обновляется почасово; завершённый день загружается однократно. Ошибки списков повторяются в последних семи завершённых датах; начальная загрузка сохраняет прежнее окно 21 день для остатков. Незавершённые отправления любого возраста проверяются по ID. FBO фильтруется по `posting_numbers`, FBS по `order_numbers` с последующей проверкой точного набора отправлений. Отсутствующее запрошенное отправление — ошибка, а не отмена. `ordered_at` существующей строки при обновлении не меняется. Блокировка магазина `ozon-orders:` защищает ручной и фоновый запуск. Расчёт — в [контракте выкупа](ozon-buyout.md).

Для FBO окно `since`/`to` проверяется по `in_process_at` — моменту принятия
в обработку. `created_at` остаётся исходной датой заказа для экономики:
отправление, созданное до полуночи и принятое после неё, сохраняется без
переноса даты и не прерывает загрузку следующего дня. При отсутствии
`in_process_at` используется прежняя последовательность резервных дат.
Проверка окна FBS сохраняет прежнее поведение.

При обновлении незавершённых FBO `OzonPendingPosting.filter_day` берётся из
сохранённого `raw_json`. Запрос по номерам охватывает даты принятия выбранных
отправлений, а результат обновляет исходную дату заказа. Отправление с другой
датой принятия проверяется отдельно даже после повторной загрузки списка
исходного дня. Состояние `finalized=True, ok=False` повторяется в пределах
окна повторов; признак закрытого списка сам по себе не означает успех.
Ошибка списка или раннего пакета сохраняется в состоянии дня, даже если
последующие запросы по номерам завершились успешно. Подтверждение не выставляется вручную.

Проверка исправления 19 октября 2026 года: реальные ответы TRIS воспроизведены
на временных SQLite и PostgreSQL 17. Проверены граница суток, повтор без дублей,
восстановление неуспешного закрытого дня, неверный диапазон API и ошибка первого
пакета перед успешным последним. Локальная повторная загрузка TRIS за 12–18 октября
завершилась без ошибок; FBO/FBS подтверждены для всех семи дней.

## Контракты данных заказов Ozon

Асинхронная загрузка использует модели из `app/dto/orders.py` и
`app/dto/ozon_orders.py`. API-клиент принимает DTO запросов, проверяет страницу
и вложенные данные через Pydantic и возвращает внешние DTO `OzonPosting`.
Загрузчик восстанавливает отсутствующие артикулы через каталог, затем вызывает
`prepare`, получая неизменяемые отправления `OzonOrderPosting`.
Нормализатор `normalize_postings` возвращает
`tuple[SalesOrderLine, ...]`. Репозиторий принимает `OrderSaveBatch` с магазином,
строками, периодом, временем попытки и ошибками; строки другого магазина
отклоняются. Преобразование в параметры SQL выполняется внутри репозитория
по явному списку колонок.

`sync_store` возвращает `StoreOrderSyncResult`, а `sync_all` — `OrderSyncResult`.
Ошибки содержат этап, тип, сообщение и для загрузки — схему и окно дат.
Асинхронный планировщик и ручной запуск читают свойство `error` этого отчёта;
вложенный словарь с произвольными ключами больше не является их контрактом.
Настройки описаны `TypedDict`, состояние расписания — датаклассой `JobSchedule`
в `app/dto/jobs.py`. JSON и SQL-параметры остаются словарями только на границах
сериализации; API-ключ исключён из представления `OzonCredentials`.

Обязательны идентификаторы отправления и товара, непустой статус, корректная дата заказа,
положительное целое количество и конечная неотрицательная цена. Для FBS
обязателен `posting_number`. Числовые строки преобразуются явно, приоритет
источников цены и даты сохраняется. Нулевая цена разрешена; отсутствие цены,
нечисловое значение, `NaN` и бесконечность не заменяются нулём. Отсутствующие
дата, количество и ключи не заменяются текущей датой, единицей и индексами.
Неизвестные дополнительные поля ответа допускаются; полный исходный объект
отправления сохраняется в `raw_json`, включая неописанные в модели поля.

Отсутствующий статус, `null`, пустая строка и пробелы отклоняются входным DTO.
Непустой статус приводится к нижнему регистру без крайних пробелов; новые значения
Ozon допускаются и обрабатываются по существующим правилам доставки и отмены.

Непустой `offer_id` используется как артикул. Если его нет, `AsyncCatalogRepository`
читает `stock_items` для текущего магазина и `OZON`, включая служебные товары.
Неизменяемый `OzonArticleIndex` сопоставляет `mp_sku` с множеством артикулов;
снимок читается при первой необходимости и переиспользуется до конца загрузки
магазина. Допускается ровно один уникальный непустой артикул по точному SKU.
Отсутствие SKU, совпадения или неоднозначность вызывает ошибку поля `offer_id`.
`product_id` и SKU не подставляются вместо артикула. Исходный `raw_json` остаётся
ответом API и не дополняется значениями из каталога.

Ошибка обязательного поля завершает загрузку этой схемы за окно: уже прочитанные
страницы этого окна не сохраняются. Другие схемы и магазины продолжают работу;
статус магазина остаётся ошибочным. В сообщении указывается путь поля, без
вывода полного исходного объекта. Корректная пустая страница является успехом.

Синхронная история и строгая FBS-выгрузка используют совместимый `normalize`
через адаптер `ozon_legacy`. Их прежние подстановки и словарный результат
сохранены; вычисление сумм и статусов общее с новым нормализатором. Структура
таблиц, ключи upsert, расписание и HTTP-контракт ручной кнопки не меняются.

После установки `requirements-dev.txt` проверка `python -m mypy` (или
`make typecheck`) проверяет 20 файлов этого контура в строгом режиме. Она
включена в `make check`; весь остальной проект не переводится на строгую
типизацию. Проверки поведения выполняются временными сценариями, без
постоянных тестовых файлов. Проверены SQLite и PostgreSQL 17: обязательные
поля, сохранение JSON, совместимость старого нормализатора и FBS, конкурентная
загрузка, ошибка поздней страницы, rollback, upsert, повторы и ручные `202/409`.

## Константы и перечисления заказов Ozon

`app/core/constants.py` содержит параметры загрузки заказов Ozon и используемой
общей инфраструктуры: периоды, адреса и лимиты API, расписание, повторы,
ограничения ошибок, правила нормализации, параметры HTTP, БД и блокировок.
Параметры сгруппированы в датаклассы с `frozen=True`, `slots=True`, `kw_only=True`.
Экземпляры объявлены через `Final`: `TIME`, `OZON_ORDERS`, `OZON_API`,
`ORDER_NORMALIZATION`, `HTTP`, `DATABASE`, `LOCKS`, `SCHEDULER`, `SCHEDULE_TEXTS`
и `JOBS`. Например, период загрузки — `OZON_ORDERS.lookback_days`, размер страницы
API — `OZON_API.page_size`, интервал проверки — `SCHEDULER.poll_seconds`.
Вложенные коллекции используют `tuple` и `frozenset`.

Закрытые наборы схем, этапов ошибки, состояний и причин запуска остаются Enum.
`Marketplace` определён там же; московский часовой пояс доступен через
`TIME.moscow_timezone`. Прежние имена в модулях-потребителях, включая
`domain.MOSCOW_TIMEZONE`, `api.PAGE_SIZE` и `ozon_turnover.JOB_NAME`, сохранены
как ссылки на поля групп. Плоские имена в самом `constants.py` удалены.
Группы не создают ресурсов и не читают окружение: настраиваемые значения
по-прежнему берутся из `settings`.

Внутри DTO схемы и этапы представлены Enum. На границах JSON, SQL и старого
словарного нормализатора используются прежние строковые значения. Статусы
отправлений Ozon остаются строками; неизвестные статусы сохраняются, доставка
определяется прежним набором значений, отмена — прежней проверкой `cancel`.
Общие константы переиспользуются синхронными механизмами, но отдельные настройки
рекламы, WB, Яндекса и FTP этим переносом не меняются. Ключи полей, SQL и тексты
сообщений остаются в своих модулях. Новый файл входит в строгую проверку mypy.

## Метаданные каталога задач

Централизованные метаданные задач находятся в `app/core/constants.py` в объекте
`JOBS` типа `JobCatalog`: например, `JOBS.ozon_orders`, `JOBS.stock` и
`JOBS.yandex_finance`. Его поля — неизменяемые `SyncJobMetadata` — содержат идентификатор, заголовок, описание,
статическое расписание, область действия, маркетплейсы и доступность ручного
запуска. Области действия и маркетплейсы заданы через `JobScope` и `Marketplace`;
ключи источников Яндекса — через `YandexSyncSource`. Идентификаторы задач хранятся
в их метаданных, например `JOBS.ozon_orders.name`.

`app/jobs/catalog.py` собирает четыре определения Ozon через `from_metadata()`.
При каждом вызове `job_definitions()` он заново читает флаги включения.
Прежние определения остальных задач и их динамические подписи расписаний
сохранены. Каталог содержит 41 действующую задачу; старый идентификатор рекламы
Ozon сохранён в метаданных для совместимости настроек, но не регистрируется.

Поля готового определения сохраняют прежние строковые значения, включая
`scope` и элементы `marketplaces`. Идентификаторы, порядок задач, флаги
включения и ручного запуска совместимы с API, настройками и журналом.
Отображаемые расписания описывают задачи; их фактическое выполнение по-прежнему
задают фоновые обработчики и планировщик.

Новый JSON-каталог интерфейса использует `JobScheduleView` и
`JOB_SCHEDULE_RULES`. Он передаёт часы, интервалы, дни недели и часовую зону;
подписи формирует frontend. `SCHEDULE_TEXTS` сохранён для старых потребителей
`SyncJobDefinition`. [Контракты интерфейса](ozon-web-contracts.md).

## Диагностика и остановка

```shell
python -m app.jobs.worker --healthcheck
```

Команда возвращает `0`, если БД отвечает и heartbeat свежий, иначе `1`.
Worker обновляет `scheduler-heartbeat.json` в каталоге `CHECKSTOCK_DB_PATH`
каждые 10 секунд; допустимый возраст — 60 секунд. Файл локальный и исключён
из Git. Путь можно переопределить `--heartbeat-path` одновременно у worker
и команды проверки. Проверка не выполняет миграций и не запускает загрузки.

Сервис `scheduler` имеет собственный Docker healthcheck. Вебовый `/readyz`
проверяет веб-процесс и БД, а не планировщик. Heartbeat подтверждает работу
процесса; результат конкретной загрузки проверяется по истории и логам.

SIGTERM и Ctrl+C прекращают запуск новых задач. Worker ждёт завершения активных
обработчиков и удаляет свой heartbeat. Docker даёт на остановку 60 секунд;
после принудительного завершения незаконченные попытки восстанавливаются из БД.

## Проверка изменений

Регрессионные проверки сохраняются в `tests/` согласно `checkstock-testing`: API подменяются, БД изолирована от рабочих данных. Проверки реальных внешних сервисов выполняются отдельно в соответствующем окружении. Обязательные сценарии: сбой настроек,
частичный результат, исключение, последовательность повторов и её исчерпание,
отключение, перезапуск, один запуск после простоя, конкуренция процессов,
обрыв активной попытки, атомарный rollback завершения, ручные запуски, каталог,
FTP, heartbeat и отсутствие автоматических задач в вебовом lifespan.

Для изменения 13 октября 2026 года эти сценарии проверены на временных SQLite
и PostgreSQL 17, включая два отдельных процесса и принудительное завершение
исполнителя. Временный PostgreSQL-кластер после проверки остановлен и удалён.
Отдельно проверена работа БД при 20 одновременно удерживаемых блокировках.
Также проверены YAML Compose и компиляция новой таблицы для PostgreSQL.
Docker в текущем окружении недоступен; проверка запуска контейнеров требуется
перед выпуском. Боевые API и рабочая БД при проверках не используются.


### Сравнение условий WB
`wb_standard_costs_sync` загружает последние 7 завершённых дней МСК при первом запуске через 60 секунд и затем каждые 4 часа. Повторы при ошибке: 300 и 900 секунд. Задача регистрируется при включённой общей фоновой синхронизации, учитывает настройки магазинов и имеет штатный ручной запуск. Последний успешный снимок магазина сохраняется при ошибке. См. [источники и условия публикации](wb-standard-costs.md#штатная-загрузка-и-публикация).

## Заголовок Retry-After Ozon

Синхронный клиент принимает число секунд или HTTP-дату в `Retry-After`. Отрицательное время и прошедшая дата означают нулевую паузу; NaN, Infinity и некорректные значения отклоняются, чтобы использовать штатный backoff.
Проверка асинхронного пути охватывает конкурентные магазины, изоляцию ошибок, пагинацию, `Retry-After`, атомарное сохранение и отмену. Совместимость с живой PostgreSQL и контейнерным Linux требует отдельного запуска в соответствующем окружении.

### Подтверждение полноты дней заказов Ozon

`AsyncOrdersRepository.save` атомарно сохраняет заказы, состояние загрузки и подтверждения завершённых дней в `economics_source_days`. Ошибки загрузки FBO/FBS исключают подтверждение затронутого окна; ошибка доступа или сохранения исключает новые подтверждения. Текущий московский день не подтверждается как завершённый. Старые подтверждения и известные суммы сохраняются при ошибках, а [чтение ТО](f05-economics-completeness.md#то-и-рекламные-расходы-ozon) показывает доступную часть с пометкой. Расписания и загрузка заказов не меняются.

### Почасовая реклама Ozon

`ozon_advertising_breakdown_sync` — единственная действующая задача рекламы Ozon: после готовности каталога, затем каждый час. Она обновляет текущие данные, закрывает вчерашний день после 04:30 МСК и догружает пропущенные источники последних семи завершённых дат. Повторы через 1, 5 и 15 минут читают готовые дни и пакеты из БД. Источники CPC, прочих кампаний и CPO сохраняются независимо; ошибка одного магазина не останавливает остальные. Ручной запуск доступен через общий интерфейс.

Старая задача `ozon_unit_economics_advertising_sync` удалена из расписания и каталога доступных запусков. Её история и ранее сохранённые данные не удаляются. После обновления кода уже работающий отдельный worker должен быть перезапущен штатным способом, чтобы перечитать список задач.

При суточном лимите Performance API запрет создания отчётов сохраняется в БД до `Retry-After`, а без него — на 24 часа. Попытки планировщика не обходят этот запрет. Метод вчерашней статистики по SKU работает отдельно от лимита генерации отчётов. [Хранение, повторы и учёт обращений](ozon-performance-api.md#хранение-и-http-контракт).
