# Перенос интерфейса CheckStock на React

Переноси интерфейс в существующий [React + TypeScript + Vite](../../../frontend/README.md). Действующая страница CheckStock задаёт внешний вид, тексты и поведение. При переносе сохраняй их, включая особенности площадок и разделов.

Начни с [checkstock-task-guide](../checkstock-task-guide/SKILL.md). Для серверной части применяй [checkstock-backend](../checkstock-backend/SKILL.md), для общих правил интерфейса — [checkstock-frontend](../checkstock-frontend/SKILL.md), для приёмки — [checkstock-testing](../checkstock-testing/SKILL.md). Новые React-компоненты размещай в `frontend/src/`. `templates/` и `static/` служат источником действующего интерфейса и обслуживают ещё не перенесённые страницы.

## Определи границы переноса

1. Выбери страницу или законченный пользовательский сценарий. Проследи URL и параметры, маршруты FastAPI, DTO, шаблоны, JS, фактический порядок CSS, ассеты и существующие проверки. Учти начальное состояние, настройки в URL и `localStorage`, фильтры, сортировку, навигацию и действия с данными, если они есть.
2. Зафиксируй эталон на воспроизводимых тестовых данных. Сними действующий интерфейс на широком и узком экране и в ключевых состояниях. Сверь взаимодействия, которые влияют на раскладку или доступность, включая выпадающие меню, модальные окна и длинные таблицы. Используй эти снимки и сценарии при приёмке.
3. Определи, какие API и элементы можно переиспользовать, каких данных или компонентов не хватает и какие потребители могут быть затронуты. При переносе всего сайта веди список маршрутов и общих компонентов, затем переноси их проверяемыми срезами.

## Создай или переиспользуй REST API

- Сначала найди существующие JSON-маршруты в `app/web/routers/` и проверь их DTO в `app/dto/`. Для общей оболочки проверь `GET /api/ui/context`. Контракты склада и экономики Ozon собраны в [описании веб-интерфейса Ozon](../../../docs/ozon-web-contracts.md). `/api/ui/templates` обслуживает действующий интерфейс. Разметку переносимой страницы реализуй в React.
- Для нового маршрута используй предметный путь под `/api/` и существующий прикладной сценарий, если он покрывает нужное поведение. Для чтения используй `GET` без бизнес-изменений, для создания и запуска операций — `POST`, для полной замены — `PUT`, для частичного изменения — `PATCH`, для удаления — `DELETE`. Выбирай код ответа по результату, например `201` для создания, `202` для принятой фоновой операции с доступным статусом или `204` для успеха без тела. При серверной пагинации определи границы и стабильный порядок. Для несовместимого изменения добавь отдельный контракт либо согласованно переведи всех потребителей. [Семантика HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#name-methods)
- Опиши вход и выход моделями Pydantic. Отрази запрос, успешный ответ и ожидаемые ошибки в OpenAPI. Укажи, какие поля обязательны и что означают `null`, пустой список и ноль. Форматы дат и точность денежных значений сверяй с предметным контрактом. Возвращай данные и стабильные смысловые коды ошибок. Разметку, тексты интерфейса, форматы вывода и CSS-классы определяй на клиенте. Для импорта и скачивания сохрани действующие multipart и файловые контракты. [Модели ответов FastAPI](https://fastapi.tiangolo.com/tutorial/response-model/)
- Сохрани серверную проверку сессии, доступа и входных данных. Переиспользуй существующий механизм сессии. При изменении запросов записи с cookie проверь защиту от CSRF. Исключи секреты и внутренние исключения из ответов. Для складских записей сохраняй `Idempotency-Key` при повторе той же операции. [Контракт входа](../../../docs/authentication.md), [складские повторы и транзакции](../../../docs/f03-stock-transactions.md)
- Сосредоточь HTTP-вызовы и обработку ошибок в общем клиенте с типизированными предметными функциями. Сверяй типы TypeScript с OpenAPI. Учти пустые и файловые ответы, фактические форматы ошибок и отмену устаревших запросов. Для JSON отправляй `Accept: application/json`, поскольку текущий middleware может перенаправить обычный `GET` без сессии на `/login`. Обработай `401` как необходимость входа, `403` как отказ в доступе. Для раздельного локального запуска, когда нужен единый origin, используй Vite proxy. Проверь вход, выход и относительные пути в целевой схеме запуска. [Настройки Vite proxy](https://vite.dev/config/server-options#server-proxy)

## Распредели расчёты между React и FastAPI

- Переноси в React вычисления для интерфейса и черновые оценки, если для них хватает загруженных данных и пользовательского ввода. Например, пересчитывай итог видимых строк при фильтрации и предварительную сумму при изменении процента. При пагинации явно отличай итог по загруженным строкам от итога по всей выборке.
- Оставляй на сервере итоговые бизнес-расчёты для отчётов, записей и отправки данных во внешние системы. Расчёты, которым нужны серверная выборка, закрытые данные или внешние API, выполняй в FastAPI. Для сохранения или отправки передавай исходные параметры. Сервер проверяет их и рассчитывает итог по правилам сценария. Отделяй предварительную оценку в интерфейсе от подтверждённого результата. Для Ozon сверяйся с [правилами разработки](../checkstock-task-guide/SKILL.md) и [контрактом калькулятора](../../../docs/ozon-calculator.md).
- Передавай исходные значения для локальной формулы через типизированный API. Выноси формулу в чистую функцию TypeScript и переиспользуй её в компонентах с одинаковым расчётом. Сохраняй единицы измерения, точность, правила округления и различие между нулём и отсутствующим значением. Для перенесённой формулы сравни результаты с действующей реализацией на одинаковых обычных и граничных входных данных, включая пустой ввод, ноль и границы округления, где они применимы.

## Собери страницу из общих компонентов и стилей

- Прежде чем писать компонент, найди React-аналоги и действующие реализации в `templates/layout/`, `static/common/` и предметных разделах. Переиспользуй общую оболочку и элементы с одинаковым поведением, например шапку, поля форм, фильтры, таблицы и диалоги. Выражай различия явными параметрами или композицией.
- Используй действующие CSS-переменные, шрифты, иконки и брейкпоинты. Сохраняй один источник для общих токенов и стилей компонентов. Подключай подходящий CSS как общий ресурс или выделяй используемую обеими версиями часть. Стили страницы держи рядом с ней и ограничивай область селекторов. При изменении общего CSS проверяй потребителей в React и в действующем интерфейсе.
- Переноси интерактивность в состояние и обработчики React. Оставляй React управление своим DOM. Сохраняй размеры, отступы, выравнивание, цвета, состояния наведения и фокуса, адаптивность, прокрутку и закреплённые элементы. Проверь управление клавиатурой и фокус в диалогах. Сохраняй различие между загрузкой, отсутствием результатов, неполными данными и ошибкой с повтором, где эти состояния применимы.

## Проверь и переключи маршрут

1. Проверь затронутые API и их потребителей. Для React запусти `npm run lint` и `npm run build` в `frontend/`. В браузере пройди сценарий от входа до результата и сравни действующую и новую страницы на одинаковых данных и размерах окна. Устрани расхождения внешнего вида и поведения. Проверь затронутые страницы, которые используют общие компоненты.
2. Переключай пользовательский URL после проверки среза. Сохрани параметры, закладки, прямой вход, обновление страницы и кнопки «Назад» и «Вперёд». Если нужен SPA fallback, ограничь его маршрутами React, чтобы API, файлы, вход и ещё не перенесённые страницы обслуживались своими обработчиками. На время перехода держи рабочий способ вернуть прежний обработчик. Удаляй старый код после проверки его потребителей и завершения перехода для них.
3. Укажи перенесённые маршруты, изменения API, переиспользованные компоненты и стили, выполненные проверки и оставшиеся расхождения. Если браузерное сравнение недоступно, отметь, какую часть визуального соответствия ещё требуется подтвердить.
