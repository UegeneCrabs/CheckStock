# Правила разработки, документация и планирование CheckStock

Работай в корне репозитория CheckStock: его можно узнать по `app/main.py` и `docs/llm-wiki.md`. Скил относится только к этому проекту. Для задач, не связанных с поведением приложения (например, просмотр статуса Git), достаточно применить этот скил без чтения всей документации.

## Обязательные правила разработки Ozon

Прочитай и соблюдай эти правила перед изменением кода в каждом чате CheckStock. Этот раздел — единый источник правил. Они обязательны для нового и изменяемого кода Ozon, а также затрагиваемой им общей инфраструктуры. Не расширяй задачу на WB, Яндекс Маркет или полный рефакторинг соседних модулей без соответствующего запроса.

1. **Разделяй backend и frontend.** Backend принимает запросы, проверяет права и входные данные, выполняет бизнес-операции и возвращает данные через типизированный JSON-контракт. Frontend отправляет запросы, получает ответы и решает, как отобразить данные. Авторизация, обязательная валидация, бизнес-расчёты, работа с секретами, внешними API и БД остаются на сервере; проверки frontend их не заменяют.

2. **Не формируй интерфейс в Python.** В маршрутах, сервисах, DTO и репозиториях Ozon запрещены сборка HTML, разметка форм, CSS-классы, подписи элементов управления и выбор визуального оформления статусов. Форматирование дат, чисел и денежных сумм для отображения выполняй на frontend; backend передаёт значения в согласованном машинном формате. Возвращай смысловые состояния и коды ошибок, по которым frontend выбирает текст, цвет и доступность элементов. Функция наподобие `_credential_card`, возвращающая строку `<form ...>`, нарушает это правило. Перенос её HTML или CSS-классов в Python-константу, dataclass или DTO не устраняет нарушение. Разметку, UI-тексты и оформление размещай в frontend-файлах.

3. **Передавай между слоями именованные типизированные структуры.** Используй DTO, dataclass или TypedDict для параметров и результатов. Не передавай безымянные `dict[str, Any]` и позиционные наборы разнородных значений как внутренний контракт. Обычные словари допустимы на границах JSON и SQL, с преобразованием в типизированные структуры; внутренние словари-индексы и отображения ключей в значения также допустимы при явной типизации. Входные данные проверяй на границе: аннотация TypedDict сама по себе ничего не валидирует.

4. **Соблюдай границы слоёв.** API-клиент отвечает за внешний протокол, репозиторий — за чтение и запись БД, прикладной слой — за последовательность бизнес-операций, нормализатор — за преобразование данных без сетевых запросов и SQL. Маршрут связывает HTTP-контракт с прикладным сценарием. Не помещай бизнес-сценарии и доступ к БД в frontend или нормализаторы.

5. **Используй настоящую асинхронность.** HTTP-запросы и операции БД в асинхронном сценарии Ozon выполняй асинхронными клиентами через `await`. Не подменяй их `asyncio.to_thread`, `run_in_executor` или пулом потоков с синхронными клиентами. Магазины обрабатывай конкурентно через `asyncio.TaskGroup`, с изоляцией ошибок магазинов; страницы одного магазина загружай последовательно. Сохраняй управление жизненным циклом клиентов, транзакциями, блокировками, отменой и ограничениями API.

6. **Централизуй константы и перечисления backend.** Убирай магические числа и строки из рассматриваемого кода в `app/core/constants.py`, расширяя существующие группы по смыслу. Связанные значения группируй в dataclass с `frozen=True`, `slots=True`, `kw_only=True`; экземпляры объявляй как `Final`, вложенные коллекции делай неизменяемыми. Закрытые наборы значений оформляй через Enum. Настройки окружения и развёртывания оставляй в `settings`. Открытый набор статусов Ozon не ограничивай закрытым Enum: неизвестный непустой статус сохраняй строкой. Не выноси механически каждую пустую строку, индекс или имя поля в отдельную константу.

7. **Используй единый каталог метаданных задач.** Идентификаторы, названия, описания, области действия, площадки и параметры расписаний бери из существующей группы `JOBS` и связанных структур в `app/core/constants.py`. Не дублируй литералы в `SyncJobDefinition` и потребителях. Метаданные передавай как данные; отображение расписания и состояния задачи определяет frontend. Наличие метаданных backend не разрешает переносить туда HTML, CSS-классы и подписи кнопок.

8. **Не добавляй комментарии и докстринги в рассматриваемый код.** Это относится и к докстрингам в начале Python-файлов. Названия и типы должны объяснять код; пояснения, ограничения и решения записывай в тематическую документацию. Это правило не запрещает текст инструкций и Markdown-документацию.

9. **Проверяй изменения без постоянных тестовых файлов.** Используй временные сценарии, Ruff, mypy и необходимые интеграционные проверки соразмерно изменению. Не добавляй тестовые файлы в репозиторий; удаляй созданные для проверки временные артефакты и останавливай свои временные сервисы. Не удаляй чужие файлы или существующие проверки вне задачи. Для правок только документации достаточно проверки ссылок, diff и соответствующего валидатора.

10. **Не копируй существующие нарушения.** Старый HTML-рендерер, нетипизированный соседний модуль или синхронный вызов не служит образцом для нового кода Ozon. Исправляй нарушения в рамках изменяемого сценария, сохраняя контракты остальных потребителей общей инфраструктуры. Наличие этих правил само по себе не означает, что всё старое приложение уже приведено к ним, и не разрешает менять посторонние сценарии.

## Найти контекст

1. Прочитай [карту проекта](../../../docs/llm-wiki.md) и через [индекс](../../../docs/README.md) выбери документы по теме задачи. Не загружай все документы подряд.
2. Сверь существенные утверждения выбранных документов с текущими файлами `app/`, `scripts/`, `templates/`, `static/`, `tests/` и настройками запуска. Для HTTP-контракта проверь маршруты и DTO; при доступном работающем приложении можно дополнительно сверить OpenAPI.
3. Если документация и реализация расходятся, явно отметь расхождение. Текущее поведение определяй по коду, тестам, схеме БД и конфигурации; не выдавай историческое описание за действующий контракт.

## Спланировать новую задачу

Сначала сформулируй ожидаемый результат и границы задачи. Затем укажи затронутые модули и документы, последовательность изменений, проверку результата и конкретные неопределённости или риски. Для изменений данных проверь схему, миграцию и обратную совместимость; для складских операций — [контракт повторов и транзакций](../../../docs/f03-stock-transactions.md); для экономики — [полноту исходных данных](../../../docs/f05-economics-completeness.md).

Если пользователь просит только план, представь его без изменения кода. Если пользователь просит выполнить задачу, используй план для работы и доведи реализацию до проверки, не останавливаясь на описании плана. Записывай план в файл только по запросу пользователя или когда он нужен как рабочий артефакт задачи.

При изменении поведения обнови соответствующий тематический документ. Если меняются карта модулей или набор инструкций, обнови также `docs/llm-wiki.md` и `docs/README.md`.

Перед завершением проверь diff на соблюдение обязательных правил, выполни подходящие проверки и укажи, что проверено и какие ограничения остались. Не выдавай существующее нарушение в коде за разрешённое исключение из правил.
