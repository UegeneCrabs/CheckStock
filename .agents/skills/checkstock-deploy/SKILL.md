# Выпуск CheckStock через GitHub

Сначала примени [checkstock-task-guide](../checkstock-task-guide/SKILL.md). Порядок выпуска и восстановления БД бери из [docs/releases.md](../../../docs/releases.md); перед действием сверяй его с `.github/workflows/deploy-release.yml` и `deploy/deploy-release.sh`. Не выдавай документацию за подтверждение состояния GitHub или сервера.

## Подготовка

1. Уточни цель пользователя: проверка, исправление неудачного запуска или новый выпуск. Публикуй ветки и тег только когда пользователь поручил выпуск или деплой; такое поручение уже разрешает необходимые push и запуск Actions.
2. Проверь чистоту рабочего дерева, текущую ветку, `origin/master`, `origin/dev-release`, существующие теги `v*` и их коммиты. Читай удалённые refs перед выбором версии: локальные refs могут устареть. Не перезаписывай чужие изменения, ветки и теги принудительным push.
3. Для обычного выпуска подготовь проверенный коммит в `master`, продвинь `dev-release` до него без дополнительного коммита, затем создай новый тег `vMAJOR.MINOR.PATCH` на этом коммите. Версия должна быть строго больше всех ранее опубликованных корректных релизных тегов. `deploy/VERSION` не используется. Если `dev-release` ещё нет, создай её на выбранном коммите `master`.
4. Перед тегом выполни затронутые проверки и как минимум команду Ruff из workflow и `docker compose --env-file .env.example -f deploy/docker-compose.yml config --quiet`. Исправь блокирующие ошибки; не отключай проверку ради выпуска. Если сборка образа не проверена локально, явно оставь её проверку Actions.

## Доступ и запуск

- Workflow читает **Repository Secrets** `DEV_DEPLOY_HOST`, `DEV_DEPLOY_USER`, `DEV_DEPLOY_SSH_KEY`, `DEV_DEPLOY_KNOWN_HOSTS`; необязательный порт — GitHub Variable `DEPLOY_PORT`, по умолчанию 22. Внутренние имена переменных шага без `DEV_` не являются именами Secrets. Если значения созданы как Environment Secrets, job должен явно ссылаться на этот environment; текущий workflow этого не делает. Не проси присылать секреты в чат и не выводи их в журнал.
- Убедись, что адрес из `DEV_DEPLOY_HOST` совпадает с адресом в строке `DEV_DEPLOY_KNOWN_HOSTS`, а приватный ключ соответствует публичному ключу в `authorized_keys` пользователя `DEV_DEPLOY_USER`. `known_hosts` содержит адрес, тип и публичный ключ SSH-сервера; это не ключ пользователя деплоя. Если доступ к значениям Secrets закрыт, проверяй их наличие по настройкам GitHub или ошибке Actions, не утверждай, что доступ настроен.
- Не считай окружение тестовым только из-за префикса `DEV_`: фактический сервер задаёт `DEV_DEPLOY_HOST`, а серверный скрипт работает в `/home/checkstock` и пишет дампы в `/home/bd_backup`.
- Отправка тега запускает `Deploy CheckStock release`. Дождись результата Actions и отделяй «тег отправлен» от «деплой завершился успешно». При успехе проверь сообщение о коммите, дампе и здоровье сервисов; при недоступном доступе к Actions или серверу честно укажи, что результат не подтверждён.

## Ошибки и повтор

- Читай конкретный упавший шаг. Пустые SSH-переменные означают, что требуемые Secrets отсутствуют или недоступны job; не меняй SSH-сервер для устранения этой ошибки.
- Если код и тег не меняются, повторно запусти упавший workflow/job в Actions. Не удаляй и не отправляй тот же тег заново. Если исправление требует нового коммита, подготовь следующий строго возрастающий тег: уже опубликованный номер повторно не используй.
- Серверный сценарий создаёт и проверяет дамп PostgreSQL до переключения кода, затем проверяет `app`, `scheduler`, `watchdog`; при ошибке пытается вернуть прежний код. Откат кода не восстанавливает БД. При сбое оцени журнал отката и состояние сервера, прежде чем предлагать восстановление БД из дампа.
