# CheckStock

FastAPI-приложение для синхронизации каталогов, остатков, продаж и аналитики WB, Ozon и Яндекс Маркета.

## Структура проекта

- [app](app/README.md) — серверная логика по предметным разделам.
- [templates](templates/README.md) — шаблоны страниц по разделам сайта.
- [static](static/README.md) — CSS, JavaScript и изображения тех же разделов.
- [scripts](scripts/README.md) — команды обслуживания, синхронизации, импорта, экспорта и диагностики.
- [docs](docs/README.md) — индекс инструкций; [LLM wiki](docs/llm-wiki.md) — карта кода и источников для ИИ-ассистента.
- `data` — рабочая локальная БД, состояние парсера и `backups` с резервными копиями.
- `deploy` — сборка и настройки контейнера парсера.

## Локальный запуск

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

Перед запуском положите реальные файлы доступов в `secrets/` по образцам из `secrets/example/`. `.env`, база и реальные секреты исключены из Git.

## Проверки

```powershell
python -m ruff format --check app scripts
python -m ruff check app scripts
python -m unittest discover -s tests -v
node --test tests/test_stock_mutation_ui.cjs
```

При наличии `make` доступны цели `run`, `lint` и `check` (`check` равен `lint`), а `make format` изменяет файлы.
Python-тесты запускаются через `unittest`; тесты клиентского кода — через `node --test` для файлов `tests/*.cjs`.

## Поставки на ФФ

Каждая подтверждённая загрузка Excel-файла или Google Таблицы прибавляет полное количество распознанных
товаров к текущим остаткам выбранного ФФ и маркетплейса. Имя файла, ссылка и предыдущие загрузки не
ограничивают начисление: поставки на 10, 5 и 10 единиц добавят 25 единиц, даже если имя файла одинаковое.
Новая подтверждённая загрузка одинаковых данных также добавит их ещё раз. Сетевой повтор той же
операции с прежним `Idempotency-Key` возвращает сохранённый результат без повторного начисления.
Перед записью показывается количество к добавлению. В истории каждая загрузка сохраняется отдельной
поставкой с полными добавленными количествами. Ранее сохранённые остатки автоматически не пересчитываются.

Все HTTP-операции изменения складских количеств требуют заголовок `Idempotency-Key`. UI создаёт новый
ключ для новой операции и сохраняет прежний при неопределённом результате. Остатки, партии, история,
журнал автора, отметки источников и результат запроса фиксируются одним UnitOfWork.
Контракт, схема, проверки и ограничения описаны в [docs/f03-stock-transactions.md](docs/f03-stock-transactions.md).

## Docker

```powershell
Copy-Item .env.example .env
docker compose up --build -d
docker compose logs --follow app
```

Перед запуском задайте `POSTGRES_PASSWORD` в `.env`. Приложение доступно на `http://localhost:8000`. Docker Compose использует PostgreSQL: база хранится в именованном volume `postgres-data`, секреты подключаются read-only из локального каталога `secrets/`. `/healthz` проверяет процесс, `/readyz` дополнительно проверяет соединение с настроенной БД. При обычном локальном запуске без `CHECKSTOCK_DATABASE_URL` используется SQLite в `data/checkstock.db`.

Остановка:

```text
docker compose down
```

Для удаления данных требуется отдельное явное действие `docker compose down --volumes`; обычная остановка volume не удаляет.

## Отчёт «Целевая цена» WB

`/sales/unit-economics-1c/reports/target-price` сравнивает текущую цену с СПП и кошельком
с ценой по целям кабинета. В `/admin/integrations` → «Ввод данных по кабинетам» задаются
цель ДРР (по умолчанию 8%) и цель ROI (50%). Отчёт не изменяет цены на WB.

Текущие цена с СПП и WB Кошельком, ДРР с выкупом и ROI берутся из тех же источников и
рассчитываются за те же 7 завершённых московских дней, что и показатели юнит-экономики и
отчёта «Юниточная прибыль». Подтверждённый ноль рекламы отличается от отсутствия выгрузки;
при нулевом обороте и расходах ДРР отображается как 0.

Расчёт целевой цены повторяет калькулятор и сохраняет текущие СПП, скидку WB Кошелька, ЗЦ,
логистику, комиссии и налоги. Меняются только целевые ДРР и ROI. Реклама на единицу равна
цене без СПП × целевой ДРР / 100 × процент выкупа / 100. Цена подбирается в копейках с
допуском ROI ±0,1 процентного пункта. Без обязательных данных или при недостижимой цели
выводится причина, а не выдуманная цена. Цели хранятся в двух новых колонках
`unit_economics_1c_cabinet_settings`; миграция добавляет их с DEFAULT 8 и 50 без удаления строк.

## Конфигурация и логи

Все изменяемые пути, интервалы, лимиты, retry-параметры и таймауты собраны в `app/config.py` и настраиваются переменными из `.env.example`. Некорректные значения останавливают запуск с понятной ошибкой вместо неявного fallback. Логи пишутся в stdout с уровнем, временем, именем модуля и `request_id`. Успешные обычные GET-запросы видны на `DEBUG`, изменения состояния и длительность задач — на `INFO`, клиентские ошибки — на `WARNING`, серверные ошибки со стеком — на `ERROR`. Полные payload и результаты фоновых синхронизаций в логи не выводятся.

При публикации за HTTPS установите `CHECKSTOCK_SESSION_COOKIE_SECURE=1`.

## Выгрузка в Google Таблицы

На `/admin/integrations?tab=google` суперадминистратор задаёт три файла Google Таблиц:
по одному для Яндекса, Ozon и WB. Для каждой площадки указываются своя ссылка и названия листов
остатков, FBS-заказов и FBO в пути к клиенту / от клиента; расписание по Москве общее.
Для FBO задаются отдельный лист и два столбца (по умолчанию J и L), данные при каждой
выгрузке запрашиваются по API параллельно по кабинетам. В каждый файл выгружаются все семь проектов;
одинаковые артикулы разных проектов остаются отдельными строками.
В остатках `A` содержит ключ «ПРОЕКТ БАРКОД», `B` — проект, `C:K` — основные показатели,
с `L` — детализацию по ФФ. FBS и FBO в пути записываются в выбранные столбцы существующего
листа по `ARTICLE` и `Проект`, начиная со строки под найденной шапкой. FBS-заказы охватывают 30 завершённых
московских дней, без сегодняшнего дня. Пустое название листа отключает соответствующую выгрузку.

Если подтверждённый снимок поставок устарел или последняя синхронизация завершилась ошибкой,
выгружаются последние корректно сохранённые значения с предупреждением о давности данных.
При отсутствии подтверждённых количеств «В пути на склады МП» и ТОТАЛ остаются пустыми
для соответствующих товаров; отсутствие данных не подменяется нулём.

Каждый файл нужно открыть сервисному аккаунту из `secrets/google_service_account.json` с правами
«Редактор». Общая выгрузка изначально выключена; старые настройки по магазинам сохранены в БД,
но больше не используются страницей и планировщиком. После ввода ссылок и названий листов
сначала сохраните настройки. [Формат листов и порядок перехода](docs/project-sheet-export.md).

## Ночная выгрузка себестоимости на FTP

Задачи `FTP — себестоимость WB` и `FTP — себестоимость Ozon` читают заданные в коде листы общей
Google-таблицы и отправляют соответственно `data.json` и `data_ozon.json`. По умолчанию первая
попытка выполняется в 03:15 МСК. При ошибке повторяется только неуспешная платформа каждые 20 минут
до 06:00; после успешной отправки повторов в эту ночь нет. Обе задачи можно отключать, запускать
вручную и просматривать в разделе `/admin/integrations` → «Все выгрузки».

Для работы заполните в `.env` переменные `CHECKSTOCK_FTP_HOST_*`, `CHECKSTOCK_FTP_USER_*` и
`CHECKSTOCK_FTP_PASSWORD_*`. Режимы FTP/FTPS задаются через `CHECKSTOCK_FTP_TLS`,
`CHECKSTOCK_FTP_MODE` и `CHECKSTOCK_FTP_PROT`. Используется тот же файл
`secrets/google_service_account.json`, что и для остальных Google-интеграций; публичные FTP API,
Google Apps Script и отдельный сервис `ftp-processor` не требуются.
